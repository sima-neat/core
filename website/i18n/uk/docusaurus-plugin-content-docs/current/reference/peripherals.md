# Каталог периферійних пристроїв

Використовуйте каталог периферійних пристроїв, щоб переглядати пристрої, зараз під’єднані до локального
DevKit. API доступний у C++ і Python та повертає однаковий типізований
знімок в обох мовах.

Каталог належить SiMa Sentinel (`simaai-sentinel.service`) —
локальному для плати демону, який надає його як `GET /v1/peripherals`. Sentinel повідомляє
лише факти про обладнання. Кожен виклик `list()` виконує один обмежений запит до
Sentinel, після чого Core визначає, які режими камери підтримує `CameraInput`. Core
не сканує обладнання, не кешує другий каталог і не переходить до іншого
шляху виявлення.

## Перелік периферійних пристроїв

Python:

```python
import pyneat

catalog = pyneat.peripherals.list()
for peripheral in catalog:
    print(peripheral.id, peripheral.type)
```

C++:

```cpp
#include <neat.h>

auto catalog = simaai::neat::peripherals::list();
for (const auto& peripheral : catalog) {
  // Use peripheral.id and peripheral.type.
}
```

Повернений каталог можна перебирати. Він також містить:

| Поле | Значення |
| --- | --- |
| `revision` | Змінюється щоразу, коли змінюються `devices` або `errors`. Порівнюйте його лише на рівність. |
| `observed_at` | Час початку сканування, на якому ґрунтується цей знімок; не задано, доки не завершиться перше сканування Sentinel. До того часу каталог порожній, навіть якщо пристрої під’єднано. |
| `errors` | Провайдери, що завершилися помилкою під час останнього сканування, кожен із `provider`, `code` і `reason`. Пристрої провайдера з помилкою, отримані під час його останнього успішного сканування, залишаються в `devices`. |
| `devices` | Периферійні пристрої. |

Каталог може не містити жодного пристрою. Це успішний результат.

## Відомості про камеру

Коли `peripheral.type == "camera"`, `peripheral.camera` містить:

| Поле | Значення |
| --- | --- |
| `camera_name` | Необов’язкова точна назва libcamera, яку приймає `CameraInputOptions`. Вона відсутня для камери, яку поточний API вводу не може вибрати. |
| `model` | Модель пристрою, якщо провайдер її повідомляє. |
| `backend` | Бекенд виявлення, наприклад `mipi` або `v4l2`. |
| `modes` | Дискретні розміри або явні діапазони розмірів, частота кадрів, ознака підтримки та причина відхилення. |

Значення `framerate_num`/`framerate_den` кожного режиму — це найвища частота серед
інтервалів кадрів, які Sentinel перелічує для режиму, або `0/1`, якщо він їх не перелічує. ISP
DevKit не перелічує інтервалів для режимів MIPI; `CameraInput` задає частоту через
caps.

Core пропускає запис інтервалу, чий `type` йому невідомий, а також покроковий або
неперервний діапазон, максимум якого менший за мінімум. Пропущений запис
не задає частоту й не охоплює типову частоту, але режим усе одно вважається таким,
що перелічує інтервали.

Core класифікує кожен режим для типового профілю libcamera `CameraInput`
(`profile=Default`, який вибирає камери за `camera_name`). Режим
підтримується, якщо виконуються всі наведені нижче умови, які перевіряються в такому порядку; `reason` вказує
першу умову, що не виконалася:

1. `backend` камери має значення `mipi`.
2. Формат — це типовий формат `CameraInputOptions` (`NV12`).
3. Якщо режим перелічує інтервали кадрів, один із них охоплює типову частоту кадрів
   (`30/1`): дискретний інтервал 1/30 с або покроковий чи неперервний діапазон,
   що його містить. Режим, який не перелічує інтервалів, не відхиляється через частоту й
   має частоту `0/1`. Режим, усі перелічені інтервали якого пропущено, відхиляється через
   частоту й також має частоту `0/1`.
4. Режим має вихідний розмір ISP (`isp_output` має значення true).

Core не зондує камеру, не захоплює її, не налаштовує та не передає з неї потік. Тому
підтримка в каталозі не гарантує, що подальше ексклюзивне захоплення
буде успішним.

## Відомості про периферійні пристрої будь-якого типу

Кожен периферійний пристрій, незалежно від `type`, містить увесь запис пристрою, який
Sentinel опублікував, у `details_json` у вигляді компактного JSON. Python також надає
`details`, що декодує `details_json` у новий `dict`.

`details_json` — це спосіб читати тип периферійного пристрою, для якого Core не має
типізованого засобу доступу, наприклад `microphone`. Новим типом пристрою можна користуватися, щойно
Sentinel про нього повідомить, без оновлення Core. Усі поля та значення
зберігаються, зокрема поля, яких цей випуск Core не знає; JSON
серіалізується повторно, тому порядок ключів і пробіли можуть відрізнятися від відповіді
демона. Sentinel документує поля кожного типу.

Python:

```python
for peripheral in pyneat.peripherals.list():
    if peripheral.type == "microphone":
        print(peripheral.id, peripheral.details["capture_target"])
```

C++:

```cpp
#include <nlohmann/json.hpp>

for (const auto& peripheral : simaai::neat::peripherals::list()) {
  if (peripheral.type == "microphone") {
    const auto details = nlohmann::json::parse(peripheral.details_json);
    // Read details["capture_target"] and other fields.
  }
}
```

`details_json` можна розібрати будь-якою бібліотекою JSON; у прикладі використано nlohmann/json.

Core перевіряє лише поля, які читає. Неприпустимі поля каталогу (`revision`,
`observed_at`, `errors`, `devices`) або пристрій без дійсних `id` і `type`
призводять до того, що `list()` завершується помилкою розбору. Запис камери, поля камери якого Core
не може прочитати, наприклад запис від новішого Sentinel, до цього не призводить: такий пристрій зберігає
свої `id`, `type` і `details_json`, його `camera` залишається незаданим, а всі
інші пристрої повертаються як зазвичай.

## Помилки та область дії

`list()` породжує `NeatError` зі стабільним кодом, якщо служба відсутня,
надто стара, щоб надавати каталог, або має вимкнене чи зупинене виявлення периферійних пристроїв,
якщо доступ заборонено, час очікування запиту вичерпано або відповідь
неправильна чи завелика. Повідомлення містить наступну операційну дію та,
якщо Sentinel його надає, власний текст помилки Sentinel. Див.
[каталог кодів помилок](./error-codes.md).

Якщо Sentinel не встановлено або він надто старий, щоб надавати каталог периферійних пристроїв,
встановіть або оновіть його командою `sima-cli neat install sentinel`. Якщо його встановлено,
але не запущено, запустіть `simaai-sentinel.service`.

Цей API під’єднується лише до `/run/simaai-sentinel/api.sock` на локальному
DevKit. Він не використовує SSH і не вибирає віддалену плату. Insight і майбутні клієнти CLI
під’єднуються до демона як рівноправні клієнти, а не через Core.

Цей випуск надає одноразове читання каталогу. Запити на оновлення та керування
життєвим циклом демона не входять до публічного API Core.
