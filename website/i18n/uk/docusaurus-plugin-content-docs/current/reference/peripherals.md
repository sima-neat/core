# Каталог периферійних пристроїв

Використовуйте каталог периферійних пристроїв, щоб переглядати пристрої, які зараз під'єднані до
локального DevKit. API доступний у C++ і Python та повертає однаковий типізований знімок в обох мовах.

Авторитетний каталог належить SiMa Sentinel (`simaai-sentinel.service`) — локальному для плати демону,
який надає його як `GET /v1/peripherals`. Кожен виклик `list()` виконує один обмежений у часі запит
до Sentinel. Core не сканує обладнання,
не кешує другий каталог і не переходить до іншого шляху виявлення.

## Перелік периферійних пристроїв

Python:

```python
import pyneat

catalog = pyneat.peripherals.list()
for peripheral in catalog:
    print(peripheral.id, peripheral.type, peripheral.provider)
```

C++:

```cpp
#include <neat.h>

auto catalog = simaai::neat::peripherals::list();
for (const auto& peripheral : catalog) {
  // Use peripheral.id, peripheral.type, and peripheral.provider.
}
```

Повернений каталог можна перебирати. Він також містить `instance_id` демона, `revision` каталогу,
`sequence` подій, завершений `scan_sequence`, стан актуальності й часові позначки, поточну структуровану
помилку, проблеми провайдерів і колекцію `devices`.

Готовий каталог може не містити жодного пристрою — це успішний результат. Каталог у погіршеному стані
може містити останній успішний список пристроїв; у такому разі `stale` має значення `true`, а `error` та/або
`issues` пояснюють помилку оновлення.

## Відомості про камеру

Коли `peripheral.type == "camera"`, `peripheral.camera` містить:

| Поле | Значення |
| --- | --- |
| `camera_name` | Необов'язкова точна назва libcamera, яку приймає `CameraInputOptions`. Вона відсутня для камери, яку поточний API вводу не може вибрати. |
| `model` | Модель пристрою, якщо її повідомив провайдер. |
| `backend` | Серверна частина виявлення, наприклад `mipi` або `v4l2`. |
| `modes` | Дискретні розміри або явні діапазони розмірів, частота кадрів, ознака підтримки та причина відхилення. |

Підтримку класифікує Sentinel, застосовуючи правила, які цей пакет Core встановлює в `/usr/share/simaai-sentinel/support/neat-core.json`, тож результат відповідає типовому профілю libcamera встановленого `CameraInput` (`profile=Default`, який вибирає камери за `camera_name`). Клієнт зберігає цей результат і не зондує, не перекласифіковує, не захоплює,
не налаштовує та не передає потік із камери. Тому підтримка в каталозі не гарантує, що подальше
ексклюзивне захоплення буде успішним.

Ці правила не класифікують raw V4L2 профіль Metoak SIMOR (`CameraProfile::MetoakSimor`, RAW8 1920×360, вибирається через `profile` і необов'язковий `device`). Правила не мають умов для окремих сенсорів, тому сенсор SIMOR (назва починається з `simor_metoak`), який Sentinel показує як камеру `mipi`, отримує таку саму класифікацію режимів ISP, як і будь-який інший сенсор MIPI. Для цієї камери `supported: true` означає лише, що режим відповідає серверній частині, формату, частоті кадрів і розміру виходу ISP типового профілю; це не означає, що libcamera кваліфіковано для цього сенсора. Вибирайте камеру SIMOR через `profile=MetoakSimor`, як описано в [`CameraInput`](/reference/nodes/camera-input), а не через її `camera_name` із каталогу.

## Відомості про периферійні пристрої будь-якого типу

Кожен периферійний пристрій, незалежно від `type`, містить відомості, специфічні для свого типу, у
`details_json`: це компактний об'єкт JSON, який Sentinel публікує під ключем запису з назвою `type`
(наприклад, `camera`, `microphone` або `lidar`). Якщо цей ключ відсутній або має значення `null`,
`details_json` дорівнює `"{}"`. Python також надає `details`, що декодує `details_json` у новий `dict`.

`details_json` — офіційний спосіб читати типи периферійних пристроїв, для яких Core не має типізованого
доступу. Новим типом пристрою можна користуватися, щойно Sentinel про нього повідомить, без оновлення
Core. Усі поля та значення зберігаються, зокрема поля, яких цей випуск Core не знає; JSON серіалізується
повторно, тому порядок ключів і пробіли можуть відрізнятися від відповіді демона. Камери мають і
`details_json`, і типізоване поле `camera`.

Python:

```python
for peripheral in pyneat.peripherals.list():
    if peripheral.type == "microphone":
        print(peripheral.id, peripheral.details.get("channels"))
```

C++:

```cpp
#include <nlohmann/json.hpp>

for (const auto& peripheral : simaai::neat::peripherals::list()) {
  if (peripheral.type == "microphone") {
    const auto details = nlohmann::json::parse(peripheral.details_json);
    // Read details.value("channels", 0) and other provider fields.
  }
}
```

`details_json` можна розібрати будь-якою бібліотекою JSON; у прикладі використано nlohmann/json.

Для типу, відмінного від `camera`, значення відомостей, яке не є об'єктом JSON, не призводить до
помилки `list()`: такий периферійний пристрій залишається в каталозі, а `details_json` дорівнює `"{}"`.
В іншому Core не перевіряє відомості типів, для яких не має типізованого доступу. Неправильні відомості
`camera` є дефектом протоколу, і `list()` завершується помилкою розбору. Типізовані поля, як-от `camera`,
ігнорують невідомі їм необов'язкові поля протоколу v1; ці поля залишаються доступними в `details_json`.
Core також приймає верхньорівневі журнал `changes` і стан `support`, які Sentinel публікує з кожним
знімком, але не надає їх.

## Помилки й область дії

`list()` породжує `NeatError` зі стабільним кодом, якщо служба відсутня або надто стара, щоб надавати
каталог, доступ заборонено, час запиту
вичерпано, демон не готовий або відповідь неправильна, завелика чи несумісна. Повідомлення містить
наступну операційну дію. Див. [каталог кодів помилок](./error-codes.md).

Якщо Sentinel не встановлено або він надто старий, щоб надавати каталог периферійних пристроїв,
встановіть або оновіть його командою `sima-cli neat install sentinel`.
Якщо його встановлено, але не запущено, запустіть `simaai-sentinel.service`.

Цей API під'єднується лише до `/run/simaai-sentinel/api.sock` на локальному DevKit. Він не
використовує SSH і не вибирає віддалену плату. Insight і майбутні клієнти CLI під'єднуються до демона
як рівноправні клієнти, а не через Core.

Цей випуск надає одноразове читання каталогу. Підписки на події, запити оновлення та керування життєвим
циклом демона не входять до публічного API Core.
