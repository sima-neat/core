# Діагностика та налагодження

## GraphReport

`GraphReport` збирає структуровану діагностику:
- рядок конвеєра (для відтворення)
- канонічний `error_code` (для машинної класифікації)
- `repro_note` (короткий опис для людини + підказка)
- звіти вузлів і назви елементів, що їм належать
- повідомлення шини та подробиці помилок
- необов’язкові лічильники потоку та часу

Коли виникає помилка, `NeatError` містить `GraphReport`, який можна записати в журнал або
серіалізувати.

## Таксономія помилок

Помилки фреймворку використовують стабільні сімейства кодів:

| Код помилки | Значення | Типове виправлення |
| --- | --- | --- |
| `misconfig.pipeline_shape` | Порушення контракту щодо порядку або форми вузлів | Переконайтеся, що `Input()` стоїть першим у push-конвеєрах, а `Output()` останнім у pull-конвеєрах |
| `misconfig.caps` | Невідповідність перевизначення caps у фреймворку або контрактів суміжних вузлів | Узгодьте `caps_override` та оголошені контракти вузлів |
| `misconfig.input_shape` | Форма або тип даних вхідного тензора, кадру чи зразка не відповідає контракту моделі | Подайте дані очікуваної форми й типу або налаштуйте попередню обробку моделі |
| `misconfig.runtime_abi_mismatch` | Neat і плагін середовища виконання використовують несумісні ABI | Встановіть Neat Library і середовище виконання узгоджених версій |
| `misconfig.graph_element_name` | Власному елементу неможливо призначити стабільне ім’я вузла | Призначте власним елементам стабільні унікальні імена |
| `misconfig.input_capacity` | Розміри зображення з джерела перевищують обмеження, задані для попередньої обробки | Збільште `input_max_width` / `input_max_height` або масштабуйте зображення перед етапом моделі |
| `misconfig.media_caps` | Суміжні етапи GStreamer потребують несумісних медіа-caps | Узгодьте формат, роздільну здатність і частоту кадрів або вставте перетворення |
| `misconfig.media_format` | Етап отримав непідтримуваний медіаформат | Налаштуйте підтримуваний формат або вставте перетворення формату |
| `misconfig.tensor_dtype_missing` | Контракт тензора не задає dtype або формат | Оголосіть підтримуваний dtype тензора в контракті попереднього етапу |
| `misconfig.option_out_of_range` | Параметр етапу недійсний для поточного тензора | Виберіть значення з діапазону, який показує діагностика |
| `build.parse_launch` | Збій `gst_parse_launch`, для якого немає точнішої класифікації | Перегляньте доданий звіт, щоб побачити контекст парсера |
| `build.pipeline_syntax` | Недійсний синтаксис власного фрагмента GStreamer | Виправте фрагмент і перевірте його за допомогою `gst-launch-1.0` |
| `build.plugin_missing` | Не встановлено потрібний елемент GStreamer або плагін кодека | Встановіть або замініть його й перевірте за допомогою `gst-inspect-1.0` |
| `build.property_invalid` | Властивість елемента невідома або недійсна | Перевірте назву та значення властивості за допомогою `gst-inspect-1.0` |
| `runtime.pull` | Операція pull завершилася збоєм без точнішої першопричини | Перегляньте доданий звіт і першу помилку на попередніх етапах |
| `runtime.element_failed` | Етап завершився збоєм, для якого немає точнішого зіставлення | Виправте вказаний етап і вхідні дані, що надходять до нього |
| `runtime.output_timeout` | Обчислювальне ядро (kernel) не завершило виконання за відведений час очікування | Звільняйте задіяні буфери тільки після завершення роботи ядра або підтвердженого відновлення пристрою |
| `runtime.unexpected_eos` | Конвеєр досяг EOS раніше, ніж отримано потрібний вихід | Перевірте, чи джерело не надіслало EOS передчасно, і подайте достатньо вхідних даних |
| `io.parse` | Помилка розбору або схеми JSON чи конфігурації етапу | Перевірте синтаксис конфігурації та обов’язкові поля |
| `io.open` | Помилка відкриття, читання або запису файлу під час збереження чи завантаження графа | Перевірте наявність шляху, права доступу та стан сховища |
| `io.file_not_found` | Вхідного файлу не існує | Виправте шлях і переконайтеся, що файл є на DevKit |
| `io.permission_denied` | Файл або пристрій недоступний для читання | Виправте власника або права доступу |
| `io.rtsp_connection_failed` | Не вдається з’єднатися з RTSP-джерелом | Перевірте URL, доступність, сервер і облікові дані |
| `io.camera_not_found` | Запитана камера недоступна | Виберіть камеру, про яку повідомляє система, або використайте камеру за замовчуванням |
| `io.model_not_found` | Запитаного архіву моделі не існує | Виправте шлях до моделі та переконайтеся, що її встановлено |
| `io.source_ended` | Джерело вхідних даних штатно досягло кінця | Припиніть читати з нього або подайте більше вхідних даних |
| `codec.invalid_h264_stream` | Вхідні дані не містять дійсних кадрів H.264 | Подайте повний потік H.264 або виправте кодек |
| `codec.decode_failed` | Декодер дав збій уже після того, як прийняв потік | Перевірте кодек і цілісність вхідних даних |
| `codec.encode_failed` | Кодувальник не зміг закодувати надані кадри | Перевірте формат вхідних даних, роздільну здатність і налаштування кодувальника |
| `resource.memory_allocation_failed` | Не вдалося виконати потрібне виділення пам’яті | Зменште споживання пам’яті робочим навантаженням і звільніть пам’ять, зайняту іншими застосунками або конвеєрами |
| `resource.device_memory_exhausted` | Не вдалося виділити DMA/CMA-пам’ять пристрою | Зменште кількість одночасних потоків, роздільну здатність або обсяг буферизації |
| `resource.output_pool_exhausted` | Усі вихідні буфери досі зайняті | Звільніть zero-copy виходи або використовуйте власні копії |
| `resource.buffer_too_small` | Буфер менший за оголошений обсяг корисних даних | Виправте розміри або крок (stride) чи виділіть потрібну кількість байтів |
| `resource.disk_full` | Запис не вдався, бо сховище заповнене | Звільніть місце або виберіть інше місце призначення |
| `infra.dispatcher_unavailable` | Не вдається отримати середовище виконання прискорювача | Зупиніть інші робочі навантаження, що конкурують за прискорювач, і перевірте сумісність DevKit |
| `infra.accelerator_execution_failed` | Прискорювач не зміг виконати етап моделі | Перезапустіть конвеєр і зменште кількість одночасних завдань на прискорювачі |
| `DispatcherUnavailable` | Застаріле написання `infra.dispatcher_unavailable` | Переведіть обробники на канонічний інфраструктурний код |
| `internal.plugin_failure` | Збій плагіна без класифікації, за якою користувач міг би щось виправити | Збережіть звіт і зверніться до служби підтримки |

`PullError.code` використовує ту саму таксономію (не лише шляхи з винятками).
Назви констант C++ і Python, а також рекомендації з міграції для застосунків, які зіставляли
попередні узагальнені коди, див. у [каталозі кодів помилок](/reference/error-codes).

У повідомленнях у робочому режимі навмисно не наводяться внутрішні подробиці GStreamer. Режим
докладного налагодження плагінів додає необроблені домен і код GError, фабрику елемента, повідомлення
та структуровані подробиці плагіна. Розпізнані облікові дані й секретні параметри URL, зокрема
userinfo в URI, `auth`, `playback-token`, `hdnts`, `stream-key` і `tkn`, приховуються, перш ніж
зберігається будь-яка з цих форм. У рядках конвеєра, фрагментах Node, командах відтворення та
серіалізованому JSON, що потрапляють у звіти, ці дані теж приховуються, а виконуваний конвеєр,
який зберігається всередині, не змінюється.

## Програмна обробка

```cpp
#include "pipeline/ErrorCodes.h"
#include "pipeline/NeatError.h"

try {
  auto run = graph.build(input);
  simaai::neat::Sample out;
  simaai::neat::PullError perr;
  const auto st = run.pull(500, out, &perr);
  if (st == simaai::neat::PullStatus::Error) {
    if (perr.code == simaai::neat::error_codes::kMediaCaps) {
      // Fix the incompatible upstream/downstream media contract.
    } else {
      // Handle another specific code, including future codes, or report it.
    }
  }
} catch (const simaai::neat::NeatError& e) {
  if (e.report().error_code == simaai::neat::error_codes::kPluginMissing) {
    // Install or replace the missing GStreamer component.
  }
}
```

## Параметри налагодження (змінні середовища)

Основні змінні середовища (докладніше див. у розділі [Архітектура](/develop-apps/contribute/architecture)):
- `SIMA_GST_DOT_DIR`: запис DOT-графів у разі збоїв
- `SIMA_GST_BOUNDARY_PROBES`: лічильники потоку на межах
- `SIMA_GST_ELEMENT_TIMINGS`: час виконання кожного елемента
- `SIMA_GST_FLOW_DEBUG`: лічильники потоку для кожного елемента
- `SIMA_GST_ENFORCE_NAMES`: примусове дотримання контракту іменування

Щоб додати необроблений контекст GStreamer із прихованими чутливими даними до `NeatError::what()` і
`GraphReport.repro_note`, задайте обидві змінні для команди, що завершується збоєм:

```bash
SIMA_NEAT_VERBOSE_LEVEL=2 \
SIMA_NEAT_VERBOSE_TOPICS=gstreamer \
./your-neat-application
```

`NEAT_LOG_LEVEL=debug` не є налаштуванням Neat Library. У звичайній роботі тримайте докладний вивід
вимкненим: він призначений для коротких діагностичних запусків і може містити специфічні для
розгортання шляхи або адреси медіаданих, хоча розпізнані поля облікових даних приховуються.

## Порядок налагодження

1) Спочатку зафіксуйте `GraphReport.error_code` і визначте за ним категорію збою.
2) Зафіксуйте `GraphReport.repro_note`, щоб отримати конкретний контекст і вбудовану підказку.
3) Зафіксуйте текст конвеєра: `Graph::describe_backend()` або `last_pipeline()`.
4) Зафіксуйте структуровану діагностику: `MeasureReport::to_text()` або `NeatError::report()`.
5) Знайдіть у `GraphReport.bus` джерело першої термінальної `ERROR` та її подробиці.
6) Якщо середовище виконання зависає або спрацьовують тайм-аути, увімкніть зонди на межах або елементах, щоб визначити, де зупиняється потік.

Рекомендований набір даних для служби підтримки:
- `error_code`
- `repro_note`
- повний `pipeline_string`
- перші 3–5 термінальних помилок шини (`GraphReport.bus`)
- перевизначення змінних середовища, використані під час run/validate

## Звіт про продуктивність клієнтського графа

Для звітів про пропускну здатність, затримку та споживану потужність експортуйте результати
запуску графа у форматі JSON:

```cpp
Run run = graph.build(RunOptions{});

TelemetryMonitor telemetry_monitor; // board power, temperatures, CPU usage, and memory
telemetry_monitor.start();
auto scope = run.start_measurement();
// run your normal push/pull loop here, then:
auto report = scope.stop();
Telemetry telemetry = telemetry_monitor.stop();
std::cout << report.to_text() << telemetry;
```

Експорт явно розмежовує області охоплення метрик:

- `run.graph_metrics.throughput_fps` — головний показник на рівні графа. Поле `run.graph_metrics.power`
  заповнюється лише застарілим `RunOptions::enable_board_power()`; натомість використовуйте `TelemetryMonitor`.
- `run.node_metrics[]` містить лише затримку вузлів і плагінів; споживана потужність вузлів і плагінів навмисно не наводиться.
- Поля `latency_semantics` і `aggregation` показують, чи наведено значення за весь час виконання, чи зміни за інтервал вимірювання.
- `plugin_metrics_unattributed[]` зберігає рядки ядер і плагінів, які не вдалося зіставити рівно з одним вузлом.

Для інтервалу вимірювання викличте `Run::start_measurement()` і передайте отриманий `MeasureReport` у
`run_to_json(run, report, ...)` / `save_run_json(run, report, ...)`. Значення `min_ms`/`max_ms` вузлів
за інтервал позначаються як недоступні: мінімум і максимум за окремий інтервал неможливо точно
визначити з накопичених мінімумів і максимумів без окремих лічильників за цей інтервал.

Примітка щодо споживаної потужності: на поточній платі DVT можна перевірити передавання параметрів і
структуру JSON, але її показники потужності у ватах не вважаються числово достовірними. Цільова
платформа для перевірки значень споживаної потужності — апаратне забезпечення SOM.

## Типові збої → способи усунення

| Симптом | Ймовірна причина | Виправлення |
| --- | --- | --- |
| `missing ... plugin` | Не знайдено плагін GStreamer | Перевірте `GST_PLUGIN_PATH`, виконайте `gst-inspect-1.0 <plugin>` |
| `appsink 'mysink' not found` | Немає кінцевого `Output()` | Переконайтеся, що `Output` є останнім вузлом у конвеєрах run/build |
| `caps_override is set; renegotiation disabled` | caps закріплено | Приберіть `caps_override` або тримайте вхідні caps незмінними |
| `tensor caps change not supported` | Форма або dtype тензора змінюється під час виконання | Тримайте форму й dtype тензора незмінними (без повторного узгодження) |

Структуровані помилки плагінів і практичні підказки див. у розділі
[Усунення несправностей](/reference/troubleshooting).

## Відновлення середовища виконання платформи

На Platform 3.0.0 недоступний диспетчер означає помилку, яку треба дослідити, а не сигнал
запускати застарілі служби. Core не ініціалізує пам’ять MLA і не скидає віддалені процесори
у відповідь на помилку диспетчера. Застарілий код і скрипт відновлення вилучено; використовуйте
схвалену для платформи процедуру відновлення.

Якщо драйвер повідомляє, що стан завершення операції невідомий, не звільняйте його DMA-буфери
й не повертайте до пулу буфери, які спочатку з нього отримали. Закриття файлового дескриптора, зупинка застосунку чи перезапуск
служби не доводять, що апаратура припинила звертатися до пам’яті. Перед повторною спробою
зберіть звіт про збій і виконайте схвалену для платформи процедуру відновлення.

### Узгоджуйте пакети Core і Scheduler {#keep-core-and-scheduler-packages-matched}

Встановлюйте Core разом із набором пакетів Scheduler, вибраним для цього випуску Core. До Scheduler належать узгоджені з ним залежності Runner, Kernels, Codecs і прошивки. Збіг публічного C++ ABI сам по собі не означає сумісності під час виконання.

Використовуйте опубліковані залежності, які вибирає `build.sh`, або передайте повний узгоджений набір DEB-пакетів Scheduler через `--scheduler PATH`. Див. [Локальні залежності](/develop-apps/contribute/build-test/local-dependencies/).

Щоб оновити плату, встановіть повний набір Core за інструкцією [Встановлення або оновлення Neat Library](/getting-started/neat-library/install-or-update/). Вибраний інсталятор Scheduler перевіряє набір пакетів і керує активацією прошивки. Якщо перевірка не проходить, отримайте узгоджений набір Core/Scheduler; не підміняйте записи про встановлення (receipts) і не встановлюйте примусово окремі несумісні пакети середовища виконання чи прошивки.
