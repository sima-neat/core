# Усунення несправностей

Кожен запис має вигляд **Симптом → Причина → Виправлення**. Заголовки із симптомами
містять точні рядки помилок: шукайте на цій сторінці (Ctrl-F) повідомлення, яке ви
бачите. Кожен запис перевірено за поточним вихідним кодом або відтворено на DevKit.

Якщо не знаєте, з чого почати, перейдіть до розділу
[Діагностика, якщо причина невідома](#when-youre-stuck-diagnostics).

## Встановлення та середовище

### 1. `pyneat is not importable. Either Neat is not installed, or the venv is not activated.`

:::info Причина
Віртуальне середовище `pyneat` не активоване, або wheel-пакет не встановлено в середовищі, у якому ви запускаєте код.
:::

:::tip Виправлення
Перш ніж запускати будь-що на Python, активуйте середовище DevKit:
```bash
source ~/pyneat/bin/activate
```
:::

### 2. Плагін GST не завантажується: `undefined symbol: _ZN16simaaidispatcher14DispatcherBase14submitPrepared...`

:::info Причина
Спільні бібліотеки середовища виконання Neat не входять до шляху пошуку динамічного завантажувача, тому плагіни GStreamer не можуть розв’язати символи середовища виконання під час завантаження.
:::

:::tip Виправлення
Перед запуском додайте теку середовища виконання до `LD_LIBRARY_PATH`:
```bash
export LD_LIBRARY_PATH=/usr/lib/aarch64-linux-gnu/neat/runtime:$LD_LIBRARY_PATH
```
:::

### 3. Відсутній архів моделі

:::info Причина
Архів моделі `.tar.gz`, на який посилається ваш код (або `SIMA_YOLO_TAR` / `SIMA_RESNET50_TAR` / `SIMA_MODEL_TAR`), відсутній на диску.
:::

:::tip Виправлення
Завантажте його з Model Browser, як описано в розділі [Підготовка архівів моделей](/tutorials/before-you-run#prepare-model-archives).
:::

## Збирання

### 4. `find_package(SimaNeat CONFIG)` не знаходить пакет

:::info Причина
CMake не може знайти `SimaNeatConfig.cmake` (його встановлено в `lib/cmake/SimaNeat/`). У нативних встановленнях на DevKit він лежить у стандартному системному префіксі; під час крос-збирання в SDK sysroot не входить до `CMAKE_PREFIX_PATH`.
:::

:::tip Виправлення
Експортуйте `SYSROOT` і нехай ваш `CMakeLists` додасть його до шляху префіксів (так робить [шаблон Hello Neat](/develop-apps/hello-neat/minimal)):
```cmake
if(DEFINED ENV{SYSROOT} AND NOT "$ENV{SYSROOT}" STREQUAL "")
  list(APPEND CMAKE_PREFIX_PATH "$ENV{SYSROOT}/usr/lib/aarch64-linux-gnu")
endif()
find_package(SimaNeat REQUIRED CONFIG)
```
:::

## Завантаження та налаштування моделі

### 5. `failed to read image: <path>`

:::info Причина
OpenCV (`cv2.imread` / `cv::imread`) повернув null: файлу не існує, він недоступний для читання або не є зображенням, яке можна декодувати.
:::

:::tip Виправлення
Перш ніж створювати вхідний тензор, перевірте шлях і переконайтеся, що файл є коректним JPEG/PNG.
:::

### 6. `reason=topk must be > 0` (від `boxdecode`)

:::info Причина
У моделі детекції `ModelOptions.top_k` залишився рівним `0`, а етапу декодування рамок потрібне додатне граничне значення.
:::

:::tip Виправлення
Задайте додатне значення `top_k` (у навчальних посібниках використовують `100`):
```python
opt.top_k = 100
```
*(Повідомлення походить із плагіна декодування рамок EV74.)*
:::

### 7. `preproc_upsample_not_supported`

:::info Причина
Зображення з джерела менше за вхідну роздільну здатність моделі, тому попередній обробці довелося б **збільшувати масштаб**, а старіша прошивка попередньої обробки EV74 цього не робить (вона вміє лише зменшувати).
:::

:::tip Виправлення
Подавайте зображення з джерела, не менше за вхід моделі (наприклад, ≥ 640×640 для YOLOv8), або оновіть `neat-ev74-firmware` до збірки з ядром збільшення масштабу.
*(Повідомлення походить із плагіна/прошивки попередньої обробки EV74.)*
:::

### 8. Низький `score_threshold` → стрибки затримки постобробки

:::info Причина
Що нижчий поріг детекції, то більше кандидатних рамок проходить порогову фільтрацію, а вартість NMS зростає приблизно пропорційно **квадрату** кількості рамок, що пройшли.
:::

:::tip Виправлення
Знижуйте поріг лише настільки, наскільки потрібно, щоб уловити слабкі детекції, і обмежуйте найгірший випадок за допомогою `top_k`. Див. [Зчитування рамок виявлення](/tutorials/read-detection-boxes).
:::

## Запуск інференсу

### 9. `misconfig.media_caps … Internal data stream error … reason not-negotiated (-4)`

:::info Причина
Для входу у вигляді необроблених зображень етап попередньої обробки не ввімкнено / тип входу не оголошено, тому caps не можуть узгодитися між appsrc і першим етапом.
:::

:::tip Виправлення
Оголосіть у `ModelOptions` вхід типу «зображення» та пресет попередньої обробки:
```python
opt.preprocess.kind = pyneat.InputKind.Image
opt.preprocess.preset = pyneat.NormalizePreset.COCO_YOLO
```
:::

### 10. `No channel available (all candidate channel opens failed)`

:::info Причина
Запит на виконання не зміг відкрити сумісний канал EV74. Одна з можливих причин — неузгоджений набір пакетів Scheduler, Runner, Kernels або прошивки після часткового оновлення.
:::

:::tip Виправлення
Встановіть повний комплект Core разом із вибраними для нього залежностями Scheduler за інструкцією [Встановлення або оновлення Neat Library](/getting-started/neat-library/install-or-update/). Перевіряйте [узгодженість пакетів середовища виконання](/reference/diagnostics/#keep-core-and-scheduler-packages-matched), а не порівнюйте Git-хеші не пов’язаних між собою компонентів і не встановлюйте примусово окремі пакети прошивки.
:::

### 11. `frame=N rtsp_timeout`

:::info Причина
Під час отримання RTSP-потоку сплив час очікування: URL неправильний або потік не передає кадри.
:::

:::tip Виправлення
Переконайтеся, що джерело доступне за URL-адресою RTSP і передає кадри. Перевірте транспортний протокол (TCP чи UDP). Див. [Отримання RTSP-потоку](/tutorials/consume-rtsp-stream).
:::

### 12. `Camera buffer is not one forwardable DMA-BUF and copying is disabled`

:::info Причина
`CameraInputOptions::allow_cpu_fallback` за замовчуванням має значення false, тому Neat передає далі власний DMA-BUF камери й ніколи не копіює. Стек камери видав кадр, який не є одним DMA-BUF із площинами, розташованими впритул одна за одною (наприклад, окрема площина на кожен fd або пам’ять, що не є DMA-BUF).
:::

:::tip Виправлення
Залишайте суворий режим без копіювання (zero-copy) з пакетом `libcamera` платформи. Якщо вам доводиться працювати зі стеком камери, який не видає кожен кадр як один DMA-BUF, явно ввімкніть копіювання для сумісності:

<CodeTabs>
<CodeTab label="C++" lang="cpp">

```cpp
simaai::neat::CameraInputOptions camera;
camera.allow_cpu_fallback = true;
```

</CodeTab>
<CodeTab label="Python" lang="python">

```python
camera = pyneat.CameraInputOptions()
camera.allow_cpu_fallback = True
```

</CodeTab>
</CodeTabs>

В адаптивному режимі наступні етапи CVU/MLA однаково отримують DMA-BUF. Копіювання (у CMA DMA-BUF) відбувається лише тоді, коли кадр камери не є одним DMA-BUF із площинами, розташованими впритул одна за одною.
:::

### 13. `misconfig.media_caps … libcamerasrc … not-negotiated (-4)`

:::info Причина
Запитані caps камери не відповідають жодному режиму, який може видати стек камери, або оверлей плати чи драйвер некоректно зробили камеру доступною в системі.
:::

:::tip Виправлення
Перевірте той самий формат, роздільну здатність і частоту кадрів поза Neat:

<ShellCommand prompt="devkit">
gst-launch-1.0 -e libcamerasrc ! \
  'video/x-raw,format=NV12,width=1920,height=1080,framerate=30/1' ! \
  identity eos-after=30 ! fakesink
</ShellCommand>

Якщо ця команда завершується помилкою, спочатку виправте оверлей, кабель, драйвер сенсора або режим камери. Скористайтеся [посібником з інтерфейсів камер MIPI для Modalix DevKit](https://developer.sima.ai/hardware/getting-started/standalone-mode/mipi-camera-interfaces), щоб звірити `.dtbo` і порядок перевірки через libcamera. Якщо команда проходить, порівняйте caps зі своїми `CameraInputOptions`.
:::

### 14. Кадри з камери мають зелений, фіолетовий або сильний сторонній відтінок

:::info Причина
Кадр інтерпретується з неправильним форматом пікселів або перетворенням кольорів. Найпоширеніша помилка — обробляти кадри камери у форматі `NV12` як байти RGB/BGR. Якщо такий самий відтінок з’являється ще до Neat, імовірно, проблема в налаштуванні ISP камери або в конвеєрі libcamera.
:::

:::tip Виправлення
Узгоджуйте caps камери з форматом попередньої обробки моделі:

- запитуйте `camera.format = "NV12"` для рекомендованого маршруту через модель;
- задайте `preprocess.color_convert.input_format = PreprocessColorFormat::NV12`;
- уникайте `videoconvert`/`videoscale` на CPU в робочому маршруті моделі;
- запускайте короткий димовий тест `gst-launch-1.0 libcamerasrc ... ! videoconvert ! jpegenc` лише для того, щоб з’ясувати, чи є відтінок ще до Neat.
:::

### 15. `frame=N output_timeout` у навчальному посібнику з камерою MIPI

:::info Причина
Жоден вихідний зразок не надійшов до застосунку, поки не сплив час очікування pull, заданий у навчальному посібнику. У графі «камера → модель» це може означати, що камера не видала кадри, узгодження caps не вдалося, маршрут моделі ще запускається або наступний етап, наприклад BoxDecode, не видав вихідних даних.
:::

:::tip Виправлення
Спочатку перевірте шлях лише з камерою. Потім знову запустіть навчальний посібник із довшим часом очікування та виведенням інформації про бекенд:

<ShellCommand prompt="devkit">
python3 share/sima-neat/tutorials/023_run_mipi_camera_model/run_mipi_camera_model.py \
  --model /path/to/model.tar.gz --frames 2 --decode none \
  --pull-timeout-ms 15000 --print-backend
</ShellCommand>

Робочий маршрут має містити `libcamerasrc`, `neatcamerabridge` (коли ввімкнено резервний режим), `neatkernelrunner`, `neatprocessmla` і `appsink`. Для маршрутів із BoxDecode також переконайтеся, що токен `--decode` і порогові значення відповідають архіву моделі.
:::

### 16. Низька пропускна здатність графа або втрата кадрів у потоці реального часу

:::info Причина
Граф перебуває під зворотним тиском (backpressure). Типові причини: цикл pull, який не встигає, вихідні зразки, які утримуються надто довго, журналювання під час обробки кожного кадру, політика черги, що не відповідає джерелу, або потік у реальному часі без явної політики відкидання / свіжості.
:::

:::tip Виправлення
Повторно використовуйте той самий екземпляр `Run`, а потім явно задайте політику середовища виконання:

- Використовуйте `RunPreset::Realtime` / `pyneat.RunPreset.Realtime` для входів у реальному часі, де важлива свіжість.
- Використовуйте `RunPreset::Reliable` / `pyneat.RunPreset.Reliable` для пакетної або файлової обробки, де важливий кожен вхід.
- Використовуйте `try_push(...)`, коли застосунок не повинен блокуватися на заповненій черзі.
- Задайте `on_input_drop`, щоб підраховувати відкидання за `stream_id`, `frame_id`, `port_name` і причиною.
- Забирайте дані безперервно. Заповнена вихідна черга може гальмувати весь граф.
- Звільняйте або копіюйте виходи, перш ніж подавати нові дані, якщо застосунок може утримувати буфери, що належать середовищу виконання.

Для графів із кількома потоками даних зберігайте `stream_id` і `frame_id` та перевіряйте кількість виходів для кожного потоку. Сумарний FPS може приховати один потік, якому бракує даних. Див. [Запуск графа → Оптимізуйте пропускну здатність, не вдаючись до самообману](/develop-apps/development-workflow/pipeline#tune-throughput-without-lying-to-yourself).
:::

### 17. `unknown input/output name`, `no unambiguous default input` або `no unambiguous default output`

:::info Причина
Граф має іменовані кінцеві точки, а застосунок виконав push або pull із неправильним іменем чи викликав `push(...)` / `pull(...)` без імені на графі, де можливих кінцевих точок більше однієї.
:::

:::tip Виправлення
Перегляньте імена, перш ніж виконувати push чи pull:

```python
run = graph.build()
print("inputs:", run.input_names())
print("outputs:", run.output_names())
```

Потім використовуйте точне ім’я кінцевої точки:

```python
run.push("image", [tensor])
sample = run.pull("detections", timeout_ms=2000)
```

`Graph("name")` є діагностичною міткою. Він не створює кінцевої точки. Кінцеві точки створюються через `nodes.input("name")` і `nodes.output("name")`.
:::

### 18. `pull(...)` не повертає вихідних даних до закінчення часу очікування

:::info Причина
До запитаного виходу не надійшов жоден зразок, поки не сплив час очікування. Можливо, граф ще працює, ім’я виходу неправильне, вхід перебуває під зворотним тиском, граф закрито або сталася помилка середовища виконання.
:::

:::tip Виправлення
Розрізняйте тайм-аут, закриття та помилку. У C++ використовуйте структуроване перевантаження pull:

```cpp
simaai::neat::Sample sample;
simaai::neat::PullError error;

switch (run.pull("detections", /*timeout_ms=*/1000, sample, &error)) {
case simaai::neat::PullStatus::Ok:
  break;
case simaai::neat::PullStatus::Timeout:
  // Keep waiting, push more input, or report timeout.
  break;
case simaai::neat::PullStatus::Closed:
  // End of stream.
  break;
case simaai::neat::PullStatus::Error:
  std::cerr << error.code << ": " << error.message << "\n";
  break;
}
```

Також перевірте `run.last_error()`, імена кінцевих точок, dtype/розкладку/формат входу та те, чи ваш застосунок безперервно забирає дані з кожної вихідної гілки.
:::

### 19. Старі фрагменти коду падають через `push_timeout_ms`, `pull_or_throw`, `input_max_*` на кореневому рівні або `boxdecode_original_*`

:::info Причина
Фрагмент написано для старішого набору опцій або для приватного/внутрішнього шляху. Поточний код застосунку має використовувати публічні API `ModelOptions`, `RunOptions` і `Run`.
:::

:::tip Виправлення
Використовуйте поточні публічні назви:

- Для керування тиском на вході використовуйте `RunOptions.queue_depth`, `overflow_policy` і `try_push(...)`.
- Замість `pull_or_throw` використовуйте `pull(...)` або структуроване перевантаження з `PullStatus`.
- Якщо старий фрагмент задає поля `input_max_*` на кореневому рівні, перенесіть динамічні обмеження входу в `ModelOptions.preprocess.input_max_width`, `input_max_height` і `input_max_depth` і задавайте їх лише тоді, коли вам свідомо потрібні межі.
- Щоб перерахувати координати в BoxDecode, використовуйте метадані попередньої обробки. Не задавайте в нових прикладах застарілі поля початкового розміру.

Якщо сторінка, з якої ви скопіювали код, досі показує старе написання, вважайте її застарілою документацією та створіть звіт про помилку в документації, щоб наступний читач не потрапив у ту саму пастку.
:::

## Тензори та взаємодія з Python

### 20. `… expects a TensorList; pass [tensor] instead of a single Tensor`

:::info Причина
До `run` / `push` / `build` передано окремий `Tensor` (або `Sample`); API вимагає явного списку. Так зроблено навмисно, це не помилка.
:::

:::tip Виправлення
Передайте його у списку: `model.run([tensor])`, `run.push([tensor])`, `graph.build([tensor])`.
:::

### 21. `image-mode Tensor input requires explicit image format metadata`

:::info Причина
Модель із входом-зображенням отримала тензор без формату пікселів, тому Neat не може інтерпретувати розкладку байтів.
:::

:::tip Виправлення
Створіть тензор з явно заданим форматом: `pyneat.Tensor.from_numpy(arr, image_format=pyneat.PixelFormat.RGB)`.
:::

### 22. `byte_format tensors cannot also specify image_format`

:::info Причина
Тензор створено одночасно з `byte_format=` (непрозорі байти) і `image_format=` (пікселі), а ці параметри взаємовиключні.
:::

:::tip Виправлення
Передавайте щось одне, а не обидва.
:::

### 23. Model із зображенням на вході на квантованій INT8-моделі повертає мало детекцій, жодної або низької якості

:::info Причина
Нормалізація вимкнена (Off). Її або явно задано `Off` (без попередження), або залишено в `Auto` без пресета й без явної статистики — тоді планувальник попереджає `preprocess.normalize=Auto resolved Off`. Коли нормалізація Off, етап квантує сирі значення пікселів 0–255.
:::

:::tip Виправлення
Для детектора, навченого на вході `[0,1]`, увімкніть нормалізацію. Для моделі, навченої на сирих пікселях `0–255`, залиште нормалізацію вимкненою.
:::

## Перехід з іншого стеку

- **«Де мій `.engine` / `.blob` / `.dlc` / `.hef`?»** — Neat завантажує архів моделі `.tar.gz`; це еквівалентний скомпільований артефакт.
- **«Як прив’язати роботу до потоку CUDA / черги OpenCL?»** — ніяк; натомість відокремте виробника від споживача за допомогою асинхронних `push`/`pull` і налаштуйте `RunOptions`.
- **«Чому пропускна здатність нижча за заявлені TOPS?»** — зазвичай причина в накладних витратах хоста, нестачі даних у черзі, зворотному тиску на виході або політиці відкидання, а не в прискорювачі. Див. [Запуск графа](/develop-apps/development-workflow/pipeline).

## Діагностика, якщо причина невідома

Почніть із цих перевірок, а не з припущень.

**Перевірте конвеєр / Run (Python і C++):**
- `graph.validate()` → `GraphReport`: перевіряє з’єднання за вбудованими контрактами ще до збирання. Перегляньте його `error_code`.
- `graph.describe()` → текстовий опис конвеєра з іменами вузлів і ланцюжком caps.
- `run.input_names()` / `run.output_names()` → імена, які приймають виклики push/pull під час виконання.
- `run.start_measurement()` / `MeasureReport` → лічильники, затримка, телеметрія вхідних потоків, час роботи плагінів/ребер і, за потреби, споживана потужність.
- `run.json(...)` / `run.save_json(...)` або C++ `save_run_json(...)` → дані про виконання після того, як через Run пройшли зразки.
- `NeatError::report()` → структуровані відомості про збій, коли запуск викидає виняток.


### Зберіть діагностичні дані для служби підтримки

Якщо вам потрібна допомога іншого розробника або служби підтримки SiMa.ai, надішліть дані, за якими інший розробник зможе відтворити проблему. Додайте:

- інформацію про версію/збірку Neat: Python `pyneat.build_info()` або C++ `sima_neat_version()`, `sima_neat_platform_version()` і `sima_neat_abi_version()`;
- назву артефакту моделі, шлях до моделі та те, як її отримано;
- найменший фрагмент коду, який можна запустити і який відтворює збій;
- форму, dtype, розкладку, формат пікселів і сімейство корисних даних входу, а також те, чи дані в граф подає застосунок (app-pushed), чи джерело належить самому графу (source-owned);
- імена кінцевих точок із `run.input_names()` і `run.output_names()`;
- JSON `GraphReport` з `graph.validate()` або `NeatError::report()`;
- JSON експорту запуску з `run.save_json(...)` або C++ `save_run_json(...)` після того, як через Run пройшли зразки;
- результати вимірювань, якщо проблема стосується затримки, пропускної здатності, відкидань або споживаної потужності.

Для проблем із кількома потоками також додайте для кожного потоку кількість вхідних, прийнятих, вихідних і відкинутих зразків. Сумарний FPS може приховати один потік, якому бракує даних.

Збираючи `GraphReport`, збережіть поля, які пояснюють, що сталося:

- `error_code` і `repro_note`;
- `pipeline_string`;
- `bus`;
- `repro_gst_launch` і `repro_env`;
- `dot_paths` і `caps_dump`;
- `boundaries` / `BoundaryFlowStats`, якщо є зонди на межах;
- `build_adaptation` для збоїв `build(input, ...)` з початковим входом;
- JSON експорту запуску для лічильників і метрик після виконання.

**Увімкніть налагоджувальний вивід фреймворку** за допомогою `SIMA_DEBUG_PROFILE` — списку компонентів для трасування, розділених комами. Вкажіть `all`, щоб трасувати все, або звузьте список:
```bash
export SIMA_DEBUG_PROFILE=all                 # everything
export SIMA_DEBUG_PROFILE=graph,gst,pipeline  # just these areas
```
Відомі компоненти: `pipeline`, `graph`, `gst`, `appsink`, `inputstream`, `tensor`. За замовчуванням змінна не задана (налагоджувального виводу немає).

**Вивантажте граф GStreamer**, щоб візуально перевірити, де ламаються caps:
```bash
export SIMA_GST_DOT_DIR=/tmp     # writes .dot graphs on build/failure; default: off
```

## Коди помилок

`NeatError` (а також `GraphReport::error_code` / `PullError::code`) повідомляють
код у форматі `domain.reason`. Фреймворк визначає саме ці коди: розгалужуйте логіку
за кодом, а подробиці читайте в повідомленні.

| Код | Коли виникає |
|---|---|
| `io.open` | Не вдалося відкрити файл або шлях до пристрою: файл відсутній, доступ заборонено або пристрій ядра відсутній (наприклад, `/dev/rpmsg*`). |
| `io.parse` | Помилка розбору JSON/конфігурації, зазвичай через некоректний контракт MPK або конфігурацію окремого етапу. |
| `misconfig.pipeline_shape` | Неправильна геометрія конвеєра або цілісність остаточних імен, наприклад неправильна кількість sink-елементів, цикл, відсутній кінцевий `Output` або дубльоване ім’я елемента. |
| `misconfig.caps` | Перевизначення caps або контракт суміжного вузла не пройшли перевірку фреймворку ще до початку потокової передачі. |
| `misconfig.media_caps` | Під час виконання не вдалося узгодження GStreamer між суміжними медіаетапами. |
| `misconfig.input_shape` | Вхідний тензор порушує контракт моделі (ранг, просторові розміри, кількість каналів). |
| `misconfig.runtime_abi_mismatch` | Невідповідність ABI фреймворку та плагінів середовища виконання, зазвичай через змішування артефактів `pyneat` і середовища виконання. |
| `build.plugin_missing` | Потрібний елемент GStreamer або плагін кодека недоступний. |
| `build.property_invalid` | Недійсна назва або значення властивості елемента GStreamer. |
| `build.pipeline_syntax` | Власний фрагмент GStreamer має недійсний синтаксис. |
| `build.parse_launch` | Збій `gst_parse_launch` не вдалося класифікувати точніше. |
| `runtime.pull` | Pull завершився збоєм, і точнішого коду (з попереднього етапу чи першопричини) немає. |
| `infra.dispatcher_unavailable` | Не вдалося отримати диспетчер MLA/EV74/A65: прошивку не завантажено, бракує ліцензії або стався апаратний збій. Резервного виконання на CPU немає. |

Це скорочена карта для усунення несправностей. Кожен код і назви констант C++/Python
наведено в [повному каталозі кодів помилок](/reference/error-codes).
