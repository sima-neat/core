:::tip Лише для довідки
Налаштування DevKit Sync під час встановлення SDK необов’язкове, і програма встановлення вже пропонує його виконати. Користуйтеся цією сторінкою як довідником про роботу DevKit Sync або коли згодом захочете під’єднати SDK до іншого DevKit.
:::

DevKit Sync поєднує Palette SDK із Modalix DevKit в одній мережі. Він відкриває один спільний робочий простір для хоста, контейнера Palette SDK і DevKit та надає допоміжну команду `dk` для запуску на апаратному забезпеченні команд, зібраних у SDK.

![Зіставлення робочого простору між хостом, контейнером і DevKit](@site/../docs/images/elxr-sdk-workspaces.svg)

Той самий робочий простір змонтовано в контейнер Palette SDK і на DevKit як `/workspace`, тому артефакти збірки, журнали, трасування та файли моделей видно з кожного середовища.

## Налаштування DevKit Sync

Якщо ви пропустили під’єднання DevKit під час встановлення або хочете змінити його пізніше,
виконайте на хості цю команду налаштування:

<ShellCommand prompt="host">
sima-cli sdk setup --devkit {devkit-ip}
</ShellCommand>

Під час налаштування:

- Якщо встановлено кілька образів SDK, виберіть встановлений образ Palette SDK %%release.sdk%%.
- Прийміть шлях монтування на DevKit за замовчуванням, `/workspace`, якщо вам не потрібен інший
  шлях.
- Введіть пароль адміністратора хоста, коли з’явиться запит на налаштування сервера NFS на хості.
- Введіть облікові дані користувача DevKit, коли з’явиться запит. Користувач за замовчуванням — `sima`,
  пароль за замовчуванням — `edgeai`.
- Починаючи з SDK 2.1.2.2, налаштування може перейти на rsync через SSH, якщо
  NFS не вдається налаштувати між хостом і DevKit.

Після успішного налаштування ви маєте побачити приблизно такий вивід:

```text
============================================================
  DevKit Connected
============================================================
  DevKit target : sima@192.168.91.221:22
  Mounted path  : /workspace
  Host export   : 192.168.74.48:/Users/joey/workspace

  You can now run DevKit binaries from this SDK shell:
    dk /workspace/<path-to-arm64-binary> [args...]
============================================================
```

В оболонці SDK виконайте `dk status`, щоб перевірити під’єднаний DevKit і
активний спосіб синхронізації робочого простору:

<ShellCommand prompt="sdk">
dk status
</ShellCommand>

## Оновлення під’єднання з SDK

Використовуйте цей спосіб, коли Palette SDK уже встановлено і потрібно під’єднати інший DevKit або оновити під’єднання після зміни IP-адреси DevKit.

У контейнері Palette SDK виконайте:

<ShellCommand prompt="sdk">
source devkit.sh {devkit-ip}
</ShellCommand>

Замініть `{devkit-ip}` на IP-адресу DevKit, який ви хочете використовувати.

Приклад:

<ShellCommand prompt="sdk">
source devkit.sh 192.168.91.221
</ShellCommand>

## Налаштування SDK без DevKit Sync

Якщо DevKit недоступний із хоста Palette SDK, ви однаково можете налаштувати робочий простір SDK без під’єднання:

<ShellCommand prompt="host">
sima-cli sdk setup
</ShellCommand>

Ви, як і раніше, можете збирати виконувані файли в контейнері Palette SDK, але для тестування їх доведеться вручну переносити на DevKit. Переконайтеся, що на DevKit встановлено сумісну версію Neat Library.

## Обмін файлами через DevKit Sync

DevKit Sync поєднує три середовища:

1. Хост
2. Контейнер Palette SDK
3. DevKit

`sima-cli sdk setup --devkit {devkit-ip}` налаштовує NFS так, щоб той самий робочий простір був доступний у всіх трьох середовищах:

- Теку робочого простору хоста експортовано через NFS на хості.
- Цю теку змонтовано в контейнер Palette SDK як
  `/workspace`.
- Той самий вміст доступний на DevKit як `/workspace` через NFS.
- Назва змонтованої теки за замовчуванням — `/workspace`, її можна змінити під час
  налаштування.

Таке налаштування дає прямий робочий процес для артефактів збірки:

- Артефакти, створені в Palette SDK, одразу видно
  на DevKit без окремого кроку розгортання.
- Агенти мають доступ до журналів, результатів, трасувань та інших проміжних файлів, що створюються,
  поки застосунок працює на DevKit.
- Розробники та агенти можуть переглядати ті самі файли в контексті одного робочого простору.

За допомогою Insight робочий простір можна переглядати у веббраузері. Деякі специфічні для SiMa.ai архіви моделей, як-от артефакти моделей `*.tar.gz`, автоматично оптимізуються для зручнішого перегляду.

## Запасний варіант через rsync

Починаючи з SDK 2.1.2.2, DevKit Sync може використовувати rsync через SSH як запасний варіант, якщо налаштувати NFS не вдалося. Це корисно в мережах або на хостах, де SSH-з’єднання з DevKit працює, але DevKit не може змонтувати NFS-експорт хоста.

Коли активний запасний варіант через rsync:

- Хост і контейнер SDK, як і раніше, використовують локальну теку `/workspace`.
- DevKit використовує синхронізований віддалений робочий простір, зазвичай
  `/workspace-rsync`.
- `dk status` показує `Sync method : rsync`, а також шляхи до локального й віддаленого
  робочих просторів.
- `dk <file> [args...]` перетворює шляхи з робочого простору SDK на шляхи в rsync-робочому просторі DevKit,
  перш ніж віддалено виконати команду.
- Перш ніж `dk` запустить файл, він автоматично синхронізує теку верхнього рівня робочого простору,
  яка містить цей файл. Наприклад, `dk apps/demo.py` синхронізує
  теку `/workspace/apps`, перш ніж запустити копію файлу на стороні DevKit.

Перевірте поточне під’єднання та спосіб синхронізації:

<ShellCommand prompt="sdk">
dk status
</ShellCommand>

Синхронізуйте поточну область робочого простору вручну:

<ShellCommand prompt="sdk">
dk sync
</ShellCommand>

Синхронізуйте певний файл або теку:

<ShellCommand prompt="sdk">
dk sync /workspace/apps
</ShellCommand>

Синхронізуйте весь робочий простір:

<ShellCommand prompt="sdk">
dk sync --all
</ShellCommand>

Коли активний запасний варіант через rsync, тримайте файли, потрібні одній команді `dk`, в одній теці верхнього рівня робочого простору. Якщо команду запущено з `/workspace/apps`, аргументи, що вказують на `/workspace/models`, лежать поза областю автоматичної синхронізації, тому їх слід синхронізувати окремо командою `dk sync
/workspace/models` або організувати проєкт так, щоб потрібні файли лежали в одній теці верхнього рівня.

## Запуск на DevKit за допомогою dk

SDK містить допоміжну команду `dk`, також відому як `devkit-run`, для запуску виконуваних файлів ARM64 на під’єднаному DevKit з оболонки SDK.

Коли ви викликаєте `dk`, SDK запускає команду на під’єднаному DevKit і перетворює шляхи, щоб файлові аргументи з контейнера правильно знаходилися на DevKit.

<ShellCommand prompt="sdk">
dk <file> [args...]
</ShellCommand>

Після компіляції застосунку C++ у робочому просторі SDK запустіть отриманий виконуваний файл ARM64 на DevKit:

<ShellCommand prompt="sdk">
dk build/sima_neat_hello
</ShellCommand>

Після створення або копіювання скрипту Python у робочий простір SDK запустіть його на під’єднаному DevKit:

<ShellCommand prompt="sdk">
dk hello_neat.py
</ShellCommand>

Для скриптів Python `dk` запускає скрипт на під’єднаному DevKit і використовує
середовище виконання PyNeat на DevKit. SDK і далі корисний як єдиний
робочий простір і середовище оркестрування, але для робочих процесів лише на Python інструментарій крос-компіляції C++ не потрібен.

:::note Звідки береться `dk`
`dk` — це функція оболонки, визначена у файлі `~/devkit-sync.rc` всередині контейнера SDK.
Оболонка завантажує її через файл `~/.bashrc`, тому вона доступна в інтерактивних сеансах.
:::
