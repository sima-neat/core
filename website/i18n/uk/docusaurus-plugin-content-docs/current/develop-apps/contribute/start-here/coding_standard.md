# Стандарт кодування

Цей посібник визначає правила внеску для коду, який потрапляє до бібліотеки SiMa.ai Neat.

## Обмеження щодо мови та API

- Використовуйте **C++20**.
- Зміни публічного API мають бути навмисними й мінімальними (`include/*` вважається стабільним).
- Надавайте перевагу зворотно сумісним розширенням над змінами, що порушують сумісність.
- Не допускайте внутрішніх деталей реалізації у встановлені/публічні заголовні файли.

## Форматування та дотримання єдиного стилю

- Форматування коду C/C++ забезпечується за допомогою `clang-format` (`.clang-format` у кореневій теці репозиторію).
- Дотримання стилю CMake забезпечується за допомогою `scripts/check_cmake_style.py`.
- Дубльовані директиви include у файлах початкового коду C/C++ заборонено.
- `.editorconfig` визначає базові правила щодо пробільних символів (LF, символ нового рядка в кінці файлу, без пробілів у кінці рядків).

Перед надсиланням змін (push) запустіть:

```bash
bash scripts/check_format.sh --changed-only
bash scripts/check_cmake_format.sh --changed-only
bash scripts/check_duplicate_includes.sh --changed-only
```

## Політика сумісності API

Сумісність публічного API — обов’язкова вимога для всіх встановлених заголовних файлів у `include/*`.

- Перевага надається доповненням, що не порушують сумісність (нові перевантаження, нові необов’язкові поля, нові API).
- Зміни сигнатур, що порушують сумісність (перейменування/видалення/зміна типу/зміна порядку параметрів/порушення поведінкового контракту), перед злиттям мають пройти процес рецензування.
- Якщо зміни, що порушує сумісність, не уникнути, спершу краще передбачити період виведення з ужитку (зберегти стару сигнатуру + додати шлях переходу на заміну), а вже потім видаляти.

### Обов’язковий процес для змін сигнатур API, що порушують сумісність

Перед злиттям зміни API, що порушує сумісність:

1. Опишіть зміну в розділі `API, ABI, and migration` опису PR.
2. Додайте аналіз впливу: заголовні файли/символи, яких стосується зміна, очікувані порушення роботи залежного коду та кроки міграції.
3. Вкажіть наміри щодо версіонування/випуску (коли цю несумісну зміну дозволено випускати).
4. Оновіть документацію та приклади під новий API в тому самому наборі змін.
5. Отримайте явне схвалення супровідника для змін API, що порушують сумісність.

## Межі модулів

Дотримуйтеся суворих правил щодо залежностей:

- `builder/` не повинен залежати від GStreamer або `pipeline/`.
- `gst/` не повинен залежати від `pipeline/`.
- `nodes/` не повинен залежати від `pipeline/`.
- `pipeline/` є оркестратором і може залежати від `gst/`, `builder/`, `nodes/`, `contracts/`, `policy/` та внутрішніх компонентів моделі.

## Вимоги до детермінованості

- Вихідні дані вузла мають бути детермінованими за однакових вхідних даних/конфігурації.
- Забезпечте стабільність і відтворюваність назв елементів.
- За можливості зберігайте детерміноване генерування рядка конвеєра.
- Змінюючи правила іменування, переконайтеся, що діагностика та перевірка й далі зіставляють елементи з вузлами, яким вони належать.

## Обробка помилок і діагностика

- Надавайте перевагу структурованим збоям із практично корисним контекстом.
- Переконайтеся, що нові шляхи збою містять достатньо подробиць для діагностики `PipelineReport`.
- Уникайте тихих резервних варіантів, які приховують помилки плагінів, caps або середовища виконання.
- Діагностика має бути потокобезпечною; оновлення з боку probe мають використовувати атомарні операції або еквівалентні примітиви без блокувань.

## Паралельність і життєвий цикл

- Ніколи не блокуйте виконання на невизначений час у шляхах завершення роботи.
- Захисно обробляйте переходи станів під час виконання (`EOS`, `NULL`, шляхи завершення роботи, стійкі до тайм-ауту).
- Логіка в потоці передавання даних (streaming thread) має бути легкою, з контрольованими побічними ефектами.

## Обов’язки щодо документації

Оновлюйте документацію, якщо наявні вказівки стають неточними або зміна запроваджує суттєві зміни в публічному API, архітектурі, контракті чи робочому процесі користувача. Оновлюйте відповідну наявну сторінку; сторінку [Архітектура](/develop-apps/contribute/architecture) змінюйте лише в разі змін архітектури або задокументованих контрактів.

Виправлення помилок, діагностика та внутрішній рефакторинг самі по собі не вимагають оновлення документації. Обґрунтування реалізації залишайте в PR або коментарях до коду, а докази перевірки — у PR. Якщо наявні вказівки залишаються точними й не потрібно пояснювати нову концепцію чи робочий процес, виберіть `No docs update needed`.

## Планка якості PR

Внесок готовий, якщо він містить:

- Чітке обґрунтування в коді та в повідомленні коміту/PR.
- Тести для нової поведінки та регресій.
- Оцінку впливу на документацію згідно з наведеною вище політикою.
- Оцінку сумісності API для змін у публічних заголовних файлах (і повний процес для змін, що порушують сумісність, у відповідних випадках).
