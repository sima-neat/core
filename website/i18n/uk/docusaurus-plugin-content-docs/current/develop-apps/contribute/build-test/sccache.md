# Neat `sccache`: короткий довідник

Neat використовує [`sccache`](https://github.com/mozilla/sccache) як засіб для запуску компіляторів C і C++. Він кешує результати компіляції, а не кінцеві пакети Neat, результати тестування, завантаження залежностей або образи Docker.

Більшості розробників нічого не потрібно встановлювати чи налаштовувати: використовуйте `build.sh` як зазвичай і перегляньте статистику кешу, яку буде виведено наприкінці.

## У двох словах

| Збірка | Рівні кешу | Куди записує | Зберігається після `--clean` |
|---|---|---|---|
| Локальна | Локальний диск користувача | Локальний диск | Так |
| Vulcan, `develop` або `main` | Локальний диск раннера, потім S3 захищеної гілки | Локальний диск і власний захищений простір імен S3 | S3 — так |
| Vulcan, push у feature-гілку | Локальний диск раннера, потім S3 гілки | Локальний диск і власний ізольований простір імен гілки | До видалення гілки |
| Vulcan, тег або непряме посилання | Локальний диск раннера, потім найближчий захищений S3 | Лише локальний диск | Постійного стану раннера немає |

Підтримувана точка входу завжди така:

```bash
./build.sh <options>
```

Не викликайте `sccache` замість компілятора й не додавайте параметри засобу запуску вручну. `build.sh` сам задає обидва засоби запуску CMake:

```text
CMAKE_C_COMPILER_LAUNCHER
CMAKE_CXX_COMPILER_LAUNCHER
```

## Локальні збірки

### Звичайне використання

Кешування ввімкнено в режимі `auto`:

```bash
./build.sh --dev-only
./build.sh --all --clean
```

Розташування кешу та його ліміт за замовчуванням:

```text
~/.cache/sima-neat/sccache
10 GiB
```

Кеш розташований поза `build/`. Видалення `build/` або параметр `--clean` не видаляє кешовані результати компіляції.

Якщо `sccache` немає в `PATH`, `build.sh` завантажує зафіксований випуск до:

```text
${XDG_CACHE_HOME:-$HOME/.cache}/sima-neat/tools/sccache/<version>/
```

Архів перевіряється на відповідність хешу SHA-256, який міститься у файлі
`scripts/configure_sccache.sh`. Підтримуються операційні системи Linux і macOS на архітектурах arm64 та x86-64.

### Поширені налаштування

```bash
# Explicitly require sccache. Fail the build if it cannot be configured.
SIMANEAT_SCCACHE=on ./build.sh --all

# Disable caching for a reproducibility comparison.
SIMANEAT_SCCACHE=off ./build.sh --all --clean

# Put the local cache on a larger or faster volume.
SCCACHE_DIR=/mnt/nvme/sccache ./build.sh --all

# Change the local cache limit.
SCCACHE_CACHE_SIZE=20G ./build.sh --all
```

`SIMANEAT_SCCACHE=auto` є значенням за замовчуванням. У цьому режимі збій початкового налаштування (bootstrap) спричиняє попередження, і збірка триває без кешування. `on` робить цей збій фатальним.

### Перегляд або очищення локального кешу

Використовуйте той самий бінарний файл, який вибрав `build.sh`, або `sccache`, якщо він є в `PATH`:

```bash
sccache --show-stats
sccache --zero-stats
sccache --show-adv-stats
```

Щоб звільнити місце, зупиніть сервер і видаліть лише налаштовану теку кешу:

```bash
sccache --stop-server
rm -rf "${XDG_CACHE_HOME:-$HOME/.cache}/sima-neat/sccache"
```

Перед видаленням перевірте остаточний шлях. Не видаляйте всю теку кешу користувача.

## Хмарні збірки Vulcan

Vulcan надає той самий локальний дисковий кеш, а також зашифрований рівень S3:

```text
s3://sima-neat-compiler-cache-production/
  core/
    sccache-v1/
      <architecture>/
        <sdk-cache>/
          <build-mode>/
            develop/
              branches/<encoded-feature-branch>/
            main/
              branches/<encoded-feature-branch>/
```

Наприклад:

```text
core/sccache-v1/arm64/sdk-develop/standard/develop/
```

Простір імен навмисно містить:

- `sccache-v1`: схема кешу, що дає змогу навмисно виконати глобальне скидання
- архітектура: запобігає змішуванню результатів компіляції для arm64 та x86-64
- ідентифікатор кешу SDK: запобігає змішуванню результатів, отриманих із несумісними SDK/наборами інструментів
- режим збірки: розділяє стандартну інструментацію та інструментацію для фазинг-тестування
- захищена базова гілка: не дає `develop` і `main` записувати в той самий простір імен

Бакет S3 приватний, зашифрований власним ключем KMS і відокремлений від бакета артефактів. Він не має дистрибуції CloudFront, оскільки об’єкти кешу компілятора приватні й не потребують збереження. Об’єкти автоматично видаляються через 45 днів.

### Доступ для гілок

| Посилання Git | Роль OIDC | Режим S3 |
|---|---|---|
| Точно `refs/heads/develop` | Редактор захищених гілок | `READ_WRITE` у `develop/` |
| Точно `refs/heads/main` | Редактор захищених гілок | `READ_WRITE` у `main/` |
| Прямий push у feature-гілку | Редактор гілки | `READ_WRITE` у межах `<base>/branches/<branch>/` |
| Тег або непряме посилання | Читач | `READ_ONLY` з вибраної захищеної базової гілки |

Під час першої збірки feature-гілка копіює кеш із найближчого захищеного предка в Git (`develop` або `main`) у власний простір імен. Далі збірка читає й записує лише простір імен цієї гілки. Наступні збірки повторно використовують його, доки подія видалення гілки в GitHub не прибере всі простори імен цієї гілки для кожної архітектури, SDK і режиму збірки. Feature-гілки не можуть записувати в жоден із захищених кешів.

Автоматичне визначення предка порівнює відстань до merge-base з `develop` і з `main`. Повторно використовуваний або запущений вручну робочий процес може задати `cache_base_branch=develop|main`, якщо винятковій гілці потрібна явно задана базова гілка. Облікові дані AWS — це короткочасні облікові дані GitHub OIDC; жоден довготривалий ключ AWS не зберігається ні в GitHub, ні в контейнері SDK.

Порожній захищений простір імен — очікувана ситуація до першої збірки захищеної гілки з правом запису. Feature-гілка все одно може заповнити власний простір імен, але не отримає жодного початкового влучання в кеш, якщо вибрана захищена базова гілка порожня.

Vulcan явно перевіряє запуск `sccache` перед налаштуванням CMake. Якщо S3, KMS, мережа або тимчасові облікові дані не дають кеш-серверу запуститися, робочий процес виводить попередження та компілює без `sccache`. Отже, доступність віддаленого кешу є оптимізацією і не може заблокувати компіляцію. Локальний кеш раннера не використовується як резервний варіант, оскільки раннери Vulcan тимчасові. Локальні збірки розробників зберігають свій звичайний постійний кеш на диску.

## Перегляд статистики збірки

Кожна збірка з кешуванням завершується виведенням, подібним до такого:

```text
Compile requests                    623
Cache hits                          619
Cache misses                          4
Cache hits rate                   99.36 %
Cache timeouts                        0
Cache read errors                     0
Cache write errors                    0
Compilations                          4
```

Важливі поля означають таке:

| Поле | Значення |
|---|---|
| Запити на компіляцію (Compile requests) | Виклики компілятора, які побачив `sccache` |
| Влучання в кеш (Cache hits) | Запити, результат яких відновлено без запуску компілятора |
| Промахи кешу (Cache misses) | Запити, що потребували компіляції |
| Компіляції (Compilations) | Фактично запущені процеси компілятора |
| Некешовані виклики (Non-cacheable calls) | Виклики, які `sccache` навмисно пропустив повз кеш |
| Помилки читання/запису (Read/write errors) | Збої бекенда кешу; з’ясуйте причину, якщо значення ненульове в локальних збірках або збірках із правом запису |
| Розташування кешу (Cache location) | Активний бекенд, наприклад локальний диск або багаторівневий |

Низька частка влучань — нормальне явище для першої збірки з новим набором інструментів, кешем SDK, архітектурою, режимом збірки або суттєво зміненим деревом початкового коду. Оцінюйте кеш за другою збіркою того самого коміту з тією самою конфігурацією.

Якщо будь-який рівень доступний лише для читання, `sccache` v0.16 може повідомляти про спроби збереження як про помилки запису, хоча збірка в режимі лише для читання завершується успішно. Це стосується тегів та інших непрямих контекстів. Прямі push у feature-гілки мають показувати `READ_WRITE`; помилки запису в таких збірках слід дослідити.

## Швидка перевірка

### Перевірка локального повторного використання

Запустіть ту саму чисту збірку двічі:

```bash
SIMANEAT_SCCACHE=on SIMANEAT_SCCACHE_ZERO_STATS=ON \
  ./build.sh --dev-only --clean --no-dist

SIMANEAT_SCCACHE=on SIMANEAT_SCCACHE_ZERO_STATS=ON \
  ./build.sh --dev-only --clean --no-dist
```

Другий запуск має показати значно вищу частку влучань. Точні цифри залежать від
змін у початковому коді, перевірок компілятора (probes), згенерованих файлів і вибраної збірки.

### Перевірка конфігурації Vulcan

У журналі збірки GitHub Actions знайдіть рядки:

```text
sccache enabled: sccache <version>
sccache local cache: <path> (<limit>)
sccache remote cache: s3://<bucket>/<prefix> (READ_ONLY|READ_WRITE)
```

Потім переконайтеся, що підсумкова статистика не містить неочікуваних помилок читання, запису, тайм-аутів чи помилок кешу.

## Усунення несправностей

### `sccache` не ввімкнено

- Переконайтеся, що для збірки використовується `build.sh`.
- Перевірте, що `SIMANEAT_SCCACHE` не має значення `off`.
- Запустіть повторно з `SIMANEAT_SCCACHE=on`, щоб помилки початкового налаштування стали фатальними.
- Переконайтеся, що доступні `curl`, `tar`, а також `sha256sum` або `shasum`.

### Друга локальна збірка досі дає промахи

- Переконайтеся, що обидві збірки використовують той самий компілятор, SDK, режим збірки та прапорці.
- Переконайтеся, що `SCCACHE_DIR` вказує на ту саму постійну теку.
- Пошукайте згенеровані вхідні файли з мітками часу або абсолютними шляхами, що змінюються.
- Перевірте `Non-cacheable calls` та `Unsupported compiler calls`.
- Переконайтеся, що кеш не було витіснено через ліміт `SCCACHE_CACHE_SIZE`.

### Vulcan показує нуль віддалених влучань

- Переконайтеся, що кеш вибраної базової гілки `develop` або `main` уже заповнено.
- Для feature-гілки переконайтеся, що журнал показує очікувану базову гілку та
  її закодований префікс для конкретної гілки.
- Порівняйте архітектуру, ідентифікатор кешу SDK та режим збірки.
- Переконайтеся, що журнал показує очікуваний бакет і префікс.
- Вважайте «холодний» простір імен нормою; порівнюйте дві однакові збірки.

### Запуск S3 завершується помилкою `AccessDenied`

Ролям кешу потрібен дозвіл `s3:ListBucket` з обмеженням за префіксом для перевірки `.sccache_check`, а також дозволи на об’єкти:

- читач: `GetObject`
- редактор: `GetObject` і `PutObject`

Обом ролям також потрібні відповідні дозволи KMS. Не додавайте дозволи S3 чи KMS до ролі раннера EC2 як обхідний шлях; натомість виправте роль кешу GitHub OIDC у Vulcan.

### Обхід кешу під час діагностики збою компілятора

```bash
SIMANEAT_SCCACHE=off ./build.sh --all --clean
```

Якщо збій не зникає, його причина не в кешованому результаті компіляції.

## Відповідальність і джерело істини

| Аспект | Джерело |
|---|---|
| Локальне початкове налаштування, версія, контрольні суми, параметри кешу за замовчуванням | `scripts/configure_sccache.sh` |
| Інтеграція засобів запуску CMake і статистика | `build.sh` |
| Вибір ролі для гілки та простір імен кешу | `.github/workflows/vulcan-ci.yml` |
| Вхідні параметри повторно використовуваного робочого процесу Vulcan і налаштування OIDC | `sima-neat/.github` |
| S3, KMS, життєвий цикл і ролі IAM для кешу | `sima-neat/vulcan` |

Змінюючи схему кешу, межу сумісності набору інструментів або модель доступу, оновіть усі відповідні репозиторії та цю сторінку одночасно.
