# Збірка Neat

Цей посібник описує збирання Neat з початкового коду.
Інструкції щодо встановлення попередньо зібраного пакета див. у [Neat Library](/getting-started/neat-library/).

`build.sh` — це підтримувана точка входу для збирання. Він виконує перевірку залежностей, необов’язкову синхронізацію залежностей, налаштування та збирання за допомогою CMake, необов’язкове генерування документації, перевірку коректності встановлення та пакування.

## Середовища збирання

`build.sh` автоматично визначає активне середовище:

- Нативне середовище Modalix DevKit
- Середовище Palette SDK (крос-компіляція)

Ви можете виконувати одні й ті самі команди `build.sh` в будь-якому з цих середовищ.

### Необхідні умови для крос-компіляції

Використовуйте Palette SDK для крос-компіляції. Налаштуйте його на підтримуваному хості Ubuntu, Windows/WSL або macOS за інструкцією [Встановлення SDK](/getting-started/dev-environment/install-the-environment/), а потім відкрийте оболонку SDK:

```bash
sima-cli sdk neat
```

SDK містить набір інструментів і `sima-cli`. Скрипт Core `build.sh` готує відповідні залежності Scheduler та LLiMa; див. [Локальні залежності](/develop-apps/contribute/build-test/local-dependencies/). Якщо до SDK підключено DevKit, команда `./build.sh --install` також розгортає на ньому відповідні артефакти. Для нативних збірок на DevKit SDK не потрібен.

## Параметри збірки

Підтримувані параметри `build.sh`:

- `--dev-only`: Зібрати лише основну бібліотеку та заголовні файли (за замовчуванням).
- `--all`: Зібрати бібліотеку + тести + навчальні матеріали + Python wheel; вмикає документацію та залежності.
- `--python`: Зібрати прив’язки для Python (`pyneat`) на додаток до вибраних цілей.
- `--install-neat-internals`, `--install-deps`: Завантажити та встановити артефакти залежностей перед збиранням.
- `--doc`: Зібрати лише документацію.
- `--install`: Після збирання/пакування встановити згенеровані артефакти в поточне середовище. Якщо до Palette SDK підключено DevKit, цей параметр також розгортає та встановлює на ньому відповідні артефакти.
- `--no-dist`: Пропустити створення дистрибутивного пакета.
- `--clean`: Видалити `build/` перед налаштуванням.
- `--no-doc`: Пропустити збирання документації (навіть з `--all`).
- `--no-node`: Пропустити встановлення Node.js (збирання документації може завершитися помилкою, якщо Node відсутній).
- `--install-deps-only`: Встановити системні залежності та заголовні файли залежностей, а потім завершити роботу.

## Кеш компілятора

`build.sh` автоматично вмикає `sccache`, і його кеш залишається доступним після `--clean`. Локальні збірки використовують локальний дисковий кеш користувача. Vulcan надає окремі захищені кеші для гілок `develop` і `main`; feature-гілка створює ізольований кеш із правом запису, заповнюючи його з найближчої захищеної базової гілки, і зберігає його до видалення гілки.

Локальні налаштування, правила доступу до хмари, простори імен кешу, статистику, перевірку та усунення несправностей див. у [короткому довіднику Neat sccache](/develop-apps/contribute/sccache).

## Типові збірки

Лише основна бібліотека (за замовчуванням):

```bash
./build.sh
```

Повна збірка (бібліотека, тести, навчальні матеріали, документація, wheel, пакування):

```bash
./build.sh --all
```

Основна бібліотека + прив’язки для Python:

```bash
./build.sh --dev-only --python
```

Лише документація:

Ця команда також працює на macOS.

```bash
./build.sh --doc
```

Під час збирання документації генерується довідник з API Insight на основі специфікації OpenAPI,
яку autodoc завантажує до
`build/autodoc/insight/neat_insight/openapi.json`. Для локальної розробки ви можете
перевизначити це значення за замовчуванням за допомогою `INSIGHT_OPENAPI_SPEC`:

```bash
INSIGHT_OPENAPI_SPEC=../insight/neat_insight/openapi.json ./build.sh --doc
```

Відносні шляхи перевизначення розв’язуються відносно кореневої теки репозиторію Core і перетворюються на абсолютні шляхи перед запуском генератора Docusaurus. Якщо вибраного файлу не існує, крок генерування API Insight пропускається, а цей шлях виводиться в повідомленні.

Повна збірка з очищенням:

```bash
./build.sh --all --clean
```

Встановлення залежностей без збирання Core:

```bash
./build.sh --install-deps-only
```

## Результати

- Дерево збірки: `build/`
- Згенерований сайт Docusaurus (якщо виконується збирання документації): `website/build/`
- Префікс для перевірки коректності встановлення: унікальна тимчасова тека (`${TMPDIR:-/tmp}/sima-neat-install-test.XXXXXX`), шлях до якої виводиться під час збирання; у разі успіху тека видаляється, у разі збою зберігається для аналізу.
- Артефакти пакетів Neat (`*.deb`) створюються під час повних збірок у Linux, якщо не використано `--no-dist`.
- Пакет додаткових компонентів (`*extras.tar.gz`) створюється під час повної збірки в Linux, якщо не використовується параметр `--no-dist`.
- Пакет Python у форматі wheel (`dist/*.whl`) створюється, коли ввімкнено збірку Python.

Пакет Python wheel містить розширення `_pyneat_core`, створене під час основної збірки CMake. Під час створення пакета wheel друге дерево CMake не налаштовується й не компілюється, тому бібліотека, пакети DEB, архів додаткових компонентів і пакет wheel використовують одну й ту саму компіляцію.

## Профілі збірки та параметри CMake

Файл `CMakeLists.txt` верхнього рівня фреймворку надає кілька параметрів, які визначають, що саме буде зібрано та яким чином. Параметри, перелічені нижче, є найважливішими.

### Профілі збірки

Фреймворк підтримує три іменовані профілі:

| Профіль | Сценарій використання | Що компілюється |
|---------|----------|-----------------|
| **Production** | Збірки для клієнтів | Усі публічні вузли, завантаження архівів моделей, бекенди Modalix, оптимізація |
| **Developer** | Інженери фреймворку | Набір Production + вузли налагодження + розширена діагностика + тести |
| **Sandbox** | Розгортання для кількох орендарів (multi-tenant) | Набір Production + посилені налаштування безпеки архівів моделей за замовчуванням |

Виберіть профіль під час налаштування за допомогою `-DSIMA_NEAT_PROFILE=Production|Developer|Sandbox` або залиште значення за замовчуванням із файлу `CMakeLists.txt`.

### Найпоширеніші параметри CMake

| Параметр | За замовчуванням | Дія |
|--------|---------|--------|
| `SIMA_NEAT_BUILD_TESTS` | `ON` (Developer) | Збирає набір тестів gtest. Вимкніть, щоб пришвидшити CI для виробничих збірок. |
| `SIMA_NEAT_BUILD_TUTORIALS` | `OFF` | Збирає виконувані файли навчальних посібників. |
| `SIMA_NEAT_BUILD_PYTHON` | `ON` | Збирає модуль nanobind `pyneat`. |
| `SIMA_NEAT_BUILD_INTERNALS` | `OFF` (публічний) | Збирає внутрішній рівень наскрізного доступу (`core/src/pipeline/internal/sima/`). |
| `SIMA_NEAT_ENABLE_TVM_FALLBACK` | `ON` | Компілює резервні ядра на основі TVM для операцій, які не може обробити MLA. |
| `SIMA_NEAT_ENABLE_RTSP` | `ON` | Збирає вузли джерела/приймача RTSP. |
| `SIMA_NEAT_DEBUG_PLUGINS` | `OFF` | Перенаправляє налагоджувальний вивід плагінів GStreamer у stdout. |
| `SIMA_NEAT_USE_SYSTEM_GSTREAMER` | `ON` (хост) / `OFF` (крос-компіляція) | Компонує із системним GStreamer замість вбудованого. |
| `SIMA_NEAT_WARN_AS_ERROR` | `OFF` | Перетворює попередження компіляції на помилки. Рекомендовано для CI. |

### Параметри набору інструментів

Для крос-компіляції під Modalix:

```bash
cmake -B build \
  -DCMAKE_TOOLCHAIN_FILE=cmake/modalix.cmake \
  -DSIMA_NEAT_PROFILE=Production
```

Для розробки на стороні хоста:

```bash
cmake -B build -DSIMA_NEAT_PROFILE=Developer
```

Щоб переглянути параметри, які надає ваше дерево збірки:

```bash
cmake -L -B build       # list all cache variables
cmake -LA -B build      # include advanced
```

Файл `CMakeLists.txt` верхнього рівня є джерелом істини для назв параметрів.

Core успадковує прошивку й точну версію sysroot із квитанції вибраного пакета Scheduler, не оголошуючи прошивку окремо. Платформа й канал SDK у квитанції мають відповідати Core. CI зберігає цю політику разом з артефактами збірки та використовує її, щоб вибрати точний DevKit без резервного варіанта. Перед встановленням LLiMa Core порівнює опубліковані для LLiMa прошивку, платформу й канал SDK зі Scheduler та перевіряє, що вибрані DEB належать тій самій публікації. LLiMa не публікує точної квитанції sysroot, тому ця перевірка підтверджує заявлену сумісність прошивки, а не ідентичність переліків пакетів sysroot. Для локальної збірки `--llima PATH` вкажіть корінь дистрибутива LLiMa з DEB core/dev/cli, `llima-package-manifest.json` і `metadata.json`. Відсутні або суперечливі дані зупиняють збірку. Перед повторною збіркою Core зберіть і опублікуйте Kernels → Runner → Scheduler та відповідну LLiMa.
