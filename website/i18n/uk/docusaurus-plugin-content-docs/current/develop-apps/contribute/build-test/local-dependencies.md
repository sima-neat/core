# Збирання Core з локальними Kernels, Runner і Scheduler

Виконайте звичайну команду зі своєї робочої копії Core в середовищі розробки Neat:

```bash
./build.sh --all --no-doc --install
```

Збирання готує **Kernels → Runner → Scheduler → Core**, а потім виконує наявне
завершальне встановлення або розгортання. Дочірні збирання ніколи не встановлюють
компоненти в SDK, не розгортають їх на DevKit, не виконують цільові тести, не
компілюють прошивку EV і не активують її.

Для автоматичного виявлення джерел розмістіть робочі копії поруч:

```text
development/
├── core/
├── kernels/
├── runner/
└── scheduler/
```

Runner містить незалежні від фреймворків засоби виконання, підготовки, пам’яті та
нативного транспорту. Scheduler містить інтеграцію GStreamer, зовнішні модулі й
адаптери сумісності. Кожен має власний корінь джерел та встановлений пакет.
Робочі копії не обов’язково мають містити каталог `.git`; підтримуються робочі
дерева й знімки джерел.

## Вибір джерел або наявних локальних пакетів

Для робочої копії в іншому місці задайте `NEAT_KERNELS_SOURCE`, `NEAT_RUNNER_SOURCE` або `NEAT_SCHEDULER_SOURCE`:

```bash
NEAT_RUNNER_SOURCE=/path/to/simaai-runtime ./build.sh --all --no-doc
```

Щоб натомість повторно використати локально зібраний пакет, задайте
`NEAT_KERNELS_PACKAGE_DIR`, `NEAT_RUNNER_PACKAGE_DIR` або `NEAT_SCHEDULER_PACKAGE_DIR`.
Кожний каталог пакета має містити встановлене дерево `usr/`, запис збирання й
відповідний пакет Debian, створений канонічним процесом пакування компонента.
Kernels використовує стандартні кроки налаштування, збирання й встановлення
CMake та власний засіб створення пакетів; Runner і Scheduler використовують
відповідні кореневі точки входу `build.sh`:

```bash
NEAT_RUNNER_PACKAGE_DIR=/path/to/runner/dist/package \
  ./build.sh --all --no-doc
```

Пріоритет вибору: явне перевизначення, потім допустимі сусідні джерела, потім
сусідній `dist/package`. Явний вибір пакета переважає сусідні джерела. Одночасне
задання джерела й пакета для одного компонента є помилкою. Невдале локальне
збирання зупиняє весь процес; переходу на старіший пакет немає.

Локальний `build.sh` потребує вибраних джерел або пакетів і не завантажує заміну автоматично.
Явне отримання артефактів описано в розділі [Опубліковані залежності CI](#published-ci-dependencies).
Використовуйте `--no-llima`, якщо необов’язковий бекенд LLiMa не потрібен.

## Залежності від платформи

Використовуйте той самий SDK і набір інструментів Platform 3.0 для всіх чотирьох
репозиторіїв. Задайте `CMAKE_TOOLCHAIN_FILE`, якщо вибираєте нестандартний набір
інструментів. Записи Kernels і Runner мають узгоджуватися за ціллю, компілятором,
контрактами ядер та використаною конфігурацією збирання. Канонічний процес
пакування також потребує точної ідентичності використаного вмісту Kernels.
Після зміни пакета Kernels перебудуйте пакет Runner із вибраним SDK, навіть якщо
джерела Runner не змінилися. Потім Core повторно компонується з відповідною
реалізацією клієнта Scheduler; нижчі числові пакети споживає Scheduler.
DEB-пакети Core, зібрані насамперед із джерел, фіксують вибрані версії Scheduler
і числового SDK. Runner фіксує Kernels; Scheduler — Runner, Kernels і ввімкнений
бекенд кодеків. Збирання Core з тестами також потребують окремого пакета
Scheduler `simaai-scheduler-client-test-dev` від того самого виробника.
Збирання з джерел запитують його через `--client-test-support`; збирання з пакетів
вибирають сусідній каталог `client-test-support/` або
`NEAT_SCHEDULER_CLIENT_TEST_PACKAGE_DIR`. Координатор перевіряє його запис
виробничого збирання, джерела, вміст та архів, перш ніж надати тестовий компонент
CMake. Збирання лише середовища виконання не потребують його. Процес формує
сумісність `simaai-runtime`, що містить лише метадані, з точними залежностями
Runner і Scheduler. Канонічні пакети володіють файлами без дублювання; лише
Runner володіє наявною конфігурацією завантажувача. Завжди встановлюйте повний
узгоджений дистрибутив замість заміни одного пакета.

### Перенесення володіння заголовками GStreamer

У невипущеній версії Core `0.6.0` володіння
`/usr/include/gst/SimaaiGstErrors.h` переходить до Scheduler. Шлях включення
не змінюється. Core більше не містить власної реалізації й не встановлює цей
файл; споживачі використовують встановлені заголовки Scheduler і ціль
`SimaScheduler::Headers`.

Оновлюйте Core і Scheduler разом із повного узгодженого дистрибутива.
Scheduler оголошує перенесення заголовка для невипущеної лінійки пакетів 0.6.0,
не позначаючи виправлені пакети Core 0.6.0 як несумісні. Перед зміною файлів
через APT інсталятор використовує автентифіковану перевірку володіння Scheduler:
попередній пакет-власник має бути замінений у тому самому наборі пакетом без
цього файла або підпадати під явно оголошене й схвалене виведення з використання.
Дублювання власників у вхідних пакетах і сторонні конфлікти володіння відхиляються.

На Platform 3.0 повний набір розділених пакетів також виводить із використання
монолітні `neat-runtime`, `neat-gst-plugins` і `neat-internals-dev` лінійок 0.4,
0.5 та 0.6.0, включно зі збірками для розробки. Для цього нові пакети-власники
мають оголосити відповідні `Breaks` і `Replaces` з обмеженим діапазоном версій;
версії від `0.6.1~` і вище не охоплюються. Це не дозволяє видаляти сторонні
пакети й не означає сумісності з виведеними з використання API.
Scheduler оголошує передавання файлів середовища виконання та плагінів;
повне середовище виконання також потребує відповідного Runner як залежності
для виконання. Окреме встановлення Runner не виводить із використання
монолітні пакети 0.6.0.

Дистрибутиви Modalix з увімкненим EV потребують відповідного пакета
`simaai-kernels-firmware`, вибраного Scheduler. Відсутня або невідповідна
прошивка спричиняє помилку перевірки допуску.
Для заміни старого пакета `neat-ev74-firmware` саме вибраний пакет прошивки
має оголосити `Replaces` та `Breaks` або `Conflicts`, що відповідають його версії;
звичайні перевірки транзакції та видалення також застосовуються.
Для активації прошивки використовується лише єдиний вхідний пакет, який
постачає допоміжний засіб активації. Ідентичність установленого пакета,
власник допоміжного засобу, права виконання та байти мають відповідати
вибраному пакету. Невідповідність вибраного засобу спричиняє помилку інсталяції.
Для дистрибутивів, які не потребують прошивки EV74, відсутність такого засобу
не змінює наявну прошивку. Інсталятор ніколи не використовує засіб,
залишений попередньою інсталяцією.

Якщо встановлення на DevKit перервалося, повторно запустіть повний перевірений дистрибутив.
Інсталятор може відновити незавершені пакети лише тоді, коли вони належать до
вхідного набору й мають відповідну архітектуру. Відновлення має встановити точні
вибрані версії без зміни сторонніх пакетів. Можна видалити лише налаштовані
попередні пакети без утримання, виведення яких із використання явно оголошене
вхідним набором і схвалене наявними перевірками видалення. Відновлення спочатку
завершує схвалений перехід, перевіряє стан пакетів, а потім повторно встановлює
кожен вибраний пакет із забороною видалення. Інсталяція вважається успішною лише
після цього остаточного перевстановлення. Сторонні
порушення стану бази пакетів потребують окремого виправлення: інсталятор не
виконує загального відновлення APT і не гарантує відкату.

Не встановлюйте лише DEB Scheduler поверх наявного пакета розробки Core,
не використовуйте `--force-overwrite` і не видаляйте файли, що належать dpkg.
Окремий тестовий образ Scheduler не потребує встановленого Core; наявне
встановлення Core потребує узгодженого оновлення.

### Постачальники бекендів

Scheduler потребує окремо встановлених платформних бекендів. Цей процес
не копіює їх до Scheduler і не завантажує їх:

- Задайте `NEAT_CODECS_PACKAGE_DIR` як каталог окремо зібраного пакета Codecs.
  Коли Scheduler вмикає кодеки, цей каталог має містити точний встановлений
  префікс `usr/`, який він використав, та відповідні пакети Debian `neat-codecs`
  і `neat-codecs-dev`. Координатор залежностей Scheduler перевіряє їхній вміст,
  володіння й контрольні поля залежностей; Core зберігає перевірений повний
  набір залежностей і включає обидва архіви до кінцевого дистрибутива. Він не
  збирає Codecs і не підставляє іншу версію.
- Використовуйте відповідні SDK бібліотеки MLA Runtime, візуалізації та трасування/журналювання.
- Якщо шляхи SDK треба вибрати явно, передайте визначення CMake через
  `NEAT_SCHEDULER_CMAKE_ARGS`, наприклад
  `-DSIMA_RUNTIME_MLART_LIBRARY=/path/to/libmlart.so` та відповідний каталог
  заголовків. Використовуйте назви параметрів із посібника зі збирання Scheduler.

Аргументи в `NEAT_RUNNER_CMAKE_ARGS` і `NEAT_SCHEDULER_CMAKE_ARGS` розбираються як
слова оболонки, а не виконуються як її код. Вони не можуть перевизначити
вибрані пакети залежностей або структуру встановлення.

## Інкрементне збирання та встановлення

Збирання й пакети залежностей, якими керує Core, містяться в `deps/backend/`,
окремо від автономного каталогу збирання кожного репозиторію. CMake збирає
інкрементно; `--clean` очищує вибрані локальні збирання залежностей і збирання Core.

Перед компонуванням координатор залежностей Scheduler звіряє встановлені
заголовки ядер із їхнім записом і перевіряє використаний Runner контракт та
точний вхід Runner для Scheduler. Перед підготовкою пакетів розгортання він
перевіряє відповідність вмісту `/usr` кожного пакета Debian вибраному
встановленому дереву. Старі пакети Internals не вибираються й не завантажуються.

Core використовує встановлений клієнтський компонент `SimaScheduler`, а не
заголовки сусідніх джерел чи нижчі інтерфейси розробки. Ідентичності нижчих
компонентів середовища виконання зберігаються в перевіреному наборі залежностей.
Згенерований вибір залежностей записується в `build/resolved_manifest.json`
і `build/buildinfo.json`. Лише повністю завершене збирання переходить до
кінцевого встановлення; це не гарантує транзакційного відкату встановлення
в SDK чи на пристрій.

Інформація про збирання пакета до налаштування CMake є попередньою. Після
компіляції `build.sh` оновлює її з кешу CMake цього збирання, налаштованого
компілятора, цільових заголовків Python і зібраного розширення, перш ніж
перевіряти встановлення чи пакувати. Прапорці ABI цільового Python мають
відповідати суфіксу розширення; версія Python хоста не використовується.
Збирання без Python записують цей профіль без ABI Python.

`compatibility.host_sdk` описує спостережений випуск SDK хоста збирання;
`compatibility.target_sdk` — вибрані sysroot і компілятор. Відсутній випуск
цільового SDK залишається недоступним, навіть якщо випуск SDK хоста відомий.
Версія платформи в маніфесті є окремою вимогою сумісності, а не заміною
неспостереженої версії SDK. `ELXR_SDK_RELEASE_FILE` вибирає файл випуску хоста.
`NEAT_TARGET_SDK_RELEASE_FILE` може явно задати файл випуску цілі, але він має
узгоджуватися з файлом випуску вибраного sysroot. `NEAT_BUILDINFO_TOOLCHAIN`
зберігає явну відображувану мітку поряд з ідентичністю налаштованого компілятора,
а не замість неї.

Перевірка метаданих відхиляє суперечливі sysroot компіляції, заголовки й мітки
ABI розширення. Окремі sysroot компіляції та компонування, а також додаткові
контексти аргументів, цілі або набору інструментів компілятора CMake цим шляхом
метаданих не підтримуються; він завершується помилкою замість повідомлення
неперевіреної ідентичності цілі. Вимоги NumPy з маркерами зберігаються дослівно
з `pyproject.toml`, а не зводяться до одного безумовного мінімуму.

Запис джерел використовує фактичний коміт робочої копії та стан її зміненості.
Він окремо записує відстежувані зміни та ідентичності неігнорованих
невідстежуваних файлів і символічних посилань; ігноровані продукти збирання не є
знімком джерел. Сам вихідний файл метаданих виключається з дайджесту
невідстежуваного вмісту, щоб уникнути самопосилання. Змінений локальний кандидат
не ідентифікується як чистий опублікований артефакт.

Для підготовки лише заголовків залежностей `--install-deps-only` потребує
локальних перевизначень пакетів. Він копіює заголовки без збирання або виконання
коду A65/EV. Для нативного аналізу clang-tidy використовуйте
`scripts/run_cpp_tidy.sh` із префіксами вибраного Scheduler і відповідного пакета
підтримки тестів. `TIDY_INSTALL_DEPS=1` встановлює нативні передумови аналізу хоста.
Сценарій безпосередньо використовує їхні публічні експорти CMake, не активуючи й не
змінюючи sysroot SDK. Файли реалізації GenAI з LLiMa залишаються поза
цим профілем аналізу лише хоста. Сценарій не підставляє довільний пакет LLiMa
навколишнього SDK замість залежності вибраного збирання. Збирання лише
документації не готують нативні залежності.

Збирання для пристрою EV залишаються окремим ліцензованим процесом. Жодна з цих
команд не викликає MetaWare, не замінює прошивку й не кваліфікує її зміну неявно.

## Опубліковані залежності CI {#published-ci-dependencies}

Звичайне збирання Vulcan один раз визначає політику Scheduler із
`deps/manifest.json` через `sima-cli`, а потім завантажує цей незмінний випуск.
Політика snap вибирає поточну гілку; неопублікована гілка спричиняє помилку
замість переходу на іншу. `tools/ci/acquire_scheduler.py` перевіряє хеші видавця
перед запуском початкового завантажувача Scheduler. Встановлений координатор
Scheduler розподіляє й перевіряє включені архіви Runner, Kernels і Codecs.
Core не визначає ці репозиторії незалежно.

Вибраний пакет Scheduler встановлює свою точну політику SDK. В одноразовому
контейнері SDK для CI `scripts/ci/prepare_scheduler_sdk.sh` використовує офіційну
команду налаштування sysroot цієї ревізії та зберігає завантажені архіви платформи.
Координатор перевіряє фактичні версію й ціль GCC14 та ідентичності цільового SDK,
а потім вибирає точні архіви постачальників середовища виконання, використані
Runner, через `NEAT_RUNNER_PLATFORM_RUNTIME_DEBS`. Виконувані файли нативного
ARM64-компілятора й кроскомпілятора не обов’язково мають бути побайтово
ідентичними. Їхній цільовий ABI та вибрана платформа мають збігатися.
На цьому кроці нічого не встановлюється на пристрій і прошивка не кваліфікується.

Локальні перевизначення джерел і пакетів залишаються авторитетними.
Завантаження для CI є явним; невдале локальне збирання з джерел ніколи не
завантажує заміну. Наявна команда
`tools/ci/materialize_dependencies.py --manifest ... --output-root ...` залишається
необов’язковим засобом доставки окремо перевіреного незмінного маніфесту.
Це не типовий процес, і неявного `ci/dependencies.json` немає.

Перевірка чистоти коду використовує `tools/ci/acquire_scheduler.py`, щоб незалежно
отримати опублікований Scheduler за тією самою політикою залежностей, не очікуючи
на збирання Core. Початкове налаштування Scheduler перевіряє набір пакетів.
Аналіз хоста використовує експорти CMake його клієнтської частини та відповідної
підтримки тестів без активації SDK або виконання на цільовому пристрої.

Див. [Володіння апаратними тестами](./hardware-test-safety.md) щодо супервізора
на цільовому пристрої, потрібного захищеному шляху перевірки продуктивності.

## Перевірка готового дистрибутива

`build.sh --all` перевіряє готовий дистрибутив після формування метаданих пакетів.
`scripts/ci/verify_core_dist.sh` виконує ту саму перевірку лише для читання в CI,
використовуючи середовище Python вибраного `sima-cli`. Явно задайте
`SIMA_CLI_PYTHON`, якщо інтерпретатор не розміщено поряд із вибраним виконуваним
файлом CLI.

Перевірка звіряє байти пакетів залежностей, поля сумісності, список дозволів
інсталятора, усі контрольні суми ресурсів, ізоляцію публічного wheel та
встановлені дерева CTest. Вона використовує наявні записи виробників, а не
визначає чи виправляє залежності. Розрізняйте ці документи:

- `dist/manifest.json`: сумісність платформи, Model Zoo та ABI.
- `dist/resolved-deps-manifest.json`: вибраний запис бекенду, скопійований точно.
- `build/resolved_manifest.json`: повніший результат визначення збирання Core.

Не замінюйте файли й не перераховуйте вибрані контрольні суми після цієї
перевірки. Якщо артефакт змінився, перебудуйте метадані та знову перевірте весь
дистрибутив.


## Явні пакети платформних постачальників

Виробнича публікація рамок і масок Core використовує координати int32.
Виберіть Scheduler, зібраний із канонічною візуалізацією Kernels та відповідними
API виконання Runner. `SIMANEAT_REQUIRE_INT32_RENDERER` типово відповідає вимозі
артефакту середовища виконання та спричиняє помилку налаштування, якщо
встановлений Scheduler не має цієї можливості. Задавайте `OFF` лише для профілю
Core, який не використовує візуалізацію рамок або масок Core.

Візуалізація використовує вибрані пакети Kernels/Runner, а не окремий архів
платформного засобу візуалізації. Для ревізії 2 API запитів перебудуйте весь
набір компонентів разом.

Перед запуском `build.sh` Core для збирання насамперед із джерел надайте:

- `NEAT_RUNNER_PLATFORM_RUNTIME_DEBS`: JSON-масив абсолютних шляхів до точних
  DEB-пакетів постачальників середовища виконання, вибраних Runner. Включіть
  обов’язковий архів середовища виконання SimaHeap, а також архіви середовищ
  виконання MLA й TVM, якщо ці бекенди ввімкнено. Не включайте до цього масиву
  архіви розробки. Runner перевіряє фактичні назви завантажувача й байти бібліотек.
  Scheduler зберігає точні ідентичності архівів та переліки вмісту як докази
  збирання. Постачальники, які Runner оголосив власністю Platform, залишаються
  поза набором встановлюваних DEB Core; неоголошені постачальники зберігають
  точне включення архівів.

Цей вибір залишається явним і з перевизначеннями попередньо зібраних пакетів
Runner/Scheduler. Незмінний матеріалізатор чотирьох компонентів не завантажує
архіви платформних постачальників. Отримайте їх у підтримуваного виробника
перед викликом Core; відсутні або невикористані постачальники спричиняють помилку
замість резервного вибору із sysroot. Для компіляції використовуйте відповідні
пакети розробки. На DevKit автентифікований засіб допуску Scheduler перевіряє
встановлених постачальників Platform щодо вхідних споживачів перед зміною
пакетів. Інсталятор відхиляє плани APT, які замінюють або видаляють цих
постачальників, а потім перевіряє їхню ідентичність і повний набір залежностей
встановлених споживачів. `FORCE_INSTALL` не скасовує ці перевірки.
Не перебудовуйте DEB лише для позначення приватної DSO як випущеного постачальника.

Формування пакета перевіряє неперекривне володіння вмістом, точні версії
залежностей і незмінені архіви. Ці перевірки під час збирання не кваліфікують
числове виконання, динамічні маски чи апаратне завершення. Для цього потрібні
відповідні інтеграційні тести на вибраному цільовому наборі компонентів.
