# Контрольний список випуску

Цей документ — авторитетна політика допуску до випуску.

## Поточні версії в документації

Після оновлення `deps/manifest.json` один раз оновіть `website/release-data/current.json` для випуску. Виконайте `npm --prefix website run sync:release-readmes` і закомітьте згенеровану команду README з конкретною версією. Виконайте `npm --prefix website run check:releases` та `./build.sh --doc`, щоб перевірити токени, винятки для історичних версій, локалізацію та відображені команди. Підтримуйте сторінку сумісності вручну, зазначаючи конкретні версії. Залишайте версії в історичних примітках до випусків незмінними. Зміни лише даних випуску не потребують оновлення перекладів або хешів джерел. Розподіл відповідальності за поля та правила токенів описано в `website/release-data/README.md`.

## Умови, що блокують випуск

Випуск заблоковано, якщо хоча б одна з наведених нижче умов не виконується:

1. У відстежуваних файлах коду/документації немає маркерів конфліктів злиття.
2. Перевірки гігієни іменування для публічної документації проходять успішно.
3. Перевірка коректності конфігурування/збірки проходить успішно (`cmake -S . -B ...` та `cmake --build ... --target sima_neat`).
4. Перевірки посилань у документації проходять у суворому режимі (`DOCS_STRICT_LINKS=1`).
5. Після кроків генерування робоче дерево чисте.
6. Немає невирішених аварійних збоїв чи помилок коректності — ні перед push, ні на ref випуску.
7. Vulcan CI (`.github/workflows/vulcan-ci.yml`) пройшов саме на тому коміті, на який ставиться тег.
8. Перевірка відсутності пропущених тестів (`scripts/ci/run_zero_skip_gate.sh`) проходить у тестових групах Vulcan CI.
9. Обов’язкові файли керування проєктом наявні й коректні:
   - `.github/CODEOWNERS`
   - `.github/PULL_REQUEST_TEMPLATE.md`
   - `CONTRIBUTING.md`
   - `docs/develop-apps/contribute/release-maintenance/release-checklist.md`
10. Метадані випуску повні:
   - `package-version` у `deps/manifest.json` на коміті з тегом дорівнює версії випуску, наприклад `0.7.0` для `v0.7.0`
   - `platform-version` оновлено в `deps/manifest.json`, коли це потрібно
   - `modelzoo-version` явно вибирає перевірений випуск Model Zoo, якщо він відрізняється від
     `platform-version`; якщо параметр не вказано, версія Model Zoo за замовчуванням визначається за `platform-version`
   - `abi-version` у `deps/manifest.json` збільшується лише тоді, коли структура публічного типу C++ або
     експортований бінарний контракт змінюється несумісно і `develop` досі використовує ту саму версію ABI,
     що й `main`. Якщо `develop` уже має вищу версію ABI для наступного випуску, зберігайте її для подальших
     несумісних змін ABI до випуску. Після несумісних змін перезберіть усі застосунки C++ і прив’язки Python
     з відповідними заголовними файлами та бібліотеками.
   - примітки до випуску підготовлено в описі випуску/тегу

У процесі випуску не допускається список «відомих аварійних збоїв». Будь-яка регресія з аварійним збоєм блокує випуск, доки її не буде виправлено.

## Тестові групи за розкладом

Ці групи не блокують випуск. Перевірки аварійних збоїв і коректності, стрес-тестування, санітайзери та
фазинг-тестування запускаються щоночі. Тривалі тести стабільності й довгі тести запускаються щотижня.

- `.github/workflows/test-crash-correctness-nightly.yml`
- `.github/workflows/test-stress-nightly.yml`
- `.github/workflows/sanitizers.yml`
- `.github/workflows/vulcan-fuzz-nightly.yml`
- `.github/workflows/test-soak-weekly.yml`
- `.github/workflows/long-tests-weekly.yml`

## Захист гілок і тегів у GitHub

Налаштуйте параметри репозиторію GitHub:

1. Захистіть `main`:
   - Вимагайте PR перед злиттям.
   - Вимагайте щонайменше одного схвалення від власника коду (рекомендовано два, якщо це можливо).
   - Скасовуйте застарілі схвалення після нових комітів.
   - Вимагайте проходження всіх обов’язкових перевірок статусу.
   - Забороніть примусовий push.
   - Використовуйте лише squash-злиття або лінійну історію.
2. Захистіть теги `v*`, щоб обмежити коло тих, хто може створювати теги випуску.

## Процес випуску

Випускайте одразу з остаточним тегом, наприклад `v0.7.0`. Не створюйте теги кандидатів на випуск.
Основні та патч-випуски використовують той самий робочий процес, **Actions → Release**. Він створює
`release-X.Y` від `main` для нової лінійки або повторно використовує наявну `release-X.Y`, ставить тег
на останній коміт цієї гілки і створює чернетку випуску на GitHub. Його перше завдання перевіряє, що
`package-version` на цьому коміті дорівнює `tag`. Він вимагає, щоб усі issue з Target Release
`core-X.Y.Z` мали статус Done, і потім задає їм Release Status `released`.

### Основний випуск

У цьому прикладі випускається `v0.7.0` у новій лінійці.

1. У `develop` задайте `package-version` у `deps/manifest.json` як `0.7.0`. Оновіть `platform-version`, `modelzoo-version` і `abi-version`, коли цього вимагають умови, що блокують випуск, і оновіть дані випуску, як описано в розділі «Поточні версії в документації».
2. Злийте `develop` у `main` через PR.
3. Виконайте `git fetch origin`. Коміт для тегу — `git rev-parse origin/main`. Нічого не зливайте в `main`, доки тег не буде створено.
4. Виконайте на цьому коміті перевірки з розділу «Перед створенням тегу».
5. Відкрийте **Actions → Release → Run workflow**. Задайте `release_line` як `0.7` і `tag` як `0.7.0`, залиште `main` як `source_branch`, `prerelease` вимкненим, а `latest` увімкненим. Робочий процес створює `release-0.7` від `main`, ставить тег `v0.7.0` і створює чернетку випуску.
6. Перейдіть до розділів «Після створення тегу» і «Публікація».

### Патч-випуск

У цьому прикладі випускається `v0.6.3` у наявній гілці `release-0.6`.

1. Підготуйте `release-0.6`:
   - Якщо всі зміни, які потраплять у `release-0.6` під час злиття `develop` через `main`, призначені для `0.6.3`, використайте цей шлях злиття: задайте `package-version` як `0.6.3` у `develop`, як у кроці 1 основного випуску, злийте `develop` у `main`, а потім злийте `main` у `release-0.6` через PR.
   - Інакше створіть гілку від `release-0.6`, перенесіть лише потрібні виправлення командою `git cherry-pick -x`, задайте `package-version` як `0.6.3` і відкрийте PR назад у `release-0.6`.
2. Виконайте `git fetch origin`. Коміт для тегу — `git rev-parse origin/release-0.6`. Нічого не зливайте в `release-0.6`, доки тег не буде створено.
3. Виконайте на цьому коміті перевірки з розділу «Перед створенням тегу».
4. Відкрийте **Actions → Release → Run workflow**. Задайте `release_line` як `0.6` і `tag` як `0.6.3`, залиште `main` як `source_branch`, а `prerelease` вимкненим. Вимкніть `latest`, якщо новішу лінійку вже опубліковано. Робочий процес повторно використовує `release-0.6`, бо `branch_exists_behavior` за замовчуванням має значення `reuse`, ставить на її останній коміт тег `v0.6.3` і створює чернетку випуску.
5. Перейдіть до розділів «Після створення тегу» і «Публікація».

### Спільні кроки

`<commit>` — це коміт для тегу з кроку 3 основного випуску або з кроку 2 патч-випуску.
У командах використано `0.7.0`; для патч-випуску підставте його версію, наприклад `0.6.3`.

#### Перед створенням тегу

1. Перевірте версію. `git show <commit>:deps/manifest.json` має показати `"package-version": "0.7.0"`. Якщо це не так, робочий процес Release зупиняється в першому завданні, перш ніж створити гілку чи тег.
2. Перевірте, що стандартний Vulcan CI пройшов саме на цьому коміті. `gh run list --repo sima-neat/core --workflow vulcan-ci.yml --commit <commit>` показує його запуски, і наявний успішний запуск у `main` або в гілці випуску можна використати повторно. Якщо такого немає, запустіть його командою `gh workflow run vulcan-ci.yml --repo sima-neat/core --ref main`, а для патч-випуску з `--ref release-0.6`. Переконайтеся, що `headSha` нового запуску — це цей коміт, і дочекайтеся результату командою `gh run watch <run-id> --repo sima-neat/core --exit-status`.
3. Перевірте умову допуску за issue. У проєкті Neat Releases (`https://github.com/orgs/sima-neat/projects/6`) щонайменше одне issue має мати Target Release `core-0.7.0`, і всі issue з цим Target Release мають мати статус Done. Запуск Release з увімкненим `dry_run` виконує цю перевірку та перевірку версії, не виконуючи push і не змінюючи issue.

#### Після створення тегу

1. Перевірте, що **Target SHA** у підсумку запуску Release — це цей коміт. Якщо ні, не публікуйте чернетку випуску.
2. Запустіть стандартний Vulcan CI для тегу командою `gh workflow run vulcan-ci.yml --repo sima-neat/core --ref v0.7.0`. Тег, який ставить робочий процес, сам не запускає жодного робочого процесу. Цей запуск публікує версійні пакети, які встановлює `sima-cli neat install core@v0.7.0`, а також офлайн-набори.
3. Дочекайтеся командою `gh run watch <run-id> --repo sima-neat/core --exit-status`, поки весь запуск завершиться успішно, зокрема завдання `Publish develop and release offline bundles`. `latest.tag` оновлюється ще до початку цього завдання, тому він не свідчить про те, що запуск завершено.

#### Публікація

1. Відкрийте чернетку випуску на GitHub, перевірте примітки до випуску й натисніть **Publish release**.
2. Створіть задачі на доопрацювання після випуску.

## Експлуатаційні примітки

- Жодних випусків із «брудних» гілок.
- Жодних випусків коду без рецензування.
- Жодних випусків, коли обов’язкові перевірки червоні.
- Push заборонено, якщо локальна перевірка аварійних збоїв/коректності не проходить.
- Жодного ручного обходу для збоїв перевірок гігієни.

## Контракт регресії продуктивності

- Точка входу для перевірки продуктивності: `scripts/ci/run_perf_regression_gate.sh`.
- Базові значення прив’язано до профілю, вони зберігаються в `tests/perf/baselines/v2/modalix_default/`:
  - `profile.json` визначає фіксований контракт для середовища Modalix.
  - один файл сценарію на кожен ідентифікатор сценарію (`<scenario_id>.json`).
- Обов’язкові сценарії:
  - `runtime_session_sync_rgb`
  - `runtime_session_async_rgb`
  - `runtime_graph_fanout`
  - `runtime_graph_join_bundle`
  - `runtime_codec_mjpeg_decode`
  - `runtime_codec_h264_decode`
  - `runtime_codec_h265_decode`
  - `runtime_model_archive_load`
- Кожен запуск перевірки продуктивності публікує файли результатів для кожного сценарію в `build-perf-gate/perf_results/`.
- Кожен результат має містити:
  - `scenario_id`
  - `modalix_profile_id`
  - `status`
  - `failure_class`
  - `reason_code`
  - `metrics`
  - `run_meta`
  - `timestamp`
- Будь-яка класифікація `REGRESSION`, `HARNESS_ERROR` або `ENV_BROKEN` блокує групу.
