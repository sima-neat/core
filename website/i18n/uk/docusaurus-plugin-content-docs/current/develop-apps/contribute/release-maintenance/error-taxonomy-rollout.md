# Впровадження таксономії помилок

Цей контрольний список відстежує впровадження канонічної семантики помилок у Core і плагінах середовища виконання.

## Канонічні коди

[`include/pipeline/ErrorCodes.h`](/reference/cppapi/files/include-pipeline-errorcodes-h) є
джерелом істини. У [каталозі кодів помилок](/reference/error-codes) мають бути задокументовані кожна константа C++, кожне ім’я Python `ERROR_*` і перехід від загальних кодів до конкретних.

## Етапи виконання

1. Каркас таксономії
2. Присвоєння кодів під час збірки/перевірки
3. Присвоєння кодів під час отримання даних у середовищі виконання
4. Присвоєння кодів під час розбору й відкриття у введенні-виведенні графа
5. Тести + документація

## Перевірка сумісності

- Вважайте зміну точного коду, який повертає наявний збій, зміною поведінки, що порушує
  сумісність, навіть якщо жодна сигнатура C++ чи Python не змінюється.
- Задокументуйте відповідності старих кодів новим у публічній таблиці міграції.
- Залишайте резервні коди (`build.parse_launch`, `runtime.pull` і
  `runtime.element_failed`) лише для збоїв без конкретної класифікації.
- Тестуйте версіоновані ключі формату передавання `simaai-neat-error` там, де їх формує виробничий код, і розбирайте через Core справжнє
  `GstMessage`.

## Контрольний список перевірки

- `NeatError.report().error_code` непорожній у разі термінальних збоїв фреймворку.
- `PullError.code` заповнюється для помилок pull під час виконання.
- Помилки обгорток Graph містять код + контекст + підказку (без загального резервного тексту).
- Помилки розбору JSON містять `offset=` і `near='...'`.
- Негативні тести перевіряють код і стабільні фрагменти повідомлень для кожного класу таксономії.
- Документація з діагностики та архітектури містить порядок первинного аналізу (triage): прочитайте `error_code`,
  перегляньте `repro_note`, перегляньте діагностику шини, а потім відтворіть за допомогою
  `repro_gst_launch`.
