# Агентний робочий процес

Публічний API фреймворку Neat спроєктовано не лише для людей — авторів застосунків, а й для агентів ШІ, які пишуть код під Modalix від імені розробника. На цій сторінці пояснено, чому низка проєктних рішень фреймворку має саме такий вигляд: їх оптимізовано для агента, який читає поверхню API, а не лише для людини.

## Що агентові потрібно від фреймворку

Агентові ШІ, який генерує код для незнайомого API, зазвичай потрібні:

1. **Невелика публічна поверхня** — менше типів означає менше вивчати.
2. **Самоописові типи** — сигнатура типу має кодувати контракт, а не лише натякати на нього.
3. **Один спосіб для кожної дії** — кілька рівноцінних шляхів — це саме той вибір, у якому агент помиляється.
4. **Документація поруч із кодом** — агент читає блоки `@brief`, а не проєктні документи на 8000 рядків. Критичний контекст має бути поруч із символом.
5. **Детерміновані результати** — коли агент пише тестові знімки, побайтова детермінованість робить їх стабільними.
6. **Помилки, які називають першопричину** — коли щось не працює, повідомлення про помилку має вказувати, що саме не так: ядро, контракт чи параметр, а не просто «Збірка графа не вдалася».
7. **Артефакти для відтворення** — якщо код агента не працює, агент може вставити рядок `repro_gst_launch` у налагоджувач і ітерувати без повторного запуску агента.
8. **Жодних прихованих глобальних змінних** — кожна поведінка має задаватися аргументом конструктора або параметром вузла, а не змінною середовища, яку зчитують під час виконання.
9. **Стабільні ідентифікатори** — однакові вузли + однакові параметри ⇒ однакові назви елементів ⇒ однаковий рядок запуску ⇒ стабільні тестові фікстури.
10. **Архіви моделей як дані, а не код** — модель є пакетом, який завантажує фреймворк, а не заголовним файлом, з яким агент має компілювати свій код.
11. **Компоновані складові** — вузли, моделі та повторно використовувані фрагменти графа легко поєднуються; агентові не потрібно знати, які комбінації фреймворк «підтримує», бо планувальник відповідає на це під час збірки.
12. **Явна перевірка під час збірки** — збої проявляються в `Graph::build()`, а не під час першого `pull(...)`. Циклу ітерацій агента потрібно, щоб помилка вказувала на правильний рядок.
13. **Структурований `GraphReport`** — програмний доступ до того, що зробила збірка, щоб агент міг перевірити власну роботу.
14. **Поступове розкриття складності** — `Model` — простий шлях, `Graph::add()` — наступний, власні вузли — глибокий шлях. Агент спершу натрапляє на простий шлях.
15. **Версіоновані контракти MPK** — архів моделі містить достатньо метаданих, тож агентові, який генерує код для нього, не потрібно звертатися до зовнішньої документації.

Ці потреби втілено у фреймворку як конкретні проєктні рішення:

- Невелика публічна поверхня (Model, Tensor, Sample, Node, Graph і Run) — це все, що агентові потрібно вивчити для коду застосунків.
- `Graph::describe()` повертає структурований підсумок плану — агенти можуть перевіряти власні конвеєри.
- `NeatError` містить `error_code()` і `GraphReport` — агенти можуть розгалужувати логіку за кодом.
- `Node::backend_fragment()` детермінований — агенти можуть писати для конвеєрів тести з еталонними рядками (golden-string).
- `MpkContract` — єдиний авторитетний опис моделі; агентам, які генерують код з’єднань для моделі, ніколи не потрібно нічого іншого.

## Користь для авторів застосунків

Навіть якщо ви не агент, ви виграєте від дизайну API, зручного для агентів: ті самі властивості, що роблять автоматичне генерування коду надійним, також спрощують ручне рецензування коду, роблять рефакторинг безпечнішим, а розробку за допомогою ШІ (Claude Code, Copilot, Cursor) — продуктивнішою для коду Modalix.
