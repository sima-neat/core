# Контракт MPK

Цей документ визначає авторитетний контракт для приймання архівів моделей і розбору контракту MPK.

## Сфера застосування

Контракт поширюється на:

- `src/model/ModelPack.cpp`
- `src/model/ModelArchiveLoader.cpp`
- `src/model/internal/ModelArchiveLoader.h`
- `src/pipeline/internal/sima/MpkContract.cpp`
- `src/pipeline/internal/sima/static_contract/MpkDecoder.cpp`

## Допустимий формат архіву

Допустиме розширення пакета: лише `.tar.gz`, точно й у нижньому регістрі. `.mpk`, `.tgz`, `.tar` і просто `.gz` відхиляються ще до перевірки вмісту tar.

Вимоги до архіву:

- Архів має читатися як потік tar.
- Розмір архіву має бути меншим або рівним значенню `max_archive_bytes`, яке налаштовано в завантажувачі.
- Кількість записів має бути меншою або рівною значенню `max_entries`, яке налаштовано в завантажувачі.
- Розмір корисних даних запису має бути меншим або рівним значенню `max_entry_bytes`, яке налаштовано в завантажувачі.

## Допустима схема розміщення

Для видобування приймаються лише звичайні файли. Записи тек дозволені, але ігноруються.

Дозволені класи видобутих файлів:

- Конфігураційні файли JSON (`*.json`) -> видобуваються в `etc/`
- Спільні об’єкти (`*.so`) -> видобуваються в `lib/`
- Двійкові файли ELF (`*.elf`) -> видобуваються в `share/`

Обов’язковий вміст пакета:

- Контракт інференсу MPK (`mpk.json` або `*_mpk.json`)
- JSON етапів/конфігурації на боці завантажувача, потрібний середовищу виконання
- Принаймні один двійковий артефакт моделі (`*.elf` або `*.so`)

## Завантаження маніфесту MPK

Завантаження моделі, збірки підготовленого середовища виконання та хост PCIe читають `mpk.json` через `MpkDecoder::load`. Ця функція один раз читає маніфест, будує з цих байтів семантичний `MpkContract` і знаходить виконуваний файл кожного етапу всередині пакета: виконувані файли MLA — у `share/`, `lib/`, потім у корені пакета; модулі A65 — у `lib/`, у корені пакета, потім у `share/`. Допуск до виконання та хост PCIe декодують ті самі байти разом із доказами з ELF і GraphExecutor виконуваних файлів, тому план і контракт походять з тих самих байтів.

## Правила безпеки видобування

Видобування має працювати за принципом fail-closed (за будь-якої помилки — відмова).

Відхиляються такі форми шляхів:

- Абсолютні шляхи (наприклад, `/etc/passwd`)
- Сегменти обходу (`..`)
- Префікси дисків Windows (`C:`)
- Форми обходу зі змішаними роздільниками (`..\\`, `..//`)
- Недійсні байти UTF-8 у шляху
- Символи Unicode, схожі на скісну або зворотну скісну риску (наприклад, `U+FF0F`, `U+2215`, `U+FF3C`)
- Символи Unicode, схожі на крапку, у шляхах, подібних до обходу (наприклад, `U+FF0E`, `U+2024`, `U+FE52`)

Відхиляються такі типи записів:

- Записи символічних посилань
- Записи жорстких посилань
- Записи пристроїв
- Записи FIFO

Поведінка під час видобування:

- Ніколи не використовуйте шляхи з архіву безпосередньо як вихідні шляхи у файловій системі.
- Спочатку нормалізуйте та перевірте шлях запису архіву.
- Видобувайте схвалені записи потоком вмісту в контрольовану тимчасову кореневу теку.
- Ніколи не дозволяйте запис за межами кореневої теки видобування.
- Дублікати нормалізованих шляхів tar відхиляються як `invalid_archive`.
- Пошкодження заголовка/контрольної суми tar відхиляється як `invalid_archive`.

## Перевірка JSON та послідовностей

`pipeline_sequence.json` має відповідати таким вимогам:

- Об’єкт JSON з непорожнім масивом `pipelines`.
- Перший об’єкт конвеєра має містити непорожній масив `sequence`.
- Кожен запис етапу має містити:
  - `sequence_id` (ціле число)
  - `name` (непорожній рядок)
  - `pluginId` (непорожній рядок)
  - `configPath` (непорожній рядок)
  - `processor` (непорожній рядок)
  - `kernel` (непорожній рядок)
- Повторювані назви етапів не приймаються.
- Повторювані ключі JSON не допускаються.
- Вкладеність JSON, глибша за значення `max_json_depth` завантажувача, відхиляється.
- Непідтримувані значення `kernel` відхиляються.
- Залежності між етапами в `input` повинні посилатися лише на:
  - `decoder`, або
  - назви попередніх етапів після стабільного впорядкування.

## Таксономія помилок

Кожен збій приймання архіву моделі або контракту MPK має відповідати одному з таких класів:

- `invalid_archive`
- `path_traversal`
- `schema_error`
- `unsupported_version`
- `size_limit_exceeded`

Публічні повідомлення про помилки повинні містити ключ таксономії, щоб тести могли перевіряти детерміновану класифікацію.

## Вимоги до детермінізму

- Порядок послідовності має бути детермінованим у повторних запусках.
- Архіви тестових фікстур у `tests/assets/mpk` мають бути побітово відтворюваними.
- Згенеровані контрольні суми маніфесту фікстур у `test-assets/model-archive/fixtures_manifest.json` є джерелом істини для фікстур безпеки в дереві збірки.

## Вимога до зіставлення тестів

Кожен негативний тест архіву моделі/контракту MPK має перевіряти один із наведених вище ключів таксономії.
