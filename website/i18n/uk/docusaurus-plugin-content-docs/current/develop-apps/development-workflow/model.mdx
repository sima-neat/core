# Модель

[`Model`](/reference/{lsa}/classes/simaai-neat-model) завантажує скомпільований архів моделі та надає маршрут, який Neat може виконати.

Використовуйте `Model`, коли вам потрібне виконання з урахуванням моделі без ручного з’єднання кожного етапу попередньої обробки, інференсу (inference) та постобробки. Спочатку перевірте контракт. Потім запускайте модель. Жодних загадкових тензорів.

## Що дає вам `Model`?

- `input_specs()` та `output_specs()` показують, які тензори модель очікує на вході та які генерує на виході.
- `metadata()`, `info()` та Python `summary()` допомагають вам переглянути завантажену модель.
- `run(...)` виконує один безпосередній інференс.
- `build(...)` створює повторно використовуваний runner моделі для виконання в режимі push/pull.
- `graph()` повертає маршрут моделі у вигляді фрагмента `Graph`, який можна повторно використовувати.
- `preprocess()`, `inference()` та `postprocess()` визначають етапи маршруту для розширеної композиції.

Посилання:

- [`Model` API](/reference/{lsa}/classes/simaai-neat-model)
- [`Model::Options`](/reference/{lsa}/structs/simaai-neat-model-options)
- [`Model::RouteOptions`](/reference/{lsa}/structs/simaai-neat-model-routeoptions)

## Завантаження архіву моделі

Приклади на цій сторінці передбачають, що `model_path` вказує на скомпільований архів моделі, створений за допомогою Model Compiler, зазвичай це `.tar.gz`, скопійований на машину, на якій працює Neat. Спочатку використовуйте параметри за замовчуванням; додавайте `ModelOptions` лише тоді, коли це вимагається умовами контракту або джерелом вхідних даних.

<CodeTabs>
<CodeTab label="C++" lang="cpp">

```cpp
const std::string model_path = "resnet_50_model.tar.gz";
simaai::neat::Model model(model_path);

const auto info = model.info();
const auto inputs = model.input_specs();
const auto outputs = model.output_specs();
```

</CodeTab>
<CodeTab label="Python" lang="python">

```python
model_path = "resnet_50_model.tar.gz"
model = pyneat.Model(model_path)

print(model.summary())
inputs = model.input_specs()
outputs = model.output_specs()
```

</CodeTab>
</CodeTabs>

Якщо цей етап перевірки вас здивував, зупиніться. Виправте шлях до моделі, артефакт або контракт, перш ніж писати навколо цього більший застосунок.

## Вибір шляху виконання моделі

Оберіть шлях, який відповідає задачі. Smoke-тести мають бути невеликими; механізми рівня графа залишайте для задач рівня графа.

| Потрібно | Використовуйте | Повертає |
| --- | --- | --- |
| Один раз запустити модель на одному вході | `model.run(...)` | `TensorList` для тензорного входу або `Sample` для входу типу Sample |
| Повторно використовувати маршрут моделі для багатьох входів | `model.build(...)` і runner моделі | Керування push/pull навколо маршруту моделі |
| Виміряти лише виконання моделі | `model.benchmark(...)` або runner моделі з вимірюванням | `BenchmarkReport` або `MeasureReport` |
| Додати модель до робочого процесу застосунку | `graph.add(model)` | Етап `Graph` |
| Надати межі маршруту для компонування | `model.graph(route_options)` | Повторно використовуваний фрагмент `Graph` |
| Налагодити один етап моделі | `model.fragment(ModelStage::...)` | Фрагмент `Graph` для конкретного етапу |

Щоб переконатися, що модель працює, використовуйте прямі виклики моделі. Використовуйте `Graph`, коли модель стає частиною застосунку: іменовані входи, вузли-джерела, гілки, об’єднання, рендеринг, виведення відео, виведення метаданих або кілька моделей.

## Вибір параметрів моделі

Почніть із `ModelOptions` за замовчуванням. Додавайте параметри лише тоді, коли це вимагається контрактом моделі або джерелом вхідних даних.

| Мета | Параметри | Примітки |
| --- | --- | --- |
| Надсилати декодоване зображення | `preprocess.kind`, `preprocess.preset` та окремі поля попередньої обробки, як-от зміна розміру, колір, розташування осей (layout), нормалізація, квантування або теселяція | Використовуйте це, коли застосунок надсилає пікселі, а Neat має адаптувати їх до контракту моделі. |
| Передати тензори, що відповідають публічним входам моделі | Залиште параметри попередньої обробки незаданими | Зберігає потрібні адаптери Cast/Quant/Tess, зокрема для вже масштабованих і нормалізованих входів FP32. |
| Декодувати вихід виявлення | `decode_type`, `decode_type_option`, `score_threshold`, `nms_iou_threshold`, `top_k`, `num_classes` | Моделям виявлення потрібен явно заданий намір декодування. |
| Зберегти видобуті файли моделі для перегляду | `cleanup_extracted_model_data = false` | Корисно під час налагодження. Залиште значення за замовчуванням для звичайного запуску. |
| Запустити кілька маршрутів моделей в одному процесі | `name_suffix` та префікс/суфікс назв елементів графа | Зберігає згенеровані назви та діагностику читабельними. |
| Достроково зупинити маршрут моделі | `inference_terminal` | Розширений спосіб налагодження маршруту. Не використовуйте його в коді першого запуску. |
| Налаштувати розміщення виконання або внутрішні черги | `processcvu`, `processmla`, `advanced_execution` | Розширений режим. Виміряйте шлях за замовчуванням перед налаштуванням. |

### Вхідне зображення з декодуванням для виявлення об’єктів

Використовуйте цей шаблон, коли модель передбачає попередню обробку зображень і видає результати у форматі YOLO.

<CodeTabs>
<CodeTab label="C++" lang="cpp">

```cpp
simaai::neat::Model::Options options;
options.preprocess.kind = simaai::neat::InputKind::Image;
options.preprocess.preset = simaai::neat::NormalizePreset::COCO_YOLO;
options.decode_type = simaai::neat::BoxDecodeType::YoloV8;
options.score_threshold = 0.25f;
options.nms_iou_threshold = 0.45f;
options.top_k = 100;

simaai::neat::Model model(model_path, options);
```

</CodeTab>
<CodeTab label="Python" lang="python">

```python
options = pyneat.ModelOptions()
options.preprocess.kind = pyneat.InputKind.Image
options.preprocess.preset = pyneat.NormalizePreset.COCO_YOLO
options.decode_type = pyneat.BoxDecodeType.YoloV8
options.score_threshold = 0.25
options.nms_iou_threshold = 0.45
options.top_k = 100

model = pyneat.Model(model_path, options)
```

</CodeTab>
</CodeTabs>

Дотримуйтеся чіткості налаштувань: не встановлюйте значення за замовчуванням або застарілі поля, якщо вони не змінюють контракт, який вам потрібен. Якщо метадані тензора або зображення вже містять інформацію про вихідний формат, уникайте повторення цієї інформації, якщо тільки на сторінці не пояснюється, чому це необхідно.

### Довідник полів декодування виявлення

Задавайте параметри декодування виявлення, коли маршрут має повертати декодовані рамки, результати оцінки пози або сегментації замість необроблених тензорів інференсу. Залиште поля незаданими, якщо вам потрібні необроблені виходи моделі.

| Поле | Використовуйте його, коли | Значення за замовчуванням |
| --- | --- | --- |
| `decode_type` | Потрібно, щоб Neat додав етап BoxDecode для моделі виявлення. | `Unspecified`; намір декодування виявлення не задано. |
| `decode_type_option` | Порядок тензорів голови виявлення потребує конкретного варіанта. | `Auto`; рішення ухвалюють контракт моделі та планувальник маршрутів. |
| `score_threshold` | Ви хочете відкинути кандидатів із низьким рівнем достовірності під час декодування. | `0`; зберігайте список кандидатів до наступного етапу відбору. |
| `nms_iou_threshold` | Під час декодування слід застосовувати придушення немаксимумів (NMS). | `0`; зберігається значення, упаковане в модель. Якщо його немає, YOLO26 пропускає NMS, а інші декодери придушують кожну рамку, що перекривається. |
| `top_k` | Ви хочете встановити жорстке обмеження на кількість виявлених об’єктів для кожного результату. | `0`; обмеження кількості найкращих результатів (top-K) відсутнє. |
| `num_classes` | Глибину голови класів не вдається надійно визначити, наприклад для однокласової розділеної голови YOLO. | `0`; використовуються метадані MPK або застарілий спосіб визначення. |
| `multimask_output` | Декодер підказок Segment Anything має повернути відповідь з однією маскою, як для рамки або кількох точок. Значення `false` приймають лише типи декодування Segment Anything. | `true`; залишається кандидатна маска з найкращим передбаченим IoU, як для одного кліку. Див. [Маски Segment Anything](/reference/boxdecode_decode_types#segment-anything-masks). |

Для більшості моделей у стилі YOLO почніть із `decode_type`, `score_threshold`, `nms_iou_threshold` і `top_k`. Додавайте `num_classes` лише тоді, коли контракту моделі потрібна допомога. Залиште `decode_type_option` у значенні `Auto`, якщо не відомо, що порядок тензорів потребує конкретного селектора.

<CodeTabs>
<CodeTab label="C++" lang="cpp">

```cpp
simaai::neat::Model::Options options;
options.decode_type = simaai::neat::BoxDecodeType::YoloV8;
options.score_threshold = 0.25f;
options.nms_iou_threshold = 0.45f;
options.top_k = 100;
options.num_classes = 1;  // Set only when the model contract needs the class count.

simaai::neat::Model model(model_path, options);
```

</CodeTab>
<CodeTab label="Python" lang="python">

```python
options = pyneat.ModelOptions()
options.decode_type = pyneat.BoxDecodeType.YoloV8
options.score_threshold = 0.25
options.nms_iou_threshold = 0.45
options.top_k = 100
options.num_classes = 1  # Set only when the model contract needs the class count.

model = pyneat.Model(model_path, options)
```

</CodeTab>
</CodeTabs>

Не використовуйте `boxdecode_original_width` або `boxdecode_original_height` у нових прикладах. Інверсія координат використовує метадані попередньої обробки; зберігайте ці метадані замість того, щоб жорстко задавати розмір зображення.

### Необроблений тензорний вхід

Використовуйте налаштування за замовчуванням для тензорів, що відповідають `model.input_specs()`. Neat зберігає потрібні для MPK тензорні адаптери.

<CodeTabs>
<CodeTab label="C++" lang="cpp">

```cpp
simaai::neat::Model model(model_path);
```

</CodeTab>
<CodeTab label="Python" lang="python">

```python
model = pyneat.Model(model_path)
```

</CodeTab>
</CodeTabs>

Застарілий параметр `preprocess.enable = Off` не вибирає виконання лише на MLA і не видаляє потрібні для MPK адаптери Cast/Quant/Tess. Непорожній список `preprocess.transforms` має пріоритет над `Off`.

### Довідник полів попередньої обробки

`ModelOptions.preprocess` визначає, який тип вхідних даних ви надаватимете і що Neat може адаптувати перед інференсом.

| Потрібно | Поле |
| --- | --- |
| Обрати вхід: зображення чи тензор | `preprocess.kind` |
| Застаріле керування попередньою обробкою (потрібні для MPK адаптери залишаються) | `preprocess.enable` |
| Обмежити розміри динамічного вхідного зображення | `preprocess.input_max_width`, `preprocess.input_max_height`, `preprocess.input_max_depth` |
| Змінити розмір, обрізати або додати поля (letterbox) з розміщенням по центру чи у верхньому лівому куті | `preprocess.resize`, `preprocess.resize.placement` |
| Перетворити колір: RGB, BGR, NV12, I420 або відтінки сірого | `preprocess.color_convert` |
| Перетворити порядок осей: HWC, CHW або інший | `preprocess.layout_convert` |
| Застосувати нормалізацію за середнім значенням і стандартним відхиленням (mean/std) | `preprocess.normalize` або `preprocess.preset` |
| Квантувати перед інференсом | `preprocess.quantize` |
| Виконати теселяцію перед інференсом | `preprocess.tessellate` |
| Перевизначити впорядкованим списком перетворень | `preprocess.transforms` |

Задайте найменший набір параметрів, який описує вхідні дані, що ви насправді надсилаєте. Специфікації — це контракт, а остаточний (resolved) план попередньої обробки — це підтвердження.

## Перевірка специфікацій і безпосередній запуск

Перш ніж компонувати `Graph`, перевірте контракт моделі. Специфікації підкажуть, що виділити, надіслати та декодувати.

<CodeTabs>
<CodeTab label="C++" lang="cpp">

```cpp
simaai::neat::Model model(model_path, options);

const auto inputs = model.input_specs();
const auto outputs = model.output_specs();
const auto metadata = model.metadata();
const auto info = model.info();

for (const auto& input : inputs) {
  const auto& shape = input.shape;
}

for (const auto& output : outputs) {
  const auto& shape = output.shape;
}

simaai::neat::Tensor input = simaai::neat::Tensor::from_cv_mat(
    frame,
    simaai::neat::ImageSpec::PixelFormat::BGR,
    simaai::neat::TensorMemory::CPU);

simaai::neat::TensorList result = model.run(
    simaai::neat::TensorList{input},
    /*timeout_ms=*/2000);
```

</CodeTab>
<CodeTab label="Python" lang="python">

```python
model = pyneat.Model(model_path, options)

print(model.summary())
inputs = model.input_specs()
outputs = model.output_specs()
metadata = model.metadata()

for input_spec in inputs:
    input_shape = list(input_spec.shape)

for output_spec in outputs:
    output_shape = list(output_spec.shape)

tensor = pyneat.Tensor.from_numpy(
    frame,
    copy=True,
    image_format=pyneat.PixelFormat.BGR,
)

result = model.run([tensor], timeout_ms=2000)
```

</CodeTab>
</CodeTabs>

У Python передавайте список або кортеж вхідних даних. `model.run([tensor])` означає «один вхід для моделі». Це не додає розмірність пакета.

`model.run(...)` працює як одноразовий виклик, але не перезбирає модель під час кожного виклику. Внутрішній runner збирається відкладено, під час першого виклику, і кешується; наступні виклики повторно використовують цей runner і виконують через нього push/pull. Використовуйте явний `model.build(...)`, коли вам потрібні параметри маршруту, параметри середовища виконання, вимірювання, керування закриттям і спорожненням (drain) або цикл «виробник/споживач».

У C++, з підтримкою OpenCV, також доступна функція `model.run(std::vector<cv::Mat>{frame}, timeout_ms)`. Використовуйте явну функцію `Tensor::from_cv_mat(...)`, коли в прикладі необхідно вказати формат пікселів або власність пам’яті.

## Робота з кількома входами та пакетами

Модель може мати кілька вхідних портів, скомпільований розмір пакета або обидва ці параметри. Не слід змішувати ці поняття:

- **Кілька входів** означає один тензор на кожен вхід моделі. Перевірте `model.input_specs()`, щоб дізнатися про очікуваний порядок і контракти.
- **Пакет** означає, що модель була скомпільована для обробки кількох логічних зразків за один інференс. Перевірте значення `model.compiled_batch_size()`.
- **Списки входів у Python** задають перелік входів, а не розмір пакета. `model.run([tensor])` — це один вхід. Він не перетворює `tensor` на пакет розміром 1.

<CodeTabs>
<CodeTab label="C++" lang="cpp">

```cpp
const int batch = model.compiled_batch_size();
const auto specs = model.input_specs();

// Two-input model: pass one tensor per ingress.
simaai::neat::TensorList inputs{left_tensor, right_tensor};
simaai::neat::TensorList outputs = model.run(inputs, /*timeout_ms=*/2000);
```

</CodeTab>
<CodeTab label="Python" lang="python">

```python
batch = model.compiled_batch_size()
specs = model.input_specs()

# Two-input model: pass one tensor per ingress.
outputs = model.run([left_tensor, right_tensor], timeout_ms=2000)
```

</CodeTab>
</CodeTabs>

Якщо пакетна модель очікує форму `[N, ...]`, вкажіть `N` у формі тензора відповідно до специфікації входу. Не передавайте `N` окремих елементів списку Python, якщо модель не має `N` вхідних портів.

## Перевірка плану маршруту

Якщо попередня обробка, топологія виходів або вибір маршруту вас дивують, перевірте маршрут, а не вгадуйте.

| Запитання | Що перевірити |
| --- | --- |
| Які розміри тензорів і типи даних підтримує модель? | `input_specs()` та `output_specs()` |
| Що було зазначено в скомпільованому артефакті? | `info()` та `metadata()` |
| Які вхідні дані потрібні для попередньої обробки? | `preprocess_requirements()` |
| Який шлях попередньої обробки використовував Neat під час компіляції? | `resolved_preprocess_plan()` / Python `preprocess_plan()` |
| Який розмір пакета скомпільовано? | `compiled_batch_size()` |
| Який формат виходу мені потрібно декодувати? | специфікації виходів, а також `info().output_topology` |

<CodeTabs>
<CodeTab label="C++" lang="cpp">

```cpp
const auto requirements = model.preprocess_requirements();
const auto plan = model.resolved_preprocess_plan();

std::cout << "preprocess: " << plan.to_debug_string() << "\n";
```

</CodeTab>
<CodeTab label="Python" lang="python">

```python
requirements = model.preprocess_requirements()
plan = model.preprocess_plan()

print(plan.to_debug_string())
```

</CodeTab>
</CodeTabs>

Остаточний план — це журнал аудиту, який містить таку інформацію: запитані параметри, дійсні параметри, сімейство графів, вхідні контракти, контракт MLA та попередження.

### Знімок маршруту моделі

Використовуйте `info()`, коли вам потрібне стисле представлення маршруту без ручного перегляду архіву моделі. Python також надає `summary()` для швидкого текстового перегляду; C++ використовує структурований результат `info()`.

| Запитання | Поле `info()`, яке потрібно перевірити |
| --- | --- |
| Який артефакт я завантажив? | `model_name`, `mpk_json_path` |
| Які етапи-адаптери потрібні? | `needs` |
| Які етапи-адаптери доступні? | `capabilities` |
| Чи містить маршрут попередню обробку або постобробку? | `selection.include_preprocess_stage`, `selection.include_postprocess_stage` |
| Чи це маршрут лише з інференсом? | `selection.infer_only` |
| Який граф попередньої обробки або тип постобробки обрано? | `selection.preprocess_graph`, `selection.selected_post_kind` |
| Скільки виходів є фізичними, а скільки – логічними? | `output_topology.physical_outputs`, `logical_outputs`, `packed_outputs` |
| Які попередження згенерував планувальник маршруту? | `warnings` |

<CodeTabs>
<CodeTab label="C++" lang="cpp">

```cpp
const auto info = model.info();

std::cout << "model=" << info.model_name << "\n";
std::cout << "physical_outputs=" << info.output_topology.physical_outputs
          << " logical_outputs=" << info.output_topology.logical_outputs << "\n";

for (const auto& warning : info.warnings) {
  std::cerr << warning << "\n";
}
```

</CodeTab>
<CodeTab label="Python" lang="python">

```python
print(model.summary())

info = model.info()
print("model=", info.model_name)
print("physical_outputs=", info.output_topology.physical_outputs)
print("logical_outputs=", info.output_topology.logical_outputs)

for warning in info.warnings:
    print(warning)
```

</CodeTab>
</CodeTabs>

Ставтеся до попереджень щодо маршруту як до першочергової інформації. Якщо планувальник маршруту повідомляє про щось незвичайне, не намагайтеся обійти це налаштуванням. Спочатку виправте контракт або параметри.

### Що виконує модель

Використовуйте `execution_plan()`, щоб побачити вузли, які виконує модель, де виконується кожен вузол і які тензори передаються між ними. `Model::execution_plan(...)` приймає ті самі аргументи, що й `build(...)`, збирає модель без обробки кадру й закриває її після зчитування плану, тому потребує пристрою.

<CodeTabs>
<CodeTab label="C++" lang="cpp">

```cpp
const simaai::neat::ExecutionPlan plan = model.execution_plan();
std::cout << plan.to_json() << "\n";
```

</CodeTab>
<CodeTab label="Python" lang="python">

```python
plan = model.execution_plan()
print(plan.to_json())
```

</CodeTab>
</CodeTabs>

JSON перелічує вузли графа моделі в порядку конвеєра й містить одне ребро між кожною парою сусідніх вузлів.

| Поле | Значення |
| --- | --- |
| `model` | Назва моделі, `batch` (кадрів на один запуск MLA) і `memory` (пам’ять пристрою на один кадр в обробці) |
| `nodes[].kind` | Тип вузла, наприклад `Input`, `Preproc`, `Quant`, `ModelFragment`, `Dequant`, `SimaBoxDecode` або `Output` |
| `nodes[].runs_on` | Де виконується вузол: `A65` (процесорні ядра Arm), `EV74` (процесор комп’ютерного зору) або `MLA` |
| `nodes[].kernel` | Обчислювальне ядро (kernel), яке виконує вузол `EV74` або `A65` |
| `nodes[].settings` | Остаточні налаштування `Preproc` і `SimaBoxDecode` з тими самими назвами, що в `PreprocOptions` і `BoxDecodeOptions` |
| `edges[].tensors` | Тензори від одного вузла до наступного: `shape` із пакетом першим виміром, `dtype` і `quant` (`scale`, `zero_point`) для квантованих тензорів |

Налаштування `SimaBoxDecode` показують пороги й `top_k` лише тоді, коли їх задає модель або ваші параметри; інакше діє значення декодера за замовчуванням. Схема: `schemas/execution_plan_v1.schema.json`.

## Використання моделі в графі

У типовому випадку додайте модель безпосередньо між публічним входом і виходом.

<CodeTabs>
<CodeTab label="C++" lang="cpp">

```cpp
simaai::neat::Graph graph("classifier");
graph.add(simaai::neat::nodes::Input("image"));
graph.add(model);
graph.add(simaai::neat::nodes::Output("classes"));
```

</CodeTab>
<CodeTab label="Python" lang="python">

```python
graph = pyneat.Graph("classifier")
graph.add(pyneat.nodes.input("image"))
graph.add(model)
graph.add(pyneat.nodes.output("classes"))
```

</CodeTab>
</CodeTabs>

Публічний `Input` за замовчуванням, безпосередньо підключений до єдиного входу зображення моделі, успадковує його спосіб інтерпретації зображення та формат. Формат джерела можна задати явно; граф перевіряє його відповідність контракту моделі. Пам’ять джерела, розміри, часові позначки та параметри черги не змінюються. Для кількох споживачів або неоднозначних з’єднань задайте параметри входу явно.

Ця інтерпретація застосовується на межі входу Graph. Безпосередні виклики моделі й далі вимагають входів, що відповідають оголошеному контракту зображення або тензора моделі.

Використовуйте `model.graph(...)`, коли вам потрібен фрагмент, який можна повторно використовувати, або чітко визначені межі маршруту.

Параметри маршруту визначають, як цей фрагмент надає свій контракт:

| Потрібно | Параметр маршруту |
| --- | --- |
| Додати публічний вхідний вузол до отриманого графа | `include_input` |
| Додати публічний вихідний вузол до отриманого графа | `include_output` |
| Надати окремі фізичні виходи | `expose_all_outputs` |
| Усунути неоднозначність у назвах згенерованих елементів | `name_suffix` |
| Підключитися від конкретного елемента вище за потоком (за назвою) | `upstream_name` |
| Перевизначити розширені параметри виконання для цього маршруту | `advanced_execution` |

<CodeTabs>
<CodeTab label="C++" lang="cpp">

```cpp
simaai::neat::Model::RouteOptions route;
route.include_input = true;
route.include_output = true;
route.name_suffix = "_detector";

simaai::neat::Graph model_fragment = model.graph(route);
```

</CodeTab>
<CodeTab label="Python" lang="python">

```python
route = pyneat.ModelRouteOptions()
route.include_input = True
route.include_output = True
route.name_suffix = "_detector"

model_fragment = model.graph(route)
```

</CodeTab>
</CodeTabs>

Межі маршруту — це контракт. Додавайте їх, коли потрібно, щоб фрагмент надавав публічні входи або виходи. Не додавайте їх, коли модель є лише одним етапом у більшому графі.


</CodeTab>
<CodeTab label="Python" lang="python">

```python

```

</CodeTab>
</CodeTabs>

Розширені допоміжні засоби призначені для діагностики та свідомої композиції. Не використовуйте їх у коді першого запуску.

| Допоміжна функція | Мова | Використовуйте її, коли |
| --- | --- | --- |
| `backend_fragment(stage)` | C++ і Python | Під час налагодження маршруту вам потрібно перевірити фрагмент бекенду для одного з етапів моделі. |
| `input_appsrc_options(tensor_mode)` | C++ і Python | Моделі з одним входом потрібні точні `InputOptions`, які Neat вивів для межі входу. |

| `find_config_path_by_processor(processor)` | C++ і Python | Вам потрібен файл конфігурації для процесора, наприклад, MLA, CVU або APU. |
| `infer_output_name()` | C++ і Python | Вам потрібна канонічна назва вихідного елемента етапу інференсу для діагностики. |

Якщо допоміжна функція показує назви бекенду або видобуті файли, сприймайте результат як докази, а не як потік керування застосунком. Звичайний шлях застосунку мають забезпечувати публічні API `Model`, `Graph`, `Run`, `Input` та `Output`.

## Налаштування виконання моделі лише після отримання базового результату

Більшість моделей спочатку слід запускати з налаштуваннями виконання за замовчуванням. Отримавши правильний базовий результат, використовуйте розширені поля виконання, щоб перевіряти по одній зміні. Змініть одне налаштування, виміряйте результат і залиште маршрут за замовчуванням як контрольний варіант.

`advanced_execution` є рекомендованим набором параметрів для нових документів і прикладів, оскільки кожне поле чітко визначає призначення. Поля, для яких не задано значення, не впливають на результат. Параметри на рівні маршруту мають пріоритет над параметрами на рівні моделі для цього маршруту.

| Потрібно | Поле | Примітки |
| --- | --- | --- |
| Обрати, де виконується попередня обробка, якою керує модель | `advanced_execution.preprocess_target` | Використовуйте позначення цілей, як-от `"AUTO"`, `"A65"` або `"EV74"`, лише коли перевіряєте розміщення. |
| Обрати, де виконується постобробка, якою керує модель | `advanced_execution.postprocess_target` | Використовуйте для етапів постобробки, які можуть виконуватися на кількох цілях. |
| Дозволити асинхронну попередню обробку | `advanced_execution.preprocess_async` | Виміряйте затримку та пропускну здатність до та після ввімкнення цієї функції. |
| Дозволити асинхронний інференс на MLA | `advanced_execution.inference_async` | Корисно для потокових навантажень, які тримають роботу в обробці. |
| Налаштувати буферизацію виходу інференсу | `advanced_execution.inference_output_buffers` | Збільшуйте лише тоді, коли вимірювання показують, що обмеження продуктивності пов’язане з буферизацією вихідних даних. |
| Відкласти синхронізацію кешу виходу | `advanced_execution.defer_output_cache_sync` | Розширений режим. Використовуйте лише тоді, коли ви розумієте, хто є споживачем виходу та який час життя пам’яті. |
| Налаштувати внутрішню паралельність | `advanced_execution.internal_queue_depth` | Обмежує внутрішньо додані черги й кількість слотів числового виконання Runner; не перевизначає буферизацію виходу MLA. |

Про обмежене перекриття, час життя входу та вимірювання CPU на кадр див.
[Перекриття обробки кадрів без необмеженого зростання черг](/develop-apps/development-workflow/graph#overlap-frames-without-growing-queues-indefinitely).
Збережене поле `prepared_runner` потрібне для сумісності на рівні вихідного коду, а не для
вибору бекенду виконання. Залиште значення за замовчуванням; вилучені режими спричиняють
помилку під час побудови графа.

Встановіть розширені параметри виконання в найвужчій області, яка відповідає експерименту:

<CodeTabs>
<CodeTab label="C++" lang="cpp">

```cpp
simaai::neat::Model::RouteOptions route;
route.name_suffix = "_lane0";
route.advanced_execution.inference_async = true;

auto runner = model.build(route);
```

</CodeTab>
<CodeTab label="Python" lang="python">

```python
route = pyneat.ModelRouteOptions()
route.name_suffix = "_lane0"
route.advanced_execution.inference_async = True

runner = model.build_with_route_options(route)
```

</CodeTab>
</CodeTabs>

Залиште маршрут за замовчуванням як контрольний. Змініть одне поле, виміряйте, експортуйте дані, а потім вирішіть, чи варто зберігати цю зміну в застосунку.

C++ також надає доступ до низькорівневих полів `processcvu`, `processmla`, `prepared_runner` та `async_queue_depth` у `Model::Options`, `Model::RouteOptions` та `GraphOptions`. У прикладах для клієнтів віддавайте перевагу `advanced_execution`, якщо ви не зберігаєте наявний код C++ або не налагоджуєте конкретне низькорівневе поле.

## Повторне використання runner моделі

Використовуйте `build(...)`, коли ви хочете уникнути повторного збирання маршруту для кожного вхідного значення.

<CodeTabs>
<CodeTab label="C++" lang="cpp">

```cpp
auto runner = model.build();

// Convenience path: push one input and wait for its output.
simaai::neat::TensorList result = runner.run(
    simaai::neat::TensorList{input},
    /*timeout_ms=*/2000);

// Async path: push now, pull later.
runner.push(simaai::neat::TensorList{input});
simaai::neat::Sample sample = runner.pull(/*timeout_ms=*/2000);

runner.close_input();
runner.close();
```

</CodeTab>
<CodeTab label="Python" lang="python">

```python
runner = model.build()

# Convenience path: push one input and wait for its output.
result = runner.run([tensor], timeout_ms=2000)

# Async path: push now, pull later.
runner.push([tensor])
sample = runner.pull(timeout_ms=2000)

runner.close_input()
runner.close()
```

</CodeTab>
</CodeTabs>

Використовуйте `runner.run(...)`, коли кожен виклик має надіслати один вхід і дочекатися його виходу. Використовуйте `push(...)` / `pull(...)`, коли застосунку потрібно тримати кілька завдань в обробці одночасно. Використовуйте `close_input()`, коли входів більше не буде і ви хочете дочекатися спорожнення решти роботи. Використовуйте `close()`, коли runner більше не потрібен.

`push` очікує на вільне місце у вхідній черзі. Щоб надіслати дані без очікування, використовуйте `runner.try_push` із `Sample` або `TensorList` у C++, чи `runner.try_push_samples` / `runner.try_push_tensors` у Python. Встановіть `RunOptions.queue_depth` і `overflow_policy` перш ніж збирати runner. Коли обмежена черга заповнена, `KeepLatest` замінює найстаріший відкладений зразок і повертає `true`; `Block` і `DropIncoming` повертають `false`. Закритий вхід також повертає `false`. Тримайте парні тензори одного кадру разом в одному зразку TensorSet. Заміна не скасовує активний інференс, а ці методи передавання не додають копіювання корисних даних.

Використовуйте runner для конкретного маршруту, коли повторно використовуваний runner має застосовувати налаштування виконання на рівні маршруту або іменування маршруту, які відрізняються від маршруту за замовчуванням. `Model::build(...)` автоматично додає межі входу й виходу для runner.

Передайте у збірку початковий зразок (seed), коли фактичний вхід має підтвердити сумісність форми, формату або корисних даних ще до першого робочого push:

<CodeTabs>

```cpp

```

</CodeTab>

```python

```

Використовуйте збірку з початковим зразком, щоб отримати докази та раннє виявлення помилок, а не за звичкою. Якщо збірка за замовчуванням вже підтверджує контракт, залиште приклад меншим.

Для вхідного зображення початковий зразок задає поточну форму та формат пікселів; він не замінює `preprocess.input_max_width`, `input_max_height` або `input_max_depth`. Наприклад, зразок 640×640 із заданим максимальним розміром 1920×1920 дозволяє приймати наступні кадри 800×800 і 1920×1080 на тому самому runner. Кадри, що перевищують максимальний розмір, відхиляються. Якщо межі не задано, зберігається той самий визначений максимальний розмір, що й під час збірки без початкового зразка.

</CodeTab>
</CodeTabs>

Для маршруту BoxDecode опишіть геометрію вихідного зображення для синтетичного входу, щоб бенчмарк міг перерахувати виявлення з координат моделі назад:

<CodeTabs>
<CodeTab label="C++" lang="cpp">

```cpp
simaai::neat::BenchmarkOptions options;
options.num_samples = 100;
options.original_width = 1920;
options.original_height = 1080;
options.resize_mode = simaai::neat::ResizeMode::Letterbox;

simaai::neat::BenchmarkReport report = model.benchmark(options);
```

</CodeTab>
<CodeTab label="Python" lang="python">

```python
options = pyneat.BenchmarkOptions()
options.num_samples = 100
options.original_width = 1920
options.original_height = 1080
options.resize_mode = pyneat.ResizeMode.Letterbox

report = model.benchmark(options)
```

</CodeTab>
</CodeTabs>

Встановіть `original_width` і `original_height` разом. Бенчмарк все ще генерує синтетичний тензор, що має форму моделі; ці поля містять вихідну геометрію та трансформацію зміни розміру, необхідні для метаданих BoxDecode. Якщо їх не вказати, бенчмарк визначає геометрію на основі попередньої обробки та контракту вхідних даних моделі. Ці значення для кожного запуску мають пріоритет над застарілими підказками щодо геометрії BoxDecode в `ModelOptions`. Наявні виклики `benchmark(num_samples)` зберігають ту саму поведінку.

Щоб також виміряти час кожного шару або етапу MLA, встановіть `include_mla_layer_stats` або `include_mla_stage_stats`. Щоб зберегти результати, `report.save(path)` записує звіт у форматі YAML, а для шляху з `.json` — у форматі JSON. Обидва варіанти показано в [Бенчмарк моделі](/tutorials/benchmark-your-model).

### Вимірювання з власними вхідними даними {#measure-with-your-own-inputs}

Синтетичні вхідні дані можуть спотворювати результати для моделі, вартість якої залежить від даних, наприклад для декодера виявлення або сегментації. Щоб виміряти на реальних даних, задайте в `inputs` тензори, які ви передали б у `run()`, по одному на кожен вхід моделі. Бенчмарк використовує їх і для вимірювання затримки, і для вимірювання пропускної здатності.

<CodeTabs>
<CodeTab label="C++" lang="cpp">

```cpp
cv::Mat image;
cv::cvtColor(cv::imread("bus.jpg"), image, cv::COLOR_BGR2RGB);  // the format input_specs() reports

simaai::neat::BenchmarkOptions options;
options.inputs = simaai::neat::TensorList{
    simaai::neat::Tensor::from_cv_mat(image, simaai::neat::ImageSpec::PixelFormat::RGB,
                                      simaai::neat::TensorMemory::EV74)};

simaai::neat::BenchmarkReport report = model.benchmark(options);
std::cout << "input=" << report.input << " fps=" << report.fps << "\n";  // input=provided
```

</CodeTab>
<CodeTab label="Python" lang="python">

```python
image = cv2.cvtColor(cv2.imread("bus.jpg"), cv2.COLOR_BGR2RGB)  # the format input_specs() reports

options = pyneat.BenchmarkOptions()
options.inputs = [pyneat.Tensor.from_numpy(image, copy=True, image_format=pyneat.PixelFormat.RGB)]

report = model.benchmark(options)
print("input=", report.input, "fps=", report.fps)  # input= provided
```

</CodeTab>
</CodeTabs>

Якщо кількість, форма або тип вхідних даних не відповідають моделі, `benchmark()` ще до початку викидає `NeatError` з кодом помилки `misconfig.input_shape`. Колірний формат, який маршрут не може перетворити, спричиняє помилку під час збірки конвеєра, як і в `run()`. На маршруті з попередньою обробкою зображень зображення може мати будь-який розмір. Передавайте його в колірному форматі, який повідомляє `input_specs()`.

### Тривалість запуску

Бенчмарк вимірює затримку, подаючи вхідні дані по одному (single-flight), а потім виконує окремий прохід для вимірювання пропускної здатності. Кожен прохід триває, доки не виміряє щонайменше `num_samples` вхідних даних і не мине `min_duration_ms` (за замовчуванням 10 с), тож обидва проходи зупиняються за одним правилом, а показники потужності й температури проходу пропускної здатності охоплюють кілька зразків телеметрії, а не короткий сплеск. `latency_ms` — це середня затримка проходу вимірювання затримки, а `latency_p50_ms`, `latency_p95_ms` і `latency_p99_ms` — її процентилі. `throughput_samples` і `throughput_duration_ms` показують, що саме виміряв прохід пропускної здатності. Для швидкої перевірки встановіть `min_duration_ms` на 0, щоб кожен прохід зупинявся після `num_samples` вхідних даних:

<CodeTabs>
<CodeTab label="C++" lang="cpp">

```cpp
simaai::neat::BenchmarkOptions options;
options.min_duration_ms = 0;
simaai::neat::BenchmarkReport report = model.benchmark(options);
```

</CodeTab>
<CodeTab label="Python" lang="python">

```python
options = pyneat.BenchmarkOptions()
options.min_duration_ms = 0
report = model.benchmark(options)
```

</CodeTab>
</CodeTabs>

### Потужність і телеметрія плати {#power-and-board-telemetry}

Дані про потужність і телеметрію плати надходять від [Sentinel](/tools/sentinel/) —
демона телеметрії DevKit, який інсталятор Neat налаштовує на платі. Бенчмарк записує
їх за допомогою [`TelemetryMonitor`](#record-board-telemetry) під час проходу
вимірювання пропускної здатності. Він вибирає зразки після початку та до
завершення вимірювання, коли завершено всі потрібні виходи. Підготовка,
приєднання робочого потоку монітора й останнє читання Sentinel не подовжують
вимірюване навантаження. Недопустимі часові позначки зразків або виявлені
розриви годинника роблять телеметрію бенчмарку недоступною замість вибору
стороннього часового вікна. `report.telemetry` підсумовує ці дані:

| Поле | Значення |
| --- | --- |
| `avg_power_watts`, `peak_power_watts` | Оцінна середня й найвища потужність SoM під час проходу вимірювання пропускної здатності. |
| `energy_joules` | Енергія для обробки `num_samples` вхідних даних: середня потужність, помножена на час, який за виміряної пропускної здатності потрібен для обробки `num_samples` вхідних даних. Довший прохід її не збільшує. |
| `telemetry.power_mla_watts`, `telemetry.power_rails_watts` | Потужність шини живлення MLA та всіх шин живлення, про які повідомляє плата. Плати без шини MLA повідомляють її з `samples == 0`. |
| `telemetry.die_temperatures_c`, `telemetry.die_temperature_max_c` | Датчики температури кристала в зонах MLA, APU, CVU і TOP, а також найгарячіший із них у кожному зразку. |
| `telemetry.board_temperatures_c` | Датчики на верхньому й нижньому боці SoM. |
| `telemetry.cpu_usage_pct` | Завантаження CPU. Кожен зразок усереднює попередній інтервал, тож `maximum` відповідає найбільш завантаженому інтервалу. |
| `telemetry.cpu_cores_usage_pct` | Завантаження кожного ядра CPU в порядку номерів ядер CPU. Одне завантажене ядро CPU видно тут, навіть коли `cpu_usage_pct`, середнє за всіма ядрами CPU, залишається низьким. |
| `telemetry.mla_memory_mib` | Пам’ять, яку утримує MLA, у MiB: буфери з пулу пам’яті MLA, а також спільні буфери, які використовує лише MLA. Модель виділяє її під час завантаження, тож якщо нічого іншого не запущено, це пам’ять MLA моделі. |
| `telemetry.ev74_memory_mib` | Пам’ять, яку утримує EV74, у MiB, наприклад вхідні кадри, які EV74 попередньо обробляє для MLA. Спільний буфер, який використовують і EV74, і MLA, рахується тут, а не в `mla_memory_mib`, тож разом ці два значення дають пам’ять прискорювачів моделі. Кадри, створені відеодекодером або ISP камери, не входять у жодне з них. |
| `telemetry.linux_memory_used_mib` | Пам’ять, яку використовує вся плата (Linux `MemTotal - MemAvailable`), у MiB. Вона містить усі процеси та буфери EV74, тому не додавайте її до двох значень вище. |

Кожна метрика повідомляє `samples`, `mean`, `minimum`, `maximum` і `last`; `samples == 0` означає, що плата не повідомила цю метрику. Повідомлений нуль теж рахується як зразок: коли модель не завантажено, `mla_memory_mib` і `ev74_memory_mib` показують 0 MiB при `samples > 0`. Sentinel збирає зразки кожні 2 с, тож 10-секундний прохід дає близько 5 зразків. Кожне значення охоплює всю плату, зокрема інші запущені процеси.

Якщо Sentinel не запущено або прохід закороткий, щоб зібрати хоча б один зразок, бенчмарк усе одно повертає затримку та FPS. Поля потужності залишаються нульовими, `telemetry.status` містить причину (інакше він дорівнює `"ok"`), а у виведеному зведенні відображається `Power: unavailable (<reason>)`.

### Вимірювання власного циклу

Використовуйте вимірювання runner, коли ви контролюєте цикл вхідних даних і хочете виміряти цей цикл:

<CodeTab label="C++" lang="cpp">

```cpp
auto runner = model.build();
auto scope = runner.start_measurement();

for (const auto& input : inputs) {
  (void)runner.run(simaai::neat::TensorList{input}, /*timeout_ms=*/2000);
}

simaai::neat::MeasureReport report = scope.stop();
runner.close();
```

</CodeTab>
<CodeTab label="Python" lang="python">

```python
runner = model.build()
scope = runner.start_measurement()

for tensor in tensors:
    runner.run([tensor], timeout_ms=2000)

report = scope.stop()
runner.close()
```

</CodeTab>
</CodeTabs>

Не порівнюйте одноразовий smoke-тест і прогрітий runner для повторного використання. Вони відповідають на різні запитання.

### Запис телеметрії плати {#record-board-telemetry}

Використовуйте `TelemetryMonitor`, щоб записувати потужність, температури, завантаження CPU та пам’ять за будь-яке вибране вами вікно, наприклад за ваш власний цикл інференсу. Він читає ці дані із [Sentinel](/tools/sentinel/) і повертає таке саме зведення `Telemetry`, як `report.telemetry`:

<CodeTabs>
<CodeTab label="C++" lang="cpp">

```cpp
simaai::neat::TelemetryMonitor monitor;
monitor.start();

for (const auto& input : inputs) {
  (void)runner.run(simaai::neat::TensorList{input}, /*timeout_ms=*/2000);
}

simaai::neat::Telemetry telemetry = monitor.stop();
std::cout << telemetry;            // YAML
telemetry.save("telemetry.json");  // .json writes JSON; other names write YAML
```

</CodeTab>
<CodeTab label="Python" lang="python">

```python
monitor = pyneat.TelemetryMonitor()
monitor.start()

for tensor in tensors:
    runner.run([tensor], timeout_ms=2000)

telemetry = monitor.stop()
print(telemetry)                 # YAML
print(telemetry.power_som_watts.mean)
telemetry.save("telemetry.json") # .json writes JSON; other names write YAML
```

</CodeTab>
</CodeTabs>

За замовчуванням монітор читає `/run/simaai-sentinel/api.sock`. Щоб використовувати Unix-сокет Sentinel, змонтований за іншим шляхом, передайте цей шлях у `TelemetryMonitor(socket_path)` у C++ або `pyneat.TelemetryMonitor(socket_path="...")` у Python. Це вибирає кінцеву точку лише для цього монітора; не змінює `Model::benchmark()` і не запускає Sentinel. Під час створення монітор не звертається до сокета.

- `start()` починає нове вікно. Враховуються лише зразки, які Sentinel робить після цього виклику, а Sentinel збирає зразки кожні 2 с, тож коротше вікно може не мати жодного зразка; тоді про це повідомляє `status`.
- `read()` повертає зведення на поточний момент, не зупиняючи монітор. `last` кожного вимірювання — його найновіше значення, а `mean`, `minimum` і `maximum` охоплюють вікно до цього моменту.
- `stop()` повертає остаточне зведення. Повторний виклик повертає той самий результат.
- Зведення зберігає один запис на кожне вимірювання, тож використання пам’яті не змінюється, хоч би як довго тривало вікно.
- Кілька моніторів, в одному процесі чи в кількох, можуть працювати одночасно один з одним і з `Model::benchmark()`.
- Кожне значення охоплює всю плату, зокрема Sentinel, монітор та інші процеси. Кожне значення потужності отримується з одного зчитування тривалістю 250 мс на зразок, тож короткі сплески між зчитуваннями не відображаються.
- Якщо Sentinel не запущено, монітор виводить одне попередження, `status` пояснює, як установити або запустити Sentinel, а монітор починає враховувати зразки, щойно Sentinel відповість. Через проблеми із Sentinel монітор ніколи не генерує винятків.
- У Python `start()`, `read()` і `stop()` звільняють GIL на час очікування.

## Декодування виходу

Почніть зі специфікацій виходів. Декодуйте лише тоді, коли контракт виходу моделі вказує, що корисні дані мають формат виявлення, пози або сегментації.

| Контракт виходу | Використовуйте |
| --- | --- |
| Необроблений тензор | Використовуйте отриманий тензор безпосередньо або конвертуйте його за допомогою `to_numpy(...)` / `to_torch(...)` у Python. |

| Упаковані рамки як типізовані записи | C++ `simaai::neat::decode_bbox_tensor(...)` / Python `pyneat.detections.decode_bbox_tensor(...)` |
| Упакована поза | C++ `simaai::neat::decode_pose(...)` / Python `pyneat.decode_pose(...)` |
| Упакована сегментація | C++ `simaai::neat::decode_segmentation(...)` / Python `pyneat.decode_segmentation(...)` |

Використовуйте декодування тензорів, коли наступний етап потребує тензорів. Використовуйте типізоване декодування, коли коду застосунку потрібні записи з `x1`, `y1`, `x2`, `y2`, `score` та `class_id`.

```cpp
const auto decoded = simaai::neat::decode_bbox_tensor(
```

```python
decoded = pyneat.detections.decode_bbox_tensor(

    strict=True,
```

## Обробка помилок

Графи, що керуються моделлю, використовують той самий діагностичний контракт, що й звичайний `Graph`:

- `NeatError.report().error_code` для остаточних (фатальних) збоїв.
- `NeatError.report().repro_note` для надання практичної інформації та підказок.
- `NeatError.report().bus` для отримання детальної інформації про плагін або середовище виконання.

<CodeTabs>
<CodeTab label="C++" lang="cpp">

```cpp
try {
  auto result = model.run(simaai::neat::TensorList{input}, /*timeout_ms=*/2000);
} catch (const simaai::neat::NeatError& error) {
  const auto& report = error.report();
  std::cerr << report.error_code << "\n";
  std::cerr << report.repro_note << "\n";
}
```

</CodeTab>
<CodeTab label="Python" lang="python">

```python
try:
    result = model.run([tensor], timeout_ms=2000)
except pyneat.NeatError as error:
    print(error.error_code)
    print(error.repro_note)
    print(error.report_json)
```

</CodeTab>
</CodeTabs>

Почніть зі значень `error_code`, як-от `misconfig.*`, `build.*`, `runtime.*` або `io.*`. Переглядайте журнали шини лише тоді, коли на них вкаже структурована помилка.
