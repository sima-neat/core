# Запуск графа

`Graph` — це план. [`Run`](/reference/{lsa}/classes/simaai-neat-run) — це дескриптор активного виконання.

Використовуйте цю сторінку після створення графа. Якщо вам все ще потрібно визначити, які вузли або фрагменти мають бути в графі, почніть з [Граф](/develop-apps/development-workflow/graph). Якщо граф вже виглядає правильно, на цій сторінці ви можете запустити його, спорожнити (drain), виміряти та підготувати до роботи з реальними вхідними даними.

## Вибір одноразового або багаторазового виконання

Використовуйте найкоротший можливий шлях у середовищі виконання, який відповідає вимогам завдання:

| Потрібно | Використовуйте | Чому |
| --- | --- | --- |
| Введіть один набір даних і отримайте один результат | `Graph.run(...)` | Найкоротший шлях для одноразового виконання. |
| Послідовно надсилайте багато вхідних даних протягом певного часу | `Graph.build(...)` та `Run` | Повторно використовує середовище виконання та надає можливість керування за допомогою механізмів «push» і «pull». |
| Використовуйте іменовані входи або виходи | `Graph.build(...)` та іменовані `run.push(...)` / `run.pull(...)` | Забезпечує чітке визначення застосунків із кількома входами та кількома виходами. |
| Дозвольте вузлам-джерелам керувати графом | `Graph.build()` або `Graph.run()` без вхідних даних від застосунку | Використовуйте, коли граф містить камеру, файл, джерело RTSP або інший вузол-джерело. |
| Вимірюйте, експортуйте, спорожнюйте або зупиняйте свідомо | `Run` | Надає можливість контролювати життєвий цикл і проводити діагностику. |

Без жодних чарів. Зберіть граф, запустіть його, перевірте результат.

## Вибір способу надходження даних у граф

Перш ніж налаштовувати черги, визначте, кому належать вхідні дані.

| Стиль графа | Як надходять дані | Як запускати |
| --- | --- | --- |
| Граф, у який дані надсилає застосунок | Ваш застосунок викликає `Graph.run(input, ...)`, `run.run(input, ...)`, `run.push(...)` або `run.try_push(...)` | Зберіть або запустіть граф із вхідними даними. Перш ніж надсилати дані в граф із кількома входами, перевірте назви кінцевих точок. |
| Граф із власним джерелом | Граф містить вузол-джерело або фрагмент-джерело, наприклад файл, камеру, RTSP чи потоковий вхід | Зберіть або запустіть без вхідних даних від застосунку: `graph.build()` або `graph.run()`. Залежно від графа отримуйте виходи через pull, використовуйте вузли виходу або зворотні виклики. |

Якщо граф має власне джерело, не надсилайте в нього дані. Натомість перевірте, що він видає.


## Запуск графа з власним джерелом

Якщо граф містить власний вузол-джерело, зберіть або запустіть його без вхідних даних від застосунку. Не надсилайте дані в граф, який уже має власне джерело. Отримуйте іменовані виходи, коли граф їх надає; якщо граф закінчується вузлом-приймачем (sink), дозвольте приймачам обробляти вихід.

Використовуйте `graph.run()` для завдання «від джерела до приймача», коли граф сам володіє і входом, і виходом. Використовуйте `graph.build()`, коли вашому застосунку потрібно отримувати результати, вимірювати запуск або свідомо його зупиняти.

<CodeTabs>
<CodeTab label="C++" lang="cpp">

```cpp
auto run = graph.build();

while (running && run.can_pull()) {
  auto sample = run.pull("detections", /*timeout_ms=*/1000);
  if (!sample) {
    continue;
  }
  handle(*sample);
}

run.close();
```

</CodeTab>
<CodeTab label="Python" lang="python">

```python
run = graph.build()

try:
    while running and run.can_pull():
        sample = run.pull("detections", timeout_ms=1000)
        if sample is None:
            continue
        handle(sample)
finally:
    run.close()
```

</CodeTab>
</CodeTabs>

Для джерел, які працюють тривалий час, налаштуйте свій застосунок таким чином, щоб він визначав, коли потрібно вийти з циклу, і викликав `close()`. Тайм-аут означає, що протягом цього проміжку часу не було отримано жодних даних; це не завжди означає, що джерело завершило роботу.

## Одноразовий запуск

Використовуйте `Graph.run(...)`, коли вам потрібна одна синхронна операція надсилання/отримання даних у графі.

<CodeTabs>
<CodeTab label="C++" lang="cpp">

```cpp
simaai::neat::Graph graph("classifier");
graph.add(simaai::neat::nodes::Input("image"));
graph.add(model);
graph.add(simaai::neat::nodes::Output("classes"));

simaai::neat::TensorList outputs = graph.run(std::vector<cv::Mat>{frame});
```

</CodeTab>
<CodeTab label="Python" lang="python">

```python
graph = pyneat.Graph("classifier")
graph.add(pyneat.nodes.input("image"))
graph.add(model)
graph.add(pyneat.nodes.output("classes"))

outputs = graph.run([tensor])
```

</CodeTab>
</CodeTabs>

У Python передавайте список або кортеж. `graph.run([tensor])` означає «один вхід графа», а не «додати вимір пакета (batch)».

## Збірка багаторазового Run

Використовуйте `Graph.build(...)`, коли ваш застосунок керує циклом.

<CodeTabs>
<CodeTab label="C++" lang="cpp">

```cpp
auto run = graph.build();

run.push("image", std::vector<cv::Mat>{frame});
simaai::neat::TensorList outputs = run.pull_tensors("classes", /*timeout_ms=*/2000);

run.close_input();
while (auto sample = run.pull(/*timeout_ms=*/100)) {
  // Drain remaining output after end-of-input.
}
run.close();
```

</CodeTab>
<CodeTab label="Python" lang="python">

```python
run = graph.build()

run.push("image", [tensor])
outputs = run.pull_tensors("classes", timeout_ms=2000)

run.close_input()
while True:
    sample = run.pull(timeout_ms=100)
    if sample is None:
        break
run.close()
```

</CodeTab>
</CodeTabs>

Використовуйте `close_input()`, коли завершите надсилання даних і захочете, щоб поточна робота завершилася. Використовуйте `close()`, коли захочете зупинити виконання; у C++ також передбачено `stop()` як команду для негайної зупинки.

## Використання багаторазового Run для схеми «запит — відповідь»

`Graph.run(...)` — це найкоротший одноразовий шлях. Якщо вам потрібна та сама схема «запит — відповідь», але без повторної збірки графа щоразу, один раз зберіть багаторазовий `Run` і викликайте `run.run(...)`.

Використовуйте це, коли:

- граф залишається активним протягом багатьох запитів;
- кожний запит все одно має чекати на отримання власного результату;
- наразі вам не потрібні окремі потоки для виробника та споживача.

<CodeTabs>
<CodeTab label="C++" lang="cpp">

```cpp
auto run = graph.build();

for (const auto& frame : frames) {
  simaai::neat::TensorList outputs = run.run(
      std::vector<cv::Mat>{frame},
      /*timeout_ms=*/2000);
  handle(outputs);
}

run.close();
```

</CodeTab>
<CodeTab label="Python" lang="python">

```python
run = graph.build()

for tensor in tensors:
    outputs = run.run([tensor], timeout_ms=2000)
    handle(outputs)

run.close()
```

</CodeTab>
</CodeTabs>

Перейдіть від `run.run(...)` до явного використання `push(...)` / `pull(...)`, коли вам потрібно тримати в обробці кілька запитів одночасно, мати потоки виробника й споживача, неблокувальне надсилання, опитування іменованих виходів або керування спорожненням (drain).

## Перевірка кінцевих точок середовища виконання

Перш ніж надсилати дані в багатовхідний граф, запитайте у `Run`, які імена він приймає.

<CodeTabs>
<CodeTab label="C++" lang="cpp">

```cpp
auto run = graph.build();

for (const auto& name : run.input_names()) {
  std::cout << "input: " << name << "\n";
}
for (const auto& name : run.output_names()) {
  std::cout << "output: " << name << "\n";
}
```

</CodeTab>
<CodeTab label="Python" lang="python">

```python
run = graph.build()

print("inputs:", run.input_names())
print("outputs:", run.output_names())
```

</CodeTab>
</CodeTabs>

Якщо в графі є більше одного публічного входу або виходу, використовуйте іменовані `push(...)` та `pull(...)`. Не потрібно, щоб Neat намагався вгадати, який саме провід ви мали на увазі.

## Запуск графів із кількома входами та кількома виходами

Для графів із кількома входами надсилайте дані в одну іменовану кінцеву точку за раз або надсилайте неіменований список лише тоді, коли в графі є один чітко визначений вхідний маршрут.

<CodeTabs>
<CodeTab label="C++" lang="cpp">

```cpp
run.push("left", simaai::neat::TensorList{left_tensor});
run.push("right", simaai::neat::TensorList{right_tensor});

auto boxes = run.pull_tensors("detections", /*timeout_ms=*/2000);
auto preview = run.pull("preview", /*timeout_ms=*/2000);
```

</CodeTab>
<CodeTab label="Python" lang="python">

```python
run.push("left", [left_tensor])
run.push("right", [right_tensor])

boxes = run.pull_tensors("detections", timeout_ms=2000)
preview = run.pull("preview", timeout_ms=2000)
```

</CodeTab>
</CodeTabs>

Під час об’єднання потоків зберігайте відповідний ключ, який очікує граф. Для `CombinePolicy::ByFrame` потрібен `frame_id`; для `CombinePolicy::ByPts` потрібен `pts_ns`. Відсутність ключа має призводити до чіткої помилки. Безшумне об’єднання — це спосіб, за допомогою якого помилки перетворюються на проблеми архітектури.

## Вибір параметрів запуску

[`RunOptions`](/reference/{lsa}/structs/simaai-neat-runoptions) визначає поведінку під час виконання. Почніть із параметрів за замовчуванням. Змінюйте параметри, коли джерело, час життя виходів або цільова пропускна здатність вимагають іншої політики.

| Обсяг роботи | Почніть з | Чому |
| --- | --- | --- |
| Перша робоча версія застосунку | `RunOptions` за замовчуванням | Перевірте правильність налаштувань перед їх оптимізацією. |
| Відео з камери в реальному часі або вхід RTSP | `RunPreset::Realtime`; `OutputOptions::Latest()`, де важлива актуальність результатів | Свіжі кадри важливіші за повну історію. Якщо ви не перевизначите політику, пресет Realtime використовує переповнення за принципом «останній кадр». Наявні значення черг GStreamer за замовчуванням та явно задані обмеження лише за кількістю буферів зберігаються. Щоб обмежити медіачас, задайте `max-size-time` черги в наносекундах у `backend_fragment()` власного вузла. |
| Обробка файлів або пакетна обробка | `RunPreset::Reliable`; `OutputOptions::EveryFrame(...)` | Зберігає кожен вхід і робить зворотний тиск (backpressure) видимим. Якщо ви не перевизначите політику, пресет Reliable при переповненні блокує надсилання. |
| Звичайне обслуговування застосунку | `RunPreset::Balanced` | Це хороші налаштування за замовчуванням, коли граф працює належним чином. |
| Нестабільному джерелу потрібен буфер обмеженого розміру | `queue_depth` | Збільшуйте лише до необхідного рівня, щоб компенсувати коливання. Глибока черга може приховати застарілі кадри й відкласти прояв зворотного тиску. |
| Застосунок зберігає виходи після отримання (pull) | `OutputMemory::Owned` | Забезпечує незалежність часу життя виходів від буферів середовища виконання. |
| Застосунок використовує виходи без транспортного копіювання | `OutputMemory::Auto` | Зберігає стандартні виходи DMA-BUF у синхронних і асинхронних запусках; для іншого сховища діє політика пресета/режиму. |
| Час очікування за замовчуванням має бути чітко визначений | `input_timeout_ms` | Обмежує очікування для `Graph::run()` у вхідному режимі та підтримуваної попередньої перевірки збирання з початковим зразком. `Run::run()`, `Model::run()` і `pull()` використовують тайм-аут окремого виклику (`-1`: без обмеження). |
| Збірка з початковим зразком має рано виявляти помилки першого зразка | `startup_preflight = true` | Робить перевірку під час збирання з початковим зразком чесною. Вимикайте лише тоді, коли помилки першого зразка можуть проявитися пізніше через `pull(...)` або `last_error()`. |
| Час життя буфера джерела короткий | `advanced.copy_input = true` | Захищає вхідні дані в пам’яті, які можуть бути втрачені після виконання операції `push(...)`. |
| Необхідно встановити обмеження для вхідних даних | `advanced.max_input_bytes` | Відхиляє занадто великі вхідні дані, перш ніж вони будуть оброблені графом. |
| Вимірювання відкинутих вхідних даних | `inputs_dropped`, `on_input_drop` | Лічильник фіксує зразки, відкинуті за політикою переповнення. Зворотний виклик повідомляє про кадри, відкинуті під час зміни формату вхідних даних. |
| Потрібні дані на момент збірки | `run_export` | Записує знімок запуску, коли Run зібрано. |

### Утримання та звільнення виходів DMA-BUF

Апаратне декодування записує дані безпосередньо в пул DMA-BUF. Шлях файлового входу за замовчуванням зберігає це сховище: він не додає прихований `videoconvert` і не запитує SystemMemory. Споживачі на пристроях імпортують виділену пам’ять, а `Tensor::map(MapMode::Read)` відображає її для читання застосунком без копіювання пікселів. Попередня обробка може створити інше сховище результату; це обчислення, а не транспортне копіювання.

За `OutputMemory::Auto` або `ZeroCopy` утримувані виходи DMA-BUF зберігають позичені буфери пулу. `Mapping` зберігає позику навіть після звільнення Tensor. Завершивши читання, звільніть обидва об’єкти, щоб виробник міг повторно використовувати буфери. Навантаження на чергу не перемикає виходи DMA-BUF на копії й не перетворює `Block` на відкидання непомітно; явно задані політики останнього кадру/відкидання діють і надалі.

Використовуйте `OutputMemory::Owned`, коли застосунок зберігає виходи на CPU.
Кожне отримання копіює вибрані виходи в незалежну системну пам’ять, тому
утримуваний вихід не тримає ні позики пулу виробника, ні пам’яті пристрою (CMA).
Упаковані тензорні виходи спільно використовують скопійований носій; їхні
зміщення, кроки з доповненням і числові метадані зберігаються. І утримувані, і
незалежні виходи використовують `StorageKind::GstSample`; цей тип сховища
визначає носій, а не політику володіння. `Sample::owned` позначає незалежний
вихід. Помилка виділення повідомляється як помилка отримання. Щоб передати вихід
до окремого графа з вхідним етапом EV74, спершу викличте `tensor.cvu()`: метод
повертає тензори, які вже перебувають у пам’яті EV74, без змін, а решту копіює
до пам’яті EV74. `ZeroCopy` зберігає сховище виробника і не гарантує доступність для EV74.

`Tensor::cpu()` копіює тензор пристрою в пам’ять хоста, а тензор, який уже
перебуває в пам’яті хоста, як-от вихід `Owned`, повертає без копіювання. Для
незалежної копії використовуйте `clone()`. Явне програмне перетворення та `advanced.copy_input` залишаються межами
копіювання. `SIMA_OUTPUT_MEMORY_DEFAULT=owned` свідомо вибирає власний
вихід (owned) для `Auto`; це не перевизначає явно заданий вибір для окремого запуску.

<CodeTabs>
<CodeTab label="C++" lang="cpp">

```cpp
simaai::neat::RunOptions options;
options.preset = simaai::neat::RunPreset::Realtime;
options.on_input_drop = [](const simaai::neat::InputDropInfo& drop) {
  std::cerr << "dropped input from stream " << drop.stream_id
            << ": " << drop.reason << "\n";
};

auto run = graph.build(options);
```

</CodeTab>
<CodeTab label="Python" lang="python">

```python
options = pyneat.RunOptions()
options.preset = pyneat.RunPreset.Realtime

def on_drop(drop: pyneat.InputDropInfo) -> None:
    print(f"dropped input from stream {drop.stream_id}: {drop.reason}")


options.on_input_drop = on_drop

run = graph.build(options)
```

</CodeTab>
</CodeTabs>

Не потрібно регулювати кожну ручку лише тому, що вона є. Найшвидший спосіб заблукати — це налаштовувати параметри до того, як ви визначите базові значення.

### Рекомендації щодо налаштування параметрів середовища виконання

Скопіюйте структуру цих рецептів, а не числові значення. Розміри черги та обмеження вихідних даних залежать від моделі, швидкості джерела та того, як швидко ваш застосунок отримує результати.

#### Вихід у реальному часі з низькою затримкою

Використовуйте це, коли наступний кадр важливіший, ніж повна історія кадрів. Встановіть політику вихідної черги під час додавання вихідного вузла; встановіть політику обробки вхідних даних/відкидання під час збирання `Run`.

<CodeTabs>

## Обробка зворотного тиску

Зворотний тиск означає, що граф не може приймати або передавати дані так швидко, як цього потребує застосунок.

- `queue_depth` задає кількість слотів кожної черги середовища виконання, яка використовує це значення за замовчуванням. Кадри можуть одночасно перебувати в кількох чергах і на різних етапах обробки.
- `push()` чекає на вільне місце. `try_push()` застосовує `overflow_policy`, коли вхідна черга заповнена.
- `inputs_enqueued` рахує прийняті зразки. `inputs_dropped` рахує зразки, відкинуті згідно з політикою. Відмова за політики `Block` дає змогу повторити спробу й не збільшує жодного з цих лічильників.

Для організації багатопоточності використовуйте один потік для надсилання даних і один потік для отримання даних для `Run`. Не надсилайте дані до одного й того ж `Run` одночасно з кількох потоків, якщо ваш застосунок не забезпечує послідовне виконання цих операцій.

## Проста схема організації потоків

Для графів реального часу або графів із високою пропускною здатністю, у які дані надсилає застосунок, почніть із двох потоків застосунку:

1. Потік-виробник проставляє метадані й викликає `push(...)` або `try_push(...)`.
2. Потік-споживач безперервно отримує виходи й швидко звільняє або копіює їх.

Додайте більше потоків навколо власних черг, а не навколо того самого `Run`. Гарячий цикл має бути нудним. Нудне — швидке.

<CodeTabs>
<CodeTab label="C++" lang="cpp">

```cpp
auto run = graph.build(options);

std::thread producer([&] {
  while (auto sample = next_sample()) {
    sample->stream_id = current_stream_id();
    sample->frame_id = next_frame_id();

    if (!run.try_push("image", *sample)) {
      count_local_drop(sample->stream_id);
    }
  }

  run.close_input();
});

std::thread consumer([&] {
  simaai::neat::Sample output;
  simaai::neat::PullError error;

  while (true) {
    switch (run.pull("detections", /*timeout_ms=*/100, output, &error)) {
    case simaai::neat::PullStatus::Ok:
      handle_output(output);
      break;
    case simaai::neat::PullStatus::Timeout:
      continue;
    case simaai::neat::PullStatus::Closed:
      return;
    case simaai::neat::PullStatus::Error:
      record_runtime_error(error);
      return;
    }
  }
});

producer.join();
consumer.join();
run.close();
```

</CodeTab>
<CodeTab label="Python" lang="python">

```python
import threading

run = graph.build(options)
producer_done = threading.Event()

def producer() -> None:
    try:
        for sample in sample_stream():
            sample.stream_id = current_stream_id()
            sample.frame_id = next_frame_id()

            if not run.try_push("image", [sample]):
                count_local_drop(sample.stream_id)
    finally:
        producer_done.set()
        run.close_input()

def consumer() -> None:
    while True:
        timeout_ms = -1 if producer_done.is_set() else 100
        output = run.pull("detections", timeout_ms=timeout_ms)
        if output is None:
            if producer_done.is_set():
                break
            continue
        handle_output(output)

producer_thread = threading.Thread(target=producer)
consumer_thread = threading.Thread(target=consumer)
producer_thread.start()
consumer_thread.start()
producer_thread.join()
consumer_thread.join()
run.close()
```

</CodeTab>
</CodeTabs>

У C++ використовуйте перевантажену версію `pull(...)`, яка враховує стан, коли час очікування, кінець потоку та помилки мають оброблятися по-різному. У Python функція `pull(...)` повертає `None`, якщо під час виклику не повертається жоден зразок, тому поєднуйте її зі своїм власним станом виробника/завершення.

## Свідоме закриття, спорожнення або зупинка

Оберіть спосіб завершення роботи, який відповідає вашим намірам. Не надсилайте далі дані в Run, який закривається.

| Намір | Використовуйте | Що робити далі |
| --- | --- | --- |
| Завершіть обробку завдань зі списку очікування після отримання останнього входу | `close_input()` | Продовжуйте отримувати дані, поки вихід не буде спорожнено. У C++ функція отримання, яка враховує стан, повертає значення `PullStatus::Closed` наприкінці потоку (end-of-stream). |
| Скасувати зараз | `stop()` | Зупиніть виробників і дайте викликам pull, що очікують, розблокуватися. Використовуйте це для завершення роботи або обробки збоїв, а не для звичайного спорожнення під час пакетної обробки. |
| Звільніть ресурси середовища виконання | `close()` | Викличте після спорожнення або скасування, або дайте об’єкту `Run` вийти з області видимості. |

Для пакетної обробки закрийте вхід, спорожніть вихід, а потім закрийте Run. Для обробки в реальному часі спочатку зупиніть виробників, а потім зупиніть або закрийте Run. Жодних виробників-зомбі, жодних черг-привидів.

## Вибір моделі володіння виходами

`OutputMemory` визначає, як отримані тензори пов’язані з буферами в середовищі виконання:

- `Auto`: дозвольте Neat зробити вибір. Спочатку використайте це.
- `Owned`: скопіюйте вихідні дані в пам’ять, що належить фреймворку. Використовуйте це, коли інший потік або об’єкт зберігає тензори після отримання даних.
- `ZeroCopy`: використовуйте спільне сховище в середовищі виконання. Застосовуйте це лише тоді, коли сторінка або приклад пояснюють правила часу життя.

Якщо пропускна здатність різко падає, перевірте, чи не зберігає застосунок зразки вихідних даних занадто довго. Механізм «нульового копіювання» може бути швидким, але зафіксовані буфери залишаються зафіксованими буферами.

## Масштабування від одного потоку до багатьох

Почніть з одного потоку. Потім навмисно масштабуйте топологію та політику середовища виконання.

| Схема | Коли використовувати | На що зважати |
| --- | --- | --- |
| Один потік даних -> одна модель -> один результат | Створення першого правильного шляху | Форма вихідних даних, тип даних і затримка. |
| Багато потоків даних -> одна лінія моделі (lane) | Сукупна швидкість вхідних даних відповідає одній моделі | Справедливий розподіл ресурсів між окремими потоками та обробка застарілих потоків. |
| Багато потоків даних -> кілька ліній моделі | Однієї лінії недостатньо, щоб упоратися з навантаженням | Розподіл потоків, призначення імен маршрутам і ведення обліку вихідних даних. |
| Один потік даних -> декілька моделей | Для різних рішень потрібні однакові вхідні дані | Затримка на рівні гілки та FPS, нормалізований за цільовими виходами. |
| Багато потоків даних -> модель + вихідні дані у вигляді метаданих/відео | Робочий застосунок видає кілька артефактів | Підраховуйте кількість цільових результатів окремо від результатів попереднього перегляду або телеметрії. |

Під час з’єднання фрагментів графа реального часу `GraphLinkOptions` дає змогу вибрати поведінку «останній кадр для кожного потоку в реальному часі». Використовуйте цей режим, коли важливіше мати актуальні дані, ніж зберігати кожен кадр в об’єднанні (fan-in) у реальному часі.


## Запуск графів із кількома потоками даних і власним джерелом

Для застосунків із великою кількістю камер зазвичай саме граф керує потоками даних. У такому випадку групи джерел передають дані в шлях моделі, а ваш застосунок отримує результати. Вам, як і раніше, потрібно дотримуватися тієї ж дисципліни щодо пропускної здатності:

- присвойте кожному джерелу стабільний `stream_id`;
- використовуйте поведінку «останній кадр для кожного потоку в реальному часі» для з’єднань з об’єднанням (fan-in) у реальному часі, коли важлива актуальність інформації;
- постійно отримуйте дані;
- підраховуйте кількість результатів для кожного окремого потоку, а не лише загальну кількість;
- експортуйте дані запуску після завершення вимірюваного періоду, якщо один із потоків простоює без даних або відкидає кадри.

| Варіант для графа з власним джерелом | Почніть з | Чому |
| --- | --- | --- |
| Одна камера на один граф | Одна група джерел, один шлях моделі, один результат | Найпростіший спосіб підтвердити характеристики камери, моделі та умови контракту щодо результату. |
| Багато камер в одну лінію моделі | Фрагменти-джерела, з’єднані з одним фрагментом моделі через `GraphLinkOptions` для об’єднання (fan-in) у реальному часі | Забезпечує завантаженість однієї лінії моделі, одночасно зберігаючи ідентичність кожного потоку даних. |
| Багато камер на кількох лініях | Розподіліть фрагменти-джерела між кількома лініями графа | Використовуйте, коли одна лінія моделі насичена. Вимірюйте кожну лінію й кожен потік даних. |
| Відеосигнал обробляється за допомогою графа | Групи-приймачі (sink), як-от `VideoSender(...)`, або групи виходу H.264/UDP | Використовуйте, коли застосунок не має сам отримувати й передавати кожен кадр. |

Якщо граф є власником джерел, зберіть його за допомогою `graph.build()` і свідомо зупиніть. Не надсилайте вхідні дані застосунку в граф, який уже має власні вузли-джерела.

## Пропускання багатьох потоків даних через одну лінію моделі

Використовуйте одну публічну кінцеву точку для введення, коли кілька потоків даних реального часу використовують одну й ту саму лінію моделі. Позначайте кожен зразок ідентифікаторами `stream_id` та `frame_id`, використовуйте пресет Realtime і безперервно отримуйте виходи. Ця стратегія може здаватися нудною, але вона ефективна: ніколи не дозволяйте черзі вихідних даних ставати вашим прихованим вузьким місцем.

<CodeTabs>
<CodeTab label="C++" lang="cpp">

```cpp
simaai::neat::RunOptions options;
options.preset = simaai::neat::RunPreset::Realtime;

auto run = graph.build(options);

while (running) {
  for (const auto& camera : cameras) {
    auto sample = simaai::neat::Sample::from_image(
        camera.frame(),
        simaai::neat::ImageSpec::PixelFormat::BGR,
        simaai::neat::TensorMemory::CPU);
    sample.stream_id = camera.id();
    sample.frame_id = camera.next_frame_id();

    if (!run.try_push("image", sample)) {
      ++local_drop_count[camera.id()];
    }
  }

  while (auto output = run.pull("detections", /*timeout_ms=*/0)) {
    count_output_by_stream(output->stream_id);
  }
}

run.close_input();
while (auto output = run.pull("detections", /*timeout_ms=*/1000)) {
  count_output_by_stream(output->stream_id);
}
run.close();
```

## Розподіл потоків даних між лініями моделі

Коли одна лінія моделі насичена, додайте лінії замість того, щоб приховувати перевантаження за допомогою глибших черг. Зазвичай лінія складається з одного `Graph` плюс один `Run`, з власними іменами маршрутів моделі та префіксом елементів графа. Розподіліть потоки даних за стабільним ключем, а потім виміряйте кожну лінію й кожен потік даних.

<CodeTabs>
<CodeTab label="C++" lang="cpp">

```cpp
auto build_lane = [&](int lane_index) {
  const std::string lane_name = "lane" + std::to_string(lane_index);

  simaai::neat::Model::Options model_options;
  model_options.name_suffix = "_" + lane_name;
  simaai::neat::Model lane_model(model_path, model_options);

  simaai::neat::GraphOptions graph_options;
  graph_options.element_name_prefix = lane_name + "_";

  simaai::neat::Graph graph("detector_" + lane_name, graph_options);
  graph.add(simaai::neat::nodes::Input("image"));
  graph.add(lane_model);
  graph.add(simaai::neat::nodes::Output(
      "detections",
      simaai::neat::OutputOptions::Latest()));

  simaai::neat::RunOptions run_options;
  run_options.preset = simaai::neat::RunPreset::Realtime;
  return graph.build(run_options);
};

std::vector<simaai::neat::Run> lanes;
lanes.emplace_back(build_lane(0));
lanes.emplace_back(build_lane(1));

while (running) {
  for (const auto& camera : cameras) {
    auto sample = make_sample_for_camera(camera);
    const std::size_t lane_index = camera.id() % lanes.size();

    if (!lanes[lane_index].try_push("image", sample)) {
      ++drop_count_by_lane[lane_index];
    }
  }

  for (std::size_t lane_index = 0; lane_index < lanes.size(); ++lane_index) {
    while (auto output = lanes[lane_index].pull("detections", /*timeout_ms=*/0)) {
      count_output(lane_index, output->stream_id);
    }
  }
}
```

## Свідоме налаштування лінії моделі

Якщо граф є правильним, але не може забезпечити подавану швидкість потоку даних, спочатку визначте, де саме виникає вузьке місце. Не починайте з того, що збільшуєте розмір кожної черги. Це маскує перевантаження і створює умови, за яких застарілі кадри накопичуються.

Використовуйте таку стратегію:

| Симптом | Спочатку перевірте | Потім спробуйте |
| --- | --- | --- |
| Прийнятий вхідний FPS високий, а вихідний FPS низький | Лінія моделі або лінія постобробки насичена | Розподіліть потоки даних між лініями, зменште подавану швидкість або протестуйте `advanced_execution.inference_async` на маршруті моделі чи в параметрах графа. |
| Функція `try_push(...)` часто повертає значення `false` | Черга вхідних даних заповнена | Безперервно отримуйте виходи, зменште подавану швидкість або виберіть чітку політику обробки переповнення `OverflowPolicy`. |
| Один потік даних губиться в сукупних метриках | Відсутність або нерівномірність обліку `stream_id` | Підраховуйте кількість вихідних і відкинутих даних для кожного потоку; використовуйте найновіші дані для кожного потоку в режимі реального часу для об’єднання даних з кількох потоків. |
| Вивід припиняється, а вхідні дані продовжують надходити | Застосунок недостатньо швидко отримує виходи або зберігає результати, що залежать від середовища виконання | Отримуйте виходи в окремому циклі й звільняйте/копіюйте їх, перш ніж надсилати нові дані. |
| Затримка збільшується з часом | У чергах накопичуються старі завдання | Використовуйте меншу чергу, `RunPreset::Realtime`, або `OutputOptions::Latest()`, де важлива актуальність даних. |

Коли потрібно перевірити, як виконується маршрут моделі, змінюйте лише одне розширене поле виконання за раз і вимірюйте те саме навантаження до й після зміни:

```cpp
graph_options.advanced_execution.inference_async = true;

simaai::neat::Graph graph("detector", graph_options);
```

## Вибір оптимального варіанта налаштування пропускної здатності

Починайте з урахуванням обсягу роботи, а не з довільного розміру черги.

| Обсяг роботи | Форма під час виконання (у середовищі виконання) | Почніть з | Доведіть це за допомогою |
| --- | --- | --- | --- |
| Один потік даних у реальному часі | Один багаторазовий `Run`, один виробник, один споживач (puller) | `RunPreset::Realtime`; `OutputOptions::Latest()` для виведення результатів у стилі попереднього перегляду | Прийнятий показник FPS, вихідний показник FPS, кількість відкинутих кадрів і затримка. |
| Обробка файлів або пакетна обробка | Один багаторазовий `Run`; закрити вхід і спорожнити вихід | `RunPreset::Reliable`; `OutputOptions::EveryFrame(...)` | Кількість вхідних даних дорівнює кількості вихідних даних, якщо інше не передбачено в контракті моделі. |
| Багато потоків даних у реальному часі в одну лінію моделі | Вхідні `Sample`, які надсилає застосунок, із `stream_id` / `frame_id`, або фрагменти з власним джерелом, що проставляють ідентифікатори | `RunPreset::Realtime`; `GraphLinkPolicy::RealtimeLatestByStream` через `GraphLinkOptions` для забезпечення об’єднання даних у реальному часі | Кількість кадрів за секунду (FPS) і кількість відкинутих кадрів для кожного окремого потоку, а не загальна кількість кадрів за секунду. |
| Багато потоків даних у реальному часі на кількох лініях моделі | Розподіліть потоки даних між кількома екземплярами моделі або лініями графа | Як у рецепті для потоку в реальному часі, для кожної лінії | Завантаження кожної лінії, простій без даних окремих потоків і FPS, нормалізований за цільовими виходами. |
| Один вхід розгалужується на кілька моделей | Розгалужуйте один раз, а потім запускайте окремі шляхи моделей | Розгалуження/розподіл у `Graph`; виберіть бажану поведінку для кожної гілки | Затримка гілок і FPS, нормалізований за цільовими виходами. |

Якщо одна з ліній моделі насичена, не намагайтеся приховати проблему, збільшуючи довжину черги. Розподіліть навантаження між лініями, зменште подавану швидкість вхідних даних або виберіть чітку політику відкидання. Збільшення довжини черги підвищує стійкість до коливань; це не збільшує ресурс прискорювача.

## Оптимізація пропускної здатності без самообману

Пропускну здатність визначає форма циклу, а не одна чарівна опція.

1. Зберіть граф один раз.
2. Виконайте прогрів поза вікном вимірювання.
3. Підтримуйте обмежену кількість одночасних запитів.
4. Постійно отримуйте дані, щоб черги вихідних даних не стали вузьким місцем.
5. Звільніть або скопіюйте результати, перш ніж надсилати нові, якщо буфери виходів можуть використовуватися спільно з середовищем виконання.
6. Оберіть один із варіантів політики обробки перевантажень: блокування, збереження останньої версії або відкидання вхідних даних.
7. Збережіть `stream_id` та `frame_id`.
8. Перед зупинкою запуску закрийте вхідні дані та спорожніть вихід.
9. Вимірюйте правильні показники.
10. Після виміряного навантаження експортуйте дані запуску.

Виміряйте їх окремо:

| Метрика | Значення |
| --- | --- |
| Подаваний вхідний FPS | Кількість спроб обробки вхідних даних за секунду, зазвичай `streams * source_fps`. |
| Прийнятий вхідний FPS | Кількість вхідних даних, які приймаються функціями `push(...)` або `try_push(...)` за секунду. |
| Загальна кількість кадрів за секунду | Загальна кількість виведених даних за секунду для всіх вихідних каналів. |
| Кількість кадрів за секунду для кожного окремого потоку | Швидкість виведення даних для кожного `stream_id`. |
| FPS, нормалізований за цільовими виходами | Кількість виходів за секунду, що зараховуються до цільового результату застосунку. Корисно, коли один вхід розгалужується на кілька виходів. |
| Частота відкидання | Відкинуті або відхилені вхідні дані за ідентифікатором потоку `stream_id`, джерелом і причиною. |

Загальний показник FPS може виглядати чудово, навіть якщо один із потоків простоює без даних. Метрики для кожного окремого потоку допомагають виявити проблему.

### Форма циклу обробки даних

Використовуйте цю форму для графа, у який дані надсилає застосунок. Замініть `next_inputs()` на ваше джерело вхідних даних. Зробіть цикл нудним: обмежте обсяг роботи, що виконується, забезпечте безперервне отримання даних і не передбачайте експорт звітів у межах гарячого циклу.

<CodeTabs>
<CodeTab label="C++" lang="cpp">

```cpp
auto run = graph.build(options);

for (int i = 0; i < warmup_frames; ++i) {
  run.push(next_inputs());
  (void)run.pull(/*timeout_ms=*/5000);
}

auto measurement = run.start_measurement();

int in_flight = 0;
while (in_flight < max_in_flight && has_input()) {
  if (run.push(next_inputs())) {
    ++inputs_sent;
    ++in_flight;
  }
}

while (has_input() || in_flight > 0) {
  auto output = run.pull(/*timeout_ms=*/1000);
  if (output) {
    ++outputs_seen;
    --in_flight;
    output.reset();  // Do not pin runtime-backed buffers longer than needed.
  }

  while (has_input() && in_flight < max_in_flight) {
    if (!run.try_push(next_inputs())) {
      break;
    }
    ++inputs_sent;
    ++in_flight;
  }
}

run.close_input();
while (auto output = run.pull(/*timeout_ms=*/1000)) {
  ++outputs_seen;
}

simaai::neat::MeasureReport report = measurement.stop();
simaai::neat::save_run_json(run, report, "run_after_measurement.json");
run.close();
```

### Перегляд експортованих даних запуску

Експорт запуску корисний, оскільки він об’єднує топологію, параметри середовища виконання та результати вимірювань в одному артефакті. Відкриваючи файл JSON, почніть із даних, що описують поведінку, видиму користувачеві:

| Розділ або поле | На що відповідає |
| --- | --- |
| `graph.named_inputs` / `graph.named_outputs` | Які публічні кінцеві точки були відкриті під час цього запуску? |
| `graph.public_view` | Як виглядав граф застосунку до пониження (lowering) в середовищі виконання? |
| `run.output_materialization` | Які були виходи: власні (owned), без копіювання (zero-copy) чи вибрані автоматично? |
| `run.stats` | Лічильники загальної кількості вхідних даних, вихідних даних, відкинутих даних і затримок. |
| `run.graph_metrics.counters` | Вхідні дані, вихідні дані та відкидання для експортованого запуску або виміряного вікна. |
| `run.graph_metrics.window` | Виміряне часове вікно, якщо експорт містить `MeasureReport`. |
| `run.node_metrics` / `run.plugin_metrics_unattributed` | Які етапи займали найбільше часу в середовищі виконання, коли було ввімкнено детальний збір даних про час виконання. |
| `run.path_timing` | Час проходження ребер і шляхів графа, якщо збиралися дані про час шляхів. |
| `run.graph_metrics.power` | Чи дані про потужність було зібрано, пропущено, вимкнено, чи вони були недоступні. |

Звертаючись по допомогу, додайте експорт запуску разом із контрактом моделі та найменшим прикладом, що відтворює проблему. Це бортовий самописець («чорна скринька»), тільки без загадок.

## Налагодження запуску графа

Коли граф дає збій, перевірте, що саме ви зібрали, перш ніж змінювати параметри.

1. Перевірте граф.
2. Перевірте публічні кінцеві точки графа перед збіркою.
3. Перевірте кінцеві точки середовища виконання після збірки.
4. Отримуйте дані через варіант зі статусом (status-aware), коли тайм-аут, закриття та помилка мають означати різне.
5. Експортуйте результати після завершення виконання навантаження.

<CodeTabs>
<CodeTab label="C++" lang="cpp">

```cpp
simaai::neat::GraphReport report = graph.validate();
std::cout << report.to_json() << "\n";

auto run = graph.build();

simaai::neat::Sample sample;
simaai::neat::PullError error;

switch (run.pull("classes", /*timeout_ms=*/1000, sample, &error)) {
case simaai::neat::PullStatus::Ok:
  // Use sample.
  break;
case simaai::neat::PullStatus::Timeout:
  // No output arrived before the timeout.
  break;
case simaai::neat::PullStatus::Closed:
  // End of stream. Stop draining.
  break;
case simaai::neat::PullStatus::Error:
  std::cerr << error.code << ": " << error.message << "\n";
  if (error.report) {
    std::cerr << error.report->repro_note << "\n";
  }
  break;
}
```

</CodeTab>
<CodeTab label="Python" lang="python">

```python
report = graph.validate()
print(report.to_json())

run = graph.build()
print("inputs:", run.input_names())
print("outputs:", run.output_names())

sample = run.pull("classes", timeout_ms=1000)
if sample is None:
    print("no output before timeout or end of stream")
```

</CodeTab>
</CodeTabs>

## Збирання даних для служби підтримки

Коли в застосунку виникає помилка в графі, збережіть найменший пакет даних, який пояснює зовнішню поведінку. Зробіть це перед зміною параметрів. Факти переконливіші за домисли.

Включіть:

- назву артефакту моделі та спосіб його отримання;
- інформацію про версію/збірку Neat;
- форму вхідних даних, тип даних, розміщення, формат пікселів і сімейство корисних даних;
- `graph.validate().to_json()` у разі невдалої збірки або перевірки;
- `run.input_names()` та `run.output_names()` у разі збоїв кінцевих точок;
- експорт запуску у форматі JSON після обробки принаймні одного зразка, якщо проблема пов’язана з поведінкою в середовищі виконання;
- файл `MeasureReport` у форматі JSON або текстовий файл, коли проблема пов’язана з пропускною здатністю, затримкою або потужністю;
- найменший робочий фрагмент коду, який відтворює відповідну поведінку.

У Python можна безпосередньо зібрати дані про версію та запуск:

```python
print(pyneat.build_info())

report = graph.validate()
with open("graph-report.json", "w", encoding="utf-8") as f:
    f.write(report.to_json())

# After samples have moved through the run:
run.save_json("run-after.json")
```

У C++ ті самі дані можна експортувати за допомогою `GraphReport::to_json()` і `save_run_json(...)`:

```cpp
std::cout << "neat_version=" << sima_neat_version() << "\n";
std::cout << graph.validate().to_json() << "\n";

// After samples have moved through the run:
simaai::neat::save_run_json(run, "run-after.json");
```

Якщо помилка виникає лише під час навантаження, додайте експортовані дані вимірювання замість знімка, зробленого під час збірки. Експорт, зроблений під час збірки, показує, що зібрав Neat; експорт, зроблений після виконання, показує, що сталося, коли граф обробляв реальні вхідні дані.

У разі виникнення помилок перехопіть `NeatError` і прочитайте структурований звіт:

<CodeTabs>
<CodeTab label="C++" lang="cpp">

```cpp
try {
  auto run = graph.build();
} catch (const simaai::neat::NeatError& error) {
  const auto& report = error.report();
  std::cerr << report.error_code << "\n";
  std::cerr << report.repro_note << "\n";
}
```

</CodeTab>
<CodeTab label="Python" lang="python">

```python
try:
    run = graph.build()
except pyneat.NeatError as error:
    print(error.error_code)
    print(error.repro_note)
    print(error.report_json)
```

</CodeTab>
</CodeTabs>


## Вирішення проблем, пов’язаних із низькою швидкістю або відсутністю вихідних даних

Якщо пропускна здатність низька або вихідні дані зникають, спочатку перевірте наступне:

1. Чи збираєте ви граф у межах вимірюваного циклу?
2. Ви надсилаєте один вхід, чекаєте, поки весь граф перейде в неактивний стан, а потім надсилаєте наступний?
3. Чи постійно застосунок отримує нові дані?
4. Чи блокує одна гілка вихідних даних увесь граф?
5. Чи зберігаєте ви дані, отримані за допомогою механізму «нульового копіювання» або в середовищі виконання, надто довго?
6. Черги надто короткі, щоб поглинути коливання, чи надто глибокі, через що зворотний тиск не видно?
7. Чи чітко визначено правила щодо перевищення допустимих навантажень?
8. Чи показує `inputs_dropped` у звіті вимірювань кількість зразків, відкинутих за політикою переповнення?
9. Чи генерує кожен очікуваний `stream_id` вихідні дані в межах визначеного часового інтервалу?
10. Чи містяться в гарячому циклі операції запису в журнали, перевірки декодування, операції введення-виведення файлів або експорт звітів?

Спочатку досягніть правильної роботи. Потім зробіть її швидкою. А потім доведіть, що саме ви виміряли.
