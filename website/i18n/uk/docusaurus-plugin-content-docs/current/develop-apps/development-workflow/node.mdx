# Вузол

`Node` — це найменша складова одиниця в SiMa.ai Neat.
Вузли — це елементи, які з’єднуються в [`Graph`](/develop-apps/development-workflow/graph): етапи декодування, етапи попередньої обробки, етапи моделі, етапи постобробки, джерела, приймачі та межі застосунку.

Довідник:
- [Простір імен `nodes`](/reference/{lsa}/namespaces/simaai-neat-nodes)
- [Простір імен `nodes::groups`](/reference/{lsa}/namespaces/simaai-neat-nodes-groups)

## Що таке вузол

Вузол надає один логічний елемент роботи, а також метадані, необхідні для безпечного об’єднання цього елемента з іншими:

- робота під час виконання, наприклад декодування, перетворення, попередня обробка, інференс, постобробка або поведінка приймача;
- контракти входу/виходу, наприклад очікуваний тип медіаданих, форма тензора, тип даних або caps;
- детермінована схема іменування компонентів, завдяки чому `describe()`, діагностичні інструменти, метрики та засоби моніторингу залишаються стабільними.

Основне правило просте:

```text
Graph = nodes wired together
```

`Model` — це джерело вузлів, яке знає про модель. `Model` можна додати безпосередньо до `Graph` або отримати з нього повторно використовувані фрагменти етапів: попередню обробку, інференс і постобробку.

## Готові групи вузлів

Деякі поширені шаблони складаються з кількох низькорівневих вузлів. Neat надає їх як готові групи, щоб користувачам не доводилося вручну з’єднувати кожне джерело, декодер, перетворювач, чергу чи приймач.

Уявіть собі групу як міні-граф, який можна повторно використовувати: іменований набір вузлів із чітко визначеним призначенням.

Приклади:

- `VideoInputGroup(...)`: джерело (файл або відео) + шлях декодування.
- `RtspDecodedInput(...)`: джерело RTSP + шлях декодування.
- фрагменти маршруту моделі: попередня обробка + інференс + декодування/постобробка навколо скомпільованої моделі.

<CodeTabs>
<CodeTab label="C++" lang="cpp">

```cpp
#include "neat/runtime.h"
#include "neat/node_groups.h"

simaai::neat::Graph graph;

simaai::neat::nodes::groups::VideoInputGroupOptions vopt;
vopt.path = "/data/sample.mp4";
graph.add(simaai::neat::nodes::groups::VideoInputGroup(vopt));
```

</CodeTab>
<CodeTab label="Python" lang="python">

```python
import pyneat

graph = pyneat.Graph()

vopt = pyneat.VideoInputGroupOptions()
vopt.path = "/data/sample.mp4"
graph.add(pyneat.groups.video_input(vopt))
```

</CodeTab>
</CodeTabs>

Використовуйте готові групи, коли структура стандартна, а найцікавіша частина вашого застосунку не стосується внутрішньої обробки медіаданих. Якщо вам потрібна власна топологія, зберіть еквівалентний `Graph` самостійно з низькорівневіших вузлів.

Використовуйте допоміжні функції `Graph`, такі як `graphs::Branch(...)` і `graphs::Combine(...)`, для розгалуження та зведення замість того, щоб приховувати топологію за дубльованими виходами.

`nodes::H264Decode(...)` і `pyneat.nodes.h264_decode(...)` є застарілими обгортками для забезпечення сумісності. Для нових графів декодування H.264 слід використовувати `SimaDecode` з `SimaDecodeType::H264`.

## Шляхи декодування закодованих даних

Обирайте API, виходячи з того, які дані отримує ваш граф:

| Вхідні дані, доступні графу | API | Вихід |
| --- | --- | --- |
| Повні розібрані закодовані одиниці доступу | `SimaDecode(...)` | Сире декодоване відео |
| Потік RTSP, який має залишатися закодованим | `RtspEncodedInput(...)` | Розібрані закодовані одиниці доступу |
| Потік RTSP, який потрібно декодувати | `RtspDecodedInput(...)` | Сире декодоване відео |

`SimaDecode` не встановлює з’єднання з RTSP, не виконує депакетизацію RTP і не розбирає елементарний потік. Використовуйте його, коли попередній етап або застосунок уже надає повні закодовані зразки.

| Закодований вхід | Параметр нативного декодера | Типовий попередній шлях |
| --- | --- | --- |
| Одиниці доступу H.264/AVC | `SimaDecodeType::H264` або `SimaDecodeType::AVC` | Депакетизація + розбір RTSP H.264 або інше розібране джерело H.264 |
| Одиниці доступу H.265/HEVC | `SimaDecodeType::H265` або `SimaDecodeType::HEVC` | Депакетизація + розбір RTSP H.265 або інше розібране джерело H.265 |
| Окремі кадри JPEG | `SimaDecodeType::JPEG` | `JpegParse()` або закодований зразок JPEG, наданий застосунком |
| Потік кадрів MJPEG | `SimaDecodeType::MJPEG` | Демультиплексування HTTP multipart + `JpegParse()` або депакетизація RTSP JPEG + `JpegParse()` |

Псевдоніми обирають ідентичні шляхи декодера: `H264` дорівнює `AVC`, а `H265` дорівнює `HEVC`. Ті самі псевдоніми доступні через `RtspCodec` та `FormatTag` у C++ та Python.

Для вхідного потоку H.264 необхідно використовувати 8-бітну колірну субдискретизацію 4:2:0 і прогресивні кадри. Бітові потоки High 10, High 4:2:2 та черезрядкові бітові потоки не підтримуються.

Для вхідного потоку H.265 необхідно використовувати профіль HEVC Main з 8-бітною колірною субдискретизацією 4:2:0. Безпосередньо вхідний елементарний потік має бути розібраний, у форматі байтового потоку Annex-B, а також має бути вирівняний за одиницями доступу. Його набори параметрів (VPS, SPS та PPS) повинні бути передані декодеру до кадрів, які від них залежать. `RtspEncodedInput` виконує депакетизацію RTP і розбір H.265 для шляху RTSP. Бітові потоки Main 10, 10-біт, 4:2:2 та монохромні 4:0:0 не підтримуються. Для контенту в градаціях сірого кодуйте 8-бітний потік 4:2:0, де площина Y містить зображення в градаціях сірого, а зразки U та V використовують нейтральне значення 128.

Перевірте потік перед його використанням:

```bash
ffprobe -v error -rtsp_transport tcp -select_streams v:0 \
  -show_entries stream=codec_name,profile,pix_fmt \
  -of default=noprint_wrappers=1 rtsp://camera.example/live
```

Декодер H.265 вимагає `codec_name=hevc`, `profile=Main` та `pix_fmt=yuv420p`.

`SimaDecodeOptions::raw_output` керує безпосереднім виходом декодера:

| Значення | Вихід декодера |
| --- | --- |
| `true` (за замовчуванням) | Вихідні буфери декодера: за замовчуванням нативний NV12 або перетворений I420. |
| `false` | Перетворений вихід `video/x-raw(memory:SystemMemory)` для CPU-споживачів. |

`SimaDecode` запитує вихід декодера без копіювання для NV12. Вибір I420 використовує режим копіювання, що перетворює апаратні NV12 пікселі безпосередньо в кінцеві площини I420. Обидва режими використовують вихідний пул DMA-BUF декодера.
Значення `raw_output=false` додає програмний адаптер для виходу в системну пам’ять.
`RunOptions::output_memory` окремо визначає, чи кінцевий вихід спільно використовує базовий буфер (`ZeroCopy`), чи копіює його у сховище, що належить фреймворку (`Owned`).

Плагін декодера володіє апаратним сеансом. Core не резервує кількість слотів декодера через демон допуску й не утримує оренду декодера. Помилки запуску повідомляються звичайним шляхом помилок конвеєра.

Використовуйте `dec_width`, `dec_height` та `dec_fps` лише для перевизначення розмірів або частоти кадрів попереднього етапу; `-1` залишає їх визначення попередньому етапу.
Ці параметри не резервують кількість слотів декодера. Core передає явне значення `num_buffers` декодеру, який застосовує вимоги свого апаратного пулу; `-1` зберігає політику декодера.

Залиште `decoder_tuning` порожнім, щоб зберегти параметри плагіна за замовчуванням.
Явні значення, зокрема `default` і `auto`, передаються плагіну разом із
`memory_opt` та перевизначеннями кількості буферів, щоб декодер міг застосувати пріоритет налаштувань.
Канонічні пресети — `auto`, `default`, `low-memory` і `throughput-low-latency`; також приймаються псевдоніми декодера, як-от `low_memory` і `throughput`.
Регістр і пробіли на початку та в кінці значення ігноруються; з будь-яким іншим непорожнім значенням `SimaDecode` і `RtspDecodedInput` під час створення повертають помилку `misconfig.option_out_of_range`.
`throughput-low-latency` вимикає перевпорядкування декодованих кадрів і використовує глибину команд 1 для кадрів до 720p включно або 2 для більших кадрів.
Використовуйте цей режим лише для потоків без B-кадрів; для загальних потоків залишайте налаштування незаданим.

`nodes::JpegDecode()` і `pyneat.nodes.jpeg_decode()` — це окремі вузли декодування JPEG для CPU/GStreamer. Використовуйте їх для простих конвеєрів обробки зображень на CPU. Не використовуйте їх для нативного декодування відео MJPEG перед попередньою обробкою моделі.

Для RTSP віддавайте перевагу групам, що враховують кодек, коли форма джерела стандартна. За замовчуванням використовується H.264. H.265 або HEVC вибирайте явно.

### Декодування камер MJPEG

USB-камери надсилають MJPEG із субдискретизацією кольору 4:2:0 або 4:2:2; більшість використовує 4:2:2. Під час виведення без копіювання декодер записує лише власну субдискретизацію потоку, тому граф має знати її ще до збірки. Для USB-камери її повідомляє `usb_camera_info(...)` у полі `decoded_format`; використайте це значення як `out_format` декодера. Для іншого джерела MJPEG задайте `out_format` як `NV12` для 4:2:0 або `NV16` для 4:2:2. Модель читає NV16 напряму: задайте такий самий вхідний формат її попередньої обробки, і кадри 4:2:2 надходитимуть до моделі без етапу перетворення.

<CodeTabs>
<CodeTab label="C++" lang="cpp">

```cpp
#include "neat.h"

// camera: your UsbCameraInputOptions; also pass info to UsbCameraInput(camera, info).
const simaai::neat::UsbCameraInfo info = simaai::neat::usb_camera_info(camera);
simaai::neat::SimaDecodeOptions decode;
decode.type = simaai::neat::SimaDecodeType::MJPEG;
decode.out_format = info.decoded_format;  // NV12 or NV16
decode.dec_width = 1920;
decode.dec_height = 1080;
decode.dec_fps = 30;
decode.raw_output = true;  // zero-copy: the decoder writes the camera's own sampling
graph.add(simaai::neat::nodes::JpegParse());
graph.add(simaai::neat::nodes::SimaDecode(decode));

simaai::neat::Model::Options model_options;
model_options.preprocess.color_convert.input_format =
    decode.out_format == simaai::neat::FormatTag::NV16 ? simaai::neat::PreprocessColorFormat::NV16
                                                       : simaai::neat::PreprocessColorFormat::NV12;
```

</CodeTab>
<CodeTab label="Python" lang="python">

```python
import pyneat

# camera: your UsbCameraInputOptions; also pass info to usb_camera_input(camera, info).
info = pyneat.usb_camera_info(camera)
decode = pyneat.SimaDecodeOptions()
decode.type = pyneat.SimaDecodeType.MJPEG
decode.out_format = info.decoded_format  # NV12 or NV16
decode.dec_width, decode.dec_height, decode.dec_fps = 1920, 1080, 30
decode.raw_output = True  # zero-copy: the decoder writes the camera's own sampling
graph.add(pyneat.nodes.jpeg_parse())
graph.add(pyneat.nodes.sima_decode(decode))

model_options = pyneat.ModelOptions()
model_options.preprocess.color_convert.input_format = (
    pyneat.PreprocessColorFormat.NV16 if decode.out_format == pyneat.Format.NV16
    else pyneat.PreprocessColorFormat.NV12)
```

</CodeTab>
</CodeTabs>

`HttpMjpegDecodedInput(...)` і `RtspDecodedInput(...)` і надалі запитують у декодера NV12, тому підтримують лише потоки MJPEG 4:2:0.

### Збереження вхідного потоку RTSP закодованим

Використовуйте `RtspEncodedInput(...)`, щоб виконати депакетизацію та розбір потоку без його декодування:

<CodeTabs>
<CodeTab label="C++" lang="cpp">

```cpp
simaai::neat::nodes::groups::RtspEncodedInputOptions encoded;
encoded.url = "rtsp://camera.example/live";
encoded.codec = simaai::neat::nodes::groups::RtspCodec::HEVC;
encoded.source_fps = 30;

auto encoded_graph =
    simaai::neat::nodes::groups::RtspEncodedInput(encoded);
```

</CodeTab>
<CodeTab label="Python" lang="python">

```python
encoded = pyneat.RtspEncodedInputOptions()
encoded.url = "rtsp://camera.example/live"
encoded.codec = pyneat.RtspCodec.HEVC
encoded.source_fps = 30

encoded_graph = pyneat.groups.rtsp_encoded_input(encoded)
```

</CodeTab>
</CodeTabs>

`RtspEncodedInput(...)` зупиняється після депакетизації джерела та розбору/виділення кадрів.
Використовуйте його, коли вашому застосунку потрібні закодовані зразки, наприклад щоб розділити один розібраний потік на граф декодування та граф виведення відео. Для H.265 значення `source_fps` записується в caps розібраного закодованого потоку, якщо потік не повідомляє дійсну частоту кадрів.

### Декодування вхідного потоку RTSP

Використовуйте `RtspDecodedInput(...)`, щоб додати `SimaDecode(...)` і повернути сире декодоване відео:

<CodeTabs>
<CodeTab label="C++" lang="cpp">

```cpp
simaai::neat::nodes::groups::RtspDecodedInputOptions decoded;
decoded.url = "rtsp://camera.example/live";
decoded.codec = simaai::neat::nodes::groups::RtspCodec::H265;
decoded.source_fps = 30;

simaai::neat::Graph graph;
graph.add(simaai::neat::nodes::groups::RtspDecodedInput(decoded));
graph.add(simaai::neat::nodes::Output("frames"));
```

</CodeTab>

Для H.265 `RtspDecodedInput(...)` використовує `source_fps` і для розібраних caps, і для `dec-fps` декодера. Задайте його, якщо caps RTSP не містять дійсної частоти кадрів; без жодного з цих значень запуск декодера не вдасться. Neat не перевіряє URL-адресу RTSP на наявність цього значення. Він визначає частоту кадрів джерела і не запитує перетворення частоти. Щоб змінити частоту кадрів вихідного потоку, увімкніть `use_videorate` і встановіть `video_rate_fps`. Перетворення частоти відкидає зайві кадри та зберігає часові позначки джерела. Фабрики `nodes::VideoRate()` і `pyneat.nodes.video_rate()` не приймають аргументів і завжди використовують `drop-only=true`, зокрема коли їх додають групи з власним джерелом. Вони не дублюють кадри для збільшення вихідної частоти.

Для HTTP multipart MJPEG використовуйте `HttpMjpegDecodedInput(...)`. HTTP multipart MJPEG не є RTP, тому використовується `HttpSource -> MultipartJpegDemux -> JpegParse ->
SimaDecode(MJPEG)` замість депакетизації RTSP.


## Групи з власним джерелом і групи-приймачі

Використовуйте групи з власним джерелом, коли граф має сам зчитувати медіадані. Збирайте такі графи без входу від застосунку, а потім отримуйте виходи або доручіть доставку вузлам-приймачам. Використовуйте групи-приймачі, коли граф має надсилати відео назовні без того, щоб ваш застосунок отримував кожен кадр; у граф-приймач застосунок усе одно може надсилати дані, якщо в ньому є межа `Input`.

| Потрібно | Група | Основні поля, які слід задати насамперед | Поширені поля для подальшого налаштування |
| --- | --- | --- | --- |
| Статичне зображення для тестування | `nodes::groups::ImageInputGroup(...)` / `pyneat.groups.image_input(...)` | `path` | `fps`, `imagefreeze_num_buffers`, `output_caps` |
| Відеофайл | `nodes::groups::VideoInputGroup(...)` / `pyneat.groups.video_input(...)` | `path` | `out_format`, `output_caps`, `sync_mode` |
| Камера MIPI/libcamera реального часу | `nodes::CameraInput(...)` / `pyneat.nodes.camera_input(...)` | `width`, `height`, `framerate_num`, `format`; необов’язково `camera_name` | `allow_cpu_fallback`, поля черги, `buffer_name` |
| Закодований потік RTSP H.264, H.265 або MJPEG реального часу | `nodes::groups::RtspEncodedInput(...)` / `pyneat.groups.rtsp_encoded_input(...)` | `url`, `codec`, якщо не H.264 | `source_fps`, `latency_ms`, `tcp`, `drop_on_latency`, `buffer_mode`, тип корисних даних RTP |
| Декодований потік RTSP H.264, H.265 або MJPEG реального часу | `nodes::groups::RtspDecodedInput(...)` / `pyneat.groups.rtsp_decoded_input(...)` | `url`, `codec`, якщо не H.264 | `source_fps`, `latency_ms`, `tcp`, `drop_on_latency`, `buffer_mode`, декодовані ширина/висота, `out_format`, `output_caps` |
| Потік HTTP multipart MJPEG | `nodes::groups::HttpMjpegDecodedInput(...)` / `pyneat.groups.http_mjpeg_decoded_input(...)` | `url` | `out_format`, `decoder_next_element`, декодовані ширина/висота/FPS, `output_caps` |
| Вихід сирого або закодованого відео H.264/H.265/MJPEG | `nodes::groups::VideoSender(...)` / `pyneat.groups.video_sender(...)` | `VideoSenderOptions::FromRaw(encode_options)` або `Passthrough(codec)` | `host`, `channel`, `video_port_base`, параметри енкодера/RTP |
| Вихід RTP/H.264 через UDP | `nodes::groups::UdpH264OutputGroup(...)` / `pyneat.groups.udp_h264_output_group(...)` | цільовий хост/порт, коли значення за замовчуванням не підходять | `h264_caps`, `payload_type`, `config_interval` |

Граф із власним джерелом має іншу форму в середовищі виконання, ніж граф, у який дані надсилає застосунок:

```text
source group -> model -> output
```

Для камер MIPI використовуйте [`CameraInput`](/reference/nodes/camera-input) безпосередньо, а не обгортайте камеру в `Input`, у який дані надсилає застосунок. Спочатку перевірте камеру через libcamera/GStreamer, а потім зберіть граф як `CameraInput -> model -> Output`. Повний шлях описано в розділі [Використання камери MIPI](/develop-apps/advanced-concepts/mipi-camera-input).

Запустіть його за допомогою `graph.build()` або `graph.run()` без аргументу вхідних даних. Не додавайте `Input("image")` перед групою джерела, хіба що ваш застосунок справді має другий публічний вхід, у який надсилає дані.

## Поширені вузли SiMa

Деякі вузли SiMa досить поширені, тому для них створено спеціалізовані сторінки з довідковою інформацією або інструкції:

- [`Preproc`](/reference/nodes/preproc): об’єднана попередня обробка зображень CVU для зміни розміру, перетворення кольорів, нормалізації, квантування, теселяції та створення списків ROI для середовища виконання.
- [`CameraInput`](/reference/nodes/camera-input): кадри MIPI/libcamera від власного джерела з адаптивним передаванням пам’яті SiMaAI подальшим етапам обробки CVU/MLA.
- [`SimaBoxDecode`](/reference/boxdecode_decode_types): постобробка для виявлення об’єктів, яка декодує виходи моделі в обмежувальні рамки й використовує метадані попередньої обробки з попередніх етапів для відображення координат.

<a id="boundary-nodes"></a>
## Граничні вузли: `Input` та `Output`

`Input` і `Output` також є вузлами. Вони особливі, оскільки описують, звідки дані надходять або куди вони передаються у фрагменті графа.

Важлива концептуальна модель:

> `Input("name")` та `Output("name")` — це іменовані «двері».

На зовнішній межі готового застосунку ці «двері» стають публічними API середовища виконання:

- `Input("image")` перетворюється на `run.push("image", ...)`.
- `Output("classes")` перетворюється на `run.pull("classes", ...)`.

У межах більшого графа ці самі «двері» є лише точками з’єднання. Neat видаляє внутрішні граничні вузли під час створення шляху для середовища виконання та безпосередньо пов’язує реальні компоненти.

```cpp
simaai::neat::Graph route("route");
route.add(simaai::neat::nodes::Input("image"));
route.add(model);
route.add(simaai::neat::nodes::Output("classes"));
```

Використовується як повноцінний застосунок:

```cpp
auto run = route.build();
run.push("image", simaai::neat::TensorList{image_tensor});
auto classes = run.pull("classes");
```

Використовується всередині більшого застосунку:

```cpp
simaai::neat::Graph app("app");
app.connect(camera, route);
app.connect(route, telemetry);
```

Концептуально під час пониження (lowering) внутрішні граничні вузли перетворюються на пряме з’єднання:

```text
camera -> model -> telemetry
```

Імена при цьому зберігаються для діагностики, перевірки кінцевих точок, метрик і візуалізації. Просто вони не створюють додаткових черг, копій чи фіктивних приймачів середовища виконання посередині застосунку.

### Мітки не є кінцевими точками

Не плутайте ці імена:

| Ім’я | Що це | Чи створює `push(...)` / `pull(...)`? |
| --- | --- | --- |
| `Graph("detector")` | Мітка графа для діагностики, експорту та журналів. | Ні. |
| `nodes::Input("image")` / `pyneat.nodes.input("image")` | Публічна межа входу, якщо вона залишається на зовнішньому боці остаточного графа. | Так: `run.push("image", ...)`. |
| `nodes::Output("detections")` / `pyneat.nodes.output("detections")` | Публічна межа виходу, якщо вона залишається на зовнішньому боці остаточного графа. | Так: `run.pull("detections", ...)`. |
| Імена вузлів або елементів | Імена бекенду, що використовуються в діагностиці та під час пониження (lowering) конвеєра. | Ні, якщо їх не відкрито через межу `Input` або `Output`. |

Якщо виклик у середовищі виконання повідомляє, що ім’я кінцевої точки невідоме, перевірте `run.input_names()` і `run.output_names()`, а не вгадуйте. Імена нічого не коштують, а от неправильні імена обходяться дорого.

### Вхід, у який дані надсилає застосунок

Використовуйте `nodes::Input`, коли ваш застосунок уже має кадр або тензор і хоче надіслати його в Neat.

Використовуйте `InputOptions`, коли межа потребує явного контракту щодо корисних даних, формату, розміру, часу або виділення пам’яті.

| Потрібно | Поле |
| --- | --- |
| Сімейство корисних даних | `payload_type` / `PayloadType` |
| Формат | `format` / `FormatTag` |
| Фіксовані розміри | `width`, `height`, `depth` |
| Динамічні обмеження вхідних даних | `max_width`, `max_height`, `max_depth`, `max_bytes` |
| Час і caps | `fps_n`, `fps_d`, `caps_override` |
| Поведінка в режимі реального часу | `is_live`, `do_timestamp`, `block`, `stream_type` |
| Виділення пам’яті | `memory_policy`, `pool_min_buffers`, `pool_max_buffers` |
| Розширена метаінформація | `buffer_name`, `preprocess_meta` |

`use_simaai_pool` застаріла. У новому коді використовуйте `memory_policy`:

- Якщо у наявному коді використовувався параметр `use_simaai_pool=false`, використовуйте параметр `memory_policy=SystemMemory`.
- Для поведінки виділення пам’яті SiMa за замовчуванням використовуйте `memory_policy=Auto`.
- Використовуйте `Ev74` або `Dms0` лише тоді, коли для вхідної межі потрібна певна цільова область.
- Наявний код і старіші версії JSON для графа, що використовують `use_simaai_pool`, все ще підтримуються для забезпечення сумісності.
- Новий збережений файл JSON графа записує `memory_policy` замість `use_simaai_pool`.

Не задавайте поля, якщо межа графа не потребує такого контракту. Вгадування caps — найкоротший шлях у болото.

#### Рецепти для меж входу

Використовуйте ці шаблони, коли контракт межі важливий ще до першого виклику push.

| Межа | Задати | Не задавати, якщо |
| --- | --- | --- |
| Декодоване зображення фіксованого розміру | `payload_type`, `format`, `width`, `height` | Надісланий тензор або зразок уже містить повні метадані зображення. |
| Динамічне декодоване зображення | `payload_type`, `format`, `max_width`, `max_height` і необов’язковий `max_bytes` | Граф приймає лише один фіксований розмір. |
| Закодований вхід H.264 | `payload_type = Encoded`, `format = H264` і caps H.264 у надісланому `Sample` | Джерело графа володіє потоком через групу RTSP або файлову групу. |
| Закодований вхід H.265 | `payload_type = Encoded`, `format = H265` і caps H.265 у надісланому `Sample` | Джерело графа володіє потоком і розбирає його через групу RTSP або файлову групу. |
| Відображення координат виявлення | `preprocess_meta` | Маршрут моделі сам виконує попередню обробку та генерує метадані. |

### Вихід зразків (Sample)

Використовуйте `nodes::Output`, коли споживачу потрібен повний [`Sample`](/develop-apps/development-workflow/core_types#use-sample-for-metadata): корисні дані плюс метадані потоку/кадру/часової мітки.

Використовуйте `OutputOptions`, коли важлива поведінка, пов’язана з отриманням даних.

| Мета | Використовуйте |
| --- | --- |
| Зберігати найсвіжіший вихід | `OutputOptions::Latest()` / `pyneat.OutputOptions.latest()` |
| Отримувати кожен кадр | `OutputOptions::EveryFrame(...)` / `pyneat.OutputOptions.every_frame(...)` |
| Задавати темп виходу за годинником графа | `OutputOptions::Clocked(...)` / `pyneat.OutputOptions.clocked(...)` |
| Об’єднувати кількох виробників | `combine_policy = CombinePolicy::ByFrame` або `ByPts` |

<CodeTab label="C++" lang="cpp">

```cpp

graph.add(simaai::neat::nodes::Input("image"));
graph.add(model);

    "classes",
    simaai::neat::OutputOptions::EveryFrame()));
```

`OutputOptions` має чотири регулятори, але пресети підходять для більшості застосунків:

| Поле | Що воно контролює | Чому віддавати перевагу |
| --- | --- | --- |
| `max_buffers` | Скільки вихідних зразків може накопичитися в черзі, перш ніж спрацює зворотний тиск (backpressure) або почнеться відкидання. | Пресети `Latest()`, `EveryFrame(...)` або `Clocked(...)`. |
| `drop` | Чи відкидає переповнення найстаріший зразок у черзі замість блокування. | `Latest()` для виходу в стилі попереднього перегляду в реальному часі. |
| `sync` | Чи синхронізується вихід із годинником графа. | `Clocked(...)` для виходу з темпом за годинником. |
| `combine_policy` | Як один публічний `Output` об’єднує кількох виробників із попередніх етапів. | `CombinePolicy::ByFrame` застосовується лише з дійсним `frame_id`; `ByPts` застосовується лише з дійсним `pts_ns`. |

Використовуйте `EveryFrame(...)` для даних, які не можна втрачати. Використовуйте `Latest()`, коли важливіша актуальність, ніж історія. Не налаштовуйте попередній перегляд у режимі реального часу так, щоб він нагадував стенограму судового засідання.

#### Розширені налаштування: адаптація виводу зображення або відео до тензора

Для звичайних вихідних даних моделі або графа, зупиніться тут: використовуйте `nodes::Output`. Якщо корисні дані містять лише тензор і вам не потрібен повний об’єкт `Sample`, отримайте його за допомогою `pull_tensors(...)`.

Використовуйте `Graph::add_output_tensor(...)` лише тоді, коли вихідне зображення чи відео потрібно перетворити, масштабувати або змінити частоту кадрів, щоб отримати зручний для CPU тензор `UInt8`, перш ніж застосунок його отримає. Цей допоміжний модуль вставляє шлях адаптера та створює неіменований вихід. Якщо є лише один вихід, отримайте його за допомогою `run.pull_tensors(...)`.

`OutputTensorOptions` контролює `format`, `target_width`, `target_height` та `target_fps`. Залиште `dtype` як `UInt8`; поточний публічний шлях відхиляє інші типи даних. Більшості вихідних даних моделі цей допоміжний модуль не потрібен.

## Короткий посібник із вибору

- Джерело — файл, камера або RTSP: використовуйте готову групу входу з `nodes::groups`.
- Джерелом є тензор/кадр, згенерований застосунком: використовуйте `nodes::Input`.
- Споживачеві виходу потрібні метадані потоку/кадру/часової мітки: використовуйте `nodes::Output` та отримуйте об’єкти `Sample`.
- Вихід — це результат моделі або тензорні корисні дані: використовуйте `nodes::Output` і отримуйте тензори через `pull_tensors(...)`, якщо повний `Sample` не потрібен.
- Вихід — це зображення або відео, яким перед отриманням потрібно змінити розмір, формат або частоту кадрів: використовуйте розширений адаптер `add_output_tensor(...)`.
- Потрібен набір компонентів, який можна повторно використовувати: створіть фрагмент `Graph` з вузлів і додайте/під’єднайте його так само, як і будь-яку іншу складову.

## Чому це важливо

- Одна концепція охоплює атомарні етапи, оголошення меж і готові групи.
- Повторно використовувані фрагменти графа поводяться як функції: входи на вході, виходи на виході, жодних випадкових джерел чи приймачів середовища виконання посередині.
- Діагностика залишається зрозумілою, бо імена вузлів і меж зберігаються після пониження (lowering).
- Середовище виконання залишається ефективним, оскільки внутрішні межі не створюють приховані копії або черги.

## Апаратне кодування

`SimaEncodeOptions.type` вибирає H.264, H.265 або MJPEG. Енкодер приймає нативний
8-бітний NV12. Його вхідний адаптер утримує сумісні SiMaAI NV12 буфери та один раз готує підтримувані сирі CPU-розміщення.
Вихід — кодовані кадри; додавайте пакетування лише для передавання RTP.

```cpp
simaai::neat::SimaEncodeOptions encode;
encode.type = simaai::neat::SimaEncodeType::H265;
encode.fps = 30;
encode.bitrate_kbps = 4000;
encode.gop_length = 30;
encode.idr_interval = 90;
graph.add(simaai::neat::nodes::SimaEncode(encode));
```

```python
encode = pyneat.SimaEncodeOptions()
encode.type = pyneat.SimaEncodeType.MJPEG
encode.fps = 30
encode.quality = 80
graph.add(pyneat.nodes.sima_encode(encode))
```

Роздільність береться з вхідних кадрів на початку кодування. Енкодер їх не масштабує.
Для кодування іншої роздільності почніть новий запуск.
Розміри входу мають бути додатними й парними.
`nodes::SimaEncode()` і `pyneat.nodes.sima_encode()` використовують параметри H.264 за замовчуванням.
Не повторюйте розміри входу в параметрах енкодера. `fps` налаштовує кадрову частоту потоку та керування швидкістю, але не задає темп надходження входу.
H.264/H.265 підтримують `bitrate_kbps` (за замовчуванням 4000), `rate_control` (`vbr` або `cbr`),
`profile`, `level` (за замовчуванням `4.0`), `gop_length` і окремий `idr_interval`.
За замовчуванням H.264 використовує `baseline`; H.265 підтримує `main`.
Середовище виконання може підвищити запитаний рівень за вимогами потоку та повідомляє фактичне значення.
Нульовий або незаданий GOP використовує FPS; нульовий або незаданий IDR — трикратний FPS.
GOP один означає лише внутрішньокадрове кодування. Кодування B-кадрів не надається.

Параметри окремих кодеків початково незадані. MJPEG приймає `quality` від 1 до 100
(за замовчуванням 80) і відхиляє явно задані параметри лише для відео. Натомість H.264/H.265 відхиляють `quality`.
`num_buffers` вибирає від 1 до 20 вихідних кодованих буферів;
`-1` зберігає нативне значення за замовчуванням — чотири. Це не визначає розмір вхідного сховища виробника.
Цей API не підтримує нативне кодування 4:2:2 і кодування з високою бітовою глибиною.

`H264EncodeSima` та `pyneat.nodes.h264_encode_sima` — застарілі точки входу для сумісності.
Їхні аргументи, getter-и та нативна поведінка входу залишаються підтримуваними.
Як і `H264Decode`, виклики C++ попереджають, якщо перед включенням заголовків задано
`SIMA_ENABLE_LEGACY_DEPRECATION`. Виклики Python видають `DeprecationWarning`.
`H264EncodeSW` не змінено. Цей випуск змінює C++ ABI на версію 5;
перезберіть C++ споживачів і використовуйте відповідне перезібране розширення Python.

## Вибір кодека VideoSender

Для сирого входу передайте ті самі параметри енкодера до `VideoSenderOptions::FromRaw`.
Кодек визначає і кодування, і пакетування RTP:

```cpp
auto options = simaai::neat::nodes::groups::VideoSenderOptions::FromRaw(encode);
options.host = "127.0.0.1";
options.video_port_base = 9000;
auto sender = simaai::neat::nodes::groups::VideoSender(options);
```

```python
options = pyneat.VideoSenderOptions.from_raw(encode)
options.host = "127.0.0.1"
sender = pyneat.groups.video_sender(options)
```

Для кодованих кадрів використовуйте `VideoSenderOptions::Passthrough(RtspCodec::H265)` або
`pyneat.VideoSenderOptions.passthrough(pyneat.RtspCodec.H265)`.
Цей шлях розбирає та пакує вибраний кодек без кодування. Обидві фабрики також підтримують H.264 і MJPEG.
Фабрика записує режим входу; побудова графа вибирає шлях один раз.
`is_raw_input()` і `is_encoded_input()` показують цей вибір.

Типи корисних даних RTP за замовчуванням: H.264 96, H.265 98, MJPEG 26; `rtp.payload_type`
може перевизначити їх у межах 0..127. `rtp.config_interval` впливає лише на H.264/H.265.
UDP-порт — `video_port_base + channel`. `sync=true` чекає часових позначок пакетів за годинником конвеєра;
`async=true` дозволяє приймачу чекати першого preroll-буфера під час запуску.
Обидва за замовчуванням мають значення false. Python використовує `async_` і зберігає псевдонім `async`.
Ці параметри не вибирають потоки енкодера й не задають темп подання виробником.

Наявні фабрики сирого/кодованого H.264 залишаються точками входу для сумісності.
Для нових сирих передавачів використовуйте `FromRaw`.
Параметри передавача володіють копією конфігурації; зміна початкового об’єкта `encode` не впливає на неї.
Пізніші зміни застарілих полів бітрейту/профілю/рівня `options.encoder` залишаються визначальними для сирого H.264/H.265.
Python також може замінити весь цей об’єкт. MJPEG відхиляє перевизначення лише для відео, відмінні від значень за замовчуванням.
Пряме передавання кодованих кадрів ігнорує параметри енкодера.

RTP/JPEG потребує сумісного приймача, базового JPEG зі стандартними таблицями Гаффмана
й розмірів, кратних восьми, від 8 до 2040 у кожному напрямку.
Передавання сирих кадрів і пряме передавання кодованих кадрів відхиляють непідтримувані розміри
під час узгодження caps перед пакетуванням RTP.
Окремий `SimaEncode` зберігає нативний діапазон геометрії.
Це не додає перегляд MJPEG у RTP/WebRTC-переглядач Insight.
