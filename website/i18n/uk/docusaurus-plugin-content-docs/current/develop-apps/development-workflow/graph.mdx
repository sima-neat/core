# Граф

У SiMa.ai Neat `Graph` [API](/reference/{lsa}/classes/simaai-neat-graph) використовується для створення застосунку. `Graph` описує потік даних від входів, через вузли обробки, до виходів. Якщо ви маєте досвід у машинному навчанні, уявляйте `Graph` як невеликий граф моделі для застосунку, що використовує вашу модель.

- Кадри, тензори або зразки надходять через **входи** й виходять через **виходи**. Обробка відбувається посередині, у **вузлах**, як-от декодування, зміна розміру, попередня обробка, інференс, постобробка, розгалуження та власна логіка.

![Входи, етапи обробки та виходи в межах одного Graph](@site/../docs/images/graph-input-output.svg)

- Графи можуть виконуватися як окремі одиниці або використовуватися повторно всередині більшого графа.

![Фрагмент графа, який можна повторно використовувати, вбудований у більший граф застосунку.](@site/../docs/images/graph-reusable-fragment.svg)

Neat дає змогу описувати застосунок замість ручного з’єднування середовища виконання. Використовуйте попередньо створені [вузли](/develop-apps/development-workflow/node) та [групи вузлів](/develop-apps/development-workflow/node#pre-built-node-groups) для типових завдань, як-от вхід, декодування, зміна розміру, попередня обробка, інференс, постобробка та вихід. У `Graph` ви оголошуєте вузли, задаєте їхні параметри та з’єднуєте їх у порядку, потрібному вашому застосунку.

Під капотом Neat збирає виконуваний граф середовища виконання на основі GStreamer. Neat абстрагує цю реалізацію, тому ви використовуєте публічний `Graph` API замість керування елементами GStreamer, `appsrc`, `appsink`, чергами або внутрішніми портами середовища виконання.

## Вузли, групи та межі

`Graph` — це межа компонування; [`Node`](/develop-apps/development-workflow/node) — складова.

Це включає:

- атомарні вузли, як-от етапи декодування, попередньої обробки, постобробки, джерела (source) і приймача (sink);
- попередньо створені групи вузлів, які є наборами вузлів, що можна повторно використовувати;
- граничні вузли, такі як `Input("image")` і `Output("classes")`.

Детальні правила щодо попередньо створених груп і граничних вузлів наведено в [Вузол → Попередньо створені групи вузлів](/develop-apps/development-workflow/node#pre-built-node-groups) і [Вузол → Граничні вузли](/develop-apps/development-workflow/node#boundary-nodes).

Коли ви викликаєте `Graph::build()`, Neat перетворює публічний граф на єдиний граф, придатний для виконання, зберігаючи імена кінцевих точок для діагностики та іменовані API `Run`.

## Надання імен входам і виходам

Імена у вузлах `Input` та `Output` оголошують граничні кінцеві точки фрагмента графа. Межі, що залишаються зовнішніми в остаточно скомпонованому `Graph`, стають публічними кінцевими точками середовища виконання:

```cpp
simaai::neat::Graph classifier("classifier");
classifier.add(simaai::neat::nodes::Input("image"));
classifier.add(model);
classifier.add(simaai::neat::nodes::Output("classes"));
```

Тут `image` є вхідною точкою, а `classes` — вихідною точкою. Назва графа, `classifier`, є лише позначкою для діагностики та візуалізації; вона не створює вхід або вихід.

### Перевірка кінцевих точок перед збіркою

Виведіть список публічних кінцевих точок перед тим, як збирати граф. Не повинно бути жодних неактивних кінцевих точок. Якщо назва відсутня в цьому списку, `Run` не прийме її пізніше.

<CodeTabs>
<CodeTab label="C++" lang="cpp">

```cpp
for (const auto& name : classifier.inputs()) {
  std::cout << "graph input: " << name << "\n";
}
for (const auto& name : classifier.outputs()) {
  std::cout << "graph output: " << name << "\n";
}
```

</CodeTab>
<CodeTab label="Python" lang="python">

```python
print("graph inputs:", classifier.inputs())
print("graph outputs:", classifier.outputs())
```

</CodeTab>
</CodeTabs>

Після `graph.build(...)` перевірте `run.input_names()` і `run.output_names()` в активному `Run`. Імена мають відповідати публічній межі, яку ви збиралися відкрити.

## Вибір топології: вхід належить джерелу чи його надсилає застосунок

Кожен граф має відповідати на одне запитання: кому належать вхідні дані?

| Топологія | Використовуйте його, коли | Форма під час виконання |
| --- | --- | --- |
| Надсилає застосунок | У вашому застосунку вже є кадри, тензори або зразки | Додайте `nodes.input("name")`, потім надсилайте дані через `run.push("name", ...)` або використайте `Graph.run([...])`. |
| Належить джерелу | Граф має читати дані з файлу, камери, RTSP або іншого вузла-джерела | Додайте вузол-джерело або групу-джерело, потім збирайте/запускайте граф без надсилання вхідних даних із застосунку. |

Для графів, у які дані надсилає застосунок, називайте вхідну кінцеву точку за поняттям застосунку: `image`, `left_camera`, `metadata`, `prompt`. Для графів, вхід яких належить джерелу, перевірте вихідний контракт і отримуйте те, що видає шлях джерела.

## Вибір параметрів графа

Використовуйте [`GraphOptions`](/reference/{lsa}/structs/simaai-neat-graphoptions) для налаштування поведінки на рівні графа. Використовуйте `RunOptions` пізніше для налаштування поведінки під час виконання.

| Мета | Використовуйте | Примітки |
| --- | --- | --- |
| Позначити граф міткою в журналах і експортованих даних | `Graph("name")` | Це мітка, а не кінцева точка. |
| Запустити кілька графів в одному процесі | `element_name_prefix` / `element_name_suffix` | Уникайте конфліктів імен згенерованих елементів і забезпечте читабельність діагностичних даних. |
| Керування діагностикою графа | `VerboseOptions` | Почніть із продакшн-рівня виводу. Вмикайте детальніший налагоджувальний вивід лише тоді, коли збираєте докази. |
| Вибрати поведінку черги виходу | `OutputOptions::Latest()`, `EveryFrame(...)` або `Clocked(...)` | Обирайте: актуальність, повноту або доставку в узгоджений час. |
| З’єднати фрагменти графа реального часу | `GraphLinkOptions` з `RealtimeLatestByStream` | Підтримуйте актуальність кожного потоку й водночас обмежуйте допуск декодованих кадрів. |
| Обмежити тривалість роботи зворотного виклику | `callback_timeout_ms` | Використовуйте зі споживанням виходу через зворотні виклики в C++, щоб повільний зворотний виклик не маскувався під проблему графа. |
| Налаштувати розширені параметри виконання | `advanced_execution` | Використовуйте лише після того, як для графа з параметрами за замовчуванням буде виміряно базовий рівень. |
| Обмежити кількість потоків виконання обчислювальних ядер A65 | `kernel_runner_a65_workers` | За замовчуванням `2`; допустимі значення `1`–`64`. Стосується чисельних етапів A65 цього графа, а не EV74 чи MLA. |

<CodeTabs>
<CodeTab label="C++" lang="cpp">

```cpp
simaai::neat::GraphOptions options;
options.element_name_prefix = "cam0_";

simaai::neat::Graph graph("cam0_detector", options);
graph.add(simaai::neat::nodes::Input("image"));
graph.add(model);
graph.add(simaai::neat::nodes::Output(
    "detections",
    simaai::neat::OutputOptions::Latest()));
```

</CodeTab>
<CodeTab label="Python" lang="python">

```python
options = pyneat.GraphOptions()
options.element_name_prefix = "cam0_"

graph = pyneat.Graph("cam0_detector", options)
graph.add(pyneat.nodes.input("image"))
graph.add(model)
graph.add(pyneat.nodes.output(
    "detections",
    pyneat.OutputOptions.latest(),
))
```

</CodeTab>
</CodeTabs>

`Latest()` зберігає найновіший результат, коли застосунок не встигає отримувати кожен вихід. Використовуйте `EveryFrame(...)`, коли важливий кожен вихід. Використовуйте `Clocked(...)`, коли вихід має йти за годинником конвеєра.

`RunOptions::queue_depth` керує вхідними чергами графа та внутрішніми чергами середовища виконання. Він не замінює
контракт черги публічного `Output`: `OutputOptions::max_buffers` і `drop` керують
цією кінцевою чергою та мають пріоритет. Вихідні черги, створені фреймворком, використовують значення `RunOptions` за замовчуванням.

### Перекриття обробки кадрів без необмеженого зростання черг

Асинхронне подання дає змогу виконувати один кадр на пристрої, поки CPU готує або споживає інший. Зберіть граф один раз, використовуйте його повторно й тримайте в обробці обмежену кількість незалежних входів. Якщо одразу після надсилання отримувати його результат, доступним залишається лише один кадр, навіть коли граф підтримує асинхронне виконання.

Різні засоби керування мають різні завдання:

| Засіб керування | Що він обмежує |
| --- | --- |
| Вікно незавершених входів застосунку | Прийняті входи, результати яких застосунок ще не спожив. Керуйте цим вікном у циклі надсилання й отримання. |
| `advanced_execution.internal_queue_depth` | Внутрішньо вставлені черги та кількість слотів виконання чисельного Runner. Кількість слотів Runner обмежується діапазоном `1`–`64`; незадана глибина або глибина за замовчуванням вибирає 4 слоти для асинхронного виконання; синхронне виконання використовує 1 слот. |
| `advanced_execution.inference_output_buffers` | Буферизація етапу MLA. Зміна глибини черги застосунку або середовища виконання не замінює цей параметр. |
| `RunOptions::queue_depth` | Вхідні черги фреймворку та внутрішні черги середовища виконання, а не ресурс прискорювача. |
| `OutputOptions` | Буферизація публічного виходу та поведінка відкидання. Використовуйте `EveryFrame(...)`, коли вимірюєте завершену роботу без втрат. |

Асинхронне виконання MLA ввімкнене за замовчуванням. Залишайте його ввімкненим для вимірювань пропускної здатності; не додавайте потік синхронізації кешу й не вимикайте синхронізацію пам’яті заради перекриття. Завершення роботи пристрою та видимість для CPU — окремі вимоги. Середовище виконання зберігає обидві, дозволяючи незалежним кадрам просуватися паралельно.

Налаштовуйте по одному навантаженню:

1. Після побудови й прогрівання графа виміряйте один кадр в обробці як послідовну базову лінію.
2. Збільшуйте вікно застосунку по одному кроку. Для одночасних кадрів надавайте окремі доступні для запису вхідні виділення пам’яті та своєчасно звільняйте виходи.
3. Збільшуйте внутрішню буферизацію або буферизацію MLA лише тоді, коли її поточна межа заважає корисному перекриттю. Утримуваний вихід без копіювання все ще займає пул свого виробника; розмір пулу не гарантує, що кожний слот доступний застосунку.
4. Припиніть збільшувати вікно, коли пропускна здатність перестане зростати. Додаткові кадри в черзі можуть збільшити затримку та обсяг утримуваної пам’яті без додаткової роботи.

Не перезаписуйте вхідне виділення пам’яті, поки прийнята робота ще може його читати. Повторне використання незмінного входу відрізняється від повторного використання його сховища для наступного кадру камери. В обох випадках дотримуйтеся наявного контракту володіння.

Порівнюйте **час CPU на завершений кадр**, а не лише відсоток використання CPU. Для того самого вікна вимірювання поділіть суму користувацького й системного часу CPU процесу на кількість завершених виходів; поділіть цей час CPU на минулий реальний час, щоб отримати середню кількість зайнятих ядер CPU. Вища пропускна здатність може використовувати більше ядер у часі без збільшення роботи CPU на кадр. Виключайте підготовку, прогрівання та завершення; у кожному порівнянні враховуйте однакову роботу з отримання й звільнення виходів. Затримку кадру звітуйте окремо: `1 / FPS` — це інтервал пропускної здатності, а не затримка окремого кадру. Час CPU процесу не охоплює роботу, нараховану окремим робочим потокам ядра ОС, і не вимірює енергію.

### Налаштування бюджету робочих потоків A65

Задайте `GraphOptions.kernel_runner_a65_workers` перед збіркою графа. Значення за замовчуванням — `2`; використовуйте `1`, щоб обмежити чисельне виконання A65 одним робочим потоком, або збільшуйте бюджет, коли незалежні етапи A65 можуть перекриватися. Недопустимі значення спричиняють помилку під час підготовки графа, а не мовчазне обмеження.

<CodeTabs>
<CodeTab label="C++" lang="cpp">

```cpp
simaai::neat::GraphOptions options;
options.kernel_runner_a65_workers = 2;
simaai::neat::Graph graph("camera", options);
```

</CodeTab>
<CodeTab label="Python" lang="python">

```python
options = pyneat.GraphOptions()
options.kernel_runner_a65_workers = 2
graph = pyneat.Graph("camera", options)
```

</CodeTab>
</CodeTabs>

Пул робочих потоків спільний для етапів обчислювальних ядер A65 цього графа й створюється лише за потреби. Неактивні робочі потоки сплять без опитування; вони повторно використовуються між поданнями. Цей параметр не змінює глибину черги кадрів, не перевизначає обмеження ресурсів ядер і не налаштовує потоки EV74, MLA чи GStreamer. Більше робочих потоків не обов’язково означає швидше виконання: перш ніж змінювати значення за замовчуванням, порівняйте затримку, пропускну здатність і використання CPU для свого навантаження.

## Перевірка перед збіркою

Використовуйте `graph.validate(...)`, коли вам потрібні дані для підтвердження побудови графа, не запускаючи при цьому повноцінний процес.

<CodeTabs>
<CodeTab label="C++" lang="cpp">

```cpp
simaai::neat::GraphReport report = graph.validate();
std::cout << report.to_json() << "\n";
```

</CodeTab>
<CodeTab label="Python" lang="python">

```python
report = graph.validate()
print(report.to_json())
```

</CodeTab>
</CodeTabs>

`ValidateOptions.parse_launch` перевіряє згенерований рядок конвеєра. `ValidateOptions.enforce_names` виявляє елементи, які не мають назви або є несподіваними. Перегляньте звіт перед зміною параметрів графа; спочатку перевірте дані, а потім налаштовуйте параметри.

## Створення графів

### Спрощене уявлення

Щоб створити застосунок, спочатку оголосіть `Graph`, потім використовуйте `add()` для лінійного ланцюга або `connect()` для визначення конкретної топології:

- Використовуйте `add()` для типової обробки за одним шляхом, наприклад простого інференсу з однією моделлю.
- Використовуйте `connect()`, коли вам потрібен чіткий контроль над тим, як з’єднуються вузли або фрагменти.

```cpp
simaai::neat::Graph g;
g.add(...);      // continue the same linear chain
g.connect(...);  // add explicit graph topology

auto run = g.build();
```

### Збірка за допомогою `add()`

Наведений нижче приклад зчитує зображення, виконує інференс і виводить передбачені класи, отримані з моделі.

```text
image -> model inference -> classes
```

Ось як виглядатиме код:

```cpp
simaai::neat::Model model("resnet50.tar.gz");  // Load a compiled model and prepare its Graph route.

simaai::neat::Graph g("classifier");           // instantiate the Graph that will describe the app
g.add(simaai::neat::nodes::Input("image"));    // adds an input Node named "image"
g.add(model);                                  // adds the model Nodes connected to the Input
g.add(simaai::neat::nodes::Output("classes")); // adds an output Node named "classes" connected to 'model'

auto run = g.build();                          // build the Graph
```

:::note
Використовуйте `add()`, щоб додавати вузли в просту лінійну послідовність, слідуючи за попередньо доданим вузлом.
:::

### Збірка за допомогою `connect()`

Використовуйте `connect()`, коли вам потрібен явний контроль над топологією. Кожна команда `add()` спочатку з’єднує новий вузол або фрагмент після попереднього. Коли ви використовуєте обидва методи, `connect()` замінює відповідні неявні з’єднання на конкретні з’єднання, які ви визначаєте. Ви також можете використовувати `connect()` безпосередньо між іменованими кінцевими точками, вузлами, моделями або фрагментами графа, які можна повторно використовувати.

#### Розгалуження за допомогою `connect()`

Розгалуження (fan-out) надсилає один вхід на кілька виходів. Спочатку додайте кінцеві точки, щоб вони існували в графі:

```cpp
simaai::neat::Graph fan_out_graph("fan_out_graph");
fan_out_graph.add(simaai::neat::nodes::Input("image_input"));
fan_out_graph.add(simaai::neat::nodes::Output("original_image"));
fan_out_graph.add(simaai::neat::nodes::Output("model_image"));
```

Концептуально `fan_out_graph` виглядатиме так:

```text
image_input --> original_image --> model_image
```

Потім використайте `connect()`, щоб замінити лінійну схему з’єднань за замовчуванням на потрібну вам топологію:

```cpp
fan_out_graph.connect("image_input", "original_image");
fan_out_graph.connect("image_input", "model_image");
```

Концептуально `fan_out_graph` тепер матиме такий вигляд:

```text
            /--> original_image
image_input
            \--> model_image
```

#### Використання `Branch()`

Оскільки розгалуження є поширеним явищем, Neat надає [`graphs::Branch()`](/reference/{lsa}/namespaces/simaai-neat-graphs#a1feffc304100fd17cb99c5f5bff3c20c) як допоміжний інструмент. Це створює вхід, виходи та внутрішні виклики `connect()`:

```cpp
auto fan_out_graph = simaai::neat::graphs::Branch(
    "image_input",
    {"original_image", "model_image"});
```

У Python використовуються ті самі назви кінцевих точок:

```python
fan_out_graph = pyneat.graphs.branch(
    "image_input",
    ["original_image", "model_image"],
)
```

`fan_out_graph` все ще є звичайним фрагментом `Graph`. Його можна під’єднати до більшого застосунку, як і будь-який інший `Graph`.

:::note
Розгалуження може спричинити зворотний тиск. Якщо одна з гілок припиняє обробку даних, це може уповільнити або заблокувати роботу виробника, залежно від обраної політики в середовищі виконання. `Branch()` робить процес розгалуження явним, замість того щоб приховувати його за допомогою випадкових дублікатів виходів.
:::

#### Зведення (fan-in) за допомогою `connect()`

Зведення (fan-in) надсилає кілька входів на один вихід. На відміну від простого розгалуження (fan-out), зведення має також визначати, як зіставляються зразки. Ця політика застосовується до вихідної кінцевої точки.

Спочатку налаштуйте вихід і додайте кінцеві точки, щоб вони існували в графі:

```cpp
simaai::neat::OutputOptions render_options;
render_options.combine_policy = simaai::neat::CombinePolicy::ByFrame;

simaai::neat::Graph render_inputs_graph("render_inputs_graph");
render_inputs_graph.add(simaai::neat::nodes::Input("image"));
render_inputs_graph.add(simaai::neat::nodes::Input("bbox"));
render_inputs_graph.add(simaai::neat::nodes::Output("render_inputs", render_options));
```

Концептуально `render_inputs_graph` виглядатиме так:

```text
image -> bbox -> render_inputs
```

Потім використайте `connect()`, щоб замінити лінійну схему з’єднань за замовчуванням на потрібну вам топологію:

```cpp
render_inputs_graph.connect("image", "render_inputs");
render_inputs_graph.connect("bbox", "render_inputs");
```

Концептуально `render_inputs_graph` тепер виглядатиме так:

```text
image ----\
           render_inputs
bbox -----/
```

#### Використання `Combine()`

Оскільки зведення (fan-in) поширене, Neat надає [`graphs::Combine()`](/reference/{lsa}/namespaces/simaai-neat-graphs#a6f1479674758179a4bbd72af1291ea47) як допоміжний інструмент. Це створює входи, вихід, політику об’єднання та внутрішні виклики `connect()`:

```cpp
auto render_inputs_graph = simaai::neat::graphs::Combine(
    {"image", "bbox"},
    "render_inputs",
    simaai::neat::CombinePolicy::ByFrame);
```

У Python використовується `None_` для політики, яка забороняє об’єднання, оскільки `None` є зарезервованим словом:

```python
render_inputs_graph = pyneat.graphs.combine(
    ["image", "bbox"],
    "render_inputs",
    pyneat.CombinePolicy.ByFrame,
)
```

`render_inputs_graph` все ще є звичайним фрагментом `Graph`. Ви можете під’єднати його до більшого застосунку, як і будь-який інший `Graph`.

`graphs::Combine()` створює свій вихід з `OutputOptions` за замовчуванням: чотири зразки в черзі, блокування в разі переповнення, без синхронізації з годинником. Якщо цей вихід лишається публічним кінцевим виходом, спорожнюйте його паралельно з надходженням даних. Якщо скінченну партію потрібно надіслати до того, як її отримувати, зберіть явне зведення (fan-in), показане вище, і налаштуйте його вихід через `OutputOptions::EveryFrame(...)` з розміром під цю партію.
У Python використовуйте `pyneat.OutputOptions.every_frame(...)`.

:::note
`CombinePolicy` визначає, як Neat має зіставляти вхідні зразки:

- `ByFrame`: об’єднує зразки з однаковим `frame_id`.
- `ByPts`: об’єднує зразки з однаковою міткою часу відображення (`pts_ns`).
- `None`: не об’єднує декілька джерел даних; у такому разі граф не працюватиме і вимагатиме чітко визначеної політики.
- Стиль написання коду на Python: `pyneat.CombinePolicy.None_`, `ByFrame` або `ByPts`.

Прихованого запасного варіанта немає. З `ByFrame` відсутні ідентифікатори кадрів є помилкою. З `ByPts` відсутні мітки часу є помилкою. Так Neat не зможе непомітно об’єднати не ті зразки.
:::

### Повний приклад розгалуження та злиття

Тепер з’єднайте всі частини докупи. Вхідне зображення поділяється на два потоки. Один потік проходить через модель і генерує обмежувальні рамки. Інший потік зберігає оригінальне зображення, щоб воно було доступне на пізнішому етапі рендерингу.

```text
           /--> model_image -> model -> bbox --\
image_input                                     render_inputs
           \----------------> original_image --/
```

Загалом, дотримуйтеся таких кроків:

1. Спочатку оголосіть фрагмент вхідного графа розгалуження `Graph`
2. Створіть фрагмент `Graph` для інференсу моделі, який споживає `model_image` і видає `bbox`
3. Об’єднайте шлях оригінального зображення та шлях `bbox` у `render_inputs`
4. З’єднайте їх усі разом, щоб створити остаточний `Graph`, який називатиметься `app`

#### Створення прикладу з розгалуженням і злиттям

1. Спочатку створіть розгалужену структуру, використовуючи `Branch()`, як показано вище:

    ```cpp
    auto image_input_graph = simaai::neat::graphs::Branch(
        "image_input",
        {"model_image", "original_image"});
    ```

    `image_input_graph` буде побудовано так:

    ```text
                /--> original_image
    image_input
                \--> model_image
    ```

2. Створіть `model_inference_graph`:

    ```cpp
    simaai::neat::Graph model_inference_graph("model_inference_graph");
    model_inference_graph.add(simaai::neat::nodes::Input("model_image"));
    model_inference_graph.add(model);
    model_inference_graph.add(simaai::neat::nodes::Output("bbox"));
    ```

    `model_inference_graph` буде побудовано так:

    ```text
    model_image --> model --> bbox
    ```

    :::note
    У цьому прикладі передбачається, що обраний маршрут моделі видає декодовані дані BBOX. Якщо модель видає сирі тензори інференсу, додайте специфічний для моделі етап `SimaBoxDecode` перед `Output("bbox")`.
    :::

3. Потім створіть зведення (fan-in) `render_graph`:

    ```cpp
    auto render_graph = simaai::neat::graphs::Combine(
        {"original_image", "bbox"},
        "render_inputs",
        simaai::neat::CombinePolicy::ByFrame);
    ```

    `render_graph` буде побудовано так:

    ```text
    original_image ----\
                        render_inputs
    bbox --------------/
    ```

4. Насамкінець об’єднайте фрагменти в єдиний `Graph`, щоб створити цілісний застосунок:

    ```cpp
    simaai::neat::Graph app("app");
    app.connect(image_input_graph, model_inference_graph);
    app.connect(image_input_graph, render_graph);
    app.connect(model_inference_graph, render_graph);
    ```

**Повний приклад:**

```cpp
simaai::neat::Model model("yolov8s_model.tar.gz");

auto image_input_graph = simaai::neat::graphs::Branch(
    "image_input",
    {"model_image", "original_image"});

simaai::neat::Graph model_inference_graph("model_inference_graph");
model_inference_graph.add(simaai::neat::nodes::Input("model_image"));
model_inference_graph.add(model);
model_inference_graph.add(simaai::neat::nodes::Output("bbox"));

auto render_graph = simaai::neat::graphs::Combine(
    {"original_image", "bbox"},
    "render_inputs",
    simaai::neat::CombinePolicy::ByFrame);

simaai::neat::Graph app("app");
app.connect(image_input_graph, model_inference_graph);
app.connect(image_input_graph, render_graph);
app.connect(model_inference_graph, render_graph);

auto run = app.build();

auto image_sample =
    simaai::neat::make_tensor_sample("image_input", image_tensor);
image_sample.frame_id = 0;
run.push("image_input", image_sample);

auto inputs = run.pull("render_inputs");
```

Виконуваний приклад зупиняється на `render_inputs`, що містить відповідні значення `original_image` і `bbox`. Наступний вузол рендерингу або виходу може спожити цей об’єднаний результат, а потім зберегти відрендерене зображення у файл, показати його або надіслати деінде.

## Використання іменованих кінцевих точок під час виконання

Після збірки `Graph` ті самі імена кінцевих точок використовуються для надсилання даних і отримання результатів.

Якщо граф має кілька публічних входів або виходів, передайте ім’я кінцевої точки до `push()` або `pull()`:

```cpp
run.push("image", simaai::neat::TensorList{image_tensor});
run.push("metadata", simaai::neat::TensorList{metadata_tensor});

auto classes = run.pull("classes");
auto preview = run.pull("preview");
```

Для графа, який має рівно один публічний вхід або вихід, назва є необов’язковою під час виконання:

```cpp
run.push(simaai::neat::TensorList{image_tensor});
auto classes = run.pull();
```

Якщо доступно більше одного входу чи виходу, виклик `push(...)` або `pull()` без імені завершується помилкою й перелічує доступні імена кінцевих точок, а не вгадує, яку саме ви мали на увазі.

## З’єднання фрагментів реального часу

Використовуйте [`GraphLinkOptions`](/reference/{lsa}/structs/simaai-neat-graphlinkoptions), коли для з’єднання потрібна політика середовища виконання або чіткі обмеження на обробку необроблених кадрів.

Для потокового об’єднання кількох потоків у реальному часі, `RealtimeLatestByStream` зберігає останній зразок для кожного `Sample::stream_id` і справедливо розподіляє готові потоки далі по ланцюжку. Якщо джерело не мітить `stream_id`, позначте стабільний ідентифікатор у з’єднанні. Потокове об’єднання кількох потоків із політикою за замовчуванням автоматично перемикається на режим «останній зразок для кожного потоку».

<CodeTabs>
<CodeTab label="C++" lang="cpp">

```cpp
simaai::neat::GraphLinkOptions link;
link.policy = simaai::neat::GraphLinkPolicy::RealtimeLatestByStream;
link.queue_depth = 4;
link.stream_id = "camera-0";
link.max_inflight_per_stream = 4;
link.max_inflight_total = 8;

app.connect(camera_fragment, detector_fragment, link);
```

</CodeTab>
<CodeTab label="Python" lang="python">

```python
link = pyneat.GraphLinkOptions()
link.policy = pyneat.GraphLinkPolicy.RealtimeLatestByStream
link.queue_depth = 4
link.stream_id = "camera-0"
link.max_inflight_per_stream = 4
link.max_inflight_total = 8

app.connect(camera_fragment, detector_fragment, link)
```

</CodeTab>
</CodeTabs>

`RealtimeLatestByStream` завжди зберігає для кожного потоку один зразок, що очікує обробки. `queue_depth` залишається в `GraphLinkOptions` для сумісності на рівні вихідного коду й зарезервоване для цієї політики; його зміна не збільшує межу в один слот.

Зберіть граф реального часу з великою кількістю каналів за допомогою звичайного API `build()`:

```cpp
auto run = app.build(run_options);
```

```python
run = app.build(run_options)
```

Fusion (злиття) — це внутрішнє рішення компілятора, а не режим збірки. Звичайний `build()` залишає придатні приватні гілки джерел, їхній мультиплексор реального часу та споживача-модель в одному конвеєрі GStreamer і так уникає передавання пам’яті пристрою через appsink/appsrc. Топологія latest-by-stream, непридатна для злиття, використовує звичайне сегментоване середовище виконання.

Задайте `graph_options.advanced_execution.internal_queue_depth` на графі верхнього рівня, щоб етапи моделі виконувалися з перекриттям. Додатне значення вставляє обмежені глобальні черги без відкидання (non-leaky) перед етапами CVU, MLA і декодування, але не перед кінцевим виходом. `GraphLinkOptions::max_inflight_per_stream` передається до злитого мультиплексора для кожного з’єднання, тож його можна лишити на `1` заради актуальності без приватного перемикача у змінних середовища. Залиште `internal_queue_depth` незаданим або встановіть `0`, щоб зберегти шлях споживача з одним ланцюгом.

І C++, і Python надають ці поля в `GraphLinkOptions`, який передається звичайному `connect(...)`. Окремий метод з’єднання в реальному часі чи окремий режим збірки не потрібні.

| Поле | Використовуйте його, коли |
| --- | --- |
| `policy` | Для кожного потоку потрібне оновлення даних у режимі реального часу. |
| `queue_depth` | Поле сумісності. `RealtimeLatestByStream` резервує його та завжди зберігає один незавершений зразок для кожного потоку. |
| `stream_id` | Попередній (upstream) фрагмент не проставляє `Sample::stream_id`, але це з’єднання представляє один стабільний потік. |
| `max_inflight_per_stream` | З’єднання realtime-by-stream передає сирі зразки з буферів декодера й потребує явного обмеження допуску для кожного потоку. Значення поля за замовчуванням — `-1`; Core використовує `4`. Під час пониження (lowering) злитого джерела обчислене значення застосовується до відповідного потоку мультиплексора. |
| `max_inflight_total` | Для з’єднання в режимі реального часу для кожного окремого потоку необхідне жорстке глобальне обмеження для всіх потоків. Значення поля за замовчуванням — `-1`; якщо не вказано інше значення в змінних середовища, Core визначає `min(max_inflight_per_stream * stream_count, 8)`. |

:::caution Оновлення застосунків і збережених графів із preview-версії

Поля допуску в `GraphLinkOptions` є частиною його публічного розміщення в пам’яті (layout) у C++. Поточна версія C++ ABI та SONAME спільної бібліотеки Neat Library — 7. Перезберіть застосунки C++ і плагіни з відповідним пакетом Core. Не змішуйте бінарні файли, зібрані для попереднього SONAME `libsima_neat`, з `libsima_neat.so.7`.

Перенесіть вихідний код preview-версії таким чином:

| API preview-версії | Поточний API |
| --- | --- |
| `RealtimeGraphLinkOptions` | `GraphLinkOptions` |
| `graph.connect_realtime(from, to, link)` | `graph.connect(from, to, link)` |
| `graph.build_fused_realtime_sources(options)` (C++) | `graph.build(options)` |
| `graph.build_fused_realtime_source(options)` (Python) | `graph.build(options)` |
| `RealtimeEveryFrameByStream` | `RealtimeLatestByStream`, коли допустимі оновлення та заміна даних. |

`RealtimeLatestByStream` — це політика актуальності, а не заміна без втрат для `RealtimeEveryFrameByStream`. Вона зберігає для кожного потоку один зразок, що очікує обробки, і замінює його, коли надходить новіший кадр.

`Graph::load()` відхиляє збережений JSON, який містить `"link_policy": "realtime_every_frame_by_stream"`. Відтворіть граф на основі оновленого джерела. Якщо JSON є єдиним джерелом, змінюйте політику на `realtime_latest_by_stream` лише тоді, коли допустимо відкидати застарілі кадри, після чого знову завантажте та збережіть його з цією версією.

:::


## Масштабування від одного потоку до багатьох

Багатопотоковий граф потребує ідентифікації, перш ніж його можна буде налаштувати. Збережіть `stream_id` та `frame_id`, щоб показники середовища виконання, політики об’єднання та звіти про відкидання могли розрізняти один потік від іншого.

| Шаблон | Використовуйте, коли | На що зважати |
| --- | --- | --- |
| Один потік даних -> одна модель -> один результат | Ви доводите, що граф працює | Форма вихідних даних, тип даних і назви кінцевих точок. |
| Багато потоків -> одна лінія моделі | Загальна швидкість подачі даних відповідає одному шляху моделі | Справедливий розподіл ресурсів між окремими потоками та обробка застарілих потоків. |
| Багато потоків -> кілька ліній моделі | Один шлях моделі не встигає | Розподіл потоків, іменування маршрутів і облік виходів. |
| Один потік -> декілька моделей | Різним рішенням потрібен той самий вхід | Затримка на рівні гілки та FPS, нормалізований за цільовими виходами. |
| Багато потоків -> модель + виходи метаданих/відео | Робочий застосунок видає кілька артефактів | Підраховуйте кількість цільових результатів окремо від попереднього перегляду або даних телеметрії. |

Використовуйте `OutputOptions::Latest()` для виведення даних у реальному часі, коли важлива актуальність. Використовуйте `EveryFrame(...)` для виведення даних в автономному режимі або без втрат. Для зведення (fan-in) використовуйте `CombinePolicy::ByFrame` лише тоді, коли `frame_id` присутній у кожному вхідному потоці, а `CombinePolicy::ByPts` — лише тоді, коли присутні мітки часу.

Якщо вам потрібні черги середовища виконання, політика відкидання, вимірювання або поведінка спорожнення, перейдіть на сторінку [Запуск графа](/develop-apps/development-workflow/pipeline). У `Graph` ви описуєте топологію, а в `Run` нею керуєте.

## Практичні приклади

### Маршрут моделі, який можна повторно використовувати

```cpp
simaai::neat::Graph make_classifier(simaai::neat::Model& model) {
  simaai::neat::Graph classifier_route("classifier");           // create a reusable Graph fragment
  classifier_route.add(simaai::neat::nodes::Input("image"));    // declare the fragment's input
  classifier_route.add(model);                                  // add the model inference route
  classifier_route.add(simaai::neat::nodes::Output("classes")); // declare the fragment's output
  return classifier_route;                                      // return the fragment for reuse
}
```

Використовуйте окремо:

```cpp
auto classifier_route = make_classifier(model);      // create the classifier fragment
auto run = classifier_route.build();                 // build it as a standalone application
run.push("image", simaai::neat::TensorList{image});  // send data to its named input
auto classes = run.pull("classes");                  // read from its named output
```

Використовуйте всередині більшого застосунку:

```cpp
simaai::neat::Graph app("app");            // create the larger application Graph
app.connect(camera, classifier_route);     // connect the camera fragment to the classifier
app.connect(classifier_route, telemetry);  // forward classification results to telemetry
```

У більшому застосунку граничні вузли маршруту класифікатора є внутрішніми оголошеннями. Вони не стають додатковими публічними кінцевими точками для push/pull, якщо тільки не залишаються на зовнішній межі остаточного графа.

### Перехідник для прямого з’єднання

Іноді фрагмент просто перейменовує межу:

```cpp
simaai::neat::Graph adapter("adapter");            // create a reusable adapter fragment
adapter.add(simaai::neat::nodes::Input("raw"));    // declare the incoming endpoint name
adapter.add(simaai::neat::nodes::Output("image")); // declare the outgoing endpoint name
adapter.connect("raw", "image");                   // pass data directly between the endpoints
```

Коли цей елемент використовується всередині іншого графа, його можна звести до прямого з’єднання. Neat зберігає імена для зручності читання та діагностики, але не створює непотрібної роботи в середовищі виконання.

## Розширені інструменти для роботи з графами

Використовуйте їх, коли базовий варіант роботи з графом уже працює. Це довідкові інструменти, а не перший шлях знайомства з API.

| Інструмент | Мова | Використовуйте його, коли |
| --- | --- | --- |
| `add_output_tensor(...)` | C++ і Python | Удосконалений адаптер: вихід зображення або відео перед отриманням має бути перетворено на тензор `UInt8`, який легко обробляється центральним процесором (CPU), із зазначеним форматом, розміром або частотою кадрів. |
| `Graph::save(...)` / `Graph::load(...)`; Python `graph.save(...)` / `pyneat.Graph.load(...)` | C++ і Python | Ви хочете зберегти та повторно завантажити структуру графа. |
| `graph.custom(...)` | C++ і Python | Вам потрібно вставити фрагмент бекенду в лінійний граф. |
| `nodes::Custom(...)` / `pyneat.nodes.custom(...)` | C++ і Python | Вам потрібен спеціальний вузол у межах чітко визначеної топології. |
| `run_rtsp(...)` | C++ і Python | Граф має забезпечувати виведення даних у форматі H.264 через протокол RTSP. |
| `set_tensor_callback(...)` | C++ | Код на C++ потребує використання тензорів на основі зворотних викликів замість циклу отримання. Використовуйте разом із `GraphOptions.callback_timeout_ms`, коли важлива затримка зворотного виклику. |

Насамперед використовуйте публічні вузли та групи. Застосовуйте низькорівневі власні фрагменти лише тоді, коли для виконання завдання не існує стабільного вузла.

### Збереження й повторне завантаження визначень графа

Зберігайте граф, коли потрібно передати скомпоноване визначення іншому інструменту, зберегти артефакт CI або порівняти побудову графа між змінами. Завантажуйте його, коли збережене визначення є джерелом істини для запуску.

<CodeTabs>
<CodeTab label="C++" lang="cpp">

```cpp
graph.save("classifier.neat.json");

simaai::neat::Graph loaded = simaai::neat::Graph::load("classifier.neat.json");
auto run = loaded.build();
```

</CodeTab>
<CodeTab label="Python" lang="python">

```python
graph.save("classifier.neat.json")

loaded = pyneat.Graph.load("classifier.neat.json")
run = loaded.build()
```

</CodeTab>
</CodeTabs>

Розглядайте збережені файли графів як артефакти збірки, якщо тільки ваш застосунок свідомо не версіонує їх. Вони фіксують композицію графа, але не замінюють контракти моделі, вхідні дані чи вимірювання під час виконання.

## Найкращі практики

### Найменування кінцевих точок

Обирайте назви кінцевих точок, які відображають їхнє призначення в застосунку:

```cpp
nodes::Input("image");          // describes the data entering the Graph
nodes::Input("left_camera");    // identifies the input's application role
nodes::Output("classes");       // describes a classification result
nodes::Output("detections");    // describes a detection result
nodes::Output("preview");       // describes the output's intended use
```

Уникайте імен, що базуються на внутрішніх деталях середовища виконання:

```cpp
nodes::Input("appsrc0");  // exposes an internal GStreamer implementation detail
nodes::Output("sink1");   // describes runtime wiring instead of application meaning
nodes::Output("out");     // acceptable for small tests, but unclear in applications
```

Якщо фрагмент містить кілька виходів без імен, Neat призначає їм детерміновані суфікси, такі як `classes_0`, `classes_1` і `classes_2`. У коді застосунку краще використовувати явні імена.

### Загальні правила, практичні поради

- Використовуйте `Graph` для застосунків і повторно використовуваних фрагментів.
- Використовуйте `Model` безпосередньо в `Graph::add(model)`, коли вам потрібен стандартний маршрут моделі.
- Використовуйте іменовані вузли `Input` та `Output`, щоб оголосити публічний інтерфейс фрагмента.
- Використовуйте `add()` для створення прямої послідовності.
- Використовуйте `connect()` для явного визначення топології та композиції фрагментів.
- Використовуйте іменовані виклики `run.push("name", ...)` та `run.pull("name")` для застосунків із кількома входами або виходами.
- Оголосіть параметри, з’єднання та [вузли](/develop-apps/development-workflow/node), [групи вузлів](/develop-apps/development-workflow/node#pre-built-node-groups), необхідні для вашого застосунку; дозвольте Neat обробляти деталі низькорівневого середовища виконання.
