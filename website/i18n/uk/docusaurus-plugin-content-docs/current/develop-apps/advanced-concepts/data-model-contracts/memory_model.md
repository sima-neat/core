# Модель пам’яті.

У Neat фреймворку середовище виконання обробляє велику кількість байтів — закодовані відеокадри, декодовані площини YUV, вхідні тензори FP32, квантовані тайли INT8, зображення для тимчасового зберігання MLA. Виконання цього без чітко визначеної моделі пам’яті означало б копіювання на кожному етапі. На цій сторінці пояснюється, як фреймворк уникає цих копіювань.

## Трійка буферів: `(buffer_id, paddr, vaddr)`

Кожен буфер, з яким працює фреймворк, ідентифікується за трьома параметрами:

- **`buffer_id`** — стабільне ціле число, яке використовується середовищем виконання для відстеження життєвого циклу буфера (кількість посилань, власність сегмента).
- **`paddr`** — фізична адреса, яка використовується IOMMU для буфера. Апаратне забезпечення MLA / EV74 / DMA використовує цю адресу.
- **`vaddr`** — віртуальна адреса, область пам’яті, доступна для програми. Процесор використовує цю адресу для доступу до даних.

Завдяки використанню потрійного буфера, до нього можна отримати доступ з будь-якої сторони (ЦП або прискорювач) без копіювання даних. Єдиний блок пам’яті з’являється *в обох* таблицях сторінок ядра (щоб програмне забезпечення могло його зчитувати) і таблицях сторінок IOMMU (щоб апаратне забезпечення могло здійснювати прямий доступ до пам’яті).

Під час передачі даних між етапами передається саме потрійний буфер, а не окремі байти.

## Сегменти

Буфери створюються з іменованих **сегментів**. Сегмент — це суміжний регіон пам’яті, який підтримується певним алокатором (DMA-BUF, CMA, ION, звичайна купа) і містить метадані про те, хто має до нього доступ: лише ЦП, лише MLA, обидва, тощо. Під час виконання (runtime) обирається відповідний сегмент для кожного буфера, виходячи з того, які етапи обробки даних використовуватимуть його.

Приклади:

- `nv12_decode` сегмент містить декодований YUV-потік із H.264, який може бути зчитаний процесором для діагностичних цілей і зчитаний IOMMU для вузла зміни розміру.
- `mla_input` сегмент містить тесельований тензор, який передається в MLA — лише апаратне забезпечення MLA зчитує його; для доступу з боку ЦП потрібне явне відображення.
- Сегмент `model_output` містить тензори FP32 після детеселяції — вони доступні для читання процесором, тому застосунок може їх отримати.

`Tensor` містить свій сегмент разом із потрійною структурою, тому фреймворк знає, чи є допустимим доступ до даних/зміна даних із коду, що виконується на ЦП.

Для щільного числового `Tensor` із прив’язаним сховищем форма `{}` означає скаляр рангу нуль: щільний розмір дорівнює одному елементу `dtype`. Це відрізняється від форми з нульовою довжиною виміру, наприклад `{0,256}`, щільний розмір якої дорівнює нулю. Щільне копіювання байтів і `clone()` зберігають значення скаляра, перевіряючи зміщення подання та межі сховища. Для стандартного Tensor без сховища `dense_bytes_tight()` повертає нуль; щільне копіювання та клонування відхиляються. Носії, явно позначені як кодовані, байтові потоки, тесельовані або текстові, зберігають свою семантику байтів носія. Діапазон байтів, який повертає публічний `map()`, не змінюється.

## Узгодженість кешу

Scheduler готує доступ CPU/пристрою через спільного власника пам’яті Runner. Runner керує ідентичністю виділення, утриманням DMA-BUF, взаємним виключенням CPU/пристрою, перевіреними діапазонами та видимістю на основі поколінь. MLA та EV публікують завершені записи пристрою без завчасної епохи CPU READ. Потрібне обслуговування кешу READ виконується, коли відображення CPU або робітник A65 отримує перевірений доступ, **до читання**, а не під час зняття відображення чи у зворотних викликах завершення бекенду. Наступні етапи лише на пристроях не виконують роботи для видимості CPU; незалежні кадри й далі можуть перекриватися.

Викликаючи [`TensorBuffer::map()`](/reference/cppapi/structs/simaai-neat-tensorbuffer), використовуйте `Mapping` із відповідним [`MapMode`](/reference/cppapi/namespaces/simaai-neat). Відображення Tensor утримує захисний об’єкт відображення й поточне сховище/позику виробника до завершення доступу CPU. Необхідна синхронізація END, зокрема очищення записів, завершується до звільнення цих власників. Часткові записи зберігають сусідні байти кеш-лінії. Невдала синхронізація ізолює відповідне виділення, а не повертає його до звичайного повторного використання.

Кожне публічне відображення DMA утримує власну оренду Scheduler. Сумісні читання спільно використовують повноваження доступу Runner, включно з поданнями, що перекриваються; записи залишаються виключеними. Віртуальні адреси різних відображень не обов’язково однакові. Звільнення одного читача не може зробити іншого недійсним, і лише останній власник виконує потрібний перехід END.

Власна кешована CMA потребує холодного допуску платформи й експортера; помилка потребує дій, а не дозволяє резервний перехід до синхронізації всього буфера. Імпортовані DMA-BUF та інші купи зберігають контракт експортера через той самий механізм володіння.

Приватні рецепти лише для A65 можуть утримувати явний батьківський пакет; дочірні елементи потребують чинної батьківської можливості, точних дозволів і покриття діапазонів. Остаточне звільнення батька очищає записи після завершення всіх дочірніх елементів. Змішані фази пристроїв не отримують неявного членства в пакеті. Прихованої проміжної копії не додається. Записувачі через сирі FD і власні зворотні виклики все ще мають дотримуватися контракту володіння; видалення списку дозволених графів не доводить безпечності невідстежуваного доступу.

Межі транспорту зберігають ідентичність базового виділення, перевірені зсуви й довжини та початкове володіння буфером пулу. Оболонки лише з метаданими спільно використовують пам’ять і утримують батьківський буфер пулу. Імпорти EV/CVU та MLA утримують виробника до завершення. Невідоме завершення не дозволяє повторно використовувати потенційно активне сховище.

## Реалізація концепції «нульового копіювання» на практиці.

Типовий конвеєр для здійснення висновків:

```
file → demux → H.264 decode → resize → preproc → MLA → postproc → app
```

Без використання механізму «нульового копіювання» потрібно сім копій. Завдяки використанню потрійного буфера та сегментів, їх кількість зводиться до нуля — на кожному етапі передається `(buffer_id, paddr, vaddr)`, і наступний етап працює безпосередньо з цими даними.

Планувальник у рамках системи відповідає за вибір сегментів таким чином, щоб послідовні етапи могли використовувати спільні дані. Якщо два сусідні етапи мають несумісні вимоги до сегментів, планувальник вставляє `Transfer` `ConversionKind` і фіксує це в активному `ConversionTraceCollector`. Зверніть увагу на це — це єдині місця, де фактично відбувається переміщення байтів у середовищі виконання.

## Джерела зображень для камери та адаптивна пам’ять.

Кадри з камери в реальному часі надходять через стек камери платформи. `libcamerasrc` захоплює кожен кадр у власний DMA-BUF, і Neat ніколи не володіє цією пам’яттю: будь-який фізично неперервний DMA-BUF є допустимим входом EV74, і перевірка допуску EV74 у Neat приймає його, якщо він походить із купи CMA або з неперервного розподільника буферів захоплення камери (`videobuf2_dma_contig`). Приватний міст `CameraInput` запитує в джерела `GstVideoMeta` через `GST_QUERY_ALLOCATION` і передає DMA-BUF кожного кадру як єдину пам’ять наступним етапам CVU/MLA, утримуючи буфер камери, доки вони його не звільнять.

Коли кадр не є одним DMA-BUF із площинами, розташованими впритул одна за одною, і ввімкнено `allow_cpu_fallback`, міст копіює його в CMA DMA-BUF, додає очікувані метадані та передає цей буфер для попередньої обробки CVU, керованої моделлю. Ця копія є мостом сумісності; зміна розміру, перетворення кольору, нормалізація, квантування та теселяція все ще повинні виконуватися на CVU/EV74.

Не додавайте загальнодоступний `OsToSima`, `videoconvert` або `videoscale` етап лише для того, щоб забезпечити роботу вхідного потоку з MIPI-камери. Використовуйте [`CameraInput`](/reference/nodes/camera-input) і дозвольте шляху джерела керувати адаптацією пам’яті.

## Пов’язані типи

- [`TensorBuffer`](/reference/cppapi/structs/simaai-neat-tensorbuffer) — контейнер, що містить трійку буферів.
- [`Segment`](/reference/cppapi/structs/simaai-neat-segment) — дескриптор сегмента.
- [`Mapping`](/reference/cppapi/structs/simaai-neat-mapping) — дескриптор відображення RAII для безпосереднього доступу до ЦП.
- [`MemoryContract`](/reference/cppapi/files/include-contracts-contracttypes-h) — спосіб, яким вузол надає перевагу при розподілі пам’яті.
- [`ConversionKind::Transfer`](/reference/cppapi/files/include-pipeline-tensorconversion-h) — єдиний тип конвертації, який копіює дані між сегментами.
