# Асинхронне та синхронне виконання: часові характеристики

`Graph` і `Run` надають два способи керувати обробленням даних:

- **Одноразове виконання**: `Graph.run(input, ...)` передає вхідні дані й чекає на результат в одному виклику. `Graph.run()` без вхідних даних виконує граф із внутрішнім джерелом даних до кінця потоку (EOS).
- **Багаторазове виконання**: `Graph.build(...)` повертає активний `Run`. Ваш застосунок передає вхідні дані, забирає результати, закриває вхід, отримує решту результатів, вимірює і зупиняє виконання.

Обидва режими використовують той самий план `Graph` і те саме обладнання. Різниця в тому, хто керує циклом.

## Одноразовий режим

Використовуйте одноразовий режим, коли потрібно один раз подати вхідні дані й отримати результат одним викликом.

```cpp
simaai::neat::Graph graph("classifier");
graph.add(simaai::neat::nodes::Input("image"));
graph.add(model);
graph.add(simaai::neat::nodes::Output("classes"));

simaai::neat::TensorList out = graph.run(
    simaai::neat::TensorList{image_tensor});
```

Для графа з внутрішнім джерелом даних викличте `Graph.run()` без вхідних даних:

```cpp
simaai::neat::Graph graph("file_job");
graph.add(source_fragment);
graph.add(model);
graph.add(sink_fragment);

graph.run();  // Blocks until EOS or error.
```

Одноразовий режим підходить для:

- smoke-тестів;
- коротких перевірок;
- завдань із внутрішнім джерелом даних, які мають виконатися до кінця;
- коду, який не повинен керувати дескриптором середовища виконання з тривалим часом життя.

## Режим багаторазового використання Run

Використовуйте `Graph.build(...)`, коли циклом керує ваш застосунок.

```cpp
auto run = graph.build();

while (have_more_inputs()) {
  run.push("image", simaai::neat::TensorList{next_tensor()});

  if (auto out = run.pull("classes", /*timeout_ms=*/0)) {
    consume(*out);
  }
}

run.close_input();
while (auto out = run.pull("classes", /*timeout_ms=*/1000)) {
  consume(*out);
}
run.close();
```

Багаторазовий режим підходить для:

- живого відео, RTSP або камери;
- потокової обробки, де темп задає застосунок;
- графів із кількома входами або виходами;
- перевірки пропускної здатності;
- вимірювань, експорту, отримання решти результатів після закриття входу та керування зупинкою.

## Коли завершується виклик push

`push()` чекає на вільне місце за будь-якої політики переповнення. Якщо час очікування на вході графа вичерпано, метод повертає `false`. Перш ніж повторно подати окремий зразок, отримайте результати вже прийнятих зразків.

`push()` і `try_push()` можуть прийняти перші елементи набору або списку зразків Python, а потім повернути `false`. Якщо потрібно повторювати спроби, подавайте по одному зразку за виклик.

Коли вхідна черга заповнена, `try_push()` негайно повертає результат.

- `Block` повертає `false`. Виклик можна повторити.
- `DropIncoming` повертає `false` і зараховує новий зразок до відкинутих.
- `KeepLatest` замінює найстаріший зразок у черзі, зараховує його до відкинутих і повертає `true`.

## Черги всередині графа

`RunOptions::overflow_policy` керує чергою на вході `Run`. Щоб керувати чергою між вузлами графа, додайте налаштований `Queue`:

```cpp
simaai::neat::QueueOptions queue;
queue.max_buffers = 1;
queue.overflow_policy = simaai::neat::OverflowPolicy::KeepLatest;
graph.add(simaai::neat::nodes::Queue(queue));
```

```python
queue = pyneat.QueueOptions()
queue.max_buffers = 1
queue.overflow_policy = pyneat.OverflowPolicy.KeepLatest
graph.add(pyneat.nodes.queue(queue))
```

Не задавайте `max_buffers`, щоб використовувати стандартні обмеження черги. Додатне значення робить кількість буферів єдиним обмеженням місткості. `Block` чекає на вільне місце, `KeepLatest` відкидає найстаріший буфер у черзі, а `DropIncoming` відкидає новий буфер.

## Коли завершується виклик pull

`Run::pull(...)` повертає наступний доступний `Sample` із вихідної межі графа.

Застосунок може призупинити подачу даних і потім продовжити роботу з тим самим `Run`; сама лише відсутність вихідних даних не вважається помилкою. Скінченний тайм-аут `pull()` завершує це очікування, але не зупиняє Run. `RunOptions::input_timeout_ms` задає час очікування результату для `Graph::run()` із вхідними даними та для підтримуваної попередньої перевірки під час виклику build з початковими даними. `Run::run()` і `Model::run()` натомість використовують тайм-аут окремого виклику; `-1` означає без обмеження, як у `pull(-1)`. Застосунки, яким потрібно виявляти зависання, мають задавати дедлайни для незавершеної роботи.

Використовуйте спрощене перевантаження, коли тайм-аут і кінець потоку можна обробляти однаково, як «немає зразка»:

```cpp
if (auto sample = run.pull("classes", /*timeout_ms=*/1000)) {
  consume(*sample);
}
```

Використовуйте перевантаження зі статусом, коли тайм-аут, закриття і помилку треба обробляти по-різному:

```cpp
simaai::neat::Sample sample;
simaai::neat::PullError error;

switch (run.pull("classes", /*timeout_ms=*/1000, sample, &error)) {
case simaai::neat::PullStatus::Ok:
  consume(sample);
  break;
case simaai::neat::PullStatus::Timeout:
  break;
case simaai::neat::PullStatus::Closed:
  break;
case simaai::neat::PullStatus::Error:
  throw std::runtime_error(error.message);
}
```

Прихованого запасного варіанта немає: для графа з кількома виходами потрібно вказати назву в `pull("output", ...)`, якщо немає одного однозначно визначеного виходу.

## Телеметрія: вимірюйте цикл, яким керуєте ви

Використовуйте `Run::start_measurement(...)` для вимірювання навантаження, яким керує ваш застосунок. `MeasureReport` надає доступ до результатів вимірювання через публічний API і містить:

- наскрізну затримку від push до виходу та пропускну здатність;
- лічильники середовища виконання для переданих, отриманих і відкинутих зразків;
- часові показники плагінів/ядер і ребер графа, якщо це запитано в `MeasureOptions`;
- споживану потужність із застарілого `RunOptions::power_monitor`, якщо його ввімкнено.

За той самий інтервал вимірювання записуйте споживану потужність плати, температури, завантаження CPU та використання пам’яті за допомогою [`TelemetryMonitor`](/develop-apps/development-workflow/model#record-board-telemetry).

Виконуйте налаштування, завантаження файлів, журналювання кожного кадру та експорт звітів поза вимірюваним циклом, якщо тільки мета вимірювання — не оцінити сукупні витрати на виконання всього застосунку.
