# GStreamer під капотом

Конвеєри фреймворку Neat працюють на GStreamer. Майже все, що бачить застосунок, — `Graph`, `Run`, `Node` — це типізовані обгортки над поняттями GStreamer. На цій сторінці пояснено, як розподілено рівні: що приховано, що ні і коли правильне рішення — працювати з GStreamer напряму.

## Що абстрагує фреймворк

| Поняття GStreamer | Абстракція фреймворку |
|---|---|
| Текстовий фрагмент `gst-launch` | `Node::backend_fragment(int node_index)` |
| Ім’я елемента (`name=…`) | Детерміноване `n<idx>_<role>` з `Node::element_names()` |
| Рядок конвеєра (об’єднані фрагменти) | `Graph::add()` формує та об’єднує фрагменти |
| Узгодження caps | `Graph::build()` перевіряє caps через `NodeCapsBehavior` |
| `gst_pipeline_set_state()` | `Graph::run()` / `Run::start()` |
| Повідомлення шини | `GraphReport::bus_messages` |
| API push для `appsrc` | `Run::push()` (лише для вузлів із `InputRole::Push`) |
| API pull для `appsink` | `Run::pull()` |
| Часові показники окремих елементів | `MeasureReport` з `Run::start_measurement()` |

Застосунок ніколи не пише рядок запуску напряму, ніколи не задає імена елементів напряму і ніколи не звертається до C API GStreamer. Усе проходить через вузли.

## Що проступає назовні

Кілька понять GStreamer фреймворк не приховує (і не повинен приховувати):

- **Семантика caps** — які поля містять caps відео чи аудіо. Код застосунку може читати [`FormatTag`](/reference/cppapi/files/include-pipeline-formatspec-h) і перевіряти метадані `Sample`, які відображають відповідні поля caps.
- **Прапорці буферів** — розрив (discontinuity), EOS, пропуск (gap). Фреймворк передає їх у `Sample`, щоб код застосунку міг реагувати на межі потоку.
- **Порядок подій** — GStreamer гарантує, що події (caps, segment, EOS) надходять у правильному порядку відносно буферів. Фреймворк зберігає цей порядок на боці pull.

Якщо потрібно знати точний рядок запуску GStreamer для побудованого графа, викличте `Graph::describe()` — він створює детерміновану команду `gst-launch`, яка відтворює конвеєр байт у байт.

## Коли працювати з GStreamer напряму

У звичайному коді застосунку це не потрібно. Випадки, коли це доречно:

- **Власні плагіни GStreamer** — якщо вам потрібен елемент GStreamer, якого фреймворк не постачає у вигляді Node, напишіть підклас Node, який обгортає ваш плагін і генерує правильний `backend_fragment()`. Див. «Створення власного Node» у поглибленому огляді проєктування (§0.10).
- **Діагностичні інструменти** — команда відтворення `repro_gst_launch` з `Graph::describe()` — це саме той рядок запуску, який споживав би GStreamer; його можна вставити в `gst-launch-1.0` для офлайн-налагодження.
- **Створення плагінів** — власні плагіни GStreamer від SiMa (сімейство `sima*`) описано в ABI маніфесту плагінів (див. [`gst/SimaPluginStaticManifestAbi.h`](/reference/cppapi/files/include-gst-simapluginstaticmanifestabi-h)), і фреймворк завантажує їх автоматично.

## Гарантії детермінованості

Іменування елементів у фреймворку детерміноване — той самий список вузлів із тими самими параметрами завжди дає той самий рядок `gst-launch`. Саме завдяки цьому:

- поле `repro_gst_launch` справді забезпечує відтворюваність;
- знімки тестів залишаються стабільними між запусками;
- ідентифікація елементів (наприклад, для прив’язування вимірювань) зручна для машинної обробки.

Домовленість така: `n<node_index>_<role>`, де `role` — короткий стабільний ідентифікатор, який вибирає автор Node. Публічні обгортки Node, що беруть участь у цій схемі іменування, див. у [групі API вузлів](/reference/cppapi/groups/nodes).
