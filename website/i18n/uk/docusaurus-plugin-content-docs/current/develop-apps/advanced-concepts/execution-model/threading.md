# Модель багатопоточності

Активний `Run` виконує роботу в потоках фреймворку та середовища виконання. Вашому застосунку не потрібно керувати цими потоками, але його власний код для push, pull, зворотних викликів і завершення роботи має дотримуватися чітких правил.

## Перелік потоків

Для типового `Run`:

| Потік | Роль | Власник |
| --- | --- | --- |
| Потоки стримінгу GStreamer | Переміщують буфери шляхами джерела, перетворення та приймача. | Середовище виконання GStreamer |
| Потоки диспетчера MLA | Подають роботу на MLA і збирають сповіщення про завершення. | Середовище виконання Neat |
| Потоки диспетчера EV74 / CVU | Подають ядра на боці CVU й опитують їх завершення. | Середовище виконання Neat |
| Потоки очікування на боці pull і спостереження за шиною | Переміщують вихідні зразки в публічні черги й повідомляють про помилки середовища виконання. | Середовище виконання Neat |
| Потоки застосунку | Викликають `Graph.build(...)`, `Graph.run(...)`, `Run.push(...)`, `Run.pull(...)`, `Run.stop()` або зворотні виклики. | Ваш застосунок |

Фрагменти графа, вузли-джерела та вузли-приймачі можуть додавати роботу середовища виконання, але правило залишається тим самим: публічний `Run` — це дескриптор, яким керує ваш застосунок.

## Де виконується код застосунку

Код користувача виконується в таких місцях:

- **Прямі виклики API**: `build(...)`, `run(...)`, `push(...)`, `try_push(...)`, `pull(...)`, `close_input()`, `stop()` і `close()` виконуються в тому потоці застосунку, який їх викликає.
- **Зворотні виклики відкидання**: `RunOptions.on_input_drop` виконується на шляху push. Робіть його коротким: порахуйте подію й поверніть керування.
- **Тензорні зворотні виклики**: `Graph::set_tensor_callback(...)` — це споживання даних через зворотні виклики в C++. Робіть зворотні виклики короткими, бо тривала робота створює зворотний тиск на шляху середовища виконання.
- **Опис власних вузлів**: створення публічних вузлів і компонування графа відбуваються під час побудови, у потоці застосунку.

Не ховайте повільну роботу у зворотних викликах. Якщо зворотному виклику потрібно виконати важку роботу, передайте зразок у власну чергу й поверніть керування.

## Правила блокування

Вважайте `Graph`, `Run`, `Tensor` і `Sample` об’єктами з одним власником, якщо API не вказує іншого.

Підтримуваний шаблон:

- один потік-виробник викликає `push(...)` або `try_push(...)`;
- один потік-споживач викликає `pull(...)`;
- окремий потік-координатор може викликати `stop()` під час завершення роботи.

Ризикований шаблон:

- кілька потоків-виробників виконують push у той самий `Run` без блокування;
- кілька потоків-споживачів виконують pull з того самого виходу без чіткого правила володіння;
- зворотний виклик знову звертається до того самого `Run` і чекає на нову роботу.

Якщо потрібно кілька виробників, серіалізуйте доступ перед викликом `Run.push(...)`. Якщо потрібно кілька споживачів, розгалужуйте дані після того, як один потік отримає їх із Neat.

## Завершення роботи та скасування

Використовуйте примітив завершення роботи, що відповідає наміру:

| Намір | Що використовувати |
| --- | --- |
| Завершити роботу в черзі після останнього входу | `run.close_input()`, потім виконуйте pull, доки не перестануть надходити вихідні дані або не повернеться `PullStatus::Closed`. |
| Зупинити негайно й розблокувати роботу, що очікує | `run.stop()` |
| Звільнити ресурси середовища виконання | `run.close()` або дайте об’єкту `Run` вийти з області видимості |

`stop()` — це шлях скасування. Після скасування незавершені виклики pull розблоковуються, а push слід припинити. Не продовжуйте push у запуск, який закривається.

## Розподіл потоків для пропускної здатності

Для графів із живими даними або високою пропускною здатністю, у які дані подає застосунок, почніть із двох потоків застосунку:

1. Потік-виробник читає вхідні дані, проставляє `stream_id` / `frame_id` і викликає `try_push(...)` або `push(...)` відповідно до вибраної `OverflowPolicy`.
2. Потік-споживач безперервно виконує pull і звільняє або копіює виходи, щоб вони не утримували закріпленими буфери середовища виконання.

Додаткові потоки застосунку додавайте навколо власних черг, а не навколо того самого об’єкта `Run`. Гарячий цикл має бути нудним. Нудний код — швидкий код.
