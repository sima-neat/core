# Процесорні бекенди

SoC Modalix має кілька процесорів, кожен із яких підходить для різних частин конвеєра інференсу. Планувальник фреймворку Neat вибирає для кожного етапу один процесор (або ланцюжок процесорів) залежно від того, що робить етап. На цій сторінці описано кожен бекенд і те, де він трапляється в типовому конвеєрі.

## A65 — ядро застосунків

Стандартні ядра ARM A65 під керуванням Linux. Тут виконуються основний процес фреймворку, увесь код застосунку та більшість елементів GStreamer без апаратного прискорення.

Використовується для:

- циклу подій `Graph` / `Run`;
- файлового, RTSP- і мережевого введення-виведення;
- діагностичних точок перехоплення та коду застосунку на боці pull;
- легкого сполучного коду між прискореними етапами.

## EV74 / CVU — блок обчислень для комп’ютерного зору

Процесор у стилі DSP, пристосований до векторних обчислень. Фреймворк місцями називає його **EV74**, а місцями — **CVU** (Compute Vision Unit). Використовується для ядер, що мають SIMD-характер, але недостатньо великі, щоб виправдати використання MLA: попередньої обробки (зміна розміру, перетворення кольору, нормалізація), граничних ядер tess / detess / quant / dequant, об’єднаної попередньої обробки (універсальний Preproc) і постобробки BoxDecode.

Роботу EV74 диспетчеризують через окремі для кожного етапу потоки подання CVU. Бінарні файли ядер входять до архіву моделі (`lib/`).

## MLA — прискорювач машинного навчання

MLA платформи Modalix. Тут розміщуються скомпільовані ваги та граф моделі. Роботу диспетчеризують через потік подання MLA, який отримує тесельований вхід від EV74 (або безпосередньо від етапу квантування) і видає тесельований вихід, що далі детеселюється.

Робота MLA буває двох видів:

- **Інференс на MLA** — основний граф моделі.
- **Підготовчі / об’єднані операції MLA** — ядра попередньої та постобробки, скомпільовані в MLA, коли це дозволяє контракт (див. стовпець «Теселяція на MLA» на сторінці [Контракт dtype](/develop-apps/advanced-concepts/dtype_contract)).

## MLASHM — спільна пам’ять MLA

Спеціалізована область пам’яті, яку MLA може читати з найменшою затримкою. Буфери для входів MLA за можливості виділяються із сегментів MLASHM. Планувальник забезпечує, щоб попередня обробка на боці EV74 записувала дані безпосередньо в MLASHM і MLA міг споживати їх без передавання.

## APU — блок обробки аудіо

Використовується аудіошляхом і деякими етапами попередньої обробки, яким корисна робота SIMD над скалярними даними. Аудіовузли фреймворку (передискретизація, кодек) працюють на APU.

## TVM — резервний варіант, скомпільований TVM

Для операцій, які компілятор MLA не може згенерувати, фреймворк може перейти на ядра CPU, скомпільовані TVM. У плані маршруту це видно як етап із ціллю TVM. Це повільніше, ніж виконання на MLA, але гарантує покриття, коли контракт MPK описує операцію, яку бекенд MLA не підтримує.

## M4 — ядро-координатор

Невелике ядро Cortex-M4 для низькорівневої координації — RPMsg між A65 і прискорювачами, сторожовий таймер, апаратне секвенування. Код застосунку ніколи не виконується безпосередньо на M4; фреймворк взаємодіє з ним через рівень ОС.

## Як вибирає планувальник

Під час побудови графа планувальник маршрутів проходить кожен етап і з’ясовує:

1. **Який процесор може виконати це ядро?** — інференс виконується на MLA; попередня обробка — на EV74; введення-виведення — на A65.
2. **Як дістатися туди найдешевше?** — мінімізувати передавання (планувальник вставляє `ConversionKind::Transfer`, лише коли цього не уникнути).
3. **Чи можуть сусідні етапи спільно використовувати сегменти?** — що можливо, визначає [модель пам’яті](/develop-apps/advanced-concepts/memory_model); планувальник спирається на неї.

Результат — `RouteGraph`, у якому кожен етап має цільовий процесор і політику сегментів. Переглянути його можна через `Graph::describe()`.
