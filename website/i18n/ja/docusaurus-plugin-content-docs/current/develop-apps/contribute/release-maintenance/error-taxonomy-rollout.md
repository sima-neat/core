# エラー分類の展開

このチェックリストは、Coreおよびランタイムプラグイン全体で一貫したエラーセマンティクスの展開を追跡します。

## 標準コード

[`include/pipeline/ErrorCodes.h`](/reference/cppapi/files/include-pipeline-errorcodes-h) が、信頼できる情報源です。[エラーコードカタログ](/reference/error-codes) は、すべてのC++定数、すべてのPython `ERROR_*` 名、および大まかなコードから具体的なコードへの移行を文書化する必要があります。

## 実行スライス

1. 分類構造の作成
2. コーディングの構築/検証
3. ランタイムプルコーディング
4. グラフIOパーサー/オープンコーディング
5. テスト + ドキュメント

## 互換性レビュー

- 既存の失敗で返される正確なコードの変更を、たとえC++またはPythonのシグネチャが変更されなくても、動作の破壊的な変更として扱います。
- 公開移行テーブルで、古いコードと新しいコードのマッチングを文書化します。
- フォールバックコード（`build.parse_launch`、`runtime.pull`、および`runtime.element_failed`）は、特定の分類がない失敗に対してのみ保持します。
- バージョン管理された`simaai-neat-error` ワイヤキーを、本番環境のビルダーでテストし、実際の`GstMessage` をCoreを通じて解析します。

## 検証チェックリスト

- ターミナルフレームワークの失敗時に、`NeatError.report().error_code` が空でないことを確認します。
- ランタイムプルのエラー時に、`PullError.code` が設定されていることを確認します。
- グラフラッパーエラーには、コード + コンテキスト + ヒントが含まれます（一般的なフォールバックテキストは含めません）。
- JSON解析の失敗には、`offset=` と `near='...'` が含まれます。
- 否定的なテストでは、コード + 分類クラスごとの安定したメッセージフラグメントをアサートします。
- 診断ドキュメントとアーキテクチャドキュメントには、トリアージフローが含まれます。`error_code` を読み取り、`repro_note` を検査し、バス診断を検査してから、`repro_gst_launch` を使用して再実行します。
