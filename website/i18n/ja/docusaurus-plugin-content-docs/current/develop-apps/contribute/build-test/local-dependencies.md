# ローカルの Kernels、Runner、Scheduler を使って Core をビルドする

Neat 開発環境の Core チェックアウトで、通常のコマンドを実行します。

```bash
./build.sh --all --no-doc --install
```

ビルドは **Kernels → Runner → Scheduler → Core** の順に準備し、その後に既存の最終インストール/デプロイを行います。子ビルドは SDK へのインストール、DevKit へのデプロイ、ターゲットテストの実行、EV ファームウェアのコンパイルや有効化を行いません。

ソースを自動検出するには、チェックアウトを隣接して配置します。

```text
development/
├── core/
├── kernels/
├── runner/
└── scheduler/
```

Runner にはフレームワークに依存しない実行、準備、メモリ、ネイティブ転送が含まれます。Scheduler には GStreamer 統合/プラグインと互換アダプターが含まれます。それぞれが独自のソースルートとインストール済みパッケージを持ちます。チェックアウトに `.git` ディレクトリは必須ではありません。worktree とソーススナップショットにも対応します。

## ソースまたは既存のローカルパッケージを選択する

別の場所にあるチェックアウトには `NEAT_KERNELS_SOURCE`、`NEAT_RUNNER_SOURCE`、`NEAT_SCHEDULER_SOURCE` を設定します。

```bash
NEAT_RUNNER_SOURCE=/path/to/simaai-runtime ./build.sh --all --no-doc
```

ローカルでビルド済みのパッケージを再利用するには、代わりに `NEAT_KERNELS_PACKAGE_DIR`、`NEAT_RUNNER_PACKAGE_DIR`、`NEAT_SCHEDULER_PACKAGE_DIR` を設定します。各パッケージディレクトリには、そのコンポーネントの標準パッケージワークフローで生成されたインストール済み `usr/` ツリー、ビルド記録、対応する Debian パッケージが必要です。Kernels は標準の CMake configure/build/install とパッケージ生成処理を使用します。Runner と Scheduler は各リポジトリルートの `build.sh` エントリーポイントを使用します。

```bash
NEAT_RUNNER_PACKAGE_DIR=/path/to/runner/dist/package \
  ./build.sh --all --no-doc
```

選択の優先順位は、明示的な上書き、有効な隣接ソース、隣接する `dist/package` の順です。明示的なパッケージ選択は隣接ソースより優先されます。同じコンポーネントにソースとパッケージの両方の上書きを設定するとエラーになります。ローカルビルドが失敗すると全体を停止し、古いパッケージにはフォールバックしません。

## プラットフォーム依存関係

4 つのリポジトリすべてで同じ Platform 3.0 SDK/ツールチェーンを使用します。既定以外のツールチェーンを選ぶ場合は `CMAKE_TOOLCHAIN_FILE` を設定してください。Kernels と Runner の記録は、ターゲット/コンパイラー、カーネル契約、使用したビルド設定が一致する必要があります。標準パッケージワークフローでは、使用した Kernels ペイロードの正確な識別情報も必要です。Kernels パッケージを変更したら、Runner のソースが変わらなくても、選択した SDK に対して Runner パッケージを再ビルドしてください。その後 Core は対応する Scheduler クライアント実装に再リンクします。下位の数値パッケージは Scheduler が使用します。
Core のソース優先 DEB は、選択された Scheduler と数値 SDK のバージョンを固定します。Runner は Kernels を固定し、Scheduler は Runner、Kernels、有効なコーデックバックエンドを固定します。テストを有効にした Core ビルドには、同じ生成元による Scheduler の個別パッケージ `simaai-scheduler-client-test-dev` も必要です。ソースビルドでは `--client-test-support` で要求し、パッケージビルドでは隣接する `client-test-support/` ディレクトリまたは `NEAT_SCHEDULER_CLIENT_TEST_PACKAGE_DIR` を選択します。コーディネーターは本番用記録、ソース、ペイロード、アーカイブを確認してから、テスト専用の CMake コンポーネントを公開します。ランタイムのみのビルドには不要です。
ビルドでは、正確な Runner/Scheduler 依存関係を持つメタデータ専用の `simaai-runtime` 互換パッケージを構成します。標準パッケージのファイル所有権は重複せず、既存のローダー設定は Runner のみが所有します。単一パッケージを置き換えるのではなく、対応するディストリビューション全体をインストールしてください。

### GStreamer ヘッダー所有権の移行

未リリースの Core `0.6.0` では、`/usr/include/gst/SimaaiGstErrors.h` の所有権を Scheduler に移します。インクルードパスは変わりません。Core は独自実装やこのファイルのインストールを行わなくなり、コンシューマーはインストール済み Scheduler ヘッダーと `SimaScheduler::Headers` ターゲットを使用します。

対応するディストリビューションで Core と Scheduler を一緒に更新してください。Scheduler の範囲を限定した `Breaks`/`Replaces` 関係は、0.6 より前のパッケージと、明示的に監査された古い 0.6 開発アーティファクトを対象とします。修正済みの 0.6.0 リリースは拒否しません。所有権が重複する未知の開発アーティファクトは、暗黙に上書きせず、所有権の事前チェックで失敗します。`--force-overwrite` の使用や dpkg 所有ファイルの削除は避けてください。単独の Scheduler テストイメージには Core は不要ですが、既存の Core インストールは協調して更新する必要があります。

### バックエンドプロバイダー

Scheduler には別途インストールされたプラットフォームバックエンドが必要です。これらは Scheduler にコピーされず、このワークフローで取得することもありません。

- `NEAT_CODECS_PACKAGE_DIR` を、別途ビルドした Codecs パッケージディレクトリに設定します。Scheduler でコーデックを有効にする場合、このディレクトリには実際に使用したインストール済み `usr/` プレフィックスと、対応する `neat-codecs` および `neat-codecs-dev` Debian パッケージが必要です。Scheduler の依存関係コーディネーターがペイロード、所有権、依存関係の制御情報を検証します。Core は検証済みの依存関係一式を保持し、両アーカイブを最終ディストリビューションに含めます。Codecs のビルドや別バージョンへの置き換えは行いません。
- SDK に対応する MLA Runtime、レンダリング、トレース/ログのライブラリを使用します。
- SDK パスを明示的に選択する場合は、`NEAT_SCHEDULER_CMAKE_ARGS` を通して CMake 定義を渡します。たとえば `-DSIMA_RUNTIME_MLART_LIBRARY=/path/to/libmlart.so` と対応するインクルードディレクトリを指定します。オプション名は Scheduler のビルドガイドに従ってください。

`NEAT_RUNNER_CMAKE_ARGS` と `NEAT_SCHEDULER_CMAKE_ARGS` の引数は、シェル形式の単語として解析され、シェルコードとしては実行されません。選択済みの依存パッケージやインストールレイアウトを上書きすることはできません。

## 増分ビルドとインストール

Core が管理する依存関係のビルドとパッケージは、各リポジトリの単独ビルドディレクトリとは別の `deps/backend/` に置かれます。CMake は増分ビルドを行います。`--clean` は選択されたローカル依存関係のビルドと Core のビルドをクリーンにします。

リンク前に Scheduler の依存関係コーディネーターが、インストール済みカーネルヘッダーを記録と照合し、Runner が使用した契約と Scheduler の正確な Runner 入力を確認します。デプロイ用パッケージをステージングする前には、各 Debian パッケージの `/usr` ペイロードが選択済みインストールツリーと一致することを検証します。旧 Internals パッケージの選択やダウンロードは行いません。

Core が使用するのはインストール済み `SimaScheduler` クライアントコンポーネントであり、隣接ソースのインクルードや下位の開発インターフェースではありません。下位ランタイムの識別情報は検証済みの依存関係一式に残ります。生成された依存関係の選択は `build/resolved_manifest.json` と `build/buildinfo.json` に記録されます。完全なビルドだけが最終インストールに進みますが、これは SDK やデバイスへのインストールにトランザクション型ロールバックを保証するものではありません。

CMake 設定前のパッケージビルド情報は暫定値です。コンパイル後、`build.sh` はインストール確認やパッケージ化の前に、そのビルドの CMake キャッシュ、設定済みコンパイラー、ターゲット Python ヘッダー、ビルドした拡張から情報を更新します。ターゲット Python の ABI フラグは拡張のサフィックスと一致する必要があります。ホスト Python バージョンは使用しません。Python 無効ビルドは Python ABI を付けずにそのプロファイルを記録します。

`compatibility.host_sdk` はビルドホストで観測された SDK リリースを表し、`compatibility.target_sdk` は選択済み sysroot とコンパイラーを表します。ターゲット SDK リリースを取得できなければ、ホスト SDK リリースが存在しても未取得のままです。マニフェストのプラットフォームバージョンは別の互換性要件であり、未観測の SDK バージョンを代用しません。`ELXR_SDK_RELEASE_FILE` はホストのリリースファイルを選択します。`NEAT_TARGET_SDK_RELEASE_FILE` でターゲットのリリースファイルを明示できますが、選択した sysroot 内のリリースファイルと一致する必要があります。`NEAT_BUILDINFO_TOOLCHAIN` は、設定済みコンパイラー識別情報を置き換えず、その横に明示的な表示ラベルを保持します。

メタデータ確認は、矛盾するコンパイル sysroot、ヘッダー、拡張 ABI タグを拒否します。このメタデータ経路は、コンパイル/リンクで異なる sysroot や、追加の CMake コンパイラー引数/ターゲット/ツールチェーンコンテキストには対応しません。未検証のターゲット識別情報を報告するのではなく失敗します。マーカー付き NumPy 要件は、単一の無条件の最小値にまとめず、`pyproject.toml` からそのまま保持します。

ソース記録は実際のチェックアウトのコミットと変更状態を使用します。追跡対象の変更と、無視対象でない未追跡ファイル/シンボリックリンクの識別情報は別々に記録します。無視されたビルド生成物はソーススナップショットではありません。自己参照を避けるため、メタデータ出力自体は未追跡コンテンツのダイジェストから除外します。変更のあるローカル候補を、クリーンな公開アーティファクトとして識別することはありません。

ヘッダーのみの依存関係準備では、`--install-deps-only` にローカルパッケージの上書き指定が必要です。A65/EV コードのビルドや実行はせず、ヘッダーをコピーします。ネイティブ clang-tidy 解析には、選択済みパッケージの上書き指定と Scheduler プレフィックスを使って `scripts/run_cpp_tidy.sh` を実行します。`TIDY_INSTALL_DEPS=1` はネイティブホストの解析前提条件をインストールし、インストール済み Scheduler コーディネーターをヘッダーのみモードで呼び出します。SDK sysroot の有効化や変更はしません。LLiMa を使用する GenAI 実装ファイルは、このホスト専用解析プロファイルの対象外です。スクリプトは選択済みビルドの依存関係を、環境内の SDK LLiMa パッケージで置き換えません。ドキュメントのみのビルドではネイティブ依存関係を準備しません。

EV デバイスのビルドは、引き続きライセンスを必要とする別のワークフローです。これらのコマンドが暗黙に MetaWare を呼び出したり、ファームウェアを置き換えたり、変更したファームウェアを検証済みとしたりすることはありません。

## 公開済み CI 依存関係

通常の Vulcan ビルドは `deps/manifest.json` の Scheduler ポリシーを `sima-cli` で一度解決し、その不変の公開物をダウンロードします。snap ポリシーは現在のブランチを選択します。未公開のブランチは別ブランチにフォールバックせず失敗します。`tools/ci/acquire_scheduler.py` は公開元ハッシュを検証してから Scheduler のブートストラップを実行します。インストール済み Scheduler コーディネーターが、同梱された Runner、Kernels、Codecs のアーカイブを区分して検証します。Core がこれらのリポジトリを個別に解決することはありません。

選択した Scheduler パッケージは、正確な SDK ポリシーをインストールします。使い捨ての CI SDK コンテナーでは、`scripts/ci/prepare_scheduler_sdk.sh` がそのリビジョンの公式 sysroot セットアップコマンドを使い、ダウンロードしたプラットフォームアーカイブを保持します。コーディネーターは実際の GCC14 バージョン/ターゲットとターゲット SDK 識別情報を確認し、`NEAT_RUNNER_PLATFORM_RUNTIME_DEBS` を通して Runner が使用した正確なランタイムプロバイダーアーカイブを選択します。ネイティブ ARM64 コンパイラーとクロスコンパイラーの実行ファイルのバイト列は同一でなくてもかまいませんが、ターゲット ABI と選択したプラットフォームは一致する必要があります。この段階でデバイスへのインストールやファームウェアの検証は行いません。

ローカルのソース/パッケージ上書き指定は引き続き優先されます。CI 取得は明示的な操作です。ローカルソースビルドが失敗しても代替物をダウンロードしません。既存の `tools/ci/materialize_dependencies.py --manifest ... --output-root ...` コマンドは、別途レビュー済みの不変マニフェストを転送するための任意の手段として残ります。既定のワークフローではなく、暗黙の `ci/dependencies.json` もありません。

コード衛生チェックは、この実行の `neat-core-dist` をダウンロードして検証し、実際の Core 委譲ツールとインストール済み Scheduler コーディネーターをヘッダーのみモードで実行します。コーディネーターはビルドで使用したものと同じ下位パッケージおよび認証済みプラットフォームビルド証拠を確認します。Core の解析に公開されるのは Scheduler フロントエンドのプレフィックスだけです。LLiMa は引き続き Core の直接依存関係です。解析は Core のビルド記録に記載された正確な開発アーカイブをダウンロードし、別の可変な latest は使用しません。これはホストツールの検証であり、ターゲット実行ではありません。

保護された性能レーンに必要なターゲット側スーパーバイザーについては、[ハードウェアテストの所有権](./hardware-test-safety.md)を参照してください。

## 完成したディストリビューションを検証する

`build.sh --all` はパッケージメタデータを生成した後、完成したディストリビューションを確認します。CI では `scripts/ci/verify_core_dist.sh` が、選択された `sima-cli` の Python 環境で同じ読み取り専用チェックを実行します。インタープリターが選択済み CLI 実行ファイルと同じ場所にない場合は、`SIMA_CLI_PYTHON` を明示的に設定してください。

チェックでは、依存パッケージのバイト列、互換性フィールド、インストーラーの許可リスト、全リソースのチェックサム、公開 wheel の分離、インストール済み CTest ツリーを検証します。既存の生成元記録を使用し、依存関係の解決や修復は行いません。次の文書を区別してください。

- `dist/manifest.json`: プラットフォーム、Model Zoo、ABI の互換性。
- `dist/resolved-deps-manifest.json`: 選択済みバックエンド記録の完全なコピー。
- `build/resolved_manifest.json`: より詳細な Core ビルドの解決結果。

この確認後にファイルを置き換えたり、選択されたチェックサムを再計算したりしないでください。アーティファクトが変わった場合はメタデータを再生成し、ディストリビューション全体を再検証します。

## 明示的なプラットフォームプロバイダーパッケージ

Core の本番用ボックス/マスク公開は int32 座標を使用します。標準 Kernels レンダリングと対応する Runner 実行 API を使用してビルドされた Scheduler を選択してください。`SIMANEAT_REQUIRE_INT32_RENDERER` の既定値はランタイムアーティファクト要件に従い、インストール済み Scheduler にこの機能がなければ設定は失敗します。`OFF` にしてよいのは、Core のボックス/マスクレンダリングを使わない Core プロファイルだけです。

レンダリングは、個別のプラットフォームレンダラーアーカイブではなく、選択された Kernels/Runner パッケージを使用します。要求 API リビジョン 2 に向けてコホート全体を一緒に再ビルドしてください。

Core のソース優先 `build.sh` を実行する前に、次を用意します。

- `NEAT_RUNNER_PLATFORM_RUNTIME_DEBS`: Runner が選択した正確なランタイムプロバイダー DEB の絶対パスを並べた JSON 配列。必須の SimaHeap ランタイムアーカイブと、有効な場合は MLA および TVM ランタイムアーカイブを含めます。この配列に開発アーカイブを含めないでください。Runner は実際のローダー名とライブラリのバイト列を検証します。Scheduler は正確なアーカイブ識別情報とペイロード一覧をビルド証拠として保持します。Runner が Platform 所有と宣言したプロバイダーは Core のインストール可能 DEB 一式には含めず、未宣言のプロバイダーは正確なアーカイブ構成を維持します。

ビルド済み Runner/Scheduler パッケージを上書き指定する場合も、これらの選択は明示的に行います。不変の 4 コンポーネント取得ツールは、プラットフォームプロバイダーアーカイブを取得しません。Core を呼び出す前に、対応する生成元から取得してください。プロバイダーが欠けているか実際に使用されていない場合は、sysroot にフォールバックせず失敗します。コンパイルには対応する開発パッケージを使用します。DevKit では、Scheduler の認証済み実行許可ツールが、パッケージ変更の前に、インストール済み Platform プロバイダーが導入予定のコンシューマーに適合するか確認します。インストーラーはこれらのプロバイダーを置換/削除する APT 計画を拒否し、処理後にプロバイダー識別情報とインストール済みコンシューマーの依存関係全体を検証します。`FORCE_INSTALL` はこの確認を免除しません。非公開 DSO をリリース済みプロバイダーと表示するためだけに DEB を再ビルドしないでください。

パッケージ構成チェックは、ペイロード所有権の非重複、正確な依存バージョン、アーカイブが未変更であることを確認します。これらのビルド時チェックは、数値実行、動的マスク、ハードウェアの終了を検証済みとするものではありません。それらには、選択したターゲットコホートで対応する統合テストが必要です。
