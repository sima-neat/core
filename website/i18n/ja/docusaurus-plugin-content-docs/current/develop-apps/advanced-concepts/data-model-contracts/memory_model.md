# メモリモデル

Neatフレームワークのランタイムは、エンコードされたビデオフレーム、デコードされたYUVプレーン、FP32入力テンソル、INT8量子化されたタイル、MLAスクラッチパッド画像など、大量のバイトを移動させます。明示的なメモリモデルなしでこれを行うと、各ステージの境界でコピーが発生することになります。このページでは、フレームワークがこれらのコピーを回避する方法について説明します。

## バッファトリプル：`(buffer_id, paddr, vaddr)`

フレームワークが移動させるすべてのバッファは、次の3つの要素によって識別されます。

- **`buffer_id`** — ランタイムがバッファのライフサイクル（参照カウント、セグメントの所有権）を追跡するために使用する安定した整数。
- **`paddr`** — 物理アドレス。IOMMUから見たバッファのアドレス。MLA / EV74 / DMAハードウェアはこのアドレスを参照します。
- **`vaddr`** — 仮想アドレス。アプリケーションから見たアドレス。CPUコードはこのアドレスを逆参照します。

このトリプルにより、バッファはコピーなしで、CPUまたはアクセラレータのいずれか一方のアドレスで参照できます。単一の割り当ては、カーネルのページテーブル（ソフトウェアが読み取れるようにするため）とIOMMUのページテーブル（ハードウェアがDMAできるようにするため）の両方に表示されます。

ステージ間のデータ受け渡しでは、バイトではなくトリプルが渡されます。

## セグメント

バッファは、名前付きの**セグメント**から取得されます。セグメントは、特定のメモリ割り当て器（DMA-BUF、CMA、ION、プレーンヒープ）によってバックアップされ、誰がアクセスできるかに関するメタデータがタグ付けされた、連続したメモリ領域です（CPUのみ、MLAのみ、両方など）。ランタイムは、どのステージがバッファにアクセスするかに基づいて、各バッファに適切なセグメントを選択します。

例：

- `nv12_decode`セグメントには、H.264からデコードされたYUVが格納されます。CPUから読み取り可能で、診断用のタップに使用され、IOMMUから読み取り可能で、リサイズノードで使用されます。
- `mla_input`セグメントには、MLAに渡されるテッセレーションされたテンソルが格納されます。MLAハードウェアのみが読み取ります。CPUからのアクセスには、明示的なマップが必要です。
- `model_output`セグメントには、デテッセレーション後のFP32テンソルが格納されます。CPUから読み取り可能で、アプリケーションがそれらを取り出すことができます。

`Tensor`は、トリプルとともにセグメントを運びます。これにより、フレームワークはCPUコードからのピーク/ポークが有効かどうかを判断できます。

ストレージに結び付いた密な数値 `Tensor` では、形状 `{}` はランク 0 のスカラーを表し、密なデータサイズは `dtype` の 1 要素分です。これは、密なデータサイズが 0 になる、ゼロ長の次元を含む `{0,256}` などの形状とは異なります。隙間のないバイトコピーと `clone()` は、ビューのオフセットとストレージの境界を検証しながらスカラー値を保持します。ストレージを持たないデフォルトの Tensor では `dense_bytes_tight()` は 0 を返し、隙間のないコピーとクローン作成は拒否されます。エンコード済み、バイトストリーム、テッセレーション済み、テキストと明示された搬送バッファは、従来の搬送バイトの意味を維持します。公開 `map()` が返すバイト範囲は変わりません。

バックエンドが作るキャリアは、EV74 が書き込みまたは読み取る場合に CMA を使用し、MLA/A65 だけが使う場合は既定で DMS を使用します。適格な新規 A65 公開終端は、認証済みの HostCpu メモリを使用します。ファンアウトでは全コンシューマーを考慮し、ビューは元のキャリアを共有します。互換性のある外部カメラ／アプリケーション DMA-BUF は、バッキング、オフセット、ストライド、親バッファーのローンを維持します。

## キャッシュコヒーレンス

Scheduler は Runner の共有メモリ管理を通じて CPU／デバイスアクセスを準備します。Runner は割り当ての識別情報、DMA-BUF の保持、CPU／デバイスの排他、検証済み範囲、世代ベースの可視性を管理します。MLA と EV は、先行する CPU READ エポックなしで完了したデバイス書き込みを公開します。必要な READ キャッシュメンテナンスは、CPU マッピングまたは A65 ワーカーが検証済みアクセスを取得する際、**読み取り前**に行います。アンマップ時やバックエンドの完了コールバックではありません。デバイスのみの後続処理では CPU 可視性の処理を行わず、独立したフレームは引き続き重ねて処理できます。

[`TensorBuffer::map()`](/reference/cppapi/structs/simaai-neat-tensorbuffer) を呼び出すときは、適切な [`MapMode`](/reference/cppapi/namespaces/simaai-neat) で `Mapping` を使ってください。Tensor のマッピングは、CPU アクセスが終了するまでマップガードと現在のストレージ／生成元の借用を保持します。書き込みのクリーン処理を含む必要な END 同期は、これらの所有者が解放される前に完了します。部分書き込みでは隣接するキャッシュラインのバイトを保持します。同期に失敗すると、影響を受けた割り当ては通常の再利用に戻されず、隔離されます。

各公開 DMA マッピングは独自の Scheduler リースを保持します。互換性のある読み取りは、重なったビューを含め Runner のアクセス権限を共有し、書き込みは引き続き排他になります。別々のマッピングの仮想アドレスは同一である必要はありません。1 つの読み取り側を解放しても別の読み取り側を無効にできず、最後の所有者だけが必要な END 遷移を実行します。

所有されるキャッシュ付き CMA と DMS には、初期段階でのプラットフォームとエクスポーターの受け入れ検証が必要です。失敗には対処が必要であり、バッファー全体の同期へフォールバックする許可ではありません。取り込んだ DMA-BUF とほかのヒープも、同じ所有権エンジンを通じてエクスポーター契約を維持します。

内部の全 A65 レシピは、明示的な親バッチを保持できます。子には、有効な親の権限、正確なアクセス許可、範囲の包含が必要です。最後の親の解放では、すべての子が使用を終えた後に書き込みをクリーンします。デバイスを混在させたフェーズが暗黙にバッチへ所属することはありません。隠れたステージングコピーも追加しません。生の FD への書き込みやカスタムコールバックも所有権契約を守る必要があります。グラフの許可リストをなくしても、追跡されないアクセスの安全性は証明されません。

転送境界は、元の割り当ての識別、検証済みオフセットと長さ、元のプールバッファーの所有権を維持します。メタデータのみのエンベロープはメモリを共有し、プールの親を保持します。EV/CVU と MLA のインポートは、完了まで生成側を保持します。完了状態が不明な場合、まだ使用中の可能性があるストレージを再利用してはなりません。

## 実際のゼロコピー

典型的な推論パイプライン：

```
file → demux → H.264 decode → resize → preproc → MLA → postproc → app
```

ゼロコピーを使用しない場合、7回のコピーが発生します。バッファーのトリプルとセグメントを使用すると、ゼロになります。つまり、各ステージで`(buffer_id, paddr, vaddr)`を次のステージに渡し、次のステージでその場で処理を行います。

フレームワークのプランナーは、連続するステージ間で共有できるようにセグメントを選択する役割を担います。隣接する2つのステージで互換性のないセグメント要件がある場合、プランナーは`Transfer` `ConversionKind`を挿入し、アクティブな`ConversionTraceCollector`に記録します。これに注意してください。これらは、ランタイム中に実際のバイトが移動する唯一の場所です。

## カメラソースとアダプティブメモリ

ライブカメラフレームは、プラットフォームのカメラスタックを介して入力されます。`libcamerasrc`は各フレームを自身のDMA-BUFにキャプチャし、Neatはそのメモリを所有しません。物理的に連続したDMA-BUFであればどれも有効なEV74入力であり、CMAヒープまたはカメラの連続キャプチャアロケーター（`videobuf2_dma_contig`）に由来する場合は、NeatのEV74受け入れチェックがそれを受け入れます。`CameraInput`のプライベートブリッジは、`GST_QUERY_ALLOCATION`を通じてソースに`GstVideoMeta`を要求し、各フレームのDMA-BUFを1つのメモリとして下流のCVU/MLAステージに転送します。その際、これらのステージが解放するまでカメラのバッファーを保持します。

フレームが、各プレーンが連続して並んだ1つのDMA-BUFではなく、`allow_cpu_fallback`が有効になっている場合、ブリッジはそのフレームをCMA DMA-BUFにコピーし、予想されるメタデータをスタンプし、そのバッファーをモデル管理のCVUプリ処理に渡します。このコピーは互換性ブリッジです。リサイズ、カラー変換、正規化、量子化、およびテッセレーションは、CVU/EV74で実行される必要があります。

MIPIカメラ入力を動作させるために、パブリックな`OsToSima`、`videoconvert`、または`videoscale`ステージを追加しないでください。[`CameraInput`](/reference/nodes/camera-input)を使用し、ソースパスにメモリアダプテーションを任せてください。
