# 018 Отримання RTSP-потоку в реальному часі

## Metadata

## Concept

Під’єднайте живий RTSP-потік H.264 або H.265 до `Graph` за допомогою фрагмента `RtspDecodedInput`. Фрагмент підключається до RTSP, вибирає відповідний RTP-депакетизатор і парсер та декодує потік у необроблені кадри.

## Walkthrough

Це перший розділ, у якому вхідні дані надходять *ззовні програми*. У попередніх розділах ми генерували тестові зображення або читали файли з диска; тут кадри безперервно надходять із мережевого потоку, і ви споживаєте їх так швидко, як їх забираєте. Механізм — багаторазово використовуваний фрагмент `Graph` під назвою `RtspDecodedInput`, який ховає за одним інтерфейсом увесь вхідний тракт від RTSP до необроблених кадрів.

Розділ навмисно зупиняється на кроці «отримати декодовані кадри». Як передати їх у `Model`, описано в інших розділах (001 — один запуск моделі, 007 — під’єднання моделі до конвеєра, 015 — вбудовування моделі в граф). Наприкінці ви підключитеся до RTSP URL-адреси й виведете форму тензора кожного декодованого кадру — доказ того, що потік надходить.

Це лише *споживач*. Щоб опублікувати потік, запустіть окремий RTSP-сервер (наприклад, `mediamtx`) і спрямуйте на нього `--url`.

### Налаштування RTSP-клієнта {#step-configure-rtsp}

`RtspDecodedInputOptions` налаштовує джерело та декодер. `url` вибирає джерело `rtsp://...`. `codec` вибирає формат кодування. За замовчуванням використовується H.264; посібник також приймає `avc`, `h265` і `hevc`, де AVC — це H.264, а HEVC — H.265.

Задайте `source_fps`, якщо вже знаєте частоту кадрів джерела. Якщо її не вказати, посібник відкриє RTSP-джерело через OpenCV, прочитає заявлену ним частоту кадрів і передасть виявлене значення в `RtspDecodedInput`. Сама група не зондує URL-адресу. OpenCV потрібен лише для зондування, а версія для Python імпортує його тільки за потреби, тож із `--source-fps` приклад працює без нього; щоб зондувати джерело, установіть OpenCV командою `pip install opencv-python`. Для H.265 Neat передає це значення в caps розібраного потоку та в конфігурацію декодера. Частоту кадрів воно не змінює. Потік H.265 має використовувати профіль HEVC Main, 8 біт, 4:2:0.

Параметр `tcp = true` передає RTP через TCP. TCP зберігає порядок і повторно передає втрачені сегменти, що може зменшити помітні втрати порівняно з UDP, але й збільшити затримку на час відновлення втрачених даних.

### Компонування графа {#step-compose-graph}

Побудуйте `Graph` лише з двох етапів: фрагмента `RtspDecodedInput` (джерело) і простого вузла `Output` (кінцева точка для отримання даних). Додавання фрагмента — це один виклик `add(...)`: усередині він розгортається в елементи підключення/депакетизації/декодування, тож ваша композиція залишається на рівні намірів. Оскільки вхідні дані виникають *усередині* конвеєра, ми викликаємо перевантаження `build(RunOptions{})`, яке не приймає початкового зразка: передати `build()` кадр заздалегідь неможливо, бо кадри створює сам потік.

### Отримання декодованих кадрів {#step-pull-frames}

Коли запуск активний, у циклі викликайте `pull(...)` з тайм-аутом. Кожне успішне отримання повертає `Sample`, тензор якого — один декодований кадр. Посібник використовує вихід NV12 за замовчуванням, представлений як логічний тензор `[H, W]` з метаданими площин Y і UV. Якщо отримання нічого не повертає (або повертає порожній тензор), виводиться `frame=N rtsp_timeout` і цикл переривається — зазвичай це означає, що URL-адреса неправильна або потік не надходить. Саме тайм-аут не дає мертвому потоку завісити програму.

**C++:** Кадр витягується через `tensors_from_sample(*sample, true)`; перед читанням `shape` цикл перевіряє, чи список не порожній.

**Python:** Кадр зчитується з першого елемента `sample.tensors`, після чого виводиться його форма.

## Run

Цей розділ споживає живий RTSP-потік, тому потрібно передати в `--url` доступну адресу. Якщо камери немає, опублікуйте сумісне відео через RTSP-сервер і спрямуйте на нього `--url`. Команди **Python** і **C++ (prebuilt)** запускайте з **кореневої теки встановлення Neat** (теки, що містить `share/` і `lib/`), а команди **build from source** — з **кореневої теки репозиторію**.

Автоматизований регресійний тест посібників запускає обидва кодеки. Він бере першу придатну URL-адресу з `SIMANEAT_TEST_RTSP_H264_URL` або `SIMANEAT_TEST_RTSP_H264_URLS`, а також з `SIMANEAT_TEST_RTSP_H265_URL` або `SIMANEAT_TEST_RTSP_H265_URLS`. Тест зондує кожне джерело й передає виявлену частоту кадрів у групу RTSP.

**Python:**
```bash
python3 share/sima-neat/tutorials/018_consume_rtsp_stream/consume_rtsp_stream.py \
  --url rtsp://host:port/stream --source-fps 30 --frames 5
```

Для H.265:

```bash
python3 share/sima-neat/tutorials/018_consume_rtsp_stream/consume_rtsp_stream.py \
  --url rtsp://host:port/stream --codec hevc --source-fps 30 --frames 5
```

**C++ (prebuilt):**
```bash
./lib/sima-neat/tutorials/tutorial_018_consume_rtsp_stream \
  --url rtsp://host:port/stream --codec h265 --source-fps 30 --frames 5
```

**C++ (build from source):**
```bash
./build.sh --target tutorial_018_consume_rtsp_stream
./build/tutorials-standalone/tutorial_018_consume_rtsp_stream \
  --url rtsp://host:port/stream --codec h265 --source-fps 30 --frames 5
```

Очікуваний результат (форма залежить від роздільної здатності потоку та формату декодера):

```text
frame=0 shape=[720, 1280]
frame=1 shape=[720, 1280]
frame=2 shape=[720, 1280]
frame=3 shape=[720, 1280]
frame=4 shape=[720, 1280]
```

Якщо потік недоступний, натомість ви побачите `frame=0 rtsp_timeout`. Щоб інтегрувати початковий код C++ цього розділу у свій проєкт із власним файлом `CMakeLists.txt` (тека extras не потрібна), див. розділ [Як запускати навчальні посібники](/tutorials#compile-a-copy-yourself) на головній сторінці.
