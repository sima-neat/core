## Concept

Проведіть первинну діагностику конвеєра трьома перевірками — `graph.validate()`, одним виміряним `run.run()` і діагностикою `MeasureReport`, — щоб з’ясувати, чи правильно його з’єднано і як він працює, перш ніж братися за глибоке налагодження.

## Walkthrough

Коли конвеєр поводиться неправильно, виникає спокуса одразу перейти до налагодження на рівні елементів. Цей розділ навчає дешевшого першого кроку: повторюваної первинної діагностики, яка по черзі відповідає на три запитання — *Чи дійсний контракт графа? Чи вдається один запуск? Що кажуть діагностичні дані середовища виконання?* Вона виявляє більшість помилок конфігурації за лічені секунди, перш ніж ті перетворяться на багатогодинне налагодження, і працює з тим самим мінімальним графом Input → Output, який ви вже знаєте з розділу 004.

Наприкінці ви перевірите контракт графа, виконаєте один виміряний кадр і виведете звіт про вимірювання, який покаже, чи справний конвеєр.

### Перевірка контракту {#step-validate-graph}

`validate()` — це перевірка на рівні контракту, яка виконується *до* `build()`. Вона перевіряє порядок вузлів, caps і шлях розбору бекенду, не передаючи жодних потокових даних, і повертає звіт із канонічним `error_code`. Порожній код або `ok` означає, що граф структурно коректний; будь-яке інше значення відносить збій до певної категорії (див. таксономію помилок нижче), тож ви знатимете, де шукати. Якщо виконати цю перевірку першою, ви ніколи не витратите час на налагодження поведінки під час виконання для графа, який усе одно не вдалося б побудувати.

### Запуск одного виміряного кадру {#step-run-with-measurement}

Далі побудуйте граф і запустіть один детермінований кадр у вікні `start_measurement()`. `output_memory = Owned` запитує власні вихідні буфери, щоб результат залишався дійсним після виклику. Одного кадру досить: якщо він проходить успішно, конвеєр працює; якщо генерується виняток, він містить структурований звіт, який можна класифікувати так само, як результат `validate()`.

### Читання діагностики середовища виконання {#step-read-diagnostics}

Коли один запуск уже зафіксовано, `MeasureReport` підсумовує стан конвеєра: лічильники (`inputs_enqueued`, `outputs_pulled`, відкинуті дані), наскрізну затримку, метрики вузлів, час плагінів/ядер, час на ребрах графа й необов’язкові дані про споживану потужність. `MeasureReport::to_text()` — це базовий знімок, який ви фіксуєте, перш ніж переходити до зондів і DOT-графів, описаних у розділі [На практиці](#in-practice).

## Run

Запустіть програму — у stdout мають з’явитися код перевірки й звіт про вимірювання. Команди **Python** і **C++ (prebuilt)** запускайте з **кореневої теки встановлення Neat** (теки, що містить `share/` і `lib/`), а команди **build from source** — з **кореневої теки репозиторію**. Для цього розділу архів моделі не потрібен.

**Python:**
```bash
python3 share/sima-neat/tutorials/012_diagnose_a_pipeline/diagnose_a_pipeline.py
```

**C++ (prebuilt):**
```bash
./lib/sima-neat/tutorials/tutorial_012_diagnose_a_pipeline
```

**C++ (build from source):**
```bash
./build.sh --target tutorial_012_diagnose_a_pipeline
./build/tutorials-standalone/tutorial_012_diagnose_a_pipeline
```

Очікуваний результат (значення лічильників і підсумковий рядок від запуску до запуску різняться):

```text
validate.error_code=
measure.inputs_enqueued=1 outputs_pulled=1
measure.text_size=...
[OK] 012_diagnose_a_pipeline
```

(Версія для Python виводить `validate_error_code=`, `inputs_enqueued=... outputs_pulled=...` і `measure_text_size=...`.) Щоб інтегрувати початковий код C++ цього розділу у свій проєкт із власним файлом `CMakeLists.txt` (тека extras не потрібна), див. розділ [Як запускати навчальні посібники](/tutorials#compile-a-copy-yourself) на головній сторінці.

## In Practice

Структурована діагностика, таксономія помилок, параметри налагодження й порядок дій у разі збоїв плагінів — усе, до чого ви вдаєтеся, коли `validate()` / `start_measurement()` / `MeasureReport` вказують на проблему.

### GraphReport

`GraphReport` збирає структуровану діагностику:
- рядок конвеєра (для відтворення)
- канонічний `error_code` (для машинної класифікації)
- `repro_note` (короткий опис для людини + підказка)
- звіти вузлів і назви елементів, що їм належать
- повідомлення шини та подробиці помилок
- необов’язкові лічильники потоку та часу

Коли виникає помилка, `NeatError` містить `GraphReport`, який можна записати в журнал або серіалізувати.

### Таксономія помилок

Помилки фреймворку використовують стабільні сімейства кодів:

| Код помилки | Значення | Типове виправлення |
|---|---|---|
| `misconfig.pipeline_shape` | Порушення контракту щодо порядку або форми вузлів | Переконайтеся, що `Input()` стоїть першим у push-конвеєрах, а `Output()` — останнім у pull-конвеєрах |
| `misconfig.caps` | Невідповідність перевизначення caps у фреймворку або контрактів суміжних вузлів | Узгодьте `caps_override` та оголошені контракти вузлів |
| `misconfig.media_caps` | Невідповідність під час узгодження медіаданих GStreamer у середовищі виконання | Узгодьте формат, роздільну здатність і частоту кадрів або вставте перетворення |
| `misconfig.input_shape` | Невідповідність форми або розкладки вхідного тензора, кадру чи зразка | Перевірте ширину/висоту/глибину, розкладку, dtype і сховище |
| `build.plugin_missing` | Потрібний елемент або кодек GStreamer недоступний | Встановіть або замініть його й перевірте за допомогою `gst-inspect-1.0` |
| `build.property_invalid` | Недійсна назва або значення властивості GStreamer | Перевірте її за допомогою `gst-inspect-1.0 <element>` |
| `build.pipeline_syntax` | Власний фрагмент GStreamer має недійсний синтаксис | Виправте його й перевірте за допомогою `gst-launch-1.0` |
| `runtime.pull` | Операція pull завершилася збоєм без точнішої причини | Перегляньте доданий звіт і першу помилку на попередніх етапах |
| `io.parse` | Помилка розбору або схеми JSON збереженого графа | Перевірте JSON і обов’язкові поля вузлів |
| `io.open` | Помилка відкриття, читання або запису файлу під час збереження чи завантаження графа | Перевірте наявність шляху, права доступу та стан сховища |

`PullError.code` використовує ту саму таксономію (не лише шляхи з винятками).
Це короткий список для первинної діагностики. Див. [повний каталог кодів помилок](/reference/error-codes), зокрема про перехід від попередніх узагальнених кодів середовища виконання та побудови.

### Програмна обробка

```cpp
#include "pipeline/ErrorCodes.h"
#include "pipeline/NeatError.h"

try {
  auto run = graph.build(input);
  simaai::neat::Sample out;
  simaai::neat::PullError perr;
  const auto st = run.pull(500, out, &perr);
  if (st == simaai::neat::PullStatus::Error) {
    if (perr.code == simaai::neat::error_codes::kMediaCaps) {
      // Fix the incompatible upstream/downstream media contract.
    } else {
      // Handle another specific code, including future codes, or report it.
    }
  }
} catch (const simaai::neat::NeatError& e) {
  if (e.report().error_code == simaai::neat::error_codes::kPluginMissing) {
    // Install or replace the missing GStreamer component.
  }
}
```

### Параметри налагодження (змінні середовища)

Основні змінні середовища (докладніше див. у розділі [Архітектура](/develop-apps/contribute/architecture)):
- `SIMA_GST_DOT_DIR`: запис DOT-графів у разі збоїв
- `SIMA_GST_BOUNDARY_PROBES`: лічильники потоку на межах
- `SIMA_GST_ELEMENT_TIMINGS`: час виконання кожного елемента
- `SIMA_GST_FLOW_DEBUG`: лічильники потоку для кожного елемента
- `SIMA_GST_ENFORCE_NAMES`: примусове дотримання контракту іменування

Щоб виконати короткий запуск і додати до помилки необроблений контекст GStreamer із прихованими чутливими даними, використайте:

```bash
SIMA_NEAT_VERBOSE_LEVEL=2 \
SIMA_NEAT_VERBOSE_TOPICS=gstreamer \
./your-neat-application
```

`NEAT_LOG_LEVEL=debug` не є налаштуванням Neat Library.

### Порядок налагодження

1. Спочатку зафіксуйте `GraphReport.error_code` і визначте за таксономією категорію збою.
2. Зафіксуйте `GraphReport.repro_note`, щоб отримати конкретний контекст і вбудовану підказку.
3. Зафіксуйте текст конвеєра: `Graph::describe_backend()` або `last_pipeline()`.
4. Зафіксуйте структуровану діагностику: `MeasureReport::to_text()` або `NeatError::report()`.
5. Знайдіть у `GraphReport.bus` джерело першої термінальної `ERROR` та її подробиці.
6. Якщо середовище виконання зависає або спрацьовують тайм-аути, увімкніть зонди на межах або елементах, щоб визначити, де зупиняється потік.

Рекомендований набір даних для служби підтримки:
- `error_code`
- `repro_note`
- повний `pipeline_string`
- перші 3–5 термінальних помилок шини (`GraphReport.bus`)
- перевизначення змінних середовища, використані під час run/validate

### Типові збої → способи усунення

| Симптом | Ймовірна причина | Виправлення |
|---|---|---|
| `missing ... plugin` | Не знайдено плагін GStreamer | Перевірте `GST_PLUGIN_PATH`, виконайте `gst-inspect-1.0 <plugin>` |
| `appsink 'mysink' not found` | Немає кінцевого `Output()` | Переконайтеся, що `Output` є останнім вузлом у конвеєрах run/build |
| `caps_override is set; renegotiation disabled` | caps закріплено | Приберіть `caps_override` або тримайте вхідні caps незмінними |
| `tensor caps change not supported` | Форма або dtype тензора змінюється під час виконання | Тримайте форму й dtype тензора незмінними (без повторного узгодження) |

### Налагодження збоїв плагінів

Коли плагін дає збій, Neat генерує `NeatError`, повідомлення якого містить помилку GStreamer і структурований рядок налагодження. За цими полями можна швидко знайти першопричину.

1. **Прочитайте структуровані поля.** Знайдіть у тексті помилки поля `debug` вигляду «ключ/значення»:
   - `node`: назва елемента конвеєра, на якому стався збій
   - `config_path`: файл конфігурації JSON (якщо є)
   - `model_path`: шлях до моделі або пакета моделі (якщо є)
   - `hint`: практичні поради щодо виправлення
   - `detail`: додатковий контекст, наприклад відсутні ключі або стан алокатора

   Повний список див. у довіднику [Формат помилок плагінів](/reference/error_format).
2. **Перевірте контекст конвеєра.** Візьміть рядок конвеєра з `Graph::last_pipeline()` або зі звіту про помилку:
   - Переконайтеся, що назва з `node` є в конвеєрі.
   - Переконайтеся, що `config_path` існує й доступний для читання.
   - Для помилок caps перевірте елементи вище за потоком, які узгоджують caps із вузлом, де стався збій.
3. **Застосуйте типові виправлення.**
   - **Помилки конфігурації**: перевірте синтаксис JSON, обов’язкові ключі та всі шляхи до моделей.
   - **Помилки caps**: додайте або виправте елементи-парсери (наприклад, `h264parse`), переконайтеся, що caps містять обов’язкові поля, як-от `parsed=true`, `stream-format=byte-stream`, `alignment=au`.
   - **Помилки алокатора**: переконайтеся, що елементи вище за потоком використовують потрібний тип алокатора (системна пам’ять чи пам’ять/сегмент simaai).
4. **Зберіть більше діагностичних даних** за допомогою наведених вище параметрів налагодження (`SIMA_GST_DOT_DIR`, `SIMA_GST_FLOW_DEBUG`, `SIMA_GST_ELEMENT_TIMINGS`).
