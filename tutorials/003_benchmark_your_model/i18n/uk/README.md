## Concept

Запустіть скомпільовану модель на детермінованих синтетичних тензорах і виведіть основні показники затримки, пропускної здатності, потужності та енергії, які повертає `Model::benchmark()`.

## Walkthrough

Розділи 001 і 002 показали, як запустити модель один раз, а потім — як керувати нею асинхронно. Цей розділ відповідає на наступне практичне запитання: «Наскільки швидко ця модель працює на пристрої?» API бенчмарку навмисно невеликий. Ви завантажуєте модель, вибираєте, скільки зразків виміряти, викликаєте `benchmark(...)` і читаєте повернений `BenchmarkReport`.

Для створення детермінованих синтетичних вхідних даних бенчмарк використовує `input_specs()` моделі. Тому він корисний для швидкого базового (smoke) бенчмарку моделі й для порівняння скомпільованих варіантів моделі, але це не бенчмарк камери. Він не враховує декодування з камери, реальну мінливість попередньої обробки, динамічні розміри вхідних даних і поведінку постобробки, що залежить від даних.

### Завантаження моделі {#step-load-model}

Почніть із того самого скомпільованого архіву `.tar.gz`, що й у попередніх навчальних посібниках про моделі. Зображення не потрібне, бо бенчмарк створює синтетичні тензори з оголошених специфікацій входів моделі.

**C++:** Створіть `simaai::neat::Model`, передавши шлях до архіву.

**Python:** Створіть `pyneat.Model`, передавши шлях до архіву.

### Запуск бенчмарку {#step-run-benchmark}

Викличте `benchmark(samples)`. API прогріває модель, вимірює затримку одиночного запиту (single-flight), потім вимірює пропускну здатність в окремому асинхронному проході push/pull, виводить підсумок у stdout і повертає ті самі основні значення в `BenchmarkReport`.

Кожен прохід триває, доки не буде виміряно щонайменше `samples` вхідних даних і не мине 10 секунд, тож показники потужності й температури в проході пропускної здатності охоплюють кілька зразків. Задайте `BenchmarkOptions::min_duration_ms`, щоб змінити цей мінімум, або 0 для швидкої базової (smoke) перевірки, у якій кожен прохід зупиняється після `samples` вхідних даних.

Моделі виявлення, маршрут яких закінчується BoxDecode, також можуть використовувати `BenchmarkOptions`. Задайте `original_width`, `original_height` і `resize_mode`, щоб описати геометрію початкового зображення, яку BoxDecode використовує, коли переводить виявлення з координат моделі. Синтетичний тензор зберігає форму, якої очікує модель:

```cpp
simaai::neat::BenchmarkOptions options;
options.num_samples = 100;
options.original_width = 1920;
options.original_height = 1080;
options.resize_mode = simaai::neat::ResizeMode::Letterbox;
auto report = model.benchmark(options);
```

Python надає ті самі поля через `pyneat.BenchmarkOptions`. Задайте обидва початкові розміри або не задавайте жодного; якщо їх не задано, бенчмарк отримує геометрію з визначеного маршруту моделі. Геометрія бенчмарку, задана для окремого запуску, має пріоритет над застарілою геометрією BoxDecode у `ModelOptions`.

### Читання звіту {#step-read-report}

Повернений звіт починається з основних полів, потрібних більшості користувачів: середньої наскрізної затримки в мілісекундах, пропускної здатності в кадрах за секунду, середньої й пікової потужності SoM у ватах та енергії в джоулях, потрібної для обробки `samples` вхідних даних. `throughput_duration_ms` показує, скільки тривав прохід вимірювання пропускної здатності.

Дані про потужність надає Sentinel — демон телеметрії плати, який налаштовує інсталятор Neat. `report.telemetry` також містить потужність шин живлення, температури кристала й плати, завантаження CPU та пам’ять MLA для проходу вимірювання пропускної здатності; опис кожного поля див. у розділі [Вимірювання виконання моделі](/develop-apps/development-workflow/model#power-and-board-telemetry). Якщо Sentinel не запущено, бенчмарк однаково повідомляє затримку й пропускну здатність, залишає поля потужності нульовими й записує причину в `report.telemetry.status`.

### Для досвідчених: статистика шарів і етапів MLA {#step-read-mla-stats}

Два необов’язкові параметри запускають `mla-rt` після бенчмарку, щоб виміряти час виконання скомпільованого коду MLA. Обидва за замовчуванням вимкнені й потребують незайнятого DevKit без інших навантажень MLA. Додайте `--include-mla-layer-stats` або `--include-mla-stage-stats` до будь-якої з команд посібника або ввімкніть їх через API:

```cpp
simaai::neat::BenchmarkOptions options;
options.include_mla_layer_stats = true;
options.include_mla_stage_stats = true;
auto report = model.benchmark(options);
```

```python
options = pyneat.BenchmarkOptions()
options.include_mla_layer_stats = True
options.include_mla_stage_stats = True
report = model.benchmark(options)
```

Для кожного скомпільованого шару MLA `report.mla_layer_stats.layers` містить `stage_index` (нумерація з нуля), `name` і `latency_us` — апаратний час виконання з одного проходу профілювання, який запускає лише цей шар. Записи no-op із нульовим часом зберігаються. Затримки шарів у сумі не дають ні затримки етапу, ні основної затримки.

Для кожного етапу MLA `report.mla_stage_stats.stages` містить `stage_index` і `latency_us` — середній апаратний час 200 безперервних запусків цього етапу. Затримка етапу охоплює обчислення MLA та операції читання й запису DRAM, які виконує програма. Вона не враховує завантаження моделі, обробку на хості й EV74 та накладні витрати конвеєра.

Якщо `mla-rt` відсутній, завершується з помилкою або перевищує час очікування, `benchmark()` однаково повертає основні вимірювання, залишає список порожнім і записує причину в `report.mla_layer_stats.status` або `report.mla_stage_stats.status`. В інших випадках статус має значення `"not requested"` або `"ok"`. Якщо запуск `mla-rt` завершився з помилкою, перевищив час очікування або аварійно завершився, у MLA може лишатися незавершена робота, тому подальше профілювання в тому самому процесі пропускається з цією причиною. Не навантажуйте DevKit, доки не переконаєтеся, що MLA відновився.

Статистика шарів MLA враховує вибрану термінальну політику: вона вимірює лише етапи MLA у вибраному маршруті інференсу, і кожен із них зберігає свій `stage_index` у повній моделі.

### Збереження звіту {#step-save-report}

Викличте `report.save(path)`, щоб записати повний звіт у форматі YAML або JSON, разом зі статистикою шарів і етапів MLA, якщо її запитано:

```cpp
auto path = report.save("results/model/yolo_benchmark.yaml");
auto json_path = report.save("results/model/yolo_benchmark.json");
```

```python
path = report.save("results/model/yolo_benchmark.yaml")
json_path = report.save("results/model/yolo_benchmark.json")
```

Розширення `.json` означає JSON; `.yaml` і всі інші розширення — YAML. Ім’я файлу зберігається без змін.

Укажіть шлях до файлу разом з його іменем. Відсутні батьківські теки створюються, наявний файл замінюється, а метод повертає шлях записаного файлу. Збереження виконується лише явно: `benchmark()` не створює файл звіту автоматично.

До будь-якої з команд посібника додайте `--report results/model/yolo_benchmark.yaml`. Поєднайте його з `--include-mla-layer-stats` або `--include-mla-stage-stats`, щоб зберегти основні вимірювання разом із часовими показниками MLA.

## Run

Запустіть програму — ви маєте побачити підсумок бенчмарку, який виводить `benchmark()`, а після нього ті самі значення, виведені з поверненого звіту. Команди **Python** і **C++ (prebuilt)** запускайте з **кореневої теки встановлення Neat** (теки, що містить `share/` і `lib/`), а команди **build from source** — з **кореневої теки репозиторію**.

**Python:**
```bash
python3 share/sima-neat/tutorials/003_benchmark_your_model/benchmark_your_model.py \
  --model /tmp/resnet_50.tar.gz --samples 100
```

**C++ (prebuilt):**
```bash
./lib/sima-neat/tutorials/tutorial_003_benchmark_your_model \
  --model /tmp/resnet_50.tar.gz --samples 100
```

**C++ (build from source):**
```bash
./build.sh --all --no-doc
./build/tutorials/tutorial_003_benchmark_your_model \
  --model /tmp/resnet_50.tar.gz --samples 100
```

## In Practice

Використовуйте цей бенчмарк, коли потрібна швидка відповідь щодо скомпільованого архіву моделі: чи він працює, яка виміряна асинхронна пропускна здатність і які основні показники потужності плати на цій цільовій платформі?

Щоб оцінити продуктивність застосунку, виконайте бенчмарк і для реального конвеєра. Синтетичні вхідні дані моделі навмисно стабільні, тому вони не відображають джитер камери, витрати на кодек, реальну попередню обробку, планування на хості під навантаженням і логіку застосунку на подальших етапах. Про налаштування глибини черги та зворотного тиску з власноруч побудованим асинхронним запуском див. [Налаштування пропускної здатності та глибини черги](/tutorials/tune-throughput-and-queues).

`Model::benchmark()` потребує конкретних розмірів `input_specs()`. Якщо форма входу динамічна або неконкретна, бенчмарк явно завершується з помилкою, а не вгадує форму.
