## Concept

Запустіть скомпільовану модель із детермінованими синтетичними тензорами та виведіть основні показники затримки, пропускної здатності, споживання енергії, які повертає `Model::benchmark()`.

## Walkthrough

У розділах 001 і 002 було показано, як запустити модель один раз, а потім як керувати нею асинхронно. У цьому розділі дається відповідь на наступне практичне питання: «Наскільки швидко працює ця модель на пристрої?» API для тестування навмисно невеликий. Ви завантажуєте модель, вибираєте, скільки зразків потрібно виміряти, викликаєте `benchmark(...)` і зчитуєте повернутий `BenchmarkReport`.

Для тестування використовуються `input_specs()` моделі для створення детермінованих синтетичних вхідних даних. Це робить його корисним для швидкого тестування моделі та порівняння скомпільованих варіантів моделі, але це не тестування камери. Воно не включає декодування камери, реальну варіативність попередньої обробки, динамічні розміри вхідних даних або поведінку постобробки, що залежить від даних.

### Завантажте модель {#step-load-model}

Почніть з того самого скомпільованого `.tar.gz` архіву, який використовувався в попередніх навчальних посібниках з моделі. Зображення не потрібне, оскільки для тестування створюються синтетичні тензори на основі оголошених вхідних специфікацій моделі.

**C++:** Створіть `simaai::neat::Model` на основі шляху до архіву.

**Python:** Створіть `pyneat.Model` на основі шляху до архіву.

### Запустіть тестування {#step-run-benchmark}

Викличте `benchmark(samples)`. API прогріває модель, вимірює затримку на `samples` вхідних даних, подаючи їх по одному (single-flight), потім вимірює пропускну здатність в окремому асинхронному проході передачі/отримання (push/pull), виводить зведену інформацію в stdout і повертає ті самі основні значення у `BenchmarkReport`.

Прохід вимірювання пропускної здатності триває, доки не виміряє щонайменше `samples` вхідних даних і не мине 30 секунд, тож його показники потужності й температури стабільні. Задайте `BenchmarkOptions::min_duration_ms`, щоб змінити цей мінімум, або встановіть 0 для швидкої перевірки, яка зупиняється після `samples` вхідних даних.

Моделі виявлення, маршрут яких закінчується на BoxDecode, також можуть використовувати `BenchmarkOptions`. Встановіть `original_width`, `original_height` і `resize_mode`, щоб описати геометрію вихідного зображення, яку
BoxDecode використовує під час відображення виявлень з координат моделі. Синтетичний тензор залишається
розміром, як у моделі:

```cpp
simaai::neat::BenchmarkOptions options;
options.num_samples = 100;
options.original_width = 1920;
options.original_height = 1080;
options.resize_mode = simaai::neat::ResizeMode::Letterbox;
auto report = model.benchmark(options);
```

Python надає доступ до тих самих полів через `pyneat.BenchmarkOptions`. Вкажіть обидва вихідні розміри або
залиште обидва поля порожніми; якщо їх не вказано, еталонна програма визначає геометрію на основі обчисленого маршруту моделі. Геометрія, що використовується під час кожного запуску еталонної програми, має пріоритет над застарілою геометрією BoxDecode у `ModelOptions`.

### Ознайомтеся зі звітом {#step-read-report}

Звіт, що повертається, починається з основних полів, які потрібні більшості користувачів: середня затримка від кінця до кінця в мілісекундах, пропускна здатність у кадрах за секунду, середня й пікова потужність SoM у ватах та енергія в джоулях, потрібна для обробки `samples` вхідних даних. `throughput_duration_ms` показує, скільки тривав прохід вимірювання пропускної здатності.

Дані про потужність надходять від Sentinel — демона телеметрії плати, який налаштовує інсталятор Neat. `report.telemetry` також містить потужність шин живлення, температури кристала й плати, завантаження CPU та пам’ять MLA для проходу вимірювання пропускної здатності; опис кожного поля див. у розділі [Вимірювання виконання моделі](/develop-apps/development-workflow/model#power-and-board-telemetry). Якщо Sentinel не запущено або він записує іншу трасу, тест усе одно надає інформацію про затримку та пропускну здатність, залишає поля потужності нульовими та записує причину в `report.telemetry.status`.

### Розширені можливості: статистика шарів {#step-read-layer-stats}

Профілювання шарів — це розширена опція, яку потрібно ввімкнути явно. `BenchmarkOptions.include_layer_stats` за замовчуванням має значення `false`; звичайне тестування зберігає наявні основні вимірювання та не запускає профілювання шарів. Додайте `--include-layer-stats` до команди прикладу або ввімкніть опцію через `BenchmarkOptions`:

```cpp
simaai::neat::BenchmarkOptions options;
options.include_layer_stats = true;
auto report = model.benchmark(options);
```

```python
options = pyneat.BenchmarkOptions()
options.include_layer_stats = True
report = model.benchmark(options)
```

Переберіть `report.layer_stats`, щоб надрукувати `stage_index`, `name` і `total_execution_time_us` для кожного скомпільованого шару. Приклади зберігають порядок компілятора та записи no-op із нульовим часом. `stage_index` — це порядок виконуваних етапів від нуля, включно з A65.

Після закриття засобів вимірювання NEAT вибирає MLA ELF із маніфесту розпакованого MPK і зіставляє його з `<elf_stem>_stats.yaml`. YAML копіюється без змін до тимчасового каталогу, запускається `mla-rt --connect mip,ma -vs -N --per-layer-stats <copied_yaml> <elf>`, створений `_output.yaml` перевіряється й читається до звіту, а тимчасові файли видаляються. Обмеження часу — 120 секунд на етап MLA; використовуються стандартні входи mla-rt. Потрібен вільний DevKit без інших навантажень MLA та `mla-rt` у `PATH`. За значення `false` список `report.layer_stats` порожній, виводяться лише основні значення. Приклад виводу з увімкненою опцією:

```text
Layer stats (execution time in microseconds):
  stage_index=0 name=MLA_0/conv total_execution_time_us=161.95
  stage_index=0 name=MLA_0/noop total_execution_time_us=0
  stage_index=2 name=MLA_1/conv total_execution_time_us=42.5
```

Потрібен MLA-RT із виправленням передачі керування від MIP до драйвера ядра. Перевірено на eLxr B2121 з MLA-RT `2.2.0~git202610140145.603a8c6-2121` (коміт `603a8c6`). Із цим виправленням звичайний інференс можна відновити відразу після повернення `benchmark()`, без ручного скидання чи затримки. Старі збірки можуть залишати апаратне забезпечення в стані, що спричиняє збій наступного інференсу через драйвер ядра.

Підтримуються послідовні виклики `Model.run()` до й після профілювання, включно з повторним використанням кешованого засобу виконання. Перед запитом статистики шарів завершіть поточний інференс. Профілювання не повинно виконуватися одночасно з інференсом через `Model.run()`, явно створений засіб виконання чи іншу програму.

## Run

Запустіть його, і ви повинні побачити зведену інформацію про результати тестування, яку буде надруковано. `benchmark()`, після чого будуть надруковані ті самі значення з отриманого звіту. Запустіть команди **Python** і **C++ (попередньо скомпільовані)** зNeat встановити в кореневу директорію **(директорію, яка містить) `share/` і `lib/`); виконайте команди **збірки з вихідного коду** з **кореневої директорії репозиторію**.

## In Practice

Використовуйте цей тест для швидкої перевірки скомпільованого архіву моделі: чи працює він, яка виміряна асинхронна пропускна здатність і які основні показники енергоспоживання на цільовій платформі?

Для оцінки продуктивності застосунку також протестуйте реальний конвеєр. Синтетичний вхідний сигнал моделі навмисно стабільний, тому він не відображає тремтіння камери, обчислювальні витрати кодека, реальну попередню обробку, планування хоста під навантаженням або логіку застосунку на наступних етапах. Щоб налаштувати глибину черги та механізми регулювання потоку даних за допомогою власноруч створеного асинхронного запуску, див. [Налаштування пропускної здатності та глибини черги](/tutorials/tune-throughput-and-queues).

`Model::benchmark()` вимагає конкретних розмірів `input_specs()`. Якщо форма вхідних даних є динамічною або не конкретною, тест чітко покаже помилку, замість того, щоб намагатися вгадати форму.

## Збереження звіту

Викличте `report.save("results/model/yolo_benchmark.yaml")` у C++ або Python, щоб записати YAML саме до цього файлу. Відсутні батьківські каталоги створюються, а наявний файл замінюється атомарно. Повертається переданий вами шлях. У прикладі цей самий шлях можна задати через `--report`. Збереження виконується явно; `benchmark()` не створює файл звіту автоматично.

Збережені звіти також містять перцентилі затримки, метадані інтервалу вимірювання пропускної здатності та телеметрію Sentinel.

YAML містить `latency_ms`, `fps`, `avg_power_watts`, `energy_joules` і `layer_stats`. Кожен запис `LayerStats` має поля `name`, `stage_index` і `total_execution_time_us` (апаратний лічильник `run_time` у мікросекундах). Назви MLA, створені компілятором, можуть відповідати об’єднанню або розділенню початкових операторів ONNX. Записи no-op із нульовим часом також зберігаються. Профілювання шарів і основні вимірювання використовують окремі запуски та вхідні дані, тому їхні часи не слід прирівнювати. `stage_index` — це цілий індекс від нуля в порядку виконання моделі, що включає виконувані етапи MLA та A65, а не порядок файлів в архіві. Для одного етапу використовується `0`; для MLA–A65–MLA записи шарів MLA мають індекси `0` і `2`.

Відсутні файли, помилки процесу, перевищення часу та некоректна статистика спричиняють виняток. Вхідний YAML зберігається, а тимчасові файли видаляються після успіху та після помилки.
