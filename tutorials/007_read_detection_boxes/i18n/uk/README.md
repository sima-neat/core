# 007 Зчитування рамок виявлення з виходу моделі

## Metadata
| Field | Value |
| --- | --- |
| Category | Models & Inference |
| Difficulty | Intermediate |
| Estimated Read Time | 15–20 хвилин |
| Model | yolo_v8s |
| Labels | postprocessing, boxdecode, detection |

## Concept

Декодуйте необроблений вихід моделі в придатні для використання обмежувальні рамки за допомогою `SimaBoxDecode` — фільтрування за порогом, NMS і перетворення координат зібрано в одному етапі постобробки, — а потім зчитайте результат як розібрані рамки або як необроблений упакований буфер байтів.

## Walkthrough

Детектор не повертає рамки безпосередньо. Його необроблений вихід — це набір карт ознак, до яких ще треба застосувати поріг, пригнічення немаксимумів (NMS) і перетворення координат, перш ніж вони почнуть щось означати. `SimaBoxDecode` — це етап постобробки, який виконує всі три дії за один оптимізований крок і перетворює тензори інференсу на остаточні виявлення в пікселях початкового зображення.

У цьому розділі налаштовується таке декодування: `decode_type` вибирає родину моделей, поріг оцінки відсікає кандидатів із низькою впевненістю, поріг IoU для NMS пригнічує перекриття, а `top_k` обмежує кількість результатів. Потім модель запускається, і програма зчитує, скільки виявлень повернулося. У підсумку ви матимете налаштований конвеєр детектора й кількість виявлень, зчитану з його виходу, а також повний формат даних (у довідці «На практиці» нижче), щоб самостійно розбирати рамки в будь-якому середовищі виконання.

### Налаштування декодування {#step-configure-decode}

Ці параметри задають і вхідний контракт, і поведінку постобробки. `decode_type` (тут `YoloV8`) вибирає шлях декодування для родини моделей. Поріг впевненості відкидає слабких кандидатів до NMS; поріг IoU для NMS визначає, наскільки агресивно об’єднуються рамки, що перекриваються; `top_k` обмежує кінцеву кількість, щоб витрати наступних етапів були передбачуваними; а `boxdecode_original_width`/`boxdecode_original_height` переводять декодовані координати назад у пікселі початкового зображення. Поради щодо налаштування кожного з цих параметрів наведено в розділі «На практиці» нижче.

Ця YOLO-модель очікує значення RGB у діапазоні `[0,1]`, тому приклад задає `normalize.enable = On`.

**C++:** `decode_type` приймає значення переліку `BoxDecodeType::YoloV8`. Значення порогу, NMS і `top_k` передаються пізніше через `stages::BoxDecodeOptions`, а не через `Model::Options`.

**Python:** `decode_type` приймає значення переліку `pyneat.BoxDecodeType.YoloV8`, а `score_threshold`, `nms_iou_threshold`, `top_k` і `boxdecode_original_width`/`boxdecode_original_height` задаються безпосередньо в `ModelOptions`. (`score_threshold` і `detection_threshold` у C++ — це назви того самого параметра; див. примітку щодо назв у розділі «На практиці».)

### Створення моделі {#step-load-model}

Створення `Model` з архіву й параметрів прив’язує конфігурацію декодування до моделі, тож етапи інференсу й постобробки, похідні від неї, використовують наведені вище налаштування.

### Запуск попередньої обробки, інференсу й декодування {#step-run-decode}

На цьому кроці кадр проходить через попередню обробку, інференс на MLA і декодер рамок, і на виході утворюється результат виявлення.

**C++:** Шлях задано явно, етап за етапом: `stages::Preproc` створює вхідний тензор, `stages::Infer` запускає модель, а `stages::BoxDecodeOptions` (з `detection_threshold = 0.55`, `nms_iou_threshold = 0.5`, `top_k = 100`) налаштовує декодування, яке виконується далі.

**Python:** `model.run([tensor])` виконує весь налаштований шлях за один виклик і повертає `TensorList`. Коли BoxDecode підключено до маршруту моделі, перший тензор — це упакований вихід `BBOX`.

### Зчитування рамок {#step-read-boxes}

Насамкінець перетворіть вихід декодування на дані, з якими можна працювати.

**C++:** `stages::BoxDecodeResults(...)` повертає `BoxDecodeResultList`; вектор `boxes` першого результату вже розібрано у формат `{x1, y1, x2, y2, score, class_id}` з обмеженням координат межами початкового зображення, тому `decoded.boxes.size()` і є кількістю виявлень.

**Python:** Результат — один тензор `BBOX` типу `uint8` в `outputs[0]`. Перші чотири байти в порядку little-endian містять кількість виявлень (`struct.unpack_from("<I", buf, 0)`); повну структуру запису описано в розділі «На практиці». Якщо середовище виконання не підключає BoxDecode до `model.run`, повернутий `TensorList` натомість містить необроблені виходи карт ознак.

## In Practice

`SimaBoxDecode` видає один вихідний тензор із міткою `BBOX`. Тензор містить упакований буфер байтів, який парсер середовища виконання перетворює на виявлення зі значеннями з рухомою комою. Розуміння цього дворівневого контракту (буфер передавання проти розібраних записів `Box`) — ключ до зчитування виходу і з Python, і з C++.

### Тензор BBOX

Етап декодування створює один тензор `BBOX` на кожен вхідний кадр із такими характеристиками:

| Поле | Значення |
| --- | --- |
| `semantic.detection.format` | `"BBOX"` |
| `dtype` | `UInt8` |
| `shape` | ранг 1: `[N_bytes]`, де `N_bytes` — місткість буфера, заданого в архіві моделі (наприклад, `[20160]` для стандартного пакета YOLOv8) |

Форма тензора — це **кількість байтів**, а не кількість виявлень. Упаковані байти містять невеликий заголовок і неперервний масив записів рамок фіксованого розміру. `N_bytes` визначається полем `buffers.input[0].size` в архіві моделі (у конфігураційному JSON етапу boxdecode) і обмежує максимальну кількість виявлень, яку декодер може видати за один кадр (як розміри, задані під час виконання, взаємодіють зі значеннями з пакета, описано в розділі «Контракт перевизначення» нижче).

### Упакований формат передавання

Буфер `uint8` розміщено в порядку little-endian:

```
offset  size  content
------  ----  -------
  0      4    uint32  N = number of valid detections in this frame
  4     24    RawBox[0]
 28     24    RawBox[1]
  .      .      ...
  .      .    RawBox[N-1]
                   (trailing bytes up to buffer capacity are padding, ignored)
```

Кожен запис `RawBox` займає 24 байти:

| Зміщення в записі | Розмір | Тип | Поле | Значення |
| --- | --- | --- | --- | --- |
|  0 | 4 | int32 | `x`     | x верхнього лівого кута в пікселях початкового зображення |
|  4 | 4 | int32 | `y`     | y верхнього лівого кута в пікселях початкового зображення |
|  8 | 4 | int32 | `w`     | ширина в пікселях початкового зображення |
| 12 | 4 | int32 | `h`     | висота в пікселях початкового зображення |
| 16 | 4 | float32 | `score` | впевненість виявлення після NMS у діапазоні `[0.0, 1.0]` (саме це значення порівнюється з `detection_threshold`) |
| 20 | 4 | int32 | `class_id` | ідентифікатор передбаченого класу (визначається моделлю, нумерація з 0; відповідність назвам класів зберігається в метаданих архіву моделі) |

Канонічний формат Python `struct` для одного запису — `"<iiiifi"`
(little-endian, 4 цілі числа зі знаком, одне число з рухомою комою, одне ціле число зі знаком).

Допоміжні функції розбору в середовищі виконання (`parse_bbox_bytes` / `decode_bbox_tensor` в `include/pipeline/DetectionTypes.h`; контракт формату закріплює `tests/unit_testing/unit_detection_types_bbox_test.cpp`) розгортають кожен `RawBox` у структуру `Box` для подальшого коду:

```cpp
struct Box {
  float x1, y1, x2, y2;  // x2 = x + w, y2 = y + h; clamped to [0, img_w|h]
  float score;
  int   class_id;
};
```

### Простір координат

Координати, декодовані з `BBOX`, задано в **пікселях початкового зображення**, тобто в тій самій
системі координат, яку ви передали як `original_width` / `original_height` (або з якою
було упаковано архів моделі). Вони **не** нормалізовані до `[0, 1]` і **не**
задані у внутрішньому просторі входу моделі після letterbox.
Парсер обмежує `(x1, y1, x2, y2)` діапазонами `[0, original_width]` / `[0, original_height]`,
тож код, який викликає парсер, може малювати їх безпосередньо на початковому кадрі.

### Приклад розрахунку

З конфігурацією середовища виконання з навчального посібника (`original_width = 640`,
`original_height = 640`, `top_k = 100`) і стандартним пакетом YOLOv8
(`buffers.input[0].size = 20160` у конфігурації boxdecode) один декодований
кадр дає:

- `out.kind == SampleKind.Tensor`
- `out.payload_tag == "BBOX"`
- `out.tensor.dtype == UInt8`, `out.tensor.shape == [20160]`
- Байти `[0:4]` містять `N` у порядку little-endian; `0 <= N <= 100`, бо
  `top_k = 100`. `N`, що дорівнює `0`, означає «у цьому кадрі немає виявлень
  вище порогу» — цикл не виконується жодного разу, і нічого не виводиться.
- Байти `[4 : 4 + 24 * N]` містять дійсні виявлення; усе після цього
  зміщення — нулі або заповнення, яке слід ігнорувати.

Зчитування рамки в Python — це виклик `struct.unpack_from`:

```python
import struct
payload = out.tensor.copy_payload_bytes()
count = struct.unpack_from("<I", payload, 0)[0]
for i in range(count):
    x, y, w, h, score, cls = struct.unpack_from("<iiiifi", payload, 4 + 24 * i)
    # (x, y, w, h) in source pixels; x2 = x + w, y2 = y + h
```

У C++ допоміжна функція `stages::BoxDecode` повертає `BoxDecodeResult`, у якому
це розпакування вже виконано: `result.boxes[i]` — це `Box`, де
`(x1, y1, x2, y2)` уже заповнено з `(x, y, x+w, y+h)` і обмежено
розмірами зображення.

### Контракт перевизначення: розміри під час виконання проти значень за замовчуванням з архіву моделі

`SimaBoxDecode` створюється з навченого архіву моделі, у якому упаковано
значення за замовчуванням для `decode_type`, `detection_threshold`, `nms_iou_threshold`,
`top_k`, `original_width` і `original_height`. Публічний конструктор

```cpp
SimaBoxDecode(const Model& model,
              const std::string& decode_type = "",
              int original_width = 0, int original_height = 0,
              double detection_threshold = 0.0,
              double nms_iou_threshold = 0.0,
              int top_k = 0);
```

і його відповідник у Python `pyneat.nodes.sima_box_decode(model, ...)` застосовують до кожного поля просте
правило: «додатне значення перевизначає, нуль або порожнє значення зберігає».

> **Примітка щодо назв.** `detection_threshold` — це назва, яку використовує
> конструктор `SimaBoxDecode`. `ModelOptions.score_threshold` (його використовує
> навчальний посібник Python) передається в той самий аргумент. Обидві назви
> позначають той самий параметр.

| Аргумент під час виконання | Передане значення | Поведінка |
| --- | --- | --- |
| `decode_type` | `""` (порожній рядок) | зберегти значення з архіву моделі або визначене за шляхом моделі |
| `decode_type` | непорожній рядок | перевизначити значення з архіву моделі для цього запуску |
| `original_width` / `original_height` | `0` | зберегти розмір, упакований в архів моделі |
| `original_width` / `original_height` | додатне ціле число | переписати `original_width` / `original_height` у чинній конфігурації |
| `detection_threshold` | `0.0` | зберегти поріг, упакований в архів моделі |
| `detection_threshold` | `> 0.0` | перевизначити (також вмикає попередження YOLOv8 про різке зростання витрат, описане нижче) |
| `nms_iou_threshold` | `0.0` | зберегти NMS IoU, упакований в архів моделі |
| `nms_iou_threshold` | `> 0.0` | перевизначити |
| `top_k` | `0` | зберегти top-K, упакований в архів моделі |
| `top_k` | `> 0` | перевизначити |

Правило діє окремо для кожного поля:

- **Шлях Python** — навчальний посібник перевизначає кожне поле, бо
  `ModelOptions` задає додатні значення.
- **Шлях C++** — `read_detection_boxes.cpp` передає `0.55f, 0.5f, 100` (тобто
  `detection_threshold`, `nms_iou_threshold` і `top_k` перевизначено),
  а також додатні `bgr.cols, bgr.rows` (тобто `original_width` /
  `original_height` теж перевизначено).

Практичні наслідки:

- Якщо архів моделі упаковано для іншої роздільної здатності, ніж ваші початкові кадри,
  передавайте `original_width` і `original_height` явно, щоб координати
  потрапляли в пікселі початкового зображення.
- Залишити `detection_threshold` і `nms_iou_threshold` рівними `0.0` —
  найнадійніший спосіб отримати перевірені значення за замовчуванням з архіву моделі; перевизначайте їх лише тоді, коли
  свідомо їх переналаштовуєте.
- Обережно з низьким `detection_threshold`. Що він нижчий, то більше
  кандидатів проходить поріг, а витрати NMS зростають пропорційно квадрату
  кількості рамок, що пройшли поріг, — тож дуже низький поріг може різко збільшити
  обчислення й затримку постобробки. Знижуйте його лише настільки, наскільки потрібно, щоб помітити
  слабкі виявлення, і поєднуйте з `top_k`, щоб обмежити найгірший випадок.

### Типи декодування й контракти тензорів

`BoxDecodeType` — це типізований API (`simaai::neat::BoxDecodeType` / `neat.BoxDecodeType`), і для етапів декодування його слід завжди задавати явно. Наведений нижче контракт середовища виконання взято з `internals/gst_plugins/neatobjectdecode/gstneatboxdecode.cpp` (`infer_num_classes`, `infer_yolo_decoupled_classes`, `infer_yolo_packed_classes`, `compute_required_output_size`).

Основні правила контракту тензорів:
- Типи декодування родини YOLO, крім виявлення `yolov5` (`yolo`, `yolov5-seg`,
  `yolov7*`, `yolov8*`, `yolov9*`, `yolov10*`):
  - Роз’єднані виходи: глибина виходів класів має повторюватися й бути `> 4`.
  - Упаковані виходи: глибина кожного виходу має відповідати `depth = 3 * (num_classes + 5)` і бути однаковою для всіх виходів.
- Виявлення `yolov5`: рівно три недекодовані упаковані виходи P3/P4/P5
  з геометрією кроку 8/16/32 і глибиною `3 * (num_classes + 5)`.
- `yolo26`: роз’єднані згруповані виходи з 4-канальними тензорами необроблених рамок l/t/r/b і повторюваною глибиною виходів класів `> 4`.
- `detr`: кількість каналів класів визначається за максимальною глибиною серед виходів і має бути `> 4`.
- Інші типи декодування, не YOLO (`effdet`, `rcnn-stage1`, `centernet`): резервне визначення класів використовує максимальну глибину й вимагає `> 4`.
- Токени декодування сегментації (`*-seg`) вмикають у v2 розрахунок розміру виходу як для сегментації (додають корисні дані маски для кожного виявлення).

| `BoxDecodeType::YoloV7` | `yolov7` | контракт глибини YOLO для роз’єднаних або упакованих виходів |
| `BoxDecodeType::YoloV7Seg` | `yolov7-seg` | контракт глибини YOLO + шлях сегментації |
| `BoxDecodeType::YoloV8` | `yolov8` | контракт глибини YOLO для роз’єднаних або упакованих виходів |
| `BoxDecodeType::YoloV8Seg` | `yolov8-seg` | контракт глибини YOLO + шлях сегментації |
| `BoxDecodeType::YoloV8Pose` | `yolov8-pose` | контракт глибини YOLO для роз’єднаних або упакованих виходів |

| `BoxDecodeType::YoloV10Seg` | `yolov10-seg` | контракт глибини YOLO + шлях сегментації |
| `BoxDecodeType::YoloV26` | `yolo26` | згруповані виходи YOLO26 з необробленими рамками l/t/r/b + виходи оцінок класів |
| `BoxDecodeType::Detr` | `detr` | `num_classes = max(depth)` (має бути `> 4`) |
| `BoxDecodeType::EffDet` | `effdet` | резервне визначення за максимальною глибиною (`> 4`) |
| `BoxDecodeType::RcnnStage1` | `rcnn-stage1` | резервне визначення за максимальною глибиною (`> 4`) |
| `BoxDecodeType::Centernet` | `centernet` | резервне визначення за максимальною глибиною (`> 4`) |

Поведінка з негайною відмовою:
- `stages::BoxDecodeOptions` треба створювати явно, із зазначенням типу декодування.
- `stages::BoxDecode(...)` і `nodes::SimaBoxDecode(...)` одразу завершуються помилкою для `BoxDecodeType::Unspecified`.

Явне задання типу декодування:

```cpp
simaai::neat::stages::BoxDecodeOptions opt(simaai::neat::BoxDecodeType::YoloV8);
opt.detection_threshold = 0.25;
opt.nms_iou_threshold = 0.5;
opt.top_k = 100;
```

```python
opt = neat.ModelOptions()
opt.decode_type = neat.BoxDecodeType.YoloV8
```

## Run

Команди **Python** і **C++ (prebuilt)** запускайте з **кореневої теки встановлення Neat** (теки, що містить `share/` і `lib/`), а команди **build from source** — з **кореневої теки репозиторію**.

**Python:**
```bash
python3 share/sima-neat/tutorials/007_read_detection_boxes/read_detection_boxes.py \
  --model /tmp/yolo_v8s.tar.gz --width 640 --height 640
```

**C++ (prebuilt):**
```bash
./lib/sima-neat/tutorials/tutorial_007_read_detection_boxes \
  --model /tmp/yolo_v8s.tar.gz --image /path/to/frame.jpg
```

**C++ (build from source):**
```bash
./build.sh --target tutorial_007_read_detection_boxes
./build/tutorials-standalone/tutorial_007_read_detection_boxes \
  --model /tmp/yolo_v8s.tar.gz --image /path/to/frame.jpg
```

Очікуваний результат (кількість рамок залежить від кадру; синтетичний кадр дає нуль):

```text
boxes=0
[OK] 007_read_detection_boxes
```

(Версія для Python виводить `detections=...`, а якщо середовище виконання не підключає BoxDecode до `model.run`, — `raw_output_heads=...`.) Щоб інтегрувати початковий код C++ цього розділу у свій проєкт із власним файлом `CMakeLists.txt` (тека extras не потрібна), див. [Як запускати навчальні посібники](/tutorials#compile-a-copy-yourself) на головній сторінці.
