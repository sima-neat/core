## Concept

Складіть `Graph` вручну — вхідний вузол, вихідний вузол, без моделі — і пропустіть через нього один кадр. Познайомтеся з базовими елементами конвеєра окремо, перш ніж до них додасться модель.

## Walkthrough

Розділ 001 запустив модель у три рядки. Ця зручність приховує двоетапний життєвий цикл, який безпосередньо використовує кожна нетривіальна програма Neat: спочатку ви **описуєте** конвеєр як `Graph`, а потім **будуєте** з цього опису виконуваний `Run`. Цей розділ робить життєвий цикл видимим: ми складаємо найменший можливий конвеєр — один вхідний вузол, з’єднаний з одним вихідним, без моделі між ними — і проштовхуємо через нього один кадр.

Виграш тут концептуальний: `Graph` — це *визначення для повторного використання*, яке ви будуєте один раз і виконуєте багато разів, а не одноразовий виклик. Наприкінці ви створите граф, перетворите його на виконуваний конвеєр і прочитаєте ранг вихідного тензора — доказ того, що кадр пройшов крізь конвеєр.

### Опис вхідних даних {#step-configure-input}

Перш ніж з’єднувати вузли, оголосіть, який вигляд має кадр. `InputOptions` — це такий контракт: піксельний формат `format`, `width`/`height`, глибина каналу `depth` і те, чи додає середовище виконання мітку часу до кожного буфера. Вхідний вузол, створений із цих параметрів, перевіряє вхідні кадри на відповідність формі, якої очікує конвеєр.

**C++:** У C++ додатково задається `is_live = false`, щоб позначити джерело як таке, що працює не в реальному часі (файл або тензор).

### Складання графа {#step-compose-graph}

Тепер створімо структуру. Новий `Graph` — це порожня основа для композиції, а `add()` додає вузли по черзі. Ми додаємо рівно два — вхідний вузол (налаштований вище) і простий вихідний вузол. Це й уся топологія: кадри входять через вхід і виходять через вихід, а між ними нічого немає. Саме сюди в наступних розділах вбудовується модель або етап попередньої обробки.

**C++:** Вузли створюються викликами `simaai::neat::nodes::Input(...)` і `nodes::Output()`.

**Python:** Вузли створюються викликами `pyneat.nodes.input(...)` і `pyneat.nodes.output()`.

### Побудова конвеєра {#step-build-pipeline}

`build()` — це перехід від *опису* до *виконуваного* конвеєра. Він перетворює додані вузли на конкретний конвеєр, перевіряє вхідні й вихідні контракти на реальному зразку та створює дескриптор `Run` для повторного використання. Ми передаємо репрезентативний кадр, щоб `build()` міг зафіксувати узгоджені форми тензорів; на наступному кроці `Run::run(...)` використовується для детермінованого виклику по одному кадру.

**C++:** Кадр-зразок — це `cv::Mat`, а `run_opt.output_memory = Owned` просить середовище виконання повертати власні (owned) вихідні буфери.

**Python:** Спочатку ми перетворюємо кадр на `Tensor` з масиву NumPy за допомогою `Tensor.from_numpy(...)`, а потім будуємо з ним конвеєр.

### Пропускання кадру й читання результату {#step-run-frame}

Коли `Run` готовий, `run()` синхронно подає один кадр і забирає один результат. Оскільки моделі немає, вихід повторює вхідний контракт, тому прочитати *ранг* тензора достатньо, щоб переконатися, що кадр пройшов увесь шлях. У реальних конвеєрах саме через цей інтерфейс `run()`/push/pull ви керуєте інференсом.

**C++:** `run()` повертає `TensorList`; прочитайте `sample.front().shape.size()`.

**Python:** `run()` із вхідними тензорами повертає `TensorList`; прочитайте `len(outputs[0].shape)`.

## Run

Запустіть програму — у stdout має з’явитися ранг вихідного тензора. Команди **Python** і **C++ (prebuilt)** запускайте з **кореневої теки встановлення Neat** (теки, що містить `share/` і `lib/`), а команди **build from source** — з **кореневої теки репозиторію**. Для цього розділу архів моделі не потрібен.

**Python:**
```bash
python3 share/sima-neat/tutorials/004_build_inference_pipeline/build_inference_pipeline.py \
  --width 320 --height 240
```

**C++ (prebuilt):**
```bash
./lib/sima-neat/tutorials/tutorial_004_build_inference_pipeline \
  --width 320 --height 240
```

**C++ (build from source):**
```bash
./build.sh --target tutorial_004_build_inference_pipeline
./build/tutorials-standalone/tutorial_004_build_inference_pipeline \
  --width 320 --height 240
```

Очікуваний результат:

```text
tensor_rank=3
[OK] 004_build_inference_pipeline
```

(Версія для Python виводить `output_rank=...`.) Щоб інтегрувати початковий код C++ цього розділу у свій проєкт із власним файлом `CMakeLists.txt` (тека extras не потрібна), див. розділ [Як запускати навчальні посібники](/tutorials#compile-a-copy-yourself) на головній сторінці.

## In Practice

Як `build`/`run`, режими виконання, інтерфейс push/pull і `RunOptions` поєднуються між собою, коли ви виходите за межі одного синхронного виклику.

### Побудова чи запуск

- `Graph::build(...)` будує конвеєр і повертає дескриптор `Run` для керування через push/pull.
- `Graph::run(...)` — зручний синхронний шлях: він будує конвеєр (за потреби), подає один вхід і забирає один вихід.

### Синхронний чи асинхронний режим

- Для простого одноразового виклику використовуйте `Graph::run(...)`.
- Використовуйте `Graph::build(...)`, коли потрібен засіб запуску для повторного використання та явне керування через `push(...)` / `pull(...)` — див. [Асинхронний запуск інференсу](/tutorials/run-inference-async).

### API push/pull

`Run` надає:
- `push(...)` / `try_push(...)` для вхідних даних (`cv::Mat`, `Tensor` або `Sample`).
- `pull(...)`, `pull_tensor(...)`, `pull_tensor_or_throw(...)` для вихідних даних.

Якщо потрібні метадані виходу (мітки часу, ідентифікатори потоків), використовуйте `pull()`, щоб отримати `Sample`. Якщо потрібні лише корисні дані тензора, використовуйте `pull_tensor()`.

### RunOptions (простий API)

Поширені параметри:
- `preset`: профіль співвідношення затримки й надійності (`Realtime`, `Balanced`, `Reliable`).
- `queue_depth`: глибина черги середовища виконання.
- `overflow_policy`: поведінка черги в разі переповнення (`Block`, `KeepLatest`, `DropIncoming`).
- `output_memory`: політика володіння вихідними даними (`Auto`, `ZeroCopy`, `Owned`).
- `on_input_drop`: функція зворотного виклику для подій відкидання вхідних даних.

Про глибину черги, переповнення й вимірювання під навантаженням див. [Налаштування пропускної здатності та глибини черги](/tutorials/tune-throughput-and-queues).

### RunAdvancedOptions (API для досвідчених)

Розширені параметри вмикаються за бажанням у `RunOptions::advanced`:
- `advanced.max_input_bytes`: обмежує зростання вхідного буфера.
- `advanced.copy_input`: примусово створює захисні копії вхідних даних.

Використовуйте `Run::start_measurement()`, щоб переглянути затримку, пропускну здатність, лічильники вхідних даних і час роботи плагінів і ребер графа в одному вікні вимірювання.

Щоб записати потужність плати, температури, завантаження CPU та пам’ять за те саме вікно, запустіть навколо нього `TelemetryMonitor`. Він зчитує ці дані з Sentinel — демона телеметрії плати:

```cpp
auto run = graph.build(inputs, run_opt);
simaai::neat::TelemetryMonitor telemetry_monitor;
telemetry_monitor.start();
auto scope = run.start_measurement();
run.push(inputs);
(void)run.pull_tensors(5000);
auto report = scope.stop();
simaai::neat::Telemetry telemetry = telemetry_monitor.stop();
std::cout << telemetry; // YAML summary
```

```python
run = graph.build(tensor, run_opt)
telemetry_monitor = neat.TelemetryMonitor()
telemetry_monitor.start()
scope = run.start_measurement()
run.push(tensor)
_ = run.pull_tensors(5000)
report = scope.stop()
telemetry = telemetry_monitor.stop()
print(telemetry)  # YAML summary
```

Sentinel збирає зразки кожні 2 с, тому вікно, коротше за цей інтервал, може не мати жодного зразка; тоді про це повідомляє `telemetry.status`. Див. [Запис телеметрії плати](/develop-apps/development-workflow/model#record-board-telemetry).
