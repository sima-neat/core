## Concept

Складіть цикл запуску виробничого рівня з шаблонів, розглянутих у попередніх розділах: явні параметри моделі, явні параметри маршруту, явні параметри запуску та один асинхронний цикл передавання й отримання даних. Це не повноцінний фреймворк для продукту, а надійний каркас, який можна адаптувати.

## Walkthrough

Це підсумковий розділ. Досі ми розглядали по одній концепції за раз; тут вони поєднуються в єдиний шаблон, який можна перенести в реальний код розгортання. Уся мета шаблону — зробити явними три речі, які значення за замовчуванням залишають неявними: межі входу моделі (щоб порушення контракту виявлялися під час побудови, а не посеред потоку), іменування етапів (щоб діагностика залишалася зрозумілою, коли кілька моделей працюють в одному процесі) і політику черги (щоб поведінку під навантаженням можна було спостерігати, а не гадати про неї).

Структура така: налаштувати параметри запуску, налаштувати й завантажити модель, побудувати виконавця, а потім керувати ним в обмеженому асинхронному циклі. Наприкінці у вас буде `Runner`, що виконує асинхронний конвеєр із виробничими значеннями за замовчуванням, і цикл передавання й отримання, який рахує успішні виходи, — каркас середовища виконання, який варто стандартизувати для кількох моделей в одному застосунку.

### Налаштування параметрів запуску {#step-configure-run-options}

Це виробничі значення за замовчуванням для середовища виконання. `queue_depth = 8` дає невеликий обмежений буфер; `overflow_policy = Block` змушує виробника чекати, а не мовчки відкидати кадри (безпечний вибір, коли вам важливо не втрачати дані); `output_memory = Owned` гарантує, що повернуті тензори залишаються доступними після отримання. Саме явне задання цих параметрів — а не покладання на значення за замовчуванням — робить поведінку під навантаженням передбачуваною.

### Налаштування та завантаження моделі {#step-configure-model}

Тут ми робимо контракт входу моделі явним. Якщо задати `preprocess.input_max_width/height/depth` за розмірами кадру, невідповідний вхід завершиться помилкою ще під час побудови, з чітким повідомленням про порушення контракту, а не спричинить згодом незрозумілий збій під час виконання. `name_suffix = "_prod"` позначає етапи цієї моделі, щоб їх можна було розпізнати в діагностиці застосунку з кількома моделями. Потім ми створюємо `Model` зі шляху до архіву та цих параметрів.

**C++:** `Model::Options` також явно описує попередню обробку, яку очікує модель, — `InputKind::Image`, перетворення кольору в RGB і нормалізацію ImageNet із `has_explicit_stats = true`, — оскільки C++-варіант оголошує попередню обробку заздалегідь, а не покладається на значення за замовчуванням з архіву.

**Python:** `ModelOptions` задає попередню обробку зображень, межі входу, нормалізацію ImageNet і суфікс у `mopt.preprocess.*`.

### Побудова виконавця {#step-build-runner}

`ModelRouteOptions` (у C++ — `Model::RouteOptions`) визначає, які межі містить маршрут, — тут `include_input` і `include_output` обидва дорівнюють true, — і має той самий суфікс `_prod`, щоб назви елементів маршруту відповідали іменуванню моделі. Потім ми викликаємо `model.build(sample, route_options, run_options)` — шлях в один виклик, який перетворює `Model` безпосередньо на готовий до запуску `Runner` і передає параметри маршруту та запуску в базовий конвеєр. Репрезентативний зразок дає змогу під час побудови зафіксувати узгоджені форми.

**C++:** Зразок — це `TensorList`, створений за допомогою `Tensor::from_cv_mat(rgb, ..., TensorMemory::EV74)`, що розміщує вхідні дані в пам’яті, придатній для пристрою.

**Python:** Зразок — це список з одним `Tensor`, створеним через `Tensor.from_numpy(...)`.

### Запуск виробничого циклу {#step-run-loop}

Саме такий цикл виконує реальний сервіс. На кожній ітерації ми передаємо вхідні дані через `push(...)`, перевіряючи повернене булеве значення, щоб відхилене передавання (за `Block` це тимчасовий стан) було оброблено, а не неправильно пораховано, — потім викликаємо `pull(...)` зі скінченним тайм-аутом і рахуємо успішні виходи. Після циклу `close()` коректно завершує роботу виконавця. Ця схема — перевірка bool після push, pull із тайм-аутом, явне закриття — і є надійним асинхронним каркасом; підставте свої реальні вхідні дані й обробку виходів, і структура залишиться тією самою.

## Run

Для цього розділу потрібен архів моделі (`resnet_50`). Команди **Python** і **C++ (prebuilt)** запускайте з **кореневої теки встановлення Neat** (теки, що містить `share/` і `lib/`), а команди **build from source** — з **кореневої теки репозиторію**.

**Python:**
```bash
python3 share/sima-neat/tutorials/017_build_production_pipeline/build_production_pipeline.py \
  --model /tmp/resnet_50.tar.gz --iters 4
```

**C++ (prebuilt):**
```bash
./lib/sima-neat/tutorials/tutorial_017_build_production_pipeline \
  --model /tmp/resnet_50.tar.gz --iters 4
```

**C++ (build from source):**
```bash
./build.sh --target tutorial_017_build_production_pipeline
./build/tutorials-standalone/tutorial_017_build_production_pipeline \
  --model /tmp/resnet_50.tar.gz --iters 4
```

Очікуваний результат:

```text
outputs=4
[OK] 017_build_production_pipeline
```

(Версія для Python виводить `iters=4 ok=4`.)

Щоб інтегрувати початковий код C++ цього розділу у свій проєкт із власним файлом `CMakeLists.txt` (тека extras не потрібна), див. розділ [Як запускати навчальні посібники](/tutorials#compile-a-copy-yourself) на головній сторінці.
